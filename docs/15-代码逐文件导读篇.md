### 1.2 一次 OCR 的生命周期叙事（以 V1 为例，配 V2/V3/V4 差异注记）

**第 0 幕 · 装弹（启动，一次性）。** `main.c` 的 `main()` 解析完参数后调用 `ds_load()`。`detect_model_version()` 偷看一眼 `config.json` 里的关键词（`"dash"`→V4，须最先查；`sliding_window_size`→V3；`DeepEncoderV2`→V2；否则 V1），`init_config()` 据此填好整张架构超参表 `ds_config_t`（1280 维解码器、12 层、64 专家 top-6……）。`multi_safetensors_open()` 把模型目录里的 `.safetensors` 分片 **mmap** 进虚拟地址空间——注意此刻一个字节的权重都还没真正读进内存，操作系统只登记了"这段虚拟地址对应那个文件"。`load_all_weights()` 逐张量找名字：编码器权重小、按 F32 预转换（`safetensors_get_f32`）；解码器权重大、BF16 直接拿 mmap 指针（`safetensors_get_bf16_direct`，零拷贝）。`alloc_decoder_buffers()` 分配 KV 缓存（12 层 × 4096 槽 × 1280 维）、decode 每步复用的"草稿纸"缓冲、以及预计算到 4096 个位置的 RoPE cos/sin 查表。最后 `ds_metal_init()` 尝试挂上 GPU（失败不报错，纯 CPU 照跑）。

**第 1 幕 · 看图（编码，V1 约 1–3 秒）。** `ds_recognize()` 用 `ds_image_load()` 把 PNG/JPEG 解码成 RGB 像素数组（macOS 上优先 CoreGraphics 解码并自动转正 EXIF 方向）。`ds_image_to_float_chw()` 把 `[H,W,3]` uint8 归一化到 `[-1,1]` 并排成 NCHW。`ds_sam_forward_image()` 启动 SAM ViT-B：`sam_patch_embed()` 用一个"卷积核=步长=16"的 Conv2d 把 1024² 图像切成 4096 个 patch、每个压成 768 维向量；`interpolate_pos_embed()` 把 64×64 的位置编码表按需 bicubic 插值到目标网格；`sam_layer_forward()` 跑 12 层 Transformer——8 层窗口注意力（25 个 14×14 小窗并行，`window_attn_forward`）+ 4 层全局注意力（层 2/5/8/11）；`sam_neck_forward()` + `sam_downsample_forward()` 两次 stride-2 卷积把 64×64×256 压到 16×16×1024，**摊平得 256 个视觉 token**。接着 `ds_clip_encoder_forward()` 接棒：CLIP 绕过自己的 patch_embed，直接把 SAM 特征"二次精炼"24 层，输出与 SAM 特征在特征维拼接成 2048 维，`projector`（单层线性）投到解码器的 1280 维；再按 16×16 网格每行末尾插一个 `image_newline`、末尾追加 `view_seperator`——**256 个 token 变成 273 个**。
> V2 换人：`ds_dynamic_preprocess()` 把大图切成 ≤6 张 768² 局部裁剪 + 1 张 1024² 全局图，`crop_worker`/`crop_worker_global` 多线程并行编码，DeepEncoder V2 用"因果流查询"收集信息。V3/V4 换裁剪尺寸（640²）并启用动态取件池（`v3_pool_worker`）。

**第 2 幕 · 布题（prompt 构造）。** `ds_tokenizer_encode()` 把 `"\nFree OCR."` 编码成 4 个 token id（BPE 编码）。`ds_recognize_image()` 里那段 `EMBED_TOKEN` 宏把每个 id 从 `tok_embeddings_bf16` 查表：**BF16→F32 只需位模式左移 16 位**。视觉槽位不查表，直接用编码器输出覆盖。最终 `input_embeds` 是 `[~278, 1280]` 的矩阵：`[BOS] + 273 图像 token + 4 prompt token`。
> V2 的槽位几何复刻 Python `masked_scatter`；V3 用 128815 占位符；V4 还要在最前面塞一个 `<PAGE>`(128827) 并调 `ds_dash_build_coords()` 建 page2d 坐标。

**第 3 幕 · 预填充（prefill，约 0.7 秒）。** `ds_decoder_prefill()` 把 278 个 token **一次喂入**：12 层循环，每层"批量 RMSNorm → sgemm 批量 QKV → 批量 RoPE → K/V 整块写缓存 → 因果批量注意力（在线 softmax）→ Wo 投影 + 残差 → MoE（按专家分组 Gather-Compute-Scatter）"。为什么能批量？prefill 的 278 个 token 在开始时就全部已知，没有数据依赖；而它们互相之间的因果掩码由 `q_offset` 保证。prefill 结束时 KV 缓存已填满，最后一个位置的 logits 存进 `ctx->dec_logits`——**第一个生成 token 直接对它 argmax，省一次前向**。

**第 4 幕 · 逐字产出（decode，每步约 20 毫秒）。** `ds_decoder_forward()` 是自回归心脏：当前 token 的嵌入进来，12 层各自"RMSNorm → QKV matvec（单 token 用矩阵×向量）→ QK-Norm（若启用）→ RoPE → K/V 写入缓存槽位 `kv_cache_len` → 注意力（V1/V2 因果 / V3 R-SWA 参考集+滑窗 / V4 DASH 块稀疏）→ 残差 → MoE（BF16 路由 top-6 + 2 共享专家）→ 残差"，最后流式 argmax（`ds_argmax_matvec_bf16`，129280 行权重边乘边比，不物化 logits）。选出的 token 经 `ds_tokenizer_decode()` 变成 UTF-8 片段追加到输出缓冲，同时它的嵌入成为下一步输入——循环直到 EOS 或 `max_new_tokens`。

**第 5 幕 · 净化（后处理）。** 尾部空白裁剪（对齐 Python `.strip()`）；V3/V4 调 `ds_strip_det_tags()` 剥掉 `<|det|>…<|/det|>` 坐标标签；V4 再走 `ds_v4_strip_layout()` 剥布局标签、畸形行计数触发 `last_output_degenerate`（CLI 层据此自动重试一次，`main.c` 的 `recognize_file_with_retry`）；幻觉前缀（`[No text detected]` 之前的英文段）截断；最后 `main.c` 的 `cleanup_loopy_output()` 折叠内容循环残留。识别文本从 stdout 出来，统计走 stderr。

> 🗣️ **说人话**：六幕戏各有一句口诀：装弹（一次性，mmap 只登记不读盘）、看图（像素 → 273 个视觉 token）、布题（BOS+图像槽+4 个指令 token 拼成 [~278, 1280] 的嵌入矩阵）、预填充（278 个 token 一次进、~0.7 秒填满 KV 缓存，最后一个位置的 logits 直接 argmax 出第一个字）、逐字产出（每步 ~20 ms，读 ~943 MB 权重只算 ~2.4 MFLOP——带宽受限才是主矛盾，docs/04）、净化（剥标签、裁幻觉前缀、折叠循环残留）。记住两处"免费"：prefill 的首 token 不用再跑一次前向；decode 每步只算一个新 K/V，其余全靠缓存与批量摊薄。
> *边界*：各幕耗时随版本剧变——V1 编码 1–3 秒，V3 大图编码可到 43 s（docs/06 §7 的 32 裁剪上限）；"~20 ms/步"是 M2 Pro 量级的参照，不是常数。

## 2. `main.c` — CLI 入口（~1400 行）

### 2.1 模块职责与调用图位置

最外层的壳：把命令行翻译成 `ds_ctx_t` 上的推理设置，然后分派到单次识别、`--stream` 交互模式或 PDF 逐页模式。它**不含任何数学**——所有重活都在 `ds_recognize*` 系列 API 里。与 qwen-asr 共享完全相同的 main.c 结构（参数解析 → 加载模型 → 推理 → 输出）。

### 2.2 核心设计：stdout/stderr 双通道契约

识别文本走 stdout，一切反馈（提示符、进度点、性能统计、告警）走 stderr——管道重定向 `./ds_ocr ... > out.txt` 才能得到纯文本。三个回调/函数支撑这个契约：

- `stream_token`：V1/V2 非静默时挂到 `ctx->token_cb`，每个生成 token 的 UTF-8 片段立即 `fputs + fflush`（stdout 行缓冲，OCR 文本可能整段无换行，不 flush 就看不到"逐字"效果）。
- `stream_progress_cb`：V3/V4 或 `--silent` 时替代前者——**只计数打点不透出文本**。原因：V3/V4 原始流含幻觉前缀（`[No text detected]`）和布局标签，正文必须等后处理，逐 token 透出会给用户看垃圾；但大图识别数十秒毫无动静像卡死。每 32 token 打一个 `·N`，超过 512 后降频为每 128。进度状态存在 `ds_stream_progress_t {count, started, retried}`：`started` 防"只有点没有说明"的空转行、`retried` 供 ✓ 完成行标注"含 1 次退化重试"。
- `print_perf_summary`：阶段耗时（Encoding/Prefill/Decode 拆分）+ `--profile` 时的逐层 Profiler（QKV/Attention/Out proj/MLP 占解码总耗时百分比、每步平均耗时）。

> 🗣️ **说人话**：双通道契约像餐厅的出餐口与叫号屏：stdout 只出菜（识别文本），一切招呼声（提示符、`·N` 进度点、耗时统计、告警）都走 stderr——`./ds_ocr … > out.txt` 重定向出来的才是纯文本，不被进度提示污染。V1/V2 可以逐 token 透出正文（`stream_token` 里 `fputs + fflush`，不 flush 行缓冲就看不到"逐字"）；V3/V4 只打点不出字——原始流里有幻觉前缀和布局标签，正文必须等后处理，但数十秒毫无动静像死机，所以每 32 token 打一个 `·N`、超过 512 降频到每 128，`started`/`retried` 两个字段保证"不空转、标注重试"。
> *边界*：缓冲行为随 TTY/重定向变化，"逐字"效果只在终端上成立；按 piece 渲染的消费方还得自己拼多字节字符——中间态可能把一个汉字拆进两次回调（docs/07 §4.1）。

## 3. `ds_ocr.h` / `ds_ocr.c` — 公共 API 与总协调器（~3700 行 .c）

### 3.1 模块职责与调用图位置

整个引擎的"总指挥"：定义所有公共数据结构（`ds_ocr.h`），实现加载（`ds_load`）、五步推理流水线（`ds_recognize_image`）、以及多裁剪并行编码的线程编排。头文件头部的常量区是**全仓库最重要的"参数字典"**——SAM/CLIP/DeepEncoder V2/MoE 解码器的每一维都注释了来源。

### 3.2 核心数据结构（`ds_ocr.h`）

**`ds_config_t`** — 四版本共用的超参表，`init_config()` 按检测出的版本号填充。逐组解读：
- 视觉组：`image_size=1024`、`sam_patch_size=16`、`sam_embed_dim=768`、`sam_heads=12`、`sam_window_size=14`、`sam_global_attn_indexes=[2,5,8,11]`、`sam_ds2_dim`（1024 或 V2 的 896）、`visual_tokens_base=256`（= (1024/16)/4²，即 16×16）。
- 编码器组：`enc_type`（1=CLIP / 2=Qwen2 基座）；V2 时 `enc_heads=14, enc_kv_heads=2`（GQA 7:1）、`enc_rope_theta=1e6`、`enc_causal_flow_queries=256/144`。
- 解码器组：四版同构——`dec_hidden=1280`、`dec_layers=12`、`dec_heads=10`（MHA，`dec_kv_heads=10`）、`dec_head_dim=128`、`dec_moe_inter=896`、`dec_n_routed_experts=64`、`dec_top_k=6`、`dec_n_shared_experts=2`、`dec_first_k_dense=1`（层 0 用 Dense FFN）、`vocab_size=129280`。
- V3/V4 专属：`sliding_window_size=128`（V3）/`0`（V4——官方推理显式关 R-SWA，DASH 接管）、`image_token_id=128815`、`image_size_crop=640`。

**`ds_ctx_t`** — 运行时总上下文，字段按用途分六簇：
1. 权重：`vis_tokenizer`（SAM，F32）、`clip_encoder`、`encoder`（V2）、`projector`、`decoder`（MoE，BF16 零拷贝 + F32 norm/gate）。
2. KV 缓存：`kv_cache_k/v`（`[layers, max_seq, kv_row_stride]` 平铺，64 字节对齐）、`kv_bf16`（仅 V3 用 BF16 存储，省一半驻留与读流量；V4 对 KV 精度敏感保持 F32）、`kv_cache_len`（下一个写入槽位 = 当前序列长度）、`_kv_row_stride`（kv_dim 向上取整到 16 float）。
3. decode 草稿纸：`dec_x/dec_x_norm/dec_q/dec_k/dec_v/dec_attn_out/dec_proj_out` 等十几个预分配缓冲——MoE 专家串行处理，各专家可安全复用同一块 scratch，热路径零 malloc。
4. 采样与护栏：`temperature/repeat_penalty/no_repeat_ngram_size/min_new_tokens`（V3/V4 默认 32 步 EOS warmup）、`token_history`（重复惩罚 + n-gram 阻断 + V4 页坐标状态机共用）、`dec_argmax_ban[8]`（warmup 期 EOS/Ġ 排除名单，由快速 argmax 路径"事前"消费而非"事后"重选）。
5. 性能：`perf_encode_ms/perf_prefill_ms/perf_decode_ms` 与 `perf_layer_*_ms[12]`（`--profile`）。
6. V4：`dash_state`（`ds_dash_state_t*`，不透明指针避免头文件循环）、`dash_prompt_ids`（构建 page 坐标用）。

**`ds_visual_tokenizer_t`** — SAM 全部权重（F32）：`sam_patch_embed_weight [768,3,16,16]`、`sam_pos_embed [1,64,64,768]`（**无 CLS token 的纯空间网格**——三个版本的 checkpoint 都验证过）、12 层的 `attn_qkv_weight [2304,768]`（融合 QKV）与 `rel_pos_h/w [heads, head_dim, 2*window-1]`（相对位置编码）、neck 四件套、`sam_net2/net3` 降采样卷积、`image_newline [1280]`/`view_seperator [1280]` 可学习 token、V2 的 `causal_query_embeddings [256,896]` 与 768 版 `causal_query_768_embeddings [144,896]`。

**`ds_dec_layer_t`** — 解码器单层：注意力四投影 BF16（无 bias）；`q_norm/k_norm [128]`（Per-head QK RMSNorm，当前四版均未启用，`has_qk_norm=0`）；V4 专属 `dash_q/k_proj_bf16 [128,1280]`、`dash_head_cls [128]`（块聚合查询）；`input_norm/post_attn_norm`（RMSNorm，F32）；层 0 的 `dense_*_weight_bf16`；层 1–11 的 `gate_weight`（**F32+BF16 双份**——路由分数必须与 Python 的 BF16 autocast 逐位一致，选错专家输出整段跑偏）、`experts[64]` 的 gate/up/down（mmap 原生 split 布局）、`experts_int4[64]`（量化副本，`--int4` 时构建）。

> 🗣️ **说人话**：`ds_ocr.h` 是全仓库的"出厂铭牌 + 驾驶舱"：`ds_config_t` 把四代共用的每一维写死（解码器 1280 维×12 层、10 头 head_dim=128、64 路由专家 top-6+2 共享、vocab 129280；SAM patch 16、窗口 14、全局层 [2,5,8,11]），`init_config()` 按检测出的版本填表；`ds_ctx_t` 是每次识别都在变的运行状态，六簇各管一摊——权重、KV 缓存（`[12,4096,1280]` 平铺、行距 64B 对齐）、decode 草稿纸（热路径零 malloc）、采样护栏（`dec_argmax_ban[8]` 预热期禁 EOS/Ġ）、性能计数、V4 的 DASH 状态。改任何维度先来这里查"铭牌"，别在代码里猜常数。
> *边界*：铭牌与驾驶舱的边界要守住——KV 缓存放 ctx 不放 decoder 结构体，正因为它属于"运行状态"且 V3/V4 存储格式不同（§7.2）；往 config 表里塞运行时变量是常见的坏味道。

### 3.5 常见疑问

- **Q: `ds_recognize` 和 `ds_recognize_image` 什么关系？** 前者只负责把文件路径变成像素，后者是全部逻辑；PDF/PNG 最终都汇入后者。
- **Q: 为什么每次识别前要 `ctx->kv_cache_len = 0` 和 `token_history_len = 0`？** 同一 ctx 可连续识别多图/多页；历史表容量 8704，跨识别累积写满冻结后 V4 的页坐标状态机会读到错误 token——31 页实测第 14 页起必现循环（`docs/08` §8.2 的根因复盘）。
- **Q: `has_qk_norm` 是什么？** Per-head Q/K RMSNorm（DeepSeek-V2 的 QK-Norm），字段与加载逻辑都在，但当前四版 `init_config` 均置 0——权重不加载，V1/V2 也不启用。

> 🗣️ **说人话**：这组疑问共同的根是一句话：**ctx 是可复用的厨房，不是一次性餐盒**。同一 `ds_ctx_t` 要连续识别多张图/多页 PDF，所以每轮开头必须"擦台面"——`kv_cache_len=0`、`token_history_len=0` 不清，历史表（容量 8704）跨识别累积，V4 的页坐标状态机读到上一页的 token，31 页实测第 14 页起必现循环（docs/08 §8.2 的根因）。`has_qk_norm` 则提醒"字段在 ≠ 功能开"：QK-Norm 的加载逻辑都在，四版全置 0——读代码别按字段存在性猜行为。
> *边界*：`ds_recognize` 与 `ds_recognize_image` 是"路径→像素"与"像素→文本"的分层——任何新输入格式（PDF、摄像头帧）都应汇入后者，别在入口层复制推理逻辑。

## 4. `ds_image.h` / `ds_image.c` — 图像加载与预处理（~700 行）

### 4.1 模块职责与调用图位置

流水线第一站：磁盘文件 → 内存 RGB 像素，以及所有"几何"预处理（缩放/填充/裁剪）。qwen-asr 没有对应物（音频走 Mel 频谱图）——这是两个项目最大的输入差异。

### 4.2 核心数据结构

**`ds_image_t`**：`pixels`（RGB 行主序，`pixels[y*width*3 + x*3 + c]`）、`width/height/channels`（加载后恒为 3）、`owns_stb`（**内存所有权标志**：1 = `stbi_load` 分配须用 `stbi_image_free` 释放，0 = malloc 分配用 `free`——stb_image 用自己的分配器，混用会崩）。

> 🗣️ **说人话**：`ds_image_t` 里最值得盯的是那个 `owns_stb` 标志——一张图的两个来源配两套分配器：`stbi_load` 的像素必须用 `stbi_image_free` 释放，CoreGraphics/malloc 路径的用 `free`，两家的堆不通用，混着调直接崩。这跟 docs/07 §10.3 的"一张表借用、一张表自持"是同一条纪律的另一面：**内存归谁必须在结构体上写死**，靠"记得"是靠不住的。其余字段（行主序 `pixels[y*w*3+x*3+c]`、恒 3 通道）是下游所有几何函数（resize/pad/crop）的坐标约定，动了它们等于改签名。
> *边界*：`ds_image_resize/pad/crop` 的产物一律 `owns_stb=0`（malloc 分配）——把原图的标志直接抄给派生图是隐患；释放永远走 `ds_image_free()`，别手写 free。

## 5. `ds_visual_tokenizer.h` / `ds_visual_tokenizer.c` — SAM 视觉分词器（~2000 行）

### 5.1 模块职责与调用图位置

流水线的"眼睛"：像素 → 视觉 token。SAM ViT-B（12 层、768 维、12 头）+ neck 通道压缩 + 两次 stride-2 卷积降采样。输出：1024² 输入 → 256 token；768² → 144；640² → 100。

### 5.2 核心数据结构

**`ds_visual_tokenizer_t`**（完整定义在 `ds_ocr.h`，全部 F32 预转换）逐组解读：

| 字段组 | 形状 | 作用 |
|--------|------|------|
| `sam_patch_embed_weight/bias` | [768,3,16,16] / [768] | patch 化卷积核——"卷积核=步长"的唯一例外场景是它自己（k=s=16 无重叠） |
| `sam_pos_embed` | [1,64,64,768] | 绝对位置编码，**纯空间网格、无 CLS token**（三版本 checkpoint 均验证）；1024² 之外的输入必须先 `interpolate_pos_embed` 插值 |
| `sam_layers[12]` | 每层 14 个指针 | `attn_qkv_weight [2304,768]` 是融合 QKV（行内 [Q\|K\|V] 各 768）；`rel_pos_h/w [12头,64,27]` 是窗口注意力专用的相对位置编码表（27=2×14−1）；MLP 是标准 [3072,768]/[768,3072] |
| `sam_neck_*` | conv [256,768,1,1] 等 | 1×1 卷积 + LayerNorm2d 两轮，通道 768→256 |
| `sam_net2/net3` | [512,256,3,3] / [1024,512,3,3] | 两次 stride-2 卷积，空间 64×64→16×16；net_3 输出通道决定 `sam_ds2_dim`（V2=896，其余 1024） |
| `image_newline` / `view_seperator` | [1280] | V1/V3 网格行分隔与序列终结的可学习向量（projector 之后插入，维度是解码器的 1280） |
| `causal_query_embeddings` / `_768` | [256,896] / [144,896] | V2 因果流查询（1024² 与 768² 各一套） |

为什么 SAM 权重存 F32 而解码器存 BF16？SAM 是批量 sgemm 负载，预转换摊得薄；解码器逐 token matvec 对带宽斤斤计较（`ds_visual_tokenizer.h` 的 `ds_visual_tokenizer_load` 注释）。

### 5.3 数据流与关键设计

```
[3,H,W] ──patch_embed──▶ [768, H/16, W/16] ──+pos_embed(插值)──▶ token-major [N,768]
   ──12×sam_layer_forward──▶ （窗口注意力层0/1/3/4/6/7/9/10，全局注意力层2/5/8/11）
   ──sam_neck_forward──▶ Conv768→256 + LN2d + Conv256→256 + LN2d
   ──sam_downsample_forward──▶ Conv(256→512,s2) + Conv(512→1024/896,s2)
   摊平 ──▶ [n_tokens, sam_ds2_dim]     # 64×64 → 16×16，空间 ÷16（4× 来自降采样，4× 来自 patch）
```

**窗口注意力的几何账**：64×64=4096 个 token 按 14×14 分窗装不下（64 不是 14 的倍数），`window_partition_pad()` 先把网格 pad 到 70×70，得到 5×5=**25 个窗**，每窗 196 token。分数对总数：窗口注意力 25×196²≈96 万，全图注意力 4096²≈1678 万——**约 1/17 的计算量**，代价是窗间信息隔离，由 4 个全局注意力层补课。约 650/900 GFLOP 落在窗口层，且各窗完全独立 → `sam_window_worker` 裸 pthread 并行（单 SAM 独跑时；多 crop 波次由 `ds_sam_thread_gates` 置 0 防超额订阅）。

**相对位置编码**：窗口注意力不用 RoPE，用可学习的 `rel_pos_h/w [12头, 64, 27]` 查表（27 = 2×14−1 的相对距离范围），`get_rel_pos_v2()` 按查询/键的窗口内坐标取行，与 Q·K 点积线性组合加到注意力分数上（`add_rel_pos_bias`）。

**LayerNorm2d（`layer_norm_2d`）**：与普通 LayerNorm 方向相反——普通 LN 固定 token 沿特征维归一，LN2d 固定**像素**沿 **C 个通道**归一（CHW 布局下相邻通道的同一像素隔着一整张平面，累加步长是 spatial 不是 1）。eps=1e-6。

**位置编码插值（`interpolate_pos_embed` + `bicubic_interpolate_2d`）**：checkpoint 的 `pos_embed` 是 [1,64,64,768] 纯空间网格（无 CLS）；768² 输入网格 48×48、640² 输入 40×40，需要 64→48/40 的 bicubic 插值。这里曾有两次著名事故（V1 误加 +1 CLS 偏移读越界、V3 误判无需插值），逐行注释有完整复盘（`docs/06` §6.3/6.4）。

### 5.6 常见疑问

- **Q: SAM 为什么叫"分词器"？** 它把连续像素变成离散 token 序列，角色上等价于文本侧的 BPE——视觉 token 就是"图像的词"。
- **Q: 窗口注意力会不会丢跨窗信息？** 会，靠层 2/5/8/11 的全局注意力补全；这是 Swin/SAM 家族的标准折中。
- **Q: rel_pos 为什么只有窗内版本？** 相对位置编码的表大小随窗口线性增长（2W−1），全图 4096 token 的表太大且全局层由绝对位置编码覆盖。

> 🗣️ **说人话**：SAM 为什么叫"视觉分词器"？因为它跟文本侧 BPE 干的是同一件事：把连续流切成离散 token——BPE 把字节流切成 id 序列，SAM 把像素切成 4096 个 patch 再压成 256 个向量。由此三个疑问连成一条线：窗口注意力确实丢跨窗信息（一桌人看不见邻桌），靠层 [2,5,8,11] 的全局注意力补课；`rel_pos` 表只有窗内版，因为表行数随窗口线性长（2w−1），4096 全图的表养不起，且全局层已有绝对位置编码兜底（docs/06 §3.4）。
> *边界*："分词器"是角色类比不是机制等同：BPE 词表是有限离散集合，SAM 的"词"是连续特征向量——token 数恒为 (边长/16/4)²，随分辨率变，不随"词汇"变。

## 6. `ds_deep_encoder.h` / `ds_deep_encoder.c` — CLIP 与 DeepEncoder V2（~1200 行）

### 6.1 模块职责与调用图位置

SAM 和解码器之间的"翻译层"：把偏底层（边缘/纹理）的 SAM 特征精炼成高层语义。两套编码器：
- **V1/V3/V4**：CLIP ViT-L/14（24 层、1024 维、16 头、GELU FFN 4096）做"二次精炼"，输出与 SAM 特征拼接成 2048 维 → projector → 273/111 token。
- **V2**：DeepEncoder V2（Qwen2-0.5B 架构：24 层、896 维、GQA 14Q/2KV、RoPE θ=10⁶、SwiGLU 4864）+ **因果流查询** → 257 token。

### 6.2 核心数据结构

**`ds_clip_encoder_t`**（`ds_ocr.h`，V1/V3/V4 共用，全部 F32）：
- `class_embedding [1024]`：CLS token 嵌入——拼在 patch 序列最前面当"摘要位"，输出前再剥掉；
- `patch_embedding_weight [1024,3,14,14]`：**加载了但从不使用**（CLIP 直喂 SAM 特征，见 6.3 的绕过设计）；
- `position_embedding [257,1024]`：1 CLS + 16×16 patch 的位置表；网格 ≠16×16 时按行做抗锯齿 bicubic 插值（`ds_bicubic_resample_dim`）；
- `pre_layernorm` + 24 层 `layers[24]`：每层 12 个指针（LN1 / 融合 QKV [3072,1024] / out_proj / LN2 / fc1 [4096,1024] / fc2），带 bias（CLIP 与解码器"无 bias"约定不同）；
- `final_norm`：post-LayerNorm，V1/V3 缺失（`LOAD_F32_OPT` 静默跳过）。

**`ds_deep_encoder_t`**（V2 专用，`ds_ocr.h`）：24 层 `layers[24]` 每层 Qwen2 风格 12 个指针——`layer_norm1`、**分离的** `wq [896,896]` / `wk [128,896]` / `wv [128,896]`（GQA：K/V 只有 2 头，矩阵瘦成 128 行）、`wo`、三个投影 bias、`layer_norm2`、SwiGLU 三件套 `gate/up [4864,896]` + `down [896,4864]`；加 `final_norm [896]`。因果流查询本体不在编码器结构里，而在 `ds_visual_tokenizer_t.causal_query_embeddings`——因为它们是"输入"而非"参数层"。

**`ds_projector_t`**：`weight [1280, proj_input_dim]` + `bias [1280]`——整个"编码器→解码器"维度的转接头只有一层线性。

### 6.3 关键理论点（在本文件的落点）

**CLIP 绕过 patch_embed（`ds_clip_encoder_forward`）**：V1/V3/V4 一律把 SAM 下采样输出 [N,1024] 直接当 CLIP 的 patch_embeds——SAM 已完成"patch 化+投影"，CLIP 再从像素按 14×14 切一遍既与 SAM 网格不兼容也浪费算力；CLIP 的 `patch_embedding` 权重加载了但从不使用。**拼接顺序以代码为准：`cat(clip_output, sam_features, dim=-1)`，CLIP 在前**（文件头示意图顺序相反，头注释已勘误）。

**image_newline 的 2D 网格布局**：256 个 token 是 16×16 网格，每行末尾插 1 个 `image_newline`（可学习向量），末尾加 1 个 `view_seperator`——16×17+1=**273**。newline 告诉解码器"图像有行结构"，这是 OCR 模型对版面的先验注入。手算：1024² 全局图 273 token；640² 裁剪 10×(10+1)+1=**111**。

**CLIP 的 GELU 用精确 erf 式**：`0.5x(1+erf(x/√2))`（`ds_gelu`，`ds_kernels.c`），不是 tanh 近似——与 HF CLIP 逐位对齐。

**DeepEncoder V2 的混合注意力（`enc_gqa_mixed_attention`）**：序列 = 视觉 token（前段）+ 因果查询（后段）。第 qi 个 token 的可见域上界：
- `qi < n_tokens`（视觉段）→ `vis_end = n_tokens`：全部视觉 token 互相可见（双向）；
- `qi ≥ n_tokens`（查询段）→ `vis_end = qi + 1`：因果，只看 ≤ 自身。

两种掩码只差这一个上界。类比：双向注意力=全员开会讨论；因果查询=逐个汇报总结。查询天然覆盖全部视觉段+之前的查询，输出序列自带顺序性，更适合自回归解码（`docs/06` §9）。

**GQA（Grouped-Query Attention）**：14 个 Q 头共享 2 组 KV 头（7:1）。KV 缓存与计算量按 KV 头数计——省 7 倍 KV 存储。Q 头 h 读 KV 头 `h / (n_q_heads/n_kv_heads)`。

**enc_apply_rope 的 RoPE**：编码器用 θ=10⁶ 的 1D RoPE（支持长序列），解码器 θ=10⁴（详见 §7 的完整推导）。

## 7. `ds_moe_decoder.h` / `ds_moe_decoder.c` — MoE 解码器（~2200 行）

### 7.1 模块职责与调用图位置

流水线的"嘴巴和大脑"，也是**耗时大头**（decode 占总时长约 1/3，MoE 又占解码的 74-77%）。DeepSeek3B-MoE-A570M：总参 ~3B，每 token 只激活 ~570M——"3B 的知识，570M 的计算"。

### 7.2 核心数据结构

**`ds_moe_decoder_t`**（`ds_ocr.h`）：`tok_embeddings_bf16 [129280,1280]`（词嵌入表，与 `lm_head_bf16` tied）、`layers[12]`、`norm [1280]`（final RMSNorm，F32）、`lm_head_bf16 [129280,1280]`。

**`ds_dec_layer_t`** 逐组（完整字段见 §3.2，这里补内存账）：
- 注意力四投影 `wq/wk/wv/wo`：各 [1280,1280] BF16 = 3.28MB/个，无 bias（DeepSeek 约定）；
- `input_norm/post_attn_norm [1280]`：F32（维度小、精度敏感——norm 缩放系数差一点，整层激活分布就漂）；
- 层 0：`dense_gate/up [6848,1280]` + `dense_down [1280,6848]` BF16 ≈ 52MB；
- 层 1–11 MoE：`gate_weight [64,1280]`（路由器，F32+BF16 双份共 ~660KB）；`experts[64]` 每个 gate/up/down 各 [896,1280] 或 [1280,896] BF16 ≈ 2.2MB → 单层路由专家 ~143MB，11 层 ~1.6GB——**解码器参数的大头**；`shared_*` 等效 2 个专家拼成 [1792,1280]；
- `expert_block_bf16/gate_up_fused_bf16`：恒为 NULL 的历史字段（拷贝版连续布局，r2 实验移除，见 7.11 疑问）；
- `experts_int4[64]` + `int4_enabled`：量化副本（§12），`--int4` 时构建。

KV 缓存不在 `ds_moe_decoder_t` 里而在 `ds_ctx_t`——因为它属于"运行状态"而非"模型参数"，且 V3/V4/V1 的存储格式不同（`kv_bf16` 开关）。

> 🗣️ **说人话**：解码器的内存大头是"专科医生"不是"主刀医生"：11 层 MoE 每层 64 个专家各 ~2.2MB（gate/up/down），单层 ~143MB、合计 ~1.6GB；注意力四投影每块才 3.28MB——这就是为什么 `--int4` 只量化专家（§12）、为什么 prefill 要按专家分组 Gather-Compute-Scatter（docs/05 §3）。两个易踩的细节：路由 `gate_weight` 存 **F32+BF16 双份**（~660KB——路由分数必须与 Python 的 BF16 autocast 逐位一致，选错专家整段跑偏）；KV 缓存不住在本结构体而在 `ds_ctx_t`，它是运行状态不是参数。
> *边界*：`expert_block_bf16/gate_up_fused_bf16` 恒为 NULL 是历史字段（r2 移除拷贝布局，§7.11）——看到非空判断别以为真有 fused 布局；层 0 是 Dense FFN（6848 中间维），不参与"64 选 6"。

### 7.3 核心理论：MoE 路由数学（完整手算）

**直觉/类比**：一家 64 人的医院（专家），每个病人（token）由分诊台（router）指定 6 位专科医生会诊（top-6），另有 2 位全科医生（shared experts）谁都看——通用处理+专科处理的分工。

**数学**：路由器是 `[64,1280]` 的线性层。`moe_forward()`（`ds_moe_decoder.c`）的三步：

1. **打分**：`scores[e] = x · W_gate[e]`（`ds_moe_router_bf16`——**必须用 BF16 权重**：F32 与 BF16 在排名相近的专家上次序可交换，选错专家输出系统性偏离 Python）。
2. **全局 softmax**（先对全部 64 个归一，再选 top-6——旧实现"先选后归一"权重系统性偏大，无法与 Python 对齐）：

   `p_e = exp(s_e − max_s) / Σ_e' exp(s_e' − max_s)`（max-subtract 防上溢）
3. **无放回 top-6**，权重直接取全局 softmax 概率，**不做 renormalize**（Σw<1，剩余概率质量留给未选中专家——DeepSeek-V2 风格，以代码为准）。

**手算小算例**（缩到 4 个专家、top-2）：scores=[2, 1, 0.5, 0] → exp = [7.389, 2.718, 1.649, 1.0]，Σ=12.756 → p = [0.579, 0.213, 0.129, 0.078]。选 top-2：专家 0（w=0.579）与专家 1（w=0.213），组合输出 `0.579·E0(x) + 0.213·E1(x) + shared(x)`，权重和 0.792<1（未 renorm）。

**稀疏激活的账**：每层 MoE 参数 = 64×3×(896×1280) ≈ 2.2 亿，激活 top-6 = 6×3×896×1280 ≈ 2060 万 ≈ **1/10.7**；再加 2 共享专家（1792 中间维）。这就是"容量-算力解耦"。

**为什么层 0 用 Dense FFN（`dec_first_k_dense=1`）**：第一层处理原始输入特征，语义尚未分化，路由器没有可靠信号可学，分工无从谈起。intermediate=6848（SwiGLU 三明治）。

**SwiGLU（`dense_ffn_forward` / `ds_swiglu_direct`）**：
```
gate = x @ W_gate^T        [1280→6848]
up   = x @ W_up^T          [1280→6848]
h    = SiLU(gate) ⊙ up     SiLU(x) = x·σ(x) = x/(1+e^−x)
out  = h @ W_down^T        [6848→1280]
```
手算：SiLU(2) = 2/(1+e⁻²) = 2/1.1353 ≈ 1.762；若 up=0.5 则该位置贡献 0.881。SiLU 在 x<0 时先降后回（x≈−1.28 处最小 −0.278），比 ReLU 平滑。为什么用 SwiGLU 而不是普通 FFN？门控让网络"决定哪些特征通过"，同等参数量下质量更好（`docs/01` §7.3）。

> 🗣️ **说人话**：把每层 MoE 想成一个"投票现场"：先给 64 个专家全部亮牌打分（全局 softmax，分母含所有 64 个），再只请票数最高的 6 位上台，且上台时**沿用原票数、不重新瓜分**——于是 6 张票加起来永远凑不满 1。就算某 token 是"全能选手"，它也只动用 1/10.7 的算力（2060 万 vs 2.2 亿参数），这才是"一次运 3GB 级模型却跑得动"的根因。
> *边界*：这套"不 renorm、全局 softmax"是按本仓库代码与 DeepSeek-V2 风格定的；换个厂商若改成"先选后归一"，同样的 scores 会算出偏大的权重，此时 §7.3 的手算数字不再成立。

### 7.4 核心理论：Prefill vs Decode（计算差异完整推导）

**直觉**：prefill 是"全班一起上课"（278 个 token 并行），decode 是"点名回答问题"（一次一个，且下一个依赖上一个——自回归串行依赖）。

**算术强度分析**（以一步 decode 为例）：
- 权重读取：12 层 × (QKV 3×1280×1280 + Wo + FFN/MoE + …) ≈ 612MB + LM head 129280×1280×2B ≈ 331MB → **每步 ~943MB**；
- 计算：单 token 全程 ~2.4 MFLOP；
- 算术强度 ≈ 2.4M/943M ≈ 0.0025 FLOP/B ——**极度内存带宽受限**。M2 Pro 带宽 ~200GB/s → 理论下限 ~4.7ms/步，实测 ~23ms（效率 ~20%，受 BF16 转换与缓存未命中拖累）。
- prefill 时 278 行摊薄权重读取（权重读一遍算 278 行），瓶颈转为计算吞吐 → BLAS sgemm 的利用率远高于 matvec。**逐 token prefill 需 278×12×23ms ≈ 77s；批量 prefill ~0.7s——100 倍**。

这就是 `ds_linear_nobias_bf16()` 内部 `seq_len==1 走 matvec、>1 转 F32 走 sgemm` 自动选路的根据。

### 7.5 核心理论：KV cache（为什么需要、多大、怎么存）

**为什么**：decode 第 t 步的注意力要对全部历史 K/V 打分。没有缓存，每步要重算 t−1 个位置的 K/V（O(t²) 总量）；有缓存，每步只算 1 个新 K/V（O(t)）。缓存的 K 是 **RoPE 旋转之后**的（`ds_kv_store_row` 的注释：写入发生在 RoPE 后，注意力可直接点积）。

**大小手算**（V1/V2，F32）：`12 层 × 4096 槽 × 1280 维 × 4B × 2(K和V) = 503,316,480 字节 ≈ 480 MiB`（代码注释的 "240MB→480MB" 即 K、V 各约 240MiB）。V3/V4 槽位 8192（32 裁剪前缀就 ~3800 token）。

**为什么行对齐**：`_kv_row_stride = (kv_dim+15) & ~15`——每行起始落在 64 字节（cache line）边界，SIMD 读取不跨行混叠，余量填充让 F32/BF16 两种元素宽度共用同一套偏移公式（`ds_kv_k_row`，`ds_dash.h` 里的 inline）。

**F32 vs BF16 存储的权衡**：BF16 省一半内存，但旧设计每步把整个缓存 BF16→F32 批量转换，O(seq_len) 转换主导注意力时间——改为 F32 直存（V1/V2），内存翻倍换零转换。V3 走有界实验回到 BF16（`ds_dot_bf16xf32` 精确展开，点积顺序与 F32 一致，8/8 回归全绿）；**V4/DASH 对 KV 精度敏感，保持 F32**。

> 🗣️ **说人话**：KV 缓存就像做菜时把"熬好的高汤"一锅冻起来：没有它，第 t 步要现熬 t−1 份汤底（总成本像 1+2+…+t，越吃越慢的平方级）；有了它，每步只补 1 勺新料（线性）。代价是一整柜冻汤——V1/V2 用 F32 存下来约 480 MiB，等于"汤柜"和"主食"抢同一块内存，所以 V3 才尝试换 BF16 把它瘦一半，V4 又因精度红线改回 F32。
> *边界*：缓存省的是**重复读取**、不省每步必须读的那一份权重；而且它一直在涨——序列填满 4096 槽后不是自动缩水，长上下文模型的"内存墙"正来自这里。

### 7.6 核心理论：RoPE（旋转位置编码，完整推导）

**直觉**：把 Q/K 向量看成复数，按位置乘 `e^{i·m·θ}`——两个位置的点积就只依赖角度差 m−n，"相对位置"免费获得。

**数学**（NeoX/Llama 风格，`ds_compute_rope_neox`/`ds_apply_rope_neox`）：
- 第 i 对频率 `ω_i = θ^(−2i/d)`（θ=10000，head_dim=128，i=0..63）：低维 ω 大转得快（分辨相邻位置），高维 ω 小转得慢（编码远距离）；
- 位置 m 的旋转角 `θ_{m,i} = m·ω_i`；
- **拆半配对**：维度 d 与 d+64 组成旋转对，`out[d] = x[d]·cos − x[d+64]·sin`，`out[d+64] = x[d]·sin + x[d+64]·cos`，cos/sin 表前后半相同。注意这与 GPT-J 的"相邻维配对"不同，以代码为准。
- 相对性：`R(m)·R(n)^T = R(m−n)`，所以 `Q_m·K_n` 只依赖 m−n。

**手算小算例**（缩到 2 维、ω=1）：位置 2 的 Q=(1,0) 旋转 2 rad → (cos2, sin2)=(−0.416, 0.909)；位置 0 的 K=(1,0)。点积 = cos2 = cos(2−0)——只差相对距离 2。

**工程化**：`alloc_decoder_buffers()` 启动时一次算好 4096 个位置的 cos/sin 查表（`rope_cache_cos/sin`），decode 直接查，避免每步算三角函数。V4 换用 `ds_dash_rope_row()` 的 page2d 表（见 §8）。

### 7.7 核心理论：RMSNorm 与 Per-head QK Norm

**RMSNorm（`ds_rms_norm`）**：
```
out = x / sqrt(mean(x²) + eps) · γ        eps=1e-6
```
与 LayerNorm 的唯一数学差异：不减均值（省一趟求和）。手算：x=[3,4]，mean(x²)=(9+16)/2=12.5，rms=3.536 → norm=[0.849, 1.131]，再逐元素乘 γ。

**Per-head QK RMSNorm（`ds_rms_norm_per_head`）**：统计范围是单个 head 的 128 维段而非整行。动机：训练后期个别通道 q/k 幅值膨胀 → 点积 logits 爆炸 → 注意力过早饱和；逐头归一把 Q/K 钉回单位 RMS，与 1/√d 缩放构成双保险。**顺序必须在 RoPE 之前**：RoPE 是正交旋转，先旋转再逐通道乘 γ 不可交换，会破坏 Q·K 只依赖相对位置的性质（`decoder_layer_forward` 注释）。

### 7.8 核心理论：在线 softmax（online softmax）

`ds_causal_attention_aligned` 内核不物化 [1, seq] 分数行，一边点积一边维护 (run_max m, run_sum s, 输出 O) 三元组：新最大值 m′ 出现时按 `corr = e^{m−m′}` 修正已累加的 O 和 s——与 FlashAttention 同一数学、块大小退化为 1（推导见 `docs/13` §2）。手算：分数依次 [2, 5]，V 两行 v1/v2。处理 2：m=2, s=1, O=v1。处理 5：m′=5, corr=e⁻³≈0.0498 → s=0.0498+1=1.0498, O=0.0498·v1+v2。最终除以 s 即正确 softmax 加权和。

### 7.11 常见疑问

- **Q: `gate_up_fused_bf16` 为什么恒为 NULL？** 历史版本把 gate+up 拷贝成连续块换单次 matvec，但 mmap 源页与拷贝双份驻留把峰值 RSS 顶到 11-12GB（ru_maxrss 是高水位，事后 madvise 救不回）——r2 实验移除拷贝，decode 走 split 布局 + `ds_grouped_matvec_bf16`，fused/Metal-MoE/INT4-fused 路径自动旁路（休眠保留）。
- **Q: 解码器是 GQA 吗？** 不是：10 Q 头 = 10 KV 头（MHA），`dec_kv_heads=10`；GQA 在 V2 编码器里（14Q/2KV）。
- **Q: tied embeddings 是什么？** `tok_embeddings` 与 `lm_head` 共享同一矩阵：查表是它的"正向"，argmax 是它的"转置投影"。

> 🗣️ **说人话**：`gate_up_fused_bf16` 恒为 NULL 是一条用内存换来的教训：历史上把 gate+up 拷成连续块换"单次 matvec"，结果 mmap 源页与拷贝双份驻留，峰值 RSS 顶到 11–12GB——而 `ru_maxrss` 是高水位，事后 madvise 救不回来（docs/03 §2.5）。r2 实验的结论是回退 split 布局 + `ds_grouped_matvec_bf16`：每步多一次 matvec 分派，换回几 GB 常驻。另一条别记错：解码器是 MHA 不是 GQA（10 Q 头 = 10 KV 头），GQA（14Q/2KV）住在 V2 编码器里——同一个仓库两种注意力配置，抄参数前先确认楼层。
> *边界*：fused/Metal-MoE/INT4-fused 路径并未删除、只是"休眠"——`moe_forward` 的分派条件保留着；唤醒它们的前提是 fused 布局重新存在，否则自动走 CPU split 慢路径，不会报错。

## 8. `ds_dash.h` / `ds_dash.c` — V4 DASH 块稀疏注意力（~1000 行）

### 8.1 模块职责与调用图位置

V4（Unlimited-OCR-2）解码器专用注意力路径。V3 的 R-SWA 可见集是"两段连续区间"（参考集∪滑窗）；V4 换成"局部窗 ∪ 若干离散选中块"，无法用区间扫描表达，只能逐 token 判定归属。头注释里有与官方 `modeling_deepseekv2.py` `_INFER` 路径逐步对照的完整数学。

### 8.2 核心理论：DASH 五步数学

超参：`block_size=32`（KV 分块）、`local_blocks=4`（→局部窗 128）、`K=12`（读预算槽位）、`topm=16`（entmax 窗口）、`index_dim=128`、`idx_scale=128/√128≈11.31`、`sigma=1.0`、`floor=1e-4`。

1. **索引投影**（`router_qk` + `gemma_rms_norm`）：`idx_q/idx_k = page2drope(GemmaRMS(q_proj/k_proj(层输入)))`。两个易错点：输入是**残差流层输入**而非 RMSNorm 后的 x_norm；GemmaRMS 的 scale = `(1+w)·x/rms(x)`——比标准 RMSNorm 多个"+1"。
2. **块分数**（`block_scores_headcls`）：`k_bar[b]` = 块内 `softmax(idx_k·hc/√128)` 加权平均（与 query 无关，每块算一次）；`z[q,b] = clamp(idx_q·k_bar/√128)`。
3. **remote 掩码**：块 b 对 query q 是远程 ⟺ `b ≤ q_pos/32 − local_blocks`，否则 z=−1e9。
4. **路由选择**（`route_select`）：候选域 `cand` = 同页 image 块（无候选→放开全部 remote）；`x = cand ? z·idx_scale : −1e4`（哨兵）→ top-M=16 窗口 → **entmax15** → 前 K=min(12,M) 槽位；`valid` = 槽是有效候选（哨兵槽 invalid）；`bias = (log(clamp(prior,floor)) − μ)/σ`，μ 只对 valid 求均值。
5. **带偏置注意力**（`attn_head_range`）：`m[q,k]` 取 0（局部窗）/bias（选中块）/−∞（其余），`softmax(QK^T·scale + m) @ V`。

**entmax15（`entmax15`）**：α=1.5 的稀疏 softmax，闭式解 `Y = clamp(xs − τ, 0)²`，τ 由"支持集元素平方和=1"唯一确定——支持集之外的分量被截断归零（softmax 永远做不到零）。算法：减 max ×0.5（α−1=0.5 的幂次折进尺度）→ 降序排序 → 从 r=1 递增试支持集大小，`τ_r = mean_r − sqrt(max(0,(1−ss_r)/r))`，按**计数**取 τ（不能提前 break——`τ_r − xs[r−1]` 非严格单调）。手算：x=[3,1]（已 shift+scale 后）：试支持集 {3}——mean=3、离差平方和 ss=0 → τ = 3 − sqrt((1−0)/1) = 2，τ≤3 自洽（support=1）→ Y = [clamp(3−2,0)², clamp(1−2,0)²] = **[1, 0]**——比 softmax(3,1)=[0.88,0.12] 稀疏得多。
> 注意输出按**原位置**写回，绝不能用排序后的数组（bug ④ 的根因，`docs/14` §5）。

**稀疏度算账**：全注意力每 query 扫全部 KV；DASH 可见域 ≤ 局部窗 128 + K×32 = 384，合计 ≤512 个位置——kv_cache_max=8192 满载时省 ~16×，注意力成本不再随长文档线性放大。

### 8.3 核心理论：page2d 二维 RoPE

`rope2d_cos_sin_row()`：128 维 = 64 个频率对 = **63 个 tok 角 + 1 个 page 角**：
- tok 轴：`ang[i] = tok · 10000^(−i/63)`，resample 模式在 63 对里重铺整个频谱；tok 是**页内 running count**，使页内相对距离与文档总长无关；
- page 轴：`inv_page = 256^0 = 1` → `ang[63] = (page % 2) · 1.0 rad`。**最常见实现错误是写成 p/256**——256 只是 base，page_pairs=1 时指数为 0，inv_page 恒为 1；多除一次 base 会把同页/跨页相位差抹成 ~0.004 rad，页判别全废（bug ③）。
- page%2 只表达"同页/跨页"，"第几页"的区分交给路由器的页候选。

**页坐标状态机（`ds_dash_build_coords` / `ds_dash_advance_coords`）**：三条页桶规则——① `<PAGE>` 是 1-based 计数（第一页数据 page=1）；② 保留桶 0（BOS 与最后一张图之后的指令文本 page=0，与任何真实页 Δpage≥1 不会误认同页）；③ 页内 running count 跨不连续区间累计（页 k 有 prompt 图像段+响应正文段两段区域，段内重启会让两个 token 撞坐标）。算例：`[BOS, <PAGE>, img×273, 指令×6]` → page: `0 1 1…1 0`，tok: `0 0 1..273 1..6`。decode 每步 `ds_dash_advance_coords`：新 token 是 `<PAGE>` → 换页并重置 tok 为该页 prefill 长度 `pf_cnt[新page]`；否则 tok+1。

### 8.4 核心数据结构

**`ds_dash_route_t`**（每 query 路由结果）：`blk[12]`（选中块号，可能含哨兵 −1）、`bias[12]`（log-prior 偏置，invalid 槽为 0）、`valid[12]`（是否有效候选——bug ⑤ 教训：必须查 `eff = remote ∧ 页候选` 的合取，只查页候选会让哨兵槽拿到 −3.3 偏置参与注意力）。

**`ds_dash_state_t`**：`idx_k_hist [n_layers][kv_cache_max×128]`——**按层缓存全量历史 router key**（官方 `past_kv._dash_idx_k` 追加语义）。bug ①（最致命）：早期 12 层共用一份 scratch 且 decode 只写第 0 行，层 L 的块分数读到跨层脏数据，图像 token 离开局部窗后路由全失准。另有 `cos2d/sin2d`（预计算 rope 表行）、`tok_pos/page_pos/cand_page`（坐标表）、`blk_bmin/bmax`（每块的 image 页范围）、`pf_cnt`（每页 prefill 长度）、`pp`（prompt 页数）、`mcum`（累计 marker 数；decode 候选页 `qp = mcum − 1 − pp`）。

> 🗣️ **说人话**：DASH 的状态里最要紧的是那份"每层路由笔记本"：`idx_k_hist` 按层缓存全量历史的 router key——块分数要读"从对话开始到现在的全部"idx_k，不是只读本步。bug ① 就栽在这：12 层共用一份 scratch，层 L 的块分数读到跨层脏数据，图像 token 一离开局部窗路由就全失准。规则由此而来：**每层的路由状态必须按层隔离、按全缓存长度读**——它和 KV 缓存是两本账：KV 服务注意力（点积），idx_k 服务"选块"（离散决策），后者对脏数据更敏感（§8.7 的精度话题同源）。
> *边界*：`ds_dash_reset_run()` 每页识别前必须调——块分数按全缓存长度读历史，不重置则上一页残留混入本页路由，随识别次数累积漂移（`ds_dash.h` 头注释）。

### 8.7 常见疑问

- **Q: K=12 和"12 里含局部块"是一回事吗？** 不是——部署路径直接选 12 个远程槽，局部窗另算；训练路径 `_remote_topk=16−4=12` 只是数值巧合（bug ②，`docs/14` §4.3）。
- **Q: 为什么 V4 的 KV 缓存用 F32？** r2 有界实验中 BF16 KV 在 DASH 打红（截屏 24.7% FAIL）——DASH 路由对 KV 精度敏感，与 V3 全绿相反。
- **Q: DS_V4_FULLATTN / DS_V4_NOBIAS / DS_DUMP_ROUTE 是什么？** 三个诊断开关：全量因果注意力（区分选块 vs 坐标问题）、偏置清零（区分选块 vs 偏置数值问题）、路由可视化。

> 🗣️ **说人话**：为什么 V3 能把 KV 压成 BF16、V4 不行？因为两个版本对 KV 的"用法"不同：V3 只拿 KV 做注意力点积——BF16 的均匀小误差在 softmax 加权里被抹平，8/8 回归全绿；V4 还要拿 idx_k 做**路由决策**——块分数的微小抖动会翻转"选哪块"这种离散选择，选错块比点积差一点严重得多，BF16 KV 实测截屏 24.7% FAIL，只能保 F32。另外 K=12 与训练路径 `16−4=12` 只是数值巧合（bug ②），别把两套来源当成同一条公式；查不出来的路由问题，先用三个诊断开关二分定位（全注意力→选块/坐标、清偏置→选块/数值）。
> *边界*：诊断开关是跑分工具不是生产配置——`DS_V4_FULLATTN` 打开后 ~16× 的稀疏收益归零；"全绿/打红"的判定以 `tools/regress.sh` 的冻结阈值为准。

## 9. `ds_tokenizer.h` / `ds_tokenizer.c` — GPT-2 字节级 BPE（~1600 行）

### 9.1 模块职责与调用图位置

文本与数字之间的"翻译官"：encode（prompt 文本→token id，仅 4 个 token，非性能瓶颈）与 decode（生成 id→UTF-8 文本，每步都调）。用与 Python 相同的 vocab.json/tokenizer.json，结果完全一致。

### 9.2 核心理论：byte-level BPE 的"中"字七步旅程

**直觉**：先把一切文本拆成 256 个原始字节（天然支持所有语言、永无 `<unk>`），再把高频字节对合并成新 token。为让字节"可打印"，GPT-2 做了字节→载体字符映射：**0x20（空格）→U+0120（Ġ）、0x0A（换行）→U+010A（Ċ）**，其余不可见字节映射到 256+n 区（`init_gpt2_mapping()`）。

**encode 三步**（`ds_tokenizer_encode` → `text_to_bpe_unicode` → `encode_bpe_word`）：
1. 字节→载体字符：`"Multi page parsing."` → `"MultiĠpageĠparsing."`；
2. 贪心合并：循环{扫全部相邻对，取 rank 最小者合并}直到无可合并——rank 是 merges.txt 行号（训练时被学出的轮次），rank 小的规则更"基础"先合并（`merge_rank`）；
3. 逐符号查 `vocab_map` 得 id；任一查不到 → 整体失败（调用方走 fallback 常量 id，绝不带病输出）。

**省掉预分词的代价与保险**：官方 tokenizer.json 的 pre_tokenizer 用正则切段（数字/CJK/英文），本实现省掉——合并表学自"段内"，跨段相邻对在表里基本不存在，贪心自然停在正确边界。但"基本"≠"绝不"，上游 `ds_ocr.c` 设三道保险：合理性检查（≤10 token）+ fallback id（如 `"Multi page parsing."`→[37460,4366,76466,16]）+ test_unit 钉扎断言。

**decode 零拷贝查表**：`ds_tokenizer_decode` 直接返回 `id_to_text[id]` 内部指针；中文字符"你"=UTF-8 [0xE4,0xBD,0xA0] 可能是 3 个独立字节 token，多个 piece 在输出缓冲自然拼接愈合（`docs/07` §7）。

### 9.3 核心数据结构

**`ds_tokenizer_t`**：`id_to_text [vocab]`（ID→可读文本，decode 用）、`id_to_bpe [vocab]`（ID→原始 BPE 串，保留 Ġ 等特殊表示）、`vocab_map`（字符串→ID 哈希，encode 用，FNV-1a 哈希 + 开放寻址：`fnv1a_hash`/`map_insert`/`map_get`）、`merge_map`（"a b"→rank，合并用）。为什么两个方向都要？encode 需要文本→ID，decode 需要 ID→文本，BPE 合并需要 (a,b)→rank——三个查询模式，两张表+一份合并规则。

## 10. `ds_safetensors.h` / `ds_safetensors.c` — 权重读取器（~660 行）

### 10.1 模块职责与调用图位置

模型加载的第一环：把 safetensors 文件映射进内存并提供按名查找。文件二进制布局：`[8B header长度 LE uint64][N B JSON header][数据区]`。JSON header 记录每个张量的 dtype/shape/`data_offsets`（**相对数据区起点，不是文件起点**——实际指针 = mmap基址 + 8 + header_size + data_offset）。

### 10.2 核心理论：mmap 零拷贝（完整机制）

**直觉**：`read()` 是"把书复印一遍再读"，mmap 是"直接在图书馆看书"——内核把文件的页缓存直接映射进进程虚拟地址空间。

**数学/机制**：`safetensors_open()` 走 `open() → fstat() → mmap()`。三个收益：
1. **零拷贝**：数据在内核页缓存中就地访问，无用户态缓冲复制；
2. **惰性加载**：页按需调页（page fault），启动只解析 header，权重不碰不读；
3. **BF16 直接指针**：`safetensors_get_bf16_direct()` 返回 mmap 区域内的 `uint16_t*`，matvec 内核在寄存器里逐元素左移 16 位转 F32——3GB 级权重永不翻倍。

**页生命周期**：权重加载把整份 mmap 摸一遍，清洁文件页全部驻留；`multi_safetensors_madvise_unused()` 对整段映射 `MADV_DONTNEED` 归还物理页（省 4-5GB RSS）——MAP_PRIVATE 干净页此后触碰会从 page cache 廉价重入（无磁盘 I/O），正确性不变。`ds_drop_source_pages()`（`ds_ocr.c`）是单段版本。代价提醒：`ru_maxrss` 是高水位，事后 madvise 降低不了它（`docs/09` §5.5）。

### 10.3 核心数据结构

- **`safetensor_t`**：`name[256]`（定长免动态分配）、`dtype` 枚举（BF16 的指数位与 F32 相同 8 位、尾数 7 位——范围大不易溢出，精度对深度学习足够）、`ndim/shape[8]`、`data_offset/data_size`。
- **`safetensors_file_t`**：`data`（mmap 基址）、`header_size`、`header_json`（**堆上 NUL 结尾副本**——mmap 区 JSON 后面紧跟二进制数据，指针推进式解析器依赖 '\0' 兜底，必须拷一份）、`tensors[4096]`。
- **`multi_safetensors_t`**：`shards[8]`——大模型拆 5-8 片，统一按名查找对上层透明。

## 11. `ds_kernels.h` / `ds_kernels.c` + `ds_kernels_impl.h` + 平台内核 — 数学底座（~5500 行）

### 11.1 模块职责与调用图位置

所有浮点运算的最终归宿。三层结构：

- **`ds_kernels.h`**：平台无关统一 API（上层只认 `ds_xxx` 语法）；
- **`ds_kernels_impl.h`**：分发层——"**编译期定候选、运行时定人选**"；
- **`ds_kernels_generic.c` / `_neon.c` / `_avx.c`**：标量基准 / ARM NEON / x86 AVX 实现。

### 11.2 核心理论：BF16（完整位级推导）

**直觉**：BF16 是"把 F32 砍掉后 16 位尾数"——指数位完全相同，**范围一样大、精度略低**，深度学习对动态范围的需求远大于尾数精度。

**数学**：F32 = 1 符号 + 8 指数 + 23 尾数；BF16 = 1 + 8 + 7。转换只需把 16 位位模式左移 16 位补零（指数对齐），**精确无舍入**；F32→BF16 才有舍入（+0x8000 进位）。

**手算小算例**：BF16 `0xC040` → 左移 → F32 `0xC0400000`。解码：符号 1、指数 `1000 0000`=128→2^(128−127)=2、尾数 `100 0000...`=0.25→有效数 1.25 → 值 = −1.25×2 = **−3.0**。反向：F32 的 1.0 = `0x3F800000` → BF16 `0x3F80`。

**为什么 on-the-fly 而不预转换**：decode 每步读 943MB 权重但只算 2.4 MFLOP——预转 F32 让内存翻倍、带宽翻倍，而转换本身只需一条移位指令，在寄存器里完成最便宜（`docs/03` §3.2-3.3）。

### 11.3 核心理论：三级内核分发（`ds_kernels_impl.h`）

**为什么 matvec/argmax 在 ARM 上走函数指针、其余走纯宏**：同一份 arm64 二进制要同时跑 M1（无 FEAT_BF16）和 M2+（有）——CPU 能力只能运行时探测（Apple 用 sysctl），于是 vshll 版与 bfdot 版都编进二进制，启动时 `ds_kernels_dispatch_init()` 把函数指针切到更快的一份。x86 的 AVX-512/AVX2 由 `-march=native` 编译期定死，直接宏展开静态调用（零间接开销）。

**两条 NEON 路径的指令账**：
- vshll 路径（M1 默认）：`vshll_n_u16` 把 4 个 BF16 加宽左移成 F32 位模式 + `vfmaq_f32` 乘加——每 4 个 BF16 MAC 需 2 条指令；
- bfdot 路径（M2+，FEAT_BF16）：一条 `bfdot` 完成 8 个 BF16 MAC → 4 个 F32 累加，**指令密度 4×**；代价是两个操作数都得是 BF16，F32 输入 x 要先压窄。

x86 没有 BF16 硬件点积（AVX512-BF16 仅少数服务器 CPU），统一走"u16 加宽+左移+FMADD"软件三连。AVX 文件内再按 `__AVX512F__ && __AVX512BW__` 二分 512/256 位。

**正确性纪律**：SIMD 水平求和顺序与标量不同会有末位 ULP 差异；generic 版是正确性对照基准，回归门控（`tools/regress.sh` 30 组冻结标签 + CER 阈值）保证分派切换不改变 OCR 输出。`ds_grouped_matvec_bf16` 的行对 (2r,2r+1) 永不跨线程拆分——落单行会走不同求和顺序（2 组累加器 vs 8 组），必须以行对为粒度才能逐位一致。

**fast_expf（`ds_fast_expf`）**：Schraudolph 1999 位技巧——`u.i = 12102203·x + 1064866805`，指数域给出 e^x 量级、尾数域线性近似 2^frac（12102203 ≈ 2²³/ln2）。相对误差 <1.5%、快 5×；只用于注意力/SwiGLU，编码器精度红线场景禁用（`docs/05` §10.2）。

> 🗣️ **说人话**：分发就是"同一个门牌、按你开的车换引擎"：ARM 上 M1 没装 BF16 硬件，M2 装了——编译器无法提前知道运行在哪台机器，于是两份引擎都塞进同一个二进制，开机时 bit 探测一次、把函数指针指向快的那份（指向错误型号=结果仍对，只是慢 4×）。x86 相反：机器型号在**编译时**就定死了，压根不需要指针，直接展开成指令。
> *边界*：函数指针"只在运行时选一次"的前提是 CPU 能力不会中途变；且 SIMD 与标量的求和顺序天生有末位 ULP 差，所以切换引擎后必须过 §11.3 提到的回归门控，否则"更快的那份"可能悄悄改掉 OCR 输出。

### 11.4 线程池（fork-join）

`ds_set_threads(n)` 销毁重建线程池（非线程安全，须推理前调）；`ds_parallel_for(fn, arg)` 是并行区入口：各线程领 `tid∈[0,n)`，分片写区间必须互不相交；`n≤1` 时零开销直调。`ds_dispatch_ensure_init()` 惰性初始化内核分派。worker 循环（`ds_worker_loop`）用条件变量等待派工。

> 🗣️ **说人话**：线程池是"开工前定人数的施工队"：`ds_set_threads(n)` 销毁重建整个池子——盖到一半不能加人，所以必须在推理前调；`ds_parallel_for` 是派活入口，各线程领 `tid∈[0,n)`、各写各的输出区间，互不相交就不用锁；`n≤1` 时零开销直调，单线程路径不付任何同步税。worker 常驻、用条件变量等派工，不为每个并行区现起线程——省的正是反复建队的开销。这套 fork-join 纪律配合 §11.3 的"行对为切分粒度"，才保得住多线程结果逐位一致。
> *边界*：并行区的铁律是"写区间互不相交"，读共享输入没问题——但归约类收尾（argmax 各段最大值并列）要留意合并逻辑；`ds_dispatch_ensure_init()` 只兜底内核分派，兜不了"推理中途改线程数"。

## 12. `ds_quantize.h` / `ds_quantize.c` — 逐行 INT8 量化（~430 行）

### 12.1 模块职责与调用图位置

`--int4` 旗标背后的量化模块（**历史命名，实际按 255 级量化**——INT4 只有 15 级）。把 11 层 MoE 的 64 路由 + 2 共享专家的 gate_up_fused/down 权重压到 1 字节/值（BF16 的一半），层 0 Dense FFN、注意力、路由 gate、LM head 保持 BF16。

### 12.2 核心理论：逐行不对称 INT8（完整推导与手算）

**直觉**：把一行权重的取值范围 `[min,max]` 线性压到整数 `[0,255]`——量化误差上限 = 格距的一半 = scale/2。

**数学**（`int8_quantize_row`）：
```
scale = (max − min) / 255
存储: q = clamp(round((val − min)/scale), 0, 255) − 128   # int8 载体，减 128 便于 SIMD
反量化: Ŵ = scale·(q + 128) + min
```
per-row 而非 per-tensor 的理由：同一输出通道的权重分布相近，一个 scale 够；per-tensor 会被 outlier 行拉爆格距。元数据 8B/行仅占 0.31%（[1792,1280] 的 scale+offset = 14KB vs 4.59MB 权重）。

**手算小算例**：某行 min=−0.5, max=1.5 → scale = 2/255 ≈ 0.00784。权值 0.2：q = round(0.7/0.00784) − 128 = round(89.25) − 128 = 89 − 128 = **−39**（int8 存储）。反量化：Ŵ = 0.00784·(−39+128) − 0.5 = 0.00784·89 − 0.5 = 0.698 − 0.5 = **0.198**，误差 0.002 < scale/2=0.0039。✔

**matvec 分解技巧（`ds_int4_matvec`）**：`y[r] = scale·dot(q+128, x) + offset·sum(x)`——把"逐元素反量化再乘加"拆成两个独立归约一遍扫描完成，反量化零额外内存流量（`docs/09` §3.3）。

**验收线**：RMS 误差 <0.01（理想 0.39%，实测固定种子 0.0043-0.0044、真实权重 0.007-0.010）。真 INT4 需要 per-group + GPTQ/AWQ 校准，超出教学引擎边界（`docs/09` §3.6）。

### 12.3 核心数据结构

**`ds_int4_block_t`**（名字历史遗留）：`qweight`（int8 索引 [out,in]）、`scale [out]`、`offset [out]`（存 min 而非 zero-point，省一次减法；scale 预计算倒数循环内只做乘）、`out_dim/in_dim/bytes`。

## 13. `ds_metal.h` / `ds_metal.m` / `ds_metal_shaders.metal` — Apple GPU 卸载（~560+ 行）

### 13.1 模块职责与调用图位置

CPU SIMD（bfdot/vshll/AVX）之上的可选加速层：把 decode 热路径的 MoE 专家前向、共享专家、LM head argmax、QKV matvec 提交 Metal 计算着色器。初始化失败或 `DS_NO_METAL` 时逐层回退 CPU，语义不变。

### 13.2 核心数据结构与统一内存零拷贝

**`ds_metal_ctx`**（定义在 `ds_metal.m`，对上层不透明——`ds_metal.h` 只暴露 `typedef struct ds_metal_ctx ds_metal_ctx_t`）逐字段：
- `dev / q / lib / ps`：MTLDevice、命令队列、着色器库（编译自 `ds_metal_shaders.metal`）、按名字缓存的计算管线字典；
- `wb[4096] / nwb`：权重注册表——`(host指针, MTLBuffer, 字节数)` 三元组，按指针去重避免重复包装；
- `x_b/y_b/gu_b/sw_b/eo_b/cb_b/ar_b/q_b/k_b/v_b`：中间量缓冲（输入/输出/gate_up/SwiGLU/专家输出/合并系数/argmax 归约/Q/K/V），`ensure_buf()` 按需扩容复用；
- `expert_block_bf16 / expert_block_host / expert_block_size`：连续专家块的偏移访问支持（r2 后休眠）；
- `ndispatch`：调度计数（调试用）。

**直觉**：Apple Silicon 的 CPU 和 GPU 共享同一物理内存——"零拷贝"不是传得快，而是根本没有"传"这回事。

**机制**（`get_wbuf()`）：`newBufferWithBytesNoCopy:` 直接把 mmap 区域包装成 `MTLStorageModeShared` 的 MTLBuffer，GPU 读同一物理页；失败退回 `newBufferWithBytes:`（拷贝）。权重注册表 `wbuf_t wb[4096]` 按指针去重。`get_wbuf_offset()` 支持在连续专家块内按字节偏移取 buffer（避免 64+ 个小 buffer）——r2 去拷贝后 expert_block 恒 NULL，此路径休眠。

**性能语境**：decode 每步 ~1.15 GFLOP 但要读数 GB 权重（带宽受限）——GPU 的价值是把内存延迟换成大带宽；若注册时发生拷贝，H2D 传输就把收益吃光了。

> 🗣️ **说人话**：Apple Silicon 的"零拷贝"是字面意义的：CPU 和 GPU 共享同一物理内存，`newBufferWithBytesNoCopy:` 把 mmap 区直接包装成 `MTLStorageModeShared` 的 MTLBuffer——GPU 读的就是 CPU 读的那几页，根本没有"传"这回事（与 docs/03 §2.2 的 mmap 是同一个"不搬"哲学）。价值核算：decode 每步 ~1.15 GFLOP 却要读数 GB 权重，GPU 的本事是把带宽做大；若注册时退回 `newBufferWithBytes:`（拷贝），H2D 一次性传输就把收益吃光。`wb[4096]` 注册表按 host 指针去重，同一块权重不重复包装。
> *边界*：零拷贝包装可能失败（对内存布局有要求），自动退拷贝版——语义不变、性能打折；r2 移除专家块拷贝后 Metal-MoE 休眠（split 布局无法提交），当前默认卸载的是共享专家/LM head/QKV 路径。

## 14. 支撑件：`ds_pdf`、`ds_platform_ocr`、`ds_dump.h`、`stb_image.h`

### 14.1 `ds_pdf.h` / `ds_pdf.c` / `ds_pdf.m` — PDF 逐页渲染

**职责**：引擎只认像素，PDF 是输入端的"翻译层"，与 `ds_image.c` 同级。四个 API：`ds_pdf_open/page_count/render_page/close`。核心数据结构 `ds_pdf_doc_t` 是不透明句柄（定义在 `.m`：`CGPDFDocumentRef doc` + `int n_pages`），生命周期严格 open→render×N→close。
- macOS 实现在 `.m`：CoreGraphics `CGPDFDocument` + `CGBitmapContext`。渲染 2.0×页面点阵（≈144 DPI）、长边上限 2048px（A4 → ~1224×1584，小字号仍保细节）；CoreGraphics 位图不支持 24bpp，先渲 RGBA 再抽取 RGB。
- 非 macOS：`.c` 是桩实现（返回失败），保持零依赖。
- 交叉注意：`main.c` 的 `recognize_pdf_stream()` 发现"渲染与识别必须两遍流水"（CGPDFDocument 内部状态跨页 draw 污染识别路径）——使用本模块时的关键约束。

### 14.2 `ds_platform_ocr.h` / `.c` / `.m` — 系统 OCR 备选

`ds_platform_ocr_file(path, accurate, verbosity)`：macOS + `USE_APPLE_VISION` 编译时走 Vision 框架（`VNRecognizeTextRequest`），不加载模型即可 OCR——模型文件的"备胎"与对照基准。内部：`create_vision_image()` 长边压到 1280、`sorted_observations()` 按 `observation_top()` 排序拼行、`dup_nsstring_utf8()` 桥接 NSString→malloc 字符串。非 macOS/.c 为空桩。

### 14.3 `ds_dump.h` — C↔Python 对拍工具

头文件内嵌三个 static 函数（`ds_dump_tensor/2d`、`ds_dump_init`），`DS_DUMP_TENSORS=1` 启用：对指定中间量打一行统计（mean/std/abs_mean/min/max）+ first20 到 stderr，并把完整二进制写进 `dump/` 目录的 `.bin`——与 Python 端 `dump_tensors.py` 同名 hook 输出**按名字配对**逐位对拍。`g_dump_crop_id`（定义在 `ds_ocr.c`）给多裁剪 dump 加 crop 前缀防互踩。这是 `docs/06` 两次位置编码事故的验证手段：幻觉/孤儿标签只是末端症状，mean/std 一眼定位差异在哪层引入。

### 14.4 `stb_image.h` — 第三方图像解码

单头文件库（PNG/JPEG/WebP/BMP/TIFF/GIF…），本仓库唯一的第三方依赖。本项目只调 `stbi_load`（强制 3 通道）与 `stbi_image_free`——注意它的分配器与 malloc 不通用（`ds_image_t.owns_stb` 标志存在的原因）。

## 17. 自测题（10 道，附答案要点）

**Q1. 一次 decode 步为什么要读 ~943MB 权重却只算 ~2.4 MFLOP？这决定了什么优化方向？**
> 要点：12 层全部注意力投影 + MoE 专家 + LM head（129280×1280 BF16 ≈ 331MB）每步都要完整读一遍，而单 token 只有 1280 维向量的乘加。算术强度 ≈0.0025 FLOP/B，极度带宽受限 → 优化方向是压低读流量（BF16 存储、INT8 量化、连续布局提缓存命中），而非提高 FLOPS。

**Q2. 为什么 prefill 可以一次喂 278 个 token，decode 却必须逐个？**
> 要点：prefill 的 token 在开始时全部已知、无数据依赖，可组成矩阵走 sgemm（权重读一遍摊给 278 行）；decode 的下一个 token 依赖上一步输出（自回归串行依赖），只能 matvec。逐 token prefill 需 ~77s，批量 ~0.7s。

**Q3. 手推 MoE 路由：scores=[2,1,0.5,0]，top-2 的专家与权重是多少？权重和为什么不等于 1？**
> 要点：softmax 全局归一 p≈[0.579,0.213,0.129,0.078]；选专家 0/1，权重 0.579/0.213，Σ=0.792<1——DeepSeek-V2 风格不 renormalize，剩余概率质量留给未选中专家（先全局 softmax 再 top-k，顺序不能反）。

**Q4. RoPE 的哪两个维度配成旋转对？为什么 QK-Norm 必须在 RoPE 之前？**
> 要点：NeoX 拆半配对（d 与 d+half，本模型 half=64），不是相邻维。RoPE 是正交旋转；若先旋转再逐通道乘 γ（norm），diag(g)² 与旋转矩阵不可交换，Q·K 不再只依赖相对位置 m−n。

**Q5. RMSNorm 与 LayerNorm 的数学差异？x=[3,4] 归一化后是多少（γ=1）？**
> 要点：RMSNorm 不减均值：out = x/sqrt(mean(x²)+eps)。mean(x²)=12.5，rms≈3.536 → [0.849, 1.131]。省一趟求和，效果相当。

**Q6. BF16 `0x3F80` 转 F32 是多少？转换为什么是精确的？**
> 要点：左移 16 位 → `0x3F800000` = 1.0。BF16 指数位与 F32 完全相同（8 位），截断只发生在尾数低位——反向（F32→BF16）才是舍入（+0x8000 进位）。

**Q7. mmap 加载权重后，第一次读某个张量会发生什么？`multi_safetensors_madvise_unused()` 之后指针还有效吗？**
> 要点：缺页中断 → 内核从 page cache 装入该 4KB 页（惰性加载）。madvise 后指针仍有效——MAP_PRIVATE 干净页被从驻留集摘除，再触碰会从 page cache 廉价重入，无磁盘 I/O，正确性不变；只省 RSS 不省跑分。

**Q8. V3 的 R-SWA 在 decode 时注意力可见域是哪两段？KV 缓存总量上界是多少？**
> 要点：参考集 [0, prefill_len)（视觉+prompt，永驻）∪ 最近 W=128 个生成 token（`window_start=max(prefill_len, kv_seq_len−W)`）；上界 prefill_len+W——长文档内存不随生成长度线性增长。图像证据必须全程可见是"前缀永驻"的原因（与 StreamingLLM 的 attention sink 动机不同）。

**Q9. DASH 的 entmax15 与 softmax 的本质区别？哨兵槽（−1e4）为什么"进了 top-M 窗口却不能参与注意力"？**
> 要点：entmax-1.5 输出可精确为零（Y=clamp(xs−τ,0)²，支持集外截断），softmax 永远为正。哨兵槽 prior≈0→clamp 到 floor=1e-4→logp≈−9.2，但 valid=0——不进 μ、注意力侧按"块号无效"排除；若误让其带偏置参与注意力会产生循环输出（bug ⑤）。

**Q10. 字节级 BPE 里空格变成了什么？为什么"你"可能是 3 个 token？decode 怎么还原？**
> 要点：0x20→U+0120（Ġ）。中文字符 UTF-8 占 3 字节，训练语料不足时每个字节各自成 token（低频字没学到合并规则）。decode 逐 piece 查 `id_to_text` 输出原始字节，多个 piece 在输出缓冲自然拼接成合法 UTF-8——字节级词表保证任意 id 序列都可解码。

| 因果流查询 | 双向+因果混合掩码 | `enc_gqa_mixed_attention`（ds_deep_encoder.c） |
