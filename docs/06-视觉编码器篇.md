## 1. 总览：一张图的视觉之旅

四条管线（V4 即 Unlimited-OCR-2）的视觉侧骨架完全一致，差异只在"喂给编码器什么、编码器用什么"：

```
V1: pad(1024²)          → SAM → 256 tok ─┐
V3/V4: pad(1024²)+crops → N×[SAM(640²) ──┤→ CLIP-L(24层) → concat SAM → projector → +换行/分隔符
                                        ┘   (CLIP 吃 SAM 特征)
V2: dynamic_preprocess  → N×[SAM(768²) → DeepEncoder V2(因果查询) → projector] + 全局图
```

所有版本共享同一条铁律——**视觉 token 数 ≈ (输入边长 / 16 / 4)²**：

- **÷16** 是 patch 化：SAM 的 patch embedding 用 16×16 像素一个 patch（`DS_SAM_PATCH_SIZE`）；
- **÷4** 是 SAM neck 之后的两次 2× 空间下采样（`net_2`、`net_3` 两个 stride=2 卷积）。

1024² 输入：(1024/16/4)² = 16² = 256 token；640² 裁剪：(640/16/4)² = 10² = 100 token；
768² 裁剪：(768/16/4)² = 12² = 144 token。这三个数分别对应 `ds_ocr.h` 里的
`DS_VISUAL_TOKENS_BASE`(256)、`lgrid=10`（`ds_ocr.c` 中注释 `640/16/4`）、`DS_LOCAL_CROP_TOKENS`(144)。

下面按数据流顺序把每一站拆开讲。

## 2. patch embedding：把图片当句子读

ViT（Vision Transformer）把 H×W 图片切成 P×P patch，每个 patch 展平成一个向量后过
线性投影——数学上等价于一个 **Conv2d(kernel=P, stride=P)**：卷积核恰好覆盖一个 patch、
步幅恰好不重叠，所以"滑动窗口"退化成"按格查表"。

SAM 的实现（`ds_visual_tokenizer.c: sam_patch_embed`）：

```c
/* Conv2D: weight [768, 3, 16, 16], stride 16, no padding */
ds_conv2d(patches, image_chw, weight, bias, 3, embed_dim, img_h, img_w,
          16, 16, 16, 0);   /* k_h=16, k_w=16, stride=16, pad=0 */
```

权重 `model.sam_model.patch_embed.proj.weight` 形状 [768, 3, 16, 16]，展平后是
[768, 768] 的矩阵——**输入恰好也是 768 维**（3 通道 × 16×16 像素），patch embedding
在这里是个方阵变换，纯属 3·16² = 768 的巧合（CLIP 的 3·14² = 588 就不是方阵）。

**完整算例（V3 的 640×640 裁剪，一路跟到 token 序列）**：

| 步骤 | 操作 | 形状变化 |
|---|---|---|
| 0 | 像素归一化 `ds_image_to_float_chw` | [640, 640, 3] uint8 → [3, 640, 640] f32，值域 [-1,1] |
| 1 | patch embed（16×16，s=16） | [768, 40, 40]，40 = 640/16，共 1600 个 patch |
| 2 | + 位置嵌入 [1, 64, 64, 768] 插值到 40×40 | [1600, 768]（token 主序） |
| 3 | 12 层 Transformer | [1600, 768] 不变 |
| 4 | neck + downsample（第 4 节） | [768,40,40] → [256,40,40] → [512,20,20] → [1024,10,10] |
| 5 | 摊平成 token | [100, 1024] |

1024² 全局图走同一条路：64×64 = 4096 个 patch → … → [1024, 16, 16] → 256 token。
注意两个细节：

- 归一化是 `(pixel/255 - 0.5) / 0.5`，即 [-1,1]（`ds_image.c`，与 Python 的
  `BasicImageTransform(mean=0.5, std=0.5)` 逐位一致）；
- 位置嵌入是**二维网格 [1, 64, 64, 768]、没有 CLS**——这一点曾让 C 端栽过大跟头
  （第 6 节事故二），我们用 safetensors header 逐一核验过全部四个 checkpoint 均如此。

token 数是平方复杂度：边长翻倍 → patch 数 ×4 → 注意力对数 ×16。这是第 3 节
窗口注意力存在的理由。

## 3. SAM 窗口注意力与相对位置偏置

SAM ViT-B 共 12 层（D=768，12 头，head_dim=64，FFN 中间维 3072，均为 `ds_ocr.h`
常量），独特之处是**窗口注意力**（window attention）：大部分层里，每个 token 只和
自己窗口内的 195 个邻居做注意力。实现在 `window_partition_pad` /
`window_attn_forward` / `window_unpartition_pad` 三个函数。

### 3.1 为什么要窗口化：一笔复杂度账

1024² 输入产生 64×64 = 4096 个 patch。每个注意力头每层要算的 score 对数：

```
全局注意力：4096 × 4096        = 16.8M 对
窗口注意力：25 窗 × 196 × 196  = 0.96M 对   → 少 17.5 倍
```

（64 不能被窗口 14 整除，pad 到 70 后得 5×5 = 25 个窗口，见下节。）
把整层成本摊开（乘加各算一次，单位 GFLOP）：

| 成分 | 窗口层 | 全局层 |
|---|---|---|
| QKV 投影 [4096,768]×[768,2304] | 14.5 | 14.5 |
| 注意力 score + @V | 3.0 | 51.5 |
| 输出投影 | 4.8 | 4.8 |
| FFN（768→3072→768） | 38.7 | 38.7 |
| **合计** | ≈61 | ≈109 |

8 个窗口层 + 4 个全局层 ≈ 8×61 + 4×109 ≈ **0.9 TFLOP** 一次 SAM 前向——这就是
[05-性能优化实战篇](./05-性能优化实战篇.md) 里"Encoding 优化"章节反复压榨的对象。
窗口层的 score 缓冲也从 4096² 缩到 196²：全局层每个头要一块
4096×4096×4B ≈ **67 MB** 的缓冲（`sam_global_process_head` 注释），窗口层只要 150 KB。

### 3.2 窗口划分、padding 与反划分

`window_partition_pad` 的三步（以 1024² 输入的 64×64 网格、窗口 14 为例）：

```
64×64 ──pad──▶ 70×70（右/下补零 6 行列）──切分──▶ 5×5 = 25 个 14×14 窗口
       pad_h = (14 - 64%14)%14 = 6          每窗 196 个 token
```

640² 裁剪（40×40 网格）pad 2 → 42 → 9 个窗口；768² 裁剪（48×48）pad 8 → 56 → 16 个窗口。
反划分 `window_unpartition_pad` 把 25 个窗口的输出拼回 70×70 再裁掉补的 6 行列。

一个容易踩的坑藏在调用顺序里（`sam_layer_forward` 注释）：

```c
/* Python's order: norm1 -> pad -> window_partition -> QKV -> attn -> ...
 * We must pad x_norm first, then compute QKV on the padded data,
 * so that padded positions get QKV(0) = qkv_b (non-zero), matching Python.
 * Previously we computed QKV on unpadded data then padded Q/K/V with zeros,
 * which caused real tokens near the padding boundary to have different
 * attention scores (diff max=0.209 at Block 0). */
```

补零位置的 K/V 参与 softmax 分母——先投影再补零，补的行是 K=V=0；先补零再投影，
补的行是 `QKV(0) = qkv_bias`。两种做法对边界真实 token 的注意力分数差异最大到
0.209（第 0 层实测），对齐 Python 必须选后者。

### 3.3 为什么是 [0,1,3,4,6,7,9,10] 窗口 + [2,5,8,11] 全局

`config.json` 的 `sam_vit_b.global_attn_indexes: [2,5,8,11]` 是训练时定死的：
**每 3 层插一层全局**。窗口注意力便宜但信息不出窗——一个字符的左右文如果跨过窗口
边界就看不见了；全局层让所有 patch 互见，把窗口间信息补齐。这与 Swin Transformer
的"移位窗口"异曲同工，但更简单：不做 shift，直接用 1/3 的层做全局。

C 端对应一行（`sam_layer_forward`）：

```c
int use_global_attn = (layer_idx == 2 || layer_idx == 5 ||
                       layer_idx == 8 || layer_idx == 11);
```

### 3.4 相对位置偏置：2w-1 的表怎么查

SAM 不用 RoPE，而是在注意力分数上加**相对位置偏置**（relative position bias），
且把行、列两个方向**解耦**（decomposed）：

```
attn_score[i,j] += q_i · rel_pos_h[ qy-ky + (w-1) ] + q_i · rel_pos_w[ qx-kx + (w-1) ]
```

关键在索引公式 `q_coord - k_coord + w - 1`：相对位移的取值范围是
[-(w-1), w-1]，共 2w-1 种，加 w-1 平移到 [0, 2w-2] 才能当数组下标。所以每张表的
行数是 **2w-1**：

- 窗口层（w=14）：`rel_pos_h/w` 形状 **[27, 64]**（27 = 2×14-1），窗口大小与输入无关，
  永远不用插值；
- 全局层（1024² 输入，w=64）：形状 **[127, 64]**（127 = 2×64-1）。

（以上形状从 safetensors header 实测：`blocks.0.attn.rel_pos_h` = [27, 64]，
`blocks.2.attn.rel_pos_h` = [127, 64]，四个 checkpoint 一致；表在头间共享。）

查找的朴素写法是 O(N²·head_dim)——每个 (i,j) 对做一次点积。C 实现利用了
**块结构**：`bias_h` 只依赖 (qy,ky)，同一 (qy,ky) 块内所有 kx 共享同一个 bias 值，
于是按对角线扫一遍、整块填充（`window_attn_forward` / `sam_global_process_head`）：

```c
for (int dy = 0; dy < 2 * win_h - 1; dy++) {      /* 27 条对角线 */
    int actual_dy = dy - (win_h - 1);
    const float *rh_vec = rel_pos_h + dy * head_dim;
    for (int qy = 0; qy < win_h; qy++) {
        int ky = qy - actual_dy;                  /* ← 查表索引 */
        if (ky < 0 || ky >= win_h) continue;
        ...
        for (int qx = 0; qx < win_w; qx++) {
            float bias = 0.0f;
            for (int d = 0; d < head_dim; d++)
                bias += q_vec[d] * rh_vec[d];     /* q_i · Rh[dy] */
            /* 该 (qy,ky) 块内整行同值，一次填 win_w 个 */
            for (int kx = 0; kx < win_w; kx++) row[kx] += bias;
        }
    }
}
```

**非 1024 输入的全局层**还有一步：768² 裁剪的网格是 48，需要 2×48-1 = 95 行的表，
checkpoint 里只有 127 行。SAM 官方的 `get_rel_pos()` 用 **线性插值**
（`F.interpolate(mode='linear')`，注意不是 bicubic）把 127 → 95；640² 则 127 → 79。
C 端先找预计算文件 `model_dir/rel_pos_h_layer{L}_size95.bin`，找不到就按
PyTorch `align_corners=False` 的映射 `src = (dst+0.5)·src_size/dst_size - 0.5`
现场做一维线性插值（`sam_layer_forward` 中段）。四个模型目录都没附带这些 .bin，
运行时插值是实际路径。

## 4. SAM neck 与 4× 空间下采样

12 层 Transformer 输出 [768, H/16, W/16] 的空间特征图，随后两站把它变成 token：

**neck（通道压缩）**——`sam_neck_forward`，两个 1×1/3×3 卷积夹 LayerNorm2d：

```c
ds_conv2d(conv1_out, spatial, ..., 768, 256, h, w, 1, 1, 1, 0);  /* 1×1, 768→256 */
layer_norm_2d(...);                                              /* LN over 通道 */
ds_conv2d(conv2_out, ln1_out, ..., 256, 256, h, w, 3, 3, 1, 1);  /* 3×3, s=1, p=1 */
layer_norm_2d(...);
```

`LayerNorm2d` 与第 01 篇的 LayerNorm 不同：普通 LN 对**单个 token 的 768 维**归一化，
LN2d 对**同一空间位置跨 256 个通道**归一化——因为此时数据是 [C, H·W] 布局，"特征维"
换位了。

**downsample（空间压缩）**——`sam_downsample_forward`，两个 stride=2 的 3×3 卷积：

```
net_2: Conv2d(256→512, k=3, s=2, p=1)   [256,40,40] → [512,20,20]
net_3: Conv2d(512→1024/896, k=3, s=2, p=1)  [512,20,20] → [1024,10,10]
```

输出尺寸按 `floor((h + 2p - k)/s) + 1` 算：40 → (40+2-3)/2+1 = 20 → 10。
net_3 的输出通道就是版本差异所在：V1/V3/V4 是 1024（`DS_SAM_DS2_DIM`），
V2 是 896（`DS_SAM_DS2_DIM_V2`），由 safetensors 实测证实：
`net_3.weight` 在 DeepSeek-OCR 里是 [1024, 512, 3, 3]，在 DeepSeek-OCR-2 里是 [896, 512, 3, 3]。

现在可以完整回答第 1 节的"÷16 再 ÷4"：**÷16 来自 patch embed 的 stride，
÷4 来自 net_2、net_3 两个 s=2 卷积的连乘**，64×64 网格最终收敛成 16×16 = 256 个
token，每个 1024（或 896）维。这一步把 4096 个高分辨率 patch 的信息有损压缩进
256 个向量——OCR 精度对这四个卷积的正确性极其敏感，第 6 节的 neck 3×3 事故就是证据。

## 5. CLIP-L：视觉语义精炼器

V1/V3/V4 的第二级编码器是 CLIP ViT-L/14：24 层标准 ViT（D=1024，16 头，FFN 4096，
双向注意力，GELU 用 erf 精确式），常量在 `ds_ocr.h` 的 `DS_CLIP_*`。
它在流水线里的角色是"精炼器"（refiner）：SAM 给边缘、纹理这类**几何**特征，
CLIP 的 24 层在这上面叠加**语义**先验。

### 5.1 为什么跳过 patch embedding

CLIP 自带 patch embedding `Conv2d(3→1024, k=14, s=14)`（权重
`model.vision_model.embeddings.patch_embedding.weight` = [1024, 3, 14, 14]），
但本工程**加载了却从不使用**——`ds_clip_encoder_forward` 开头就把 SAM 的下采样
输出直接当 patch_embeds 喂进去：

```c
/* Both V1 and V3: use SAM features directly as CLIP patch_embeds */
clip_n_patches = n_sam_tokens;  /* 256 for 1024×1024 input */
clip_tokens = (float *)malloc(...);
memcpy(clip_tokens, sam_features, clip_n_patches * clip_dim * sizeof(float));
```

理由：SAM 已经完成了"切 patch + 投影到 token 序列"，再让 CLIP 从像素做一遍
14×14 切分既不兼容（256 个 SAM token ≠ CLIP 期望的网格）也浪费——CLIP 直接在
SAM 的 1024 维特征上做 Transformer 精炼即可。

### 5.2 CLS 的进与出，以及维度账

标准 ViT 的输入要拼一个 **CLS token**（class embedding，[1024] 可学习向量）：

```
输入:  [CLS; 256×SAM token] = [257, 1024]
       + 位置嵌入 [257, 1024]（1 行给 CLS，256 行给 patch，第 6 节）
       → Pre-LayerNorm → 24 层（双向注意力 + GELU FFN）
输出:  丢弃 CLS（取 x[1:]）→ [256, 1024]
```

CLS 进得去、出不来：它只在 24 层里充当"全局信息汇聚点"（每层双向注意力都看它），
输出时被剥掉——OCR 要的是每个空间位置的特征，不是分类向量。V1/V3/V4 的
checkpoint 没有 post-LayerNorm（`ds_ocr.c` 里 `post_layernorm` 用 `LOAD_F32_OPT`
加载、实际不存在），24 层出来直接用。

然后是与 SAM 特征的拼接，**沿特征维 concat**：

```
[256, 1024](CLIP) ⊕ [256, 1024](SAM) → [256, 2048] → projector → [256, 1280]
```

projector 是**单层线性层**（不是多层 MLP）：权重 `model.projector.layers.weight`
实测 [1280, 2048]、bias [1280]（V2 则是 [1280, 896]），config.json 里
`projector_type: "linear"` 佐证。C 端就一次 `ds_linear`：

```c
ds_linear(projected, concat_features, ctx->projector.weight, ctx->projector.bias,
          concat_len, proj_in_dim, dec_hidden);   /* [N,2048] → [N,1280] */
```

1280 = `DS_DEC_HIDDEN`，与 MoE 解码器的隐藏维一致（解码器见
[02-MoE混合专家篇](./02-MoE混合专家篇.md)）。

## 6. 位置嵌入插值：get_abs_pos 与三次卷积的两场事故

### 6.1 为什么要插值

CLIP 的位置嵌入是 [257, 1024]（1 CLS + 16×16 网格），为 256 个 patch 训练。
1024² 输入正好 256 个 patch，直接逐行相加；但 V3 的 640² 裁剪只有 10×10 = 100 个
patch，16×16 的位置表对不上号，必须把 16×16 网格**重采样**成 10×10。Python 参考的
`get_abs_pos` 做法是：剥离 CLS 行，spatial 部分重排成 [16, 16, D]，用

```python
F.interpolate(x, size=(10,10), mode='bicubic',
              antialias=True, align_corners=False)
```

再拼回 CLS。C 端对应 `ds_deep_encoder.c` 的 `ds_bicubic_resample_dim`，H、W 两个
维度分离各做一次（与 PyTorch 的可分离实现一致）：

```c
/* H pass: (16,16,D) → (10,16,D)；W pass: (10,16,D) → (10,10,D) */
ds_bicubic_resample_dim(spatial_pos, tmp_pos, src_size, tgt_size, ...);
ds_bicubic_resample_dim(tmp_pos, resized_pos, src_size, tgt_size, ...);
```

### 6.2 bicubic 的数学直觉

**双三次插值**（bicubic interpolation）用周围 4×4 邻居的加权和代替双线性的 2×2，
权重来自三次核（cubic kernel，Keys 族）：

```
W(x) = (a+2)|x|³ - (a+3)|x|² + 1          |x| ≤ 1
     = a|x|³ - 5a|x|² + 8a|x| - 4a        1 < |x| < 2
     = 0                                   |x| ≥ 2
```

常数 a 控制曲线形状：PIL 的 BICUBIC 用 a = -0.5，PyTorch `F.interpolate(bicubic)`
用 a = -0.75。仓库里两套重采样器各随其参考：CLIP 位置表的 `ds_cubic_kernel`
取 **A=-0.75**（对齐 PyTorch），SAM 位置表的 `bicubic_weight` 取 **a=-0.5**
（对齐 PIL 风格参考）——各自和对应的 Python 输出对过数，不要凭"哪个才对"互相
"统一"，参数跟参考走。

坐标映射用 `align_corners=False` 约定：目标格点 i 的源坐标是
`src = (i + 0.5) · src_size/dst_size - 0.5`（半像素对齐，两端的格点不强制重合）。

**antialias（抗锯齿）**只影响缩小（scale<1）的情形：直接用 4×4 核缩小 1.6 倍会
跳采样——部分源行根本没被摸到，高频（位置表的行间差异）混叠成伪影。抗锯齿把核的
支撑域从 ±2 拉宽到 **±2/scale**（10/16 缩小时 ±3.2 个源格点，约 7×7 邻域），再对
权重归一化：

```c
float scale = (float)src_n / (float)dst_n;
int antialias = src_n > dst_n;
float support = antialias ? 2.0f * scale : 2.0f;   /* 降采样时核展宽 */
...
float arg = antialias ? (j - center) / scale : (j - center);
w[j - j0] = ds_cubic_kernel(arg);
...
if (wsum > 0.0f) for (...) w[j - j0] *= inv;       /* 归一化防边界漂移 */
```

放大时 support 退回 2，等价于标准 4×4 bicubic——antialias 只在"信息变密"的方向
起作用。

### 6.3 事故一：CLIP 位置表"抄前 101 行"（真实 bug）

- **症状**：V3 在多裁剪图上输出前面挂着一串孤儿 HTML 闭合标签
  （`</td></tr></table>` 前缀），封面页/小图输出整段错乱。
- **根因**：早期 C 实现遇到 total_len ≠ 257 时**直接截取
  `position_embedding[0:total_len]`**——对 10×10 网格等于拿 16×16 表的前 6 行半
  当位置编码，101 个 token 的位置信息系统性错乱（git 817b129 修复记录）。
- **错误做法 → 修复**：第一版修复换成双线性插值（bilinear，仍是 2×2 邻居，无抗锯齿），
  症状减轻但和 Python 参考仍有可测偏差；最终替换为上面的**抗锯齿 bicubic**，
  与 `F.interpolate(mode='bicubic', antialias=True, align_corners=False)` 逐位对齐
  （git e5c98d3："the 16x16→10x10 grid interpolation is now faithful"），配合输出端
  的孤儿标签清理，封面页输出恢复干净。
- **验证**：除了对拍插值结果本身，仓库还有 `tools/regress.sh` 精度回归门控
  （4 模型 × 8 图，CER 阈值冻结在 1.0%，见第 10 节）——任何触碰位置编码的改动
  都会被它拦下。

### 6.4 事故二：SAM 位置表的"CLS 幻影"（真实 bug，更隐蔽）

CLIP 的表带 CLS 行（257 行），而 **SAM 的 `model.sam_model.pos_embed` 实测是
[1, 64, 64, 768] 的纯二维网格、无 CLS**。早期 C 代码按版本写了三套索引分支
（git 4a45bc4 + eae0424 的审计记录）：

- V1 分支误以为 SAM 表也是"[577,768] 带 CLS"结构，用 `(p+1)` 偏移索引——4096 个
  patch 的位置**整体错位一行**，且 p=4095 时越界读 3 KB（AddressSanitizer 必崩）；
- V3 分支对 640² 输入（全部局部裁剪）**既不插值**，又按错误的宽度寻址；
- 同一时期 neck 的第二个卷积按 1×1 实现，而权重形状 [256, 256, 3, 3] 明示 3×3
  （4a45bc4 修复）。

**症状与验证数字**：修复前 V3 对 `test_simple.png` 输出幻觉文本
"The quick brown fox jumps over the lazy dog."；修复后正确输出 "Hello World 123"。
编码器输出与 Python 参考的**余弦相似度从 0.28（近似随机）修复到 0.97**。

最终 eae0424 把三套分支**统一成单一代码路径**：二维网格索引 + 64→目标网格的
bicubic 插值（768² 裁剪 64→48，与 Python 参考平均误差 0.36%；优先加载
`model_dir/pos_embed_48x48.bin` 等预计算文件，四个模型目录均未附带，实际走运行时
插值）。同一次审计还顺带修了 SAM 重采样核常数（a=-0.75 → -0.5，见 6.2）和
V1 全局图 stretch→pad。

> **本节教训**：位置信息是视觉侧最容易出错、又最难从 loss/日志上看出问题的部分——
> 它不炸、不报错，只是让模型"看哪儿都像看错了地方"，最后以幻觉、重复行、孤儿标签
> 这类诡异形态烧到输出上。任何"位置相关"的实现（索引、插值、网格重排）都值得
> 单独对拍。上面 0.28→0.97、0.36%、diff max=0.209 这类数字全部来自 git 提交与
> 代码注释，可复现。

## 7. 动态多裁剪：dynamic_preprocess 逐步算例

固定 1024² 意味着 A4 文档要么被压扁（横向长图）要么小字缩没。V2/V3/V4 的解法
（`ds_image.c: ds_dynamic_preprocess` + `find_closest_aspect_ratio`）是 NaViT
"保比例 + 分块"思想的工程化，五步：

1. 算原图纵横比 `aspect_ratio = w/h`；
2. 在候选网格 {(i, j) : i·j ∈ [min_num, max_num]} 里选 i/j 最接近原图比例的组合
   （i 是宽方向块数，j 是高方向块数；V2 调用参数 (768, 2, 6)，V3/V4 是 (640, 2, 32/16)）；
3. 整图 resize 到 (i·size, j·size)（抗锯齿 bicubic）；
4. 等分成 i×j 个 size×size tile，**行主序**编号（先从左到右、再从上到下）；
5. 缩略图（thumbnail）不由本函数生成（`use_thumbnail=0`），由调用方单独 pad 一张全局图。

**用 1600×2264 的图对 V3 全程算一遍**：

```
aspect_ratio = 1600/2264 = 0.7067
候选里比例最接近的: 2:3 = 0.6667（差 0.0400）; 3:4 = 0.75（差 0.0433）→ 选 2×3
（同比例的 4×6 因 tie-break 落选，见下）
resize 到 (2×640, 3×640) = 1280×1920，切成 6 个 640² tile
每个 tile: SAM 100 tok → CLIP 111 tok（含换行）→ 剥换行 100 tok
局部 6 块重排成 30 行×20 列网格，行末补换行: 30×(20+1) = 630 tok
全局图 pad 1024²: 273 tok（16 行×17 + 1 分隔符）
总 token = 630 + 272 + 1(view_seperator) = 903
```

**tie-break 的细节**值得单独看（`find_closest_aspect_ratio`）：2/3 与 4/6 的浮点
比例完全相等，此时规则是"图够大就选块数更多的组合"：

```c
} else if (diff == best_diff) {
    /* Tie-break: prefer larger ratio if image area is large */
    if (area > (long long)(0.5f * image_size * image_size * i * j)) {
        best_width_blocks = i; best_height_blocks = j;
    }
}
```

1600×2264 面积 3.62M < 0.5·640²·24 = 4.92M，所以**不**升级到 24 块——没有这条
护栏，一张中等图片会被切成远超必要的 tile 数，token 成本翻四倍。同一张图给 V2
算：候选 (768, 2, 6) 同样选出 2×3，resize 到 1536×2304，6 tile × 144 tok +
全局 256 + 分隔 1 = **1121 token**（`ds_ocr.c` 里 `DS_SKIP_ENCODER` 路径硬编码的
1121 就是它）。

**成本上限**：V3 允许最多 32 块，极端长图（1:32）会得到 1×32 网格 → 局部
320 行×(10+1) = 3520 + 273 = **3793 token**；token 数随块数线性增长，这正是
[05-性能优化实战篇](./05-性能优化实战篇.md) 里 V3 大图 43s 编码的来源。
V4 把上限收到 16（`ds_ocr.c`: `max_crops_v34 = (model_version==4) ? 16 : 32`），
注释给出理由：官方 vLLM `UnlimitedOCRProcessor` 最多 16 crop，超出训练分布的
token 数会让模型把多视图误读成多页（`<PAGE>`×N）。

## 8. 2D 网格重排：image_newline 与 view_seperator

projector 输出的一维 token 序列丢掉了二维结构——解码器不知道"第 16 个 token 换行
了"。V1/V3/V4 的 checkpoint 训练了两个可学习向量来补回这个信息：

- `model.image_newline` [1280]：插在**每行末尾**的"换行符"；
- `model.view_seperator` [1280]：追加在**整个视图序列最后**的"视图结束符"。

拼装代码（`ds_deep_encoder.c`）：

```c
int grid_h = (int)sqrtf((float)concat_len);   /* 16 */
int grid_w = concat_len / grid_h;             /* 16 */
int final_len = grid_h * (grid_w + 1) + 1;    /* 16×17 + 1 = 273 */
for (int row = 0; row < grid_h; row++) {
    memcpy(... , projected + row * grid_w * dec_hidden, ...);  /* 16 个 patch */
    memcpy(... , image_newline, dec_hidden * sizeof(float));   /* 行末换行 */
}
memcpy(... , view_sep, dec_hidden * sizeof(float));            /* 最后 1 个分隔符 */
```

所以 1024² 全局图是 **16 行 × (16 patch + 1 newline) + 1 view_sep = 273 token**；
V3 的 640² 裁剪是 10×(10+1)+1 = **111 token**。这个技巧源自 LLaVA-1.5：给解码器
显式的行边界信号，对表格、多栏版面是刚需——没有换行符，模型分不清"两列并排"和
"一行流"。

**多裁剪下的三步舞**（V3/V4 局部特征，`ds_ocr.c`）：每个 tile 先得到带换行的
111 token → **剥**掉换行还原 10×10 原始特征 → 按 tile 网格拼成 (rows·10)×(cols·10)
大网格 → **再插**换行。先剥再插是因为 tile 各自的换行只认识"自己这一行"，跨 tile
的行结构必须在大网格坐标系里重新生成：

```
6 个 tile 各 111 tok ─剥→ 6×100 ─拼→ 30×20 网格 ─插→ 30×21 = 630 tok
```

V2 的 DeepEncoder 走的是另一套：**没有 image_newline**（V2 checkpoint 里根本没有
这个张量，`ds_ocr.c` 用 `LOAD_F32_OPT` 容忍缺席），只在序列尾部追加一个
view_seperator——因为 V2 的因果流查询本身按序收集信息，行结构由 token 顺序隐式
携带。全局图 pad 后的"小块"同理：V2 小图 = 256 + 1 = **257 token**。

## 9. V1 / V2 / V3 / V4 四代视觉侧对比

| | V1 DeepSeek-OCR | V2 DeepSeek-OCR-2 | V3 Unlimited-OCR | V4 Unlimited-OCR-2 |
|---|---|---|---|---|
| SAM net_3 输出维 | 1024 | **896** | 1024 | 1024 |
| 二级编码器 | CLIP-L 24 层 | DeepEncoder V2（24 层 GQA 14Q/2KV，因果流查询，RoPE θ=10⁶） | CLIP-L 24 层 | CLIP-L 24 层 |
| projector | 2048→1280 线性 | 896→1280 线性 | 2048→1280 线性 | 2048→1280 线性 |
| 全局图 | pad 1024² | pad 1024² | pad 1024² | pad 1024² |
| 局部裁剪 | 无 | 768²，2–6 块 | 640²，2–32 块 | 640²，**2–16 块** |
| image_newline | 有 | **无** | 有 | 有 |
| 小图 token | 273 | 257 | 273 | 273 |
| 1600×2264 token | 273 | 1121（6 块） | 903（6 块） | 903（6 块） |
| 解码器注意力 | 全注意力 | 全注意力 | R-SWA 窗口 128 | **DASH** + page2d RoPE |

几点说明（全部可从代码/config 复核）：

- **V4 的视觉侧与 V3 完全同构**（`init_config` 中 version==4 分支注释：
  "与 V3 相同的视觉编码器 (SAM+CLIP-L) + linear projector"），四个 checkpoint 的
  视觉张量形状逐一比对过：pos_embed [1,64,64,768]、net_3 [1024,512,3,3]、
  projector [1280,2048]、image_newline [1280] 全部一致。差异只有两处：裁剪上限
  16 vs 32（训练分布对齐），以及解码器整体换血（[14-V4与DASH注意力篇](./14-V4与DASH注意力篇.md)）。
  V4 config 的 `per_page_image_tokens: 273` 也印证"每页 273 token"的视觉输出约定。
- **V2 是唯一" SAM 维度 + 编码器全换"的版本**：SAM 的 net_3 少 128 通道（896），
  CLIP 被替换为 Qwen2-0.5B 架构的 DeepEncoder V2——SAM 输出 [256, 896] 拼上等长
  的因果流查询 `model.qwen2_model.query_1024.weight` [256, 896]（768² 裁剪用
  `query_768.weight` [144, 896]），过 24 层"视觉双向 + 查询因果"的混合注意力，
  取查询位置的输出过 projector。视觉 token 数不变（256/144），但每个 token 的
  内容生成机制与 CLIP 路线完全不同。
- **版本自动检测**（`ds_ocr.c: detect_model_version`）读 config.json 关键字：
  先查 V4 标记（`"dash"` / `training_stage` / `sparse_attention_config`），**再**查
  V3（`sliding_window_size` / `UnlimitedOCR`），然后 V2（`DeepEncoderV2` /
  `causal_flow`），都不中则 V1。顺序不能反——V4 的 config 同样含
  `sliding_window_size: 128`，先查 V3 会把 V4 误判成 V3。

以下命令均在仓库根目录可直接执行（模型在 `models/`，测试图在根目录与
`docs/golden/images/`）。

1. **看 token 形状随输入变**。跑 V1（无裁剪）与 V3 大图各一次，观察 stderr 的



   验证 neck 输出是 256×64×64、downsample 输出是 1024×16×16（全局图）。

   `[DUMP] patch_embed manual ch0 patch(0,0) = ... conv2d output = ...`），两数应相等。

4. **neck 对拍**。`dump_sam_neck.py`（根目录）用 PyTorch 跑官方 neck/downsample 并
   存 `dump/py_sam/*.bin`；`compare_neck.py` 逐步对比 C 与 Python 的 conv1/LN/conv2/

   经 12+24 层放大所致，不影响 OCR 质量）。

5. **位置编码插值实验**。`DS_LOAD_ENC_INPUT=dump/py_enc_input_crop0.bin` 可把

## 小结

视觉侧的本质是"把图变成一串带位置语义的向量"，四个角色各司其职：**SAM patch
embed** 定空间颗粒度（÷16），**窗口注意力 + rel-pos bias** 让几何编码便宜 17.5 倍，
**neck + 下采样**再压 4× 得到 (边长/16/4)² 的 token 网格；**CLIP-L** 叠语义先验，
**动态多裁剪**让分辨率跟随版面而非固定常数；**换行符/分隔符**把一维序列缝回二维。
四代模型的差异集中在"二级编码器是谁"与"裁剪参数"上，SAM 骨架从未变过。

本仓库三次最痛的视觉侧 bug 全部发生在**位置**上：SAM 位置表的 CLS 幻影（错位 +
越界）、CLIP 位置表的截断抄写、neck 卷积核尺寸——症状都是幻觉与错乱，而非报错。
位置相关代码（索引、插值、网格重排）值得写对齐测试，也最值得被回归门控保护。
