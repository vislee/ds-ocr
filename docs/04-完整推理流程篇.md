## 1. 总览：三条推理管线 + 对照

ds-ocr 三个版本（V1、V2、V3）遵循相同的**"编码器理解图像 → 解码器生成文字"**范式，但编码器架构和解码器注意力机制各不相同：

```
┌──────────────────────────────────────────────────────────────┐
│                    通用推理管线                                │
│                                                              │
│  原始图像 → [预处理] → [视觉编码器] → [投影]                  │
│                                    ↓                         │
│           [构建 Prompt] → [Prefill] → [Decode 循环] → OCR文字 │
└──────────────────────────────────────────────────────────────┘

ds-ocr V1:  图像 → SAM ViT-B → CLIP ViT-L/14 → Concat → Projector → MoE Decoder → OCR文字
ds-ocr V2:  图像 → 多裁剪+SAM → DeepEncoder V2 → Projector → MoE Decoder → OCR文字
ds-ocr V3:  图像 → SAM ViT-B → CLIP ViT-L/14 → Concat → Projector → MoE Decoder(R-SWA) → OCR文字
```

**三版核心差异一览**：

| | V1 (DeepSeek-OCR) | V2 (DeepEncoder V2) | V3 (Unlimited-OCR) |
|--|-------------------|---------------------|---------------------|
| **编码器** | SAM + CLIP 双编码器 | SAM + Qwen2-0.5B | SAM + CLIP 双编码器 |
| **特征融合** | Concat(SAM, CLIP) → 2048-dim | 因果流查询 → 896-dim | Concat(SAM, CLIP) → 2048-dim |
| **解码注意力** | 标准因果注意力 | 标准因果注意力 | R-SWA（参考滑动窗口） |
| **图像输入** | 1024×1024 拉伸 | 动态多裁剪 | 1024×1024 拉伸 |
| **图像 token** | 273（含 newline + view_sep） | 256+（含 view_sep） | 273（含 newline + view_sep） |
| **特殊设计** | CLIP 接收 SAM 特征 | 因果流查询 | R-SWA + det/ref 标签过滤 |
| **适用场景** | 通用 OCR | 高分辨率多裁剪 | 长文档无限制解析 |

> **qwen-asr 对照**：音频 → Mel → Conv+Transformer → Proj → Dense Decoder → 转录文字。两个项目共享相同的解码骨架（RMSNorm → 注意力 → MoE/FFN）和内核实现。

### 版本自动检测

ds-ocr 通过读取 `config.json` 自动检测模型版本（`ds_ocr.c: detect_model_version()`）：

```c
/* 检测顺序：V3 → V2 → V1 */
if (strstr(buf, "sliding_window_size") || strstr(buf, "unlimited-ocr"))
    return 3;  /* V3: 有 sliding_window_size 字段 */
if (strstr(buf, "DeepEncoderV2") || strstr(buf, "causal_flow"))
    return 2;  /* V2: 有 DeepEncoderV2 或 causal_flow */
return 1;       /* V1: 默认 */
```

## 2. ds-ocr 全流程：图像 → 文字

### 2.0 入口：`ds_recognize()` → `ds_recognize_image()`

```c
char *ds_recognize(ds_ctx_t *ctx, const char *image_path) {
    ds_image_t *img = ds_image_load(image_path);  /* 加载图像 */
    return ds_recognize_image(ctx, img->pixels, img->width, img->height, img->channels);
}
```

用户调用 `ds_recognize()`，传入图像路径，返回识别出的文字。

### 2.1 Step 1: 图像预处理

**V2 多裁剪模式**（大图像 > 768×768）：
- 生成 N 个 768×768 的局部裁剪（local crops）
- 1 个 1024×1024 的全局缩略图（global view）

```c
if (width > 768 || height > 768) {
    /* V2 大图像：多裁剪 */
    crops = ds_dynamic_preprocess(&img, 768, 1, 12, 0, &n_crops);
    /* n_crops 通常 = 6 (6个768×768局部裁剪) */
    /* 全局图: 原图 pad 到 1024×1024 */
} else {
    /* 小图像：直接 pad 到 1024×1024 */
    global_img = ds_image_pad(&img, 1024, 127);
}
```

**V1/V3 单图模式**：
- 统一拉伸到 1024×1024（stretch resize，不做动态多裁剪）
- 输入分辨率固定，确保 CLIP 接收 256 个 token

> **关键差异**：V2 使用动态多裁剪以处理高分辨率图像，V1/V3 使用固定 1024×1024 拉伸。这是因为 V1/V3 的 CLIP 编码器需要固定的空间结构（16×16 grid）来与 SAM 特征对齐。

### 2.2 Step 2: SAM 视觉编码（三版共用）

每个裁剪/全局图通过 **SAM ViT-B** 提取视觉特征：

```
图像 [3, 1024, 1024]
    ↓ Patch Embed: Conv2d(3→768, k=16, s=16)
    ↓ [768, 64, 64] = 4096 patches
    ↓ + 位置编码 [577, 768]
    ↓ 12 层 Transformer (window attention + global attention)
    ↓ SAM Neck: Conv2d+LN → Conv2d+LN → 下采样
    ↓ SAM 特征
```

**输出维度因版本不同**：
- **V1/V3**：SAM Neck 输出 [n_tokens, **1024**]（`cfg->sam_ds2_dim = 1024`）
- **V2**：SAM Neck 输出 [n_tokens, **896**]（`cfg->sam_ds2_dim = 896`）

**关键细节**：
- SAM 使用**窗口注意力**（window_size=14）+ **全局注意力**（在 layer 2,5,8,11）
- 窗口注意力需要**相对位置编码**（rel_pos_h, rel_pos_w）
- 全局注意力时，所有 patch 互相可见

```c
/* SAM 前向传播 */
float *ds_sam_forward_image(ds_ctx_t *ctx, const ds_image_t *img,
                             int *out_n_tokens, float **out_patch_embeds);
/* 输出: SAM 特征 [n_tokens × sam_ds2_dim] */
/* 1024×1024 → 64/4 × 64/4 = 256 tokens */
/* 768×768 → 48/4 × 48/4 = 144 tokens */
```

**V2 多裁剪并行**：
```c
/* 6 个局部裁剪并行编码 */
for (int i = 0; i < n_crops; i++)
    pthread_create(&threads[i], NULL, crop_worker, &tasks[i]);
for (int i = 0; i < n_crops; i++)
    pthread_join(threads[i], NULL);
```

> **从 Step 3 开始，三条路径分叉**：V2 走 DeepEncoder V2（2.3），V1/V3 走 CLIP 双编码器（2.4/2.5）。

### 2.3 V2 编码管线：DeepEncoder V2

SAM 特征通过 **DeepEncoder V2**（Qwen2-0.5B 架构）进一步编码：

```
SAM 特征 [256, 896]
    ↓ + 因果流查询 [256, 896]  ← 可学习的查询向量
    ↓ 24 层 Transformer (混合注意力)
    │   视觉 token: 双向注意力
    │   因果查询: 因果注意力
    ↓ 最终 RMSNorm
    ↓ 输出 [256, 896]
```

```c
float *ds_encoder_forward_v2(ds_ctx_t *ctx, const float *visual_tokens,
                               int n_tokens, int *out_seq_len,
                               int n_causal_queries, const float *causal_queries);
```

> **因果流查询**是 DeepSeek-OCR V2 的创新：256 个可学习的查询向量通过因果注意力逐个"收集"视觉信息，输出直接传给解码器。

### 2.4 V1 编码管线：SAM + CLIP 双编码器

V1 采用 **双编码器架构**——SAM 提取底层视觉特征，CLIP 提供高层语义理解，两者特征拼接后送入解码器。

#### 2.4.1 架构总览

```
图像 [3, 1024, 1024]
    ↓ SAM ViT-B (12 层, window attention)
    ↓ SAM Neck: 256→512→1024 channels
    ↓ SAM 特征 [256, 1024]  ──────────────┐
    │                                     │ Concat (feature dim)
    ↓ CLIP ViT-L/14 (24 层, 16 heads)    │
    ↓ (SAM 特征作为 CLIP patch_embeds)    │
    ↓ CLIP 输出 [256, 1024]  ────────────┘
    ↓
    ↓ 拼接特征 [256, 2048]
    ↓ Projector: Linear(2048→1280)
    ↓ + image_newline + view_seperator
    ↓ 最终: 273 tokens [273, 1280]
```

#### 2.4.2 CLIP 如何接收 SAM 特征

这是 V1/V3 最独特的设计：**CLIP 绕过自身的 Conv2d patch_embed，直接接收 SAM 特征作为输入**。

```c
/* ds_deep_encoder.c: ds_clip_encoder_forward() */

/* Step 1: 用 SAM 特征直接作为 CLIP 的 patch_embeds
 * CLIP 的 patch_embedding Conv2d [1024, 3, 14, 14] 完全不使用！
 * SAM 的 16× 压缩已经产生了 256 个 token，CLIP 直接处理它们。
 */
clip_n_patches = n_sam_tokens;  /* 256 for 1024×1024 input */
clip_tokens = (float *)malloc(clip_n_patches * clip_dim * sizeof(float));
memcpy(clip_tokens, sam_features, clip_n_patches * clip_dim * sizeof(float));
```

**为什么要绕过 patch_embed？**
- CLIP 原始设计是对 RGB 图像做 14×14 的 patch 切分，每个 patch 投影为 1024 维向量
- 但 V1/V3 中，SAM 已经完成了类似的"patch 化 + 投影"工作，且更精细（包含多尺度信息）
- 让 CLIP 直接处理 SAM 特征，相当于"二次精炼"——SAM 提取底层特征，CLIP 提供高层语义

#### 2.4.3 CLIP 内部处理

```
SAM 特征 [256, 1024]
    ↓ 添加 CLS token → [257, 1024]
    ↓ + 位置编码 (get_abs_pos, 可能需要插值)
    ↓ Pre-LayerNorm
    ↓ 24 层 Transformer (标准 ViT: LN→MHA→残差→LN→MLP→残差)
    ↓ 移除 CLS token → [256, 1024]
```

**位置编码插值**：
CLIP 原始位置编码为 257 个（1 CLS + 16×16 = 256 patches）。当 `clip_n_patches = 256` 时完美匹配，无需插值。对于非标准尺寸，需要双线性插值：

```c
/* ds_deep_encoder.c: 位置编码插值 */
if (total_len <= 257) {
    /* 直接复制 — 257 个位置编码正好够用 */
    for (int i = 0; i < total_len; i++)
        for (int d = 0; d < clip_dim; d++)
            x[i * clip_dim + d] += clip->position_embedding[i * clip_dim + d];
} else {
    /* 双线性插值: [16×16] → [tgt_h × tgt_w] */
    int src_size = 16;  /* CLIP 原始空间尺寸 */
    int tgt_size = (int)sqrtf((float)clip_n_patches);
    /* ... bicubic interpolation code ... */
}
```

#### 2.4.4 特征拼接 + Projector

CLIP 和 SAM 的特征沿特征维度拼接：

```c
/* ds_deep_encoder.c: 特征拼接 */
/* V1/V3: CLIP 和 SAM 有相同 token 数量 (256 each for 1024×1024) */
/* Concat: [256, 1024] + [256, 1024] → [256, 2048] along feature dim */
concat_len = clip_output_len;
proj_in_dim = clip_dim + cfg->sam_ds2_dim; /* 1024 + 1024 = 2048 */
concat_features = (float *)malloc(concat_len * proj_in_dim * sizeof(float));
for (int t = 0; t < concat_len; t++) {
    memcpy(concat_features + t * proj_in_dim,
           clip_output + t * clip_dim, clip_dim * sizeof(float));
    memcpy(concat_features + t * proj_in_dim + clip_dim,
           sam_features + t * cfg->sam_ds2_dim, cfg->sam_ds2_dim * sizeof(float));
}

/* Projector: Linear(2048 → 1280) */
ds_linear(projected, concat_features, ctx->projector.weight, ctx->projector.bias,
          concat_len, proj_in_dim, dec_hidden);
```

> **对比 V2**：V2 的 Projector 输入维度是 896（仅 DeepEncoder 输出），V1/V3 的 Projector 输入维度是 2048（CLIP 1024 + SAM 1024 拼接），所以 V1/V3 的 Projector 权重更大。

#### 2.4.5 image_newline + view_seperator 布局

V1/V3 的 273 个图像 token 有特殊的空间布局：

```
16 rows × (16 patches + 1 image_newline) + 1 view_seperator = 273 tokens

Row 0:  [patch_0, patch_1, ..., patch_15, image_newline]   ← 17 tokens
Row 1:  [patch_16, patch_17, ..., patch_31, image_newline]  ← 17 tokens
...
Row 15: [patch_240, ..., patch_255, image_newline]          ← 17 tokens
Last:   [view_seperator]                                     ← 1 token
Total:  16 × 17 + 1 = 273 tokens
```

```c
/* ds_deep_encoder.c: 构建 2D grid 布局 */
int grid_h = (int)sqrtf((float)concat_len); /* 16 */
int grid_w = concat_len / grid_h;           /* 16 */
float *image_newline = ctx->vis_tokenizer.image_newline;   /* [1280] 可学习 */
float *view_sep = ctx->vis_tokenizer.view_seperator;       /* [1280] 可学习 */

/* Build: [row0_patches, newline, row1_patches, newline, ..., view_sep] */
int final_len = grid_h * (grid_w + 1) + 1; /* 16*17+1 = 273 */
for (int row = 0; row < grid_h; row++) {
    memcpy(final_out + dst * dec_hidden,
           projected + row * grid_w * dec_hidden,
           grid_w * dec_hidden * sizeof(float));
    dst += grid_w;
    memcpy(final_out + dst * dec_hidden, image_newline, dec_hidden * sizeof(float));
    dst += 1;
}
memcpy(final_out + dst * dec_hidden, view_sep, dec_hidden * sizeof(float));
```

> **为什么需要 image_newline？** 它相当于"行分隔符"，告诉解码器图像空间结构的行边界。这类似于文本中的换行符，帮助解码器理解图像 token 的二维排列。view_seperator 则标记整个图像 token 序列的结束。

#### 2.4.6 V1 的 Prompt 格式

V1 的解码器输入序列：

```
[BOS] + [img_start] + [273_图像 tokens] + [img_end] + ["\nFree OCR."]
```

- 273 图像 token = 16 行 × (16 SAM + 1 newline) + 1 view_seperator
- `image_token_id`：V1 使用 `DS_TOKEN_IMAGE_START` 作为图像占位符
- Prompt 文本：`"\nFree OCR."` → token IDs [201, 21431, 126041, 16]
- **max_position_embeddings**：8192

### 2.5 V3 编码管线：SAM + CLIP 双编码器 + R-SWA 解码

V3（Unlimited-OCR）的视觉侧与 V1 同为「SAM + CLIP 拼接」，但围绕**长文档**重新设计了三件事：动态多裁剪、网格重排、滑动窗口解码。

#### 2.5.1 编码侧：640 局部 + 1024 全局

V2 的裁剪阈值是 768，V3 改为官方 `infer()` 的 `image_size=640`（`ds_ocr.c` V3 多裁剪路径，`use_crop = width > 640 || height > 640`）：

```
大图（任一维 > 640）:
  全局视图: 一律 pad 到 1024×1024 → SAM(256 tokens) → CLIP(256) → Proj → 273
  局部裁剪: dynamic_preprocess(640, min_num=2, max_num=32) → N 个 640×640
            每个 → SAM(100 = 10×10) → CLIP(100) → Proj → 111（10 行 × 11 + view 处理）
  关键步骤: CLIP 输出的 111 tokens 自带换行 → 剥掉 → N 个 10×10 网格
            拼成大网格 → 按**新网格**重插 image_newline
  拼接: [local(N×…), global(272), view_sep(1)]

小图（≤640）: 只有全局视图 → [global(272), view_sep(1)] = 273 tokens
```

两个容易踩的坑（`ds_ocr.c` 注释原话）：
- **全局视图与图像大小无关**——小图也走 1024 视图出 273 tokens。早期 C 实现用 640 视图（111 tokens）导致 V3 小图重复行、V4 小图乱码。
- **max_crops 按版本收窄**——V4 的 vLLM 部署最多 16 crop，超出训练分布的 token 数会让模型把多视图误读成多页。

并行方式与 V2 相同（N+1 workers），但调度升级为**动态取件池**：N 个局部任务用原子索引取件（docs/05 §10.6），全局视图 worker 最先启动，与主线程的 `dynamic_preprocess` 整图缩放重叠执行。

#### 2.5.2 解码侧：R-SWA 滑动窗口

V3 解码器注意力不再是「全部历史可见」，而是分两段（实现在 `ds_kernels.c` → `ds_rswa_attention_aligned` / `ds_rswa_attention_aligned_bf16`，配置在 `ds_ocr.c` → `sliding_window_size = 128`）：

```
位置 [0, prefill_token_count)     → Reference 段：视觉 token + prompt，永远可见
位置 [prefill_token_count, ...)   → 滑动窗段：最近 128 个生成 token
```

数学上仍是 causal attention，只是注意力掩码把「历史」换成「参考段 + 窗口」。两段各自的在线 softmax 用 max-correction 合并（docs/01 §5），结果与「全量 softmax 后丢弃窗外权重」逐位一致。这让 decode 每步读的 KV 从 O(总长) 变成 O(prefill_len + W)，长文档内存恒定（docs/05 §6）。

### 2.6 Step 3: Prompt 构造——三个版本的序列布局

编码输出 `[n_encoder_tokens, 1280]` 只是「图像部分」。要喂给解码器，还要拼上特殊 token 和指令文本（`ds_ocr.c` → `prompt_construction` 段）：

| 版本 | 序列布局 | 图像 token | 指令文本 | prefix 总长 |
|------|---------|-----------|---------|------------|
| **V1** | `[BOS]` + `img_start(151655)` + 视觉 tokens + `img_end(151656)` + `"\nFree OCR."` | 273（16×17+1） | 4 tokens（ID 201, 21431, 126041, 16） | **280** |
| **V2** | `[BOS]` + 图像槽位（masked_scatter 布局）+ `"\nFree OCR."` | 全局 257 + 每 crop 100 槽 | 4 tokens | 6-crop 实测 **862** |
| **V3** | `[BOS]` + 视觉 tokens + `"\ndocument parsing."` | 273（小图）/ local+273（大图） | 4 tokens（ID 201, 34030, 76466, 16） | 小图 **116**；6-crop 实测 **908** |
| **V4** | `[BOS]` + `<PAGE>(128827)` + 视觉 tokens + `"Multi page parsing."` | 同 V3 | 4 tokens（ID 37460, 4366, 76466, 16） | V3 + 1 |

实现细节（`EMBED_TOKEN` 宏）：

```c
/* token embedding 查表：BF16 是 F32 截断低 16 位的存储格式，
 * 还原只需位模式左移 16 位——无乘法无查表 */
const uint16_t *e = ctx->decoder.tok_embeddings_bf16 + tid * hidden;
for (int i = 0; i < hidden; i++) {
    uint32_t f32 = ((uint32_t)e[i]) << 16;
    memcpy(&input_embeds[pos * hidden + i], &f32, sizeof(float));
}
/* 图像位置先用占位 token 嵌入，再整块 memcpy 覆盖为编码器输出 */
```

> **为什么指令文本用硬编码 fallback ID？** C 版 BPE 对 "\nFree OCR." 这类前导空白文本的 pre-tokenizer 切分可能与 HuggingFace 不一致，所以先 `ds_tokenizer_encode`，失败时回退到用官方 tokenizer 验证过的 ID 表（`ds_ocr.c` 各版本 fallback 注释）。

### 2.7 Step 4: Prefill——批量填充 KV 缓存

Prompt 序列就绪后，一次性送入解码器（`ds_moe_decoder.c` → `ds_decoder_prefill`，调用点在 `ds_ocr.c` Step 4）：

```c
ctx->kv_cache_len = 0;                       /* 每次识别重建缓存 */
if (ds_decoder_prefill(ctx, input_embeds, prefix_len) != 0) {
    fprintf(stderr, "Prefill failed: prefix exceeds KV cache\n");
    return NULL;                             /* 唯一的失败路径：KV 越界 */
}
```

`ds_decoder_prefill` 内部是一个「层外循环、token 内并行」的批量流水线：

```
for l in 0..11:
    madvise(WILLNEED) 第 l+1 层全部权重（含 64 个专家 mmap，~440MB）  ← 跨层预取
    批量 RMSNorm（seq_len 行）
    批量 QKV 投影：3 次 [seq,1280]×[1280,dim] sgemm
    per-head Q/K norm（V1/V2 有，V3 无）
    批量 RoPE
    K/V 整块写入 KV cache [kv_cache_len, kv_cache_len+seq)
    因果批量注意力（在线 softmax，不物化 seq×seq 矩阵）
    Wo 投影 + 残差 → post-attn norm → FFN（L0 批量 sgemm / L1-11 Gather-Compute-Scatter）
最后：kv_cache_len += seq_len；对最后一个位置算 logits → first_token
```

为什么 prefill 一次喂全部而 decode 逐 token？prefill 的所有 token 开始时就已知（无数据依赖），组成矩阵走 sgemm 后**权重读取被摊薄 1/seq**，瓶颈从带宽转为算力（docs/05 §3）；decode 的下一步依赖上一步输出，只能逐 token matvec，靠 KV 缓存避免重算历史 K/V。逐 token prefill 280 tokens × 12 层 ≈ 77s，批量 0.72s（100×，docs/05 §3）。

**first_token 的选择与净化**：prefill 产出 `ctx->dec_logits`（最后一个位置的 129280 维 logits），argmax 得 first_token。V3/V4 有一个关键修正：F32 推理下 prefill 冠军常是 EOS（Python 用 BF16 autocast 训练，16 位尾数差所致），只禁 EOS 会选中次优的 Ġ（空格前缀）形成「10.」振荡，故**成对禁用 EOS+Ġ 后重选**（`ds_ocr.c` Step 4 的 EOS-first fix）。

### 2.8 Step 5: Decode 自回归循环与终止条件

主循环在 `ds_ocr.c`（`for (int step = 0; step < ctx->max_new_tokens; step++)`），每步：

```
1. step 0 直接用 prefill 的 first_token；之后调 ds_decoder_forward(ctx, dec_input)
   ── 内部：12 层单 token 前向（双缓冲指针交换）→ kv_cache_len++
   ── 选词走两条路：temperature==0（默认）→ 流式 argmax（docs/03 §3.6）
                    temperature>0 → full_logits_path 物化全部 logits 再采样
2. 终止检查（顺序即优先级，见下表）
3. token 写入 token_history（服务重复惩罚与 n-gram 阻断）
4. ds_tokenizer_decode(token) → 文本片段 → 权威缓冲 output（含标签，最后统一清理）
   流式回调走独立的 ds_stream_filter_det（V3 边生成边剥 det 标签）
5. tok_embeddings[token] << 16 → 下一步的 dec_input
```

**终止条件全表**（按循环内实际判定顺序）：

| # | 条件 | 代码位置 | 行为 |
|---|------|---------|------|
| 1 | `kv_cache_len >= kv_cache_max` | `ds_ocr.c` 循环开头 | 打印 warning，break——输出被截断 |
| 2 | `step >= max_new_tokens`（默认 4096，`-n` 可调） | for 循环条件 | 正常退出 |
| 3 | 内容循环早停：每 16 步（且 ≥48 步）对输出尾部做**多尺度**字节级周期检测（3072/1536/768/384 字节依次检查；归一化剥数字/空白/括号后找周期 p∈[4,512]、≥3 完整周期全窗匹配） | `ds_output_tail_loopy`（`ds_ocr.c`，r4） | 命中即 break，`last_output_loopy=1`；`DS_NO_EARLY_STOP=1` 关闭。设计动机与三类循环形态见 08 篇 §8.4，算法逐行见 15 篇 §3 |
| 4 | `token == EOS(1)` 且 `step >= min_new_tokens` | 循环内 EOS 分支 | break——正常结束 |
| 5 | `token == EOS` 但 `step < min_new_tokens`（V3/V4 默认 32） | warmup 禁用：快速路径经 `dec_argmax_ban` 声明禁 EOS（V3 伴禁 Ġ=223）；全量路径置 `logits[eos]=-1e30` 后重选 | 抑制并选次优 |

min_new_tokens 存在的原因：V3 的 F32 logits 使 EOS 在早期步步偏高（`ds_load` 注释），前 32 步强制「热身」让上下文攒够内容后 EOS 才会出现在正确位置。

### 2.9 Step 6: 终态后处理链

decode 结束后的清理流水线（`ds_ocr.c` `ds_recognize_image` 尾部 + 后处理函数区），按执行顺序：

| 步骤 | 函数（均在 `ds_ocr.c`） | 适用版本 | 做什么 |
|------|------------------------|---------|--------|
| ① strip 空白 | 内联 while 循环（对齐 Python `.strip()`） | 全部 | 去尾部空格/换行/制表 |
| ② det 标签剥离 | `ds_strip_det_tags` | V3/V4 | 读写双指针原地剥 `<\|det\|>...<\|/det\|>` 与 `<\|ref\|>...<\|/ref\|><\|det\|>...<\|/det\|>` 对；不成对的碎标签保留（「不猜优于猜错」） |
| ③ V4 版面净化 | `ds_v4_warn_degenerate` + `ds_v4_strip_layout` | V4 | 全空块告警；剥离 `<BLOCK>/<FORK>` 结构化标签为纯文本；畸形行置 `last_output_degenerate`，`main.c` 据此整跑重试一次（`--raw-layout` 跳过净化保留原生结构） |
| ④ 幻觉前缀截断 | 内联搜索 `"[No text detected]"` 标记 | V3/V4 | 首 token 被迫越过 EOS 时可能先产出一段英文幻觉，从前 400 字符内找到标记即整体删除 |
| ⑤ 伪影清除 | `ds_recognize_image` 尾部内联块（终态层第⑥–⑧步，`ds_ocr.c`，编号对齐 docs/08 §6.3 表） | V3/V4 | ⑥纯点+空白占位行整段剥离；⑦首 token 即 closer 的断裂 det 片段连 fragment 一起剥（最多 4 轮）；⑧行首孤立 HTML 闭合标签（`</td></tr>…`）兜底清除 |

流式层另有独立的一条链：`ds_stream_filter_det` → `ds_try_strip_det_tag`（`ds_ocr.c` 文件头注释的 4 步缓冲策略），只影响流式显示，不动 `output` 权威缓冲——两层的完整对照表见 docs/08 §6。

### 2.10 一次 OCR 的完整 token 账与 FLOPs 账

把全链路的「数字账」用 V1（1024×1024 输入，M2 Pro 实测 233 tokens 输出）算一遍。所有常量来自 `ds_ocr.h`。

**① 从像素到 token：**

```
图像像素     1024 × 1024 × 3 = 3.15M 字节（uint8 RGB）
SAM patch    1024/16 = 64 → 64×64 = 4096 个 patch（每个 768 维）
SAM neck     两次 2× 下采样 → 16×16 = 256 个视觉 token（1024 维）
CLIP         256 tokens（+CLS 内部 257，输出剥掉 CLS）→ 256 × 1024
拼接 + 投影  [256, 2048] → Linear(2048→1280) → [256, 1280]
布局重排     16 行 × (16 patch + 1 newline) + 1 view_sep = 273 个图像 token
Prompt       BOS(1) + img_start(1) + 273 + img_end(1) + "\nFree OCR."(4) = 280 = prefill 长度
Decode       实测 233 步（EOS 停止）
```

**② Prefill 计算量：**

激活的参数量（每生成一个 token 实际走过的权重）：

```
每层注意力   WQ+WK+WV+WO = 4 × 1280×1280           =  6.55M
Layer 0 FFN  3 × 1280×6848（dense SwiGLU）          = 26.30M
MoE 层(×11)  router 1280×64 = 0.08M
             6 路由专家 6×3×1280×896 = 20.64M
             2 共享专家 2×3×1280×896 =  6.88M        = 27.61M/层
LM head      1280 × 129280                          = 165.48M
────────────────────────────────────────────────────
激活参数合计 ≈ 12×6.55 + 26.30 + 11×27.61 + 165.48 ≈ 574M  ← 这就是 "A570M" 的来历
```

$$\text{Prefill FLOPs} \approx 2 \times P_{active} \times S + \text{注意力项} = 2 \times 574\text{M} \times 280 \approx 321\ \text{GFLOPs}$$

注意力项（因果，只算下三角）：$2 \times 2 \times S^2 \times hidden \times L / 2 = 2\times280^2\times1280\times12 \approx 2.4$ GFLOPs，可忽略。实测 0.72s → **约 446 GFLOPS**，是 M2 Pro sgemm 峰值的一半——prefill 是计算-bound（docs/05 §7.3 的 Roofline）。

**③ Decode 每步：**

```
FLOPs：2 × 574M ≈ 1.15 GFLOPs/步（与 prefill 单 token 相同——MoE 不随 seq 变）
权重读：574M × 2 B ≈ 1.15 GB/步（BF16 流式读，逐层、逐专家）
KV 读：300 上下文 ≈ 37 MB/步（F32），写 120 KiB
时间账：实测 23.35 ms/步 → 45.7 tok/s
带宽账：1.15 GB ÷ 23.35 ms ≈ 49 GB/s ≈ 200 GB/s 的 25% —— 纯内存瓶颈（docs/05 §7）
总读流量：233 步 × 1.15 GB ≈ 268 GB——一次 OCR 从内存搬了近 3 个百 GB！
```

> **一眼看穿两阶段的性格**：prefill 321 GFLOPs / 0.72 s（算力喂饱，45% 峰值）；decode 233 × 1.15 GFLOPs / 5.1 s（算力只用了 ~5%，时间全花在把 268 GB 权重从内存搬进 CPU）。同一套权重，两种瓶颈——这就是 docs/05 全篇在解的题。

V2/V3 的账只有两处不同：prefix 更长（862/908 → prefill FLOPs ≈ 2×574M×S，V3 约 1.04 TFLOPs，实测 1.9s）、V3 的 decode 注意力读 KV 换成 R-SWA 两段式（docs/05 §6）。

## 3. qwen-asr 全流程：音频 → 文字

qwen-asr 的管线与 ds-ocr 同构，只是「视觉」换成了「音频」：

```
音频文件 → 解码 PCM → 重采样 16 kHz
    ↓ Mel 频谱（128 mel bins，25ms 窗/10ms 步）
    ↓ Conv2D stem（下采样 8×）→ Transformer encoder（分块处理长音频）
    ↓ proj1 + proj2（d_model → decoder hidden）
    ↓ [BOS] + 音频 tokens + 转录指令 prompt
    ↓ Prefill（批量 sgemm 填 KV cache）
    ↓ Decode 循环（逐 token matvec + GQA KV cache + 流式 argmax）
    ↓ 转录文本
```

与 ds-ocr 逐模块对照：

| 阶段 | ds-ocr | qwen-asr | 共享代码模式 |
|------|--------|----------|-------------|
| 输入预处理 | stb_image + resize/pad/crop | PCM → Mel 频谱 | 预处理纯函数，无状态 |
| 编码器 | SAM/CLIP/DeepEncoder V2 | Conv stem + Transformer | 同一套三级内核 |
| 投影 | Linear(2048/896→1280) | proj1+proj2 | `linear_nobias_bf16` |
| Prompt 构造 | 图像 token + OCR 指令 | 音频 token + 转录指令 | 嵌入查表 `<<16` |
| Prefill/Decode | `ds_decoder_prefill/forward` | `qwen_decoder_prefill/forward` | KV cache 布局、双缓冲交换同款 |
| 解码器 | MoE（top-6 of 64 + 2 shared） | Dense SwiGLU | 采样/惩罚/argmax 同款 |

> 差异最大的仍是解码器（docs/03 §9.3）：MoE 的 Gather-Compute-Scatter 是 ds-ocr 独有；qwen-asr 的 GQA（8 KV 头）让它的 KV 缓存比同规模 MHA 省 50%。

## 4. 三个版本的对比与共性

**共性（三条管线共享的骨架）**：

1. 「图像 → 连续视觉 token → 拼进 LLM 序列」的范式与 prompt 布局思想（BOS + 图像 + 指令）
2. 解码器完全同源：12 层、hidden 1280、64+2 专家、129280 词表、RMSNorm+RoPE
3. KV cache 布局 `[layers, max_seq, kv_row_stride]` 与 prefill/decode 二分法
4. 同一套内核与线程池（`ds_kernels*`）、同一个采样与后处理框架

**差异一览**：

| 维度 | V1 | V2 | V3 |
|------|----|----|----|
| 裁剪策略 | 无（1024² 拉伸） | >768 多裁剪（768²） | >640 多裁剪（640²）+ 1024 全局 |
| 编码器 | SAM→CLIP（CLIP 吃 SAM 特征） | SAM→Qwen2-0.5B（因果流查询） | SAM→CLIP（各吃各的图，拼接） |
| Projector 输入 | 2048 | 896 | 2048 |
| 图像 token | 固定 273 | 动态（257 + 100×N 槽） | 273（小图）/ local+273（大图） |
| 解码注意力 | 全因果 | 全因果 | R-SWA（参考段+128 窗） |
| KV 存储 | F32/4096 槽 | F32/4096 槽 | BF16/8192 槽 |
| 长文档能力 | 弱（拉伸糊小字） | 中（crop 上限 12） | 强（crop 上限 32 + KV 恒定读） |

选型建议：单据/截图用 V1（最快）；通用文档 V2 精度最佳；整本书/长报告 V3（docs/05 §8 有三者实测对比）。

## 5. 性能分析与优化空间：全链路时序图

**一次 V1 识别的时序图**（M2 Pro，1794×1578 截图拉伸至 1024²，总 12.2 s，`--profile` 实测口径）：

```
0s        2s        4s        6s  6.4s   7.1s                        12.2s
├─────────┼─────────┼─────────┼───┼──────┼───────────────────────────┤
│██████████████████████████████│   │      │████████████████████████████│
│        Encoding  6.4s 52%    │ P │      │       Decode  5.1s 42%     │
│  SAM 12 层×(窗口+全局注意力)  │rf │      │ 226 步 × 23.35 ms/步       │
│  CLIP 24 层 × 256 tokens     │ll │      │  MoE 占 73.7% ← docs/05   │
└──────────────────────────────┴───┴──────┴────────────────────────────┘
                                 ↑0.72s
                          Prefill 6%：280 tokens 批量 sgemm
                          + prompt 构造（纯内存操作，微秒级）
```

**各版本耗时占比表**（M2 Pro、同一 6-crop V2 测试图，数据同 docs/05 §8）：

| 阶段 | V1 (12.2s) | V2 (15.0s) | V3 (17.6s) | 占比规律 |
|------|-----------|-----------|-----------|---------|
| Encoding | 6.4s | 9.0s | 6.4s | 36–60%，SAM 全局注意力是大头 |
| Prefill | 0.72s (280 tok) | 0.93s (862 tok) | 0.70s (908 tok) | 4–6%，已被 sgemm 压到几乎不重要 |
| Decode | 5.1s (233 tok) | 5.1s (226 tok) | 10.5s (464 tok) | 42–60%，与**生成 token 数**成正比 |
| 每步延迟 | 23.35 ms | 23.35 ms | 23.35 ms | 三版本几乎相同（同解码器） |

读表三结论：**总耗时的主导项在 decode 步数**（V3 慢不是每步慢，是它多生成了一倍的 token）；**编码占比随裁剪数上升**（V2 多裁剪最贵）；**prefill 已不是瓶颈**（v0.5 时代它占 31%，现在 <6%）。优化方向优先级永远是 decode > encoding > prefill，方法见 docs/05。

M4 Max（1600×2264 文档图）同口径数字：prefill 0.7–1.5s（280 tok）/ 1.9s（862 tok）/ 1.9s（908 tok），decode 42–47 / 21–40 / 40 tok/s——平台越快，prefill 占比越低，结论不变。

## 6. 失败模式清单与排查手册

| 症状 | 根因 | 排查命令 / 对策 |
|------|------|----------------|
| **OOM / 峰值 RSS 超预期** | mmap 权重全量触碰（长文档逐页解码）+ 历史上「专家连续块拷贝」式的双份驻留（docs/05 §10.4：RSS 11.7→8.6 GB 的教训） | `DS_RSS_PROBE=1 ./ds_ocr ...` 打印 RSS 高水位时刻；`/usr/bin/time -l ./ds_ocr ...` 看 max RSS；对策：`--int4` 量化专家权重、确认没有把 mmap 数据 memcpy 成连续块 |
| **越跑越慢 / 大量 page fault** | 页缓存被挤出，冷专家权重反复从磁盘重入（mmap 惰性加载的双刃剑） | macOS：`vm_stat` 看 pageins；`--profile` 对比首识别与后续识别的 Encoding/Decode 差值；对策：`--stream` 模式连续识别热身、关掉吃内存的后台程序 |
| **`Failed to detect model version` / `Failed to open safetensors`** | 模型目录不全或 config.json 变体未被识别（`ds_ocr.c` → `detect_model_version` 靠关键字段探测） | `ls model_dir/` 应含 `*.safetensors`、`config.json`、`vocab.json`（或 `tokenizer.json`）；`cat config.json` 确认版本特征字段（V3 看 `sliding_window_size`，V2 看 `DeepEncoderV2`） |
| **`Prefill failed: prefix exceeds KV cache`** | prefix 超过 `kv_cache_max`（V1/V2 为 4096；V3 大图 32-crop 的 prefix 可达 ~3800） | 换 V3（8192 槽 + BF16）；或缩小图像降低 crop 数 |
| **`Warning: KV cache full — output truncated`** | decode 中缓存槽位用尽，输出被硬截断 | 同上；`-n` 调小 max_new_tokens 让截断更早可预期 |
| **输出提前终止（半句话停）** | EOS 提前（V1/V2 无 warmup）或内容循环早停误判 | `--min-tokens 32` 强制热身；`DS_NO_EARLY_STOP=1` 关闭循环早停验证 |
| **输出重复 /「10.」振荡 / 不出 EOS** | V3 的 F32 logits 使 EOS 偏高、EOS↔Ġ 振荡（docs/08 §4.3） | `--rp 1.1`（重复惩罚）、`--ngram 35`（V3 加载后默认开启）；确认没有手动关掉 warmup |
| **整体异常慢（数倍）** | ①Metal 回退在部分平台反而慢（README 警告 M2 Pro decode/prefill 回退）②线程数被 `-t 1` 或容器限额压死 ③DS_SLOW_PREFILL/DS_DEBUG 等调试开关残留 | `--profile` 看 `Thread pool: N threads` 行；确认没有设置 `DS_SLOW_PREFILL`、`DS_SKIP_ENCODER`、`DS_DUMP_*`；x86 上确认 BLAS 已链接（`make blas`） |
| **输出乱码（非精度问题）** | tokenizer 未加载（vocab.json/tokenizer.json 都缺）或版本判错走了错布局 | `--debug` 看加载日志；`DS_DUMP_INPUT_EMBEDS=/tmp/ie.bin` 导出 prefill 输入与 Python 对拍 |
| **数值对不上 Python** | 精度路径差异（F32 vs BF16 autocast） | `DS_BF16_SIMULATE_PYTHON=1` 开启 BF16 截断模拟对拍；回归验证用 `tools/regress.sh`（30 组冻结标签 + CER 阈值，docs/05 §10.2） |

> **通用排查姿势**：先 `--profile` 拿三段耗时与逐层 Profiler，再按「哪段异常 → 上表对症」；涉及数值正确性时一律用 dump 环境变量（`DS_DUMP_TENSORS`、`DS_DUMP_INPUT_EMBEDS`、`DS_LOAD_SAM_ALL` 等，`ds_dump.h` 有全集）做 C↔Python 分段对拍——「先分段，再怀疑」比整链路猜快一个数量级。
