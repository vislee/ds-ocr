## 1. 为什么需要子词分词

模型只认数字。分词器（tokenizer）就是"翻译官"：**编码**（encode）把 UTF-8 文本变成
token id 序列喂给模型，**解码**（decode）把模型吐出的 id 序列还原成文本。id 只是词表
（vocabulary）里的行号，真正被模型消费的是嵌入矩阵里那一行向量（见
[01-Transformer基础篇](./01-Transformer基础篇.md) 第 3 节）。

"以什么为单位切文本"有三个极端方案，各有一个致命伤：

| 方案 | 词表大小（英语为例） | 缺点 | 具体后果 |
|------|---------------------|------|---------|
| **词级**（按空格切单词） | 50 万+ 仍盖不全 | **OOV**（Out-of-Vocabulary，词表外）：没见过的词无法表示 | "DeepSeekOCRized" 这类新词直接无解 |
| **字符级**（按字母切） | ~1 千 | 序列过长、语义太碎 | 本篇实测样本 "Multi page parsing." 有 19 个字符，字符级要 19 步才能生成完；BPE 只需 4 步 |
| **BPE 子词** | 数万~十几万（本工程 128000 条基础词表） | 需要预训练一张合并表 | 高频词保留整词，低频词拆零件，任何字节都能兜底 |

BPE 的思路是"从字符开始，反复合并**语料中最高频的相邻符号对**，直到词表达到目标大小"：

- 训练期：统计 → 合并 → 再统计，产出一张**合并表**（merges）和一份词表；
- 推理期：按合并表对输入贪心切分。因为最底层是"字节级"符号（第 4 节），
  **任何字符串都有表示，彻底无 OOV**。

两个实测样本感受颗粒度（用本仓库词表 + 第 3 节算法可复现）：

```
"Multi page parsing."   19 字符 → 4 个 token（'Multi' 'Ġpage' 'Ġparsing' '.'）
"中"                     3 字节   → 1 个 token（id 525）
```

> 🗣️ **说人话**：如果给每个可能的词发一个编号，就像要给全世界每件家具都编个门牌号：编到 50 万条还没编完，而且明天冒出的新家具（"DeepSeekOCRized"）根本没有门牌可发。子词的做法反过来：不卖整件家具，只卖标准积木块。高频词像"the"是现成的整块积木，低频词和生僻词拆成小积木拼出来，最底层是 256 种通用零件，所以**任何字符串都拼得出**，永远不会有"词表外"这种尴尬。代价是要事先造一本"拼装手册"（合并表）。
> *边界*：积木拼法不是唯一的——同一块积木放左边还是右边，手册没写死的地方，不同实现会拼出不同结果（这正是 §9 bug 1 的土壤）。

## 2. BPE 训练：亲手造一张合并表

BPE 的全部知识浓缩在一张**合并表**里：每行 `A B` 表示"A 和 B 相邻时，把它们合并成
符号 AB"，行号即 **rank**（优先级）——rank 越小，说明这对在训练语料里出现得越早、
越频繁。拿一个玩具语料走三轮（受 Sennrich 论文示例启发）：

语料（词频已标注）：`low`×5、`lower`×2、`lowest`×2。
先把每个词拆成字符序列，统计所有相邻对的频次：

```
low    → l o w          (l,o)=9   (o,w)=9   (w,e)=4
lower  → l o w e r      (e,r)=2   (e,s)=2   (s,t)=2
lowest → l o w e s t
```

- **第 1 轮**：频次最高的是 (l,o)=9 与 (o,w)=9 并列，按约定取先入序的 (l,o)，
  合并出新符号 `lo`，词形变为 `lo w` / `lo w e r` / `lo w e s t`；
- **第 2 轮**：重新统计，(lo,w)=9 最高 → 合并出 `low`；
- **第 3 轮**：(low,e)=4 最高 → 合并出 `lowe`。

每轮产出一个新词表条目（合并表一行，rank = 轮次号），如此重复直到词表达到目标大小。
训练完成后，**合并表本身就是切分规则**——推理时不再需要任何频率统计，只按 rank
从低到高应用规则即可。

本仓库的合并表规模（`models/DeepSeek-OCR/tokenizer.json` 实测）：

- `model.merges` 共 **127741** 条，格式是嵌套数组 `[["Ġ", "t"], ["Ġ", "a"], ["i", "n"], …]`——
  前三条正是 rank 0/1/2 的最高频对；
- 这个格式正是 bug 1 的导火索（第 9 节）。

## 3. BPE 编码：rank 最小的相邻对先合并

编码的贪心规则只有一句话：**每一轮，在当前符号序列的所有相邻对里，找出 rank 最小的
那一对，合并之；直到没有任何相邻对在合并表里**。为什么贪心就是"对的"？因为合并表按
频率从高到低学出：rank 小的对更"基础"，先合并它们等于优先应用最可靠的规则，
这与训练时的生成顺序一致。

`ds_tokenizer.c` 的 `encode_bpe_word()`（约 L511-534）就是这句话的直接翻译：

```c
while (n_syms > 1) {
    int best_rank = INT_MAX, best_i = -1;
    for (int i = 0; i < n_syms - 1; i++) {        /* 扫描全部相邻对 */
        int r = merge_rank(tok, syms[i], syms[i + 1]);  /* 查合并表,无记录返回 INT_MAX */
        if (r < best_rank) { best_rank = r; best_i = i; }
    }
    if (best_i < 0 || best_rank == INT_MAX) break;      /* 无可合并,结束 */

    char *merged = str_concat2(syms[best_i], syms[best_i + 1]);
    free(syms[best_i]); free(syms[best_i + 1]);
    syms[best_i] = merged;                              /* 二合一 */
    for (int j = best_i + 1; j < n_syms - 1; j++) syms[j] = syms[j + 1];
    n_syms--;                                           /* 数组左移补位 */
}
```

`merge_rank()` 把符号对拼成 `"A B"` 字符串去查 `merge_map`（第 10 节的哈希表），
rank 即训练时的行号。合并结束后，把每个符号到 `vocab_map` 里查最终 id：
`'Multi'`→37460、`'Ġpage'`→4366、`'Ġparsing'`→76466、`'.'`→16。

完整算例（结果与 `test_unit.c` 钉扎断言逐一相符，见第 10 节）：

```
输入     "Multi page parsing."
字节映射  "MultiĠpageĠparsing."        ← 空格 0x20 变成载体字符 Ġ(第 4 节)
逐步合并  → ['Multi', 'Ġpage', 'Ġparsing', '.']
输出 id   [37460, 4366, 76466, 16]
```

**复杂度**：外层最多 n-1 次合并，每次全扫 O(n) 个相邻对，总计 O(n²) 次哈希查找；
`merge_rank` 每次还要 malloc/拼串/释放，常数不小。工业实现（HuggingFace tokenizers）
用优先队列 + 链表把每次"找最小"降到 O(log n)。本工程是教学级朴素实现——但分词对象
只有几个词的 prompt（`ds_ocr.c` 甚至断言编码结果不超过 10 个 token），O(n²) 无所谓，
正确性优先；这份直白也正是后面三个 bug 的温床——代码越直白，越没人怀疑它。

> 🗣️ **说人话**：初学者最容易把这两件事混成一件。训练（§2）像一本菜谱的编写过程：把语料扫一遍，数哪两样食材总挨着出现（"l"和"o"一起出现 9 次），频率最高的先合并，合并完再数一遍，如此重复 12 万多次，最后产出一张带序号的菜谱。编码（§3）则是照着这张成品菜谱做菜——**完全不再数频率**，只看序号：每轮挑当前序列里"排名最靠前（rank 最小）"的相邻对合并。所以你会看到第 1 轮先合并了最右边的 `(e,r)`（rank 5）而不是左边的 `(l,o)`（rank 4720）——**贪心 ≠ 从左往右**，谁排名高谁先合。
> *边界*：这套"谁 rank 小谁先合"只在菜谱和词表是同一套时成立；换一份 merges 配错 vocab，序号就全乱套（§9 bug 1 又是这里）。

### 3.1 逐轮手算："low lower" 的 8 步合并

第 2 节用玩具语料看了**训练**方向；现在把方向反过来——用**真实词表**对字符串
`"low lower"` 做编码推演。全部 rank 实测自
`models/DeepSeek-OCR/tokenizer.json` 的 merges 数组，可复现。字节映射后是
`lowĠlower`（空格→Ġ，第 4 节），初始符号序列 9 个：`l o w Ġ l o w e r`。
最常用的几条规则先列出来（其余 rank 在表中出现时直接给出）：
`('e','r')` rank 5、`('o','w')` rank 100、`('Ġ','l')` rank 55、
`('w','e')` rank 712、`('l','o')` rank 4720。

每一轮都执行 `encode_bpe_word()` 主循环的两个动作：**扫描**——`for` 循环对每个
相邻对调 `merge_rank()`（查不到返回 INT_MAX），记下最小者；**合并**——
`str_concat2` 拼接、数组左移 `n_syms--`。逐轮（rank = ∞ 表示该对不在合并表）：

| 轮 | 符号序列 | 各相邻对的 rank | 本轮合并 |
|---|---|---|---|
| 1 | `l o w Ġ l o w e r` | (l,o)=4720 (o,w)=100 (w,Ġ)=∞ (Ġ,l)=55 (l,o)=4720 (o,w)=100 (w,e)=712 (e,r)=**5** | `e+r→er` (5) |
| 2 | `l o w Ġ l o w er` | (l,o)=4720 (o,w)=100 (w,Ġ)=∞ (Ġ,l)=**55** (l,o)=4720 (o,w)=100 (w,er)=7199 | `Ġ+l→Ġl` (55) |
| 3 | `l o w Ġl o w er` | (l,o)=4720 (o,w)=**100** (w,Ġl)=∞ (Ġl,o)=3071 (o,w)=100 (w,er)=7199 | `o+w→ow` (100) |
| 4 | `l ow Ġl o w er` | (l,ow)=19318 (ow,Ġl)=∞ (Ġl,o)=3071 (o,w)=**100** (w,er)=7199 | `o+w→ow` (100) |
| 5 | `l ow Ġl ow er` | (l,ow)=19318 (ow,Ġl)=∞ (Ġl,ow)=2898 (ow,er)=**1085** | `ow+er→ower` (1085) |
| 6 | `l ow Ġl ower` | (l,ow)=19318 (ow,Ġl)=∞ (Ġl,ower)=**4004** | `Ġl+ower→Ġlower` (4004) |
| 7 | `l ow Ġlower` | (l,ow)=**19318** (ow,Ġlower)=∞ | `l+ow→low` (19318) |
| 8 | `low Ġlower` | (low,Ġlower)=∞ | 无可合并 → `break` 退出 |

最终符号 `['low', 'Ġlower']`，查 `vocab_map` 得 **[19577, 4263]**（两个都是
词表整词）。循环结束后那段"逐符号查 `vocab_map` 得 id"就是这最后一查。
三个观察值得停下来想：

- **贪心 ≠ 从左到右**：第 1 轮合并的是最右边的 (e,r)，只因为它 rank 最小。
  `encode_bpe_word()` 每轮重新全扫、谁 rank 小合并谁——rank 4720 的 (l,o)
  一直被更优的邻居压制，拖到第 7 轮才用上。
- **合并会创造新机会**：(ow,er) 这个对在第 1 轮根本不存在于序列里——是第 3、4
  轮造出 ow、第 1 轮造出 er 之后它们才相邻（rank 1085）。这就是为什么循环必须
  每轮重新扫描，而不是开局把所有对排一次序了事。
- **词界是自己长出来的**：本工程没有预分词（§6），整串当一个词；这里 (w,Ġ)
  不在合并表里，贪心自然停在空格边界——"基本如此"的例外与保险见 §6 的
  三道 fallback。

## 4. Byte-level BPE：一个中文字的完整旅程

GPT-2 的关键一步：把 BPE 的基础符号从"字符"换成**字节**（0-255）。中文常用字 5 万+
码位、emoji 散布在 10 万+ 区间，逐字符建基础表必然爆炸；而任何 UTF-8 文本不过是 1-4
字节的排列，**256 个字节符号就是万能地基**。

但字节不方便直接写进词表 JSON——0x20（空格）、0x0A（换行）放进字符串里既难看又易错。
GPT-2 的解法是 `bytes_to_unicode` 映射：把"可打印"的 188 个字节（`!`..`~` 共 94 个、
`¡`..`¬` 共 12 个、`®`..`ÿ` 共 82 个）映射到自身，剩下 68 个不可见字节依次映射到
U+0100 起的"载体字符"（carrier character）。`ds_tokenizer.c` 的 `init_gpt2_mapping()`
（L68-90）逐字实现了这套规则：

```c
if (b >= 33 && b <= 126)  is_normal = 1;   /* '!'..'~'      94 个,映射到自身 */
if (b >= 161 && b <= 172) is_normal = 1;   /* '¡'..'¬'      12 个 */
if (b >= 174 && b <= 255) is_normal = 1;   /* '®'..'ÿ'      82 个 */
if (is_normal) gpt2_byte_to_unicode[b] = b;
else gpt2_byte_to_unicode[b] = 256 + n++;  /* 其余 68 个 → U+0100 起 */
```

三个高频字节的去向，可以笔算验证：

- 空格 0x20：它前面 0..32 全部 33 个字节都不可见，所以它是第 33 个被重映射的
  → 256+32 = **288 = U+0120 = Ġ**（G 上带一个点）；
- 换行 0x0A → 256+10 = **266 = U+010A = Ċ**；
- 0xAD（173）：恰好落在 161-172 与 174-255 之间的唯一缝隙里，前面已有 67 个不可见字节
  → 256+67 = **323 = U+0143 = Ń**。

这就是日志里 `ĠThe`、`Ċ` 这类"奇怪拼写"的来历：**Ġ 开头的 token 意味着它前面带一个
空格**（词首），`Ċ` 就是换行本身。顺带两个词表实测：载体字符 `Ġ` 单独成 token 的 id
是 **223**，`Ċ` 是 **201**（这个数字马上会在 prompt 编码里再次出现）。

现在把汉字 **"中"**（U+4E2D）完整走一遍：

| 步骤 | 操作 | 结果 |
|------|------|------|
| 1. UTF-8 编码 | "中" → 3 字节 | `0xE4 0xB8 0xAD` |
| 2. 字节→载体字符 | 查 `gpt2_byte_to_unicode` | `0xE4`→'ä'(自身)、`0xB8`→'¸'(自身)、`0xAD`→'Ń' |
| 3. 拼成映射串 | `text_to_bpe_unicode()` | `"ä¸Ń"` |
| 4. BPE 合并 | ('ä','¸') rank=16 先合 | `"ä¸"` + 'Ń' |
| 5. 继续合并 | ('ä¸','Ń') rank=266 | `"ä¸Ń"`，无对可合，结束 |
| 6. 查词表 | `vocab_map["ä¸Ń"]` | **id 525** |
| 7. 解码还原 | 查反表 `gpt2_unicode_to_byte` | 'ä'→0xE4、'¸'→0xB8、'Ń'→0xAD → "中" |

编码与解码互为镜像：`text_to_bpe_unicode()` 正向查、`decode_gpt2_token()` 反向查，
两张表在 `init_gpt2_mapping()` 里一次性建好。`decode_gpt2_token()` 里还有一个兜底
分支——任何超出 `cp < 512` 判定或未映射的码位都替换成 `'?'`——理论上不可达（词表里的
载体字符全部在映射表内），属于典型的防御式编程。

> 🗣️ **说人话**："中"这个字在电脑里不是"一个字"，是 UTF-8 编码出来的 3 个字节 `0xE4 0xB8 0xAD`。BPE 的地基是 256 种字节，但其中不可见的那 68 种（空格、换行、以及汉字的高位字节）没法直接写进 JSON 文本里——所以 GPT-2 给它们起了"艺名"：空格 0x20 改叫 `Ġ`，换行 0x0A 改叫 `Ċ`。"中"的 3 个字节查完映射表变成 `ä ¸ Ń` 三个"艺名"，再合并两次，最后查到词表里"中"是**一个** id 525。反过来 decode 时把 `ä ¸ Ń` 的艺名查回来变 3 字节，拼起来自然又是"中"——这叫 UTF-8 自愈。
> *边界*：如果 EOS 恰好落在"中"的第 2 个字节之后（上一步出了 0xE4，该出 0xB8 时却来了 EOS），输出尾巴就是半个字——本工程刻意不修（删字节要"猜"意图），只保证不会崩。

### 4.1 UTF-8 边界安全：截断、撕裂与愈合

byte-level 的最大红利是**边界安全**——但"安全"分三个层面，各有各的答案：

**encode 方向：任何字节序列都合法。** 输入哪怕是被拦腰截断的半个"中"
（只剩 0xE4 0xB8，尾字节 0xAD 丢了），也会照常映射成载体字符序列继续合并；
`split_utf8_symbols()` 按**码位**切符号——载体字符自身的 UTF-8 表示
（如 U+0120 'Ġ' 编码为 0xC4 0xA0 两字节）永远不会被切进两个符号。不合法的
UTF-8 输入不会崩，只会得到"忠实反映字节"的 token。

**decode 方向：拼接自动愈合。** 每个 token 解出的是字节序列，逐段 memcpy 追加
（第 7 节），UTF-8 的自同步性保证拼回的总是合法文本——一个生僻字被拆成 3 个
单字节 token，三段拼起来仍是同一个字。

**真正的边界风险：生成停在字符中间。** EOS 或 `max_new_tokens` 落在多字节字符
的两个字节之间（上一步输出了 0xE4，这一步该出 0xB8 却来了 EOS），权威输出缓冲
就会以**半个字**结尾。本仓库对此不做合法化处理——不删尾巴、不补 U+FFFD，
以字节为准交给终端/文件消费。这是刻意选择：删字节需要"猜"截断意图，而半字的
危害只限最后一个字符；同理，`ds_strip_det_tags` 的换行合并等终态清理都只碰
ASCII 字节（`\n`、`<`、`>`、空格），天然不会切进多字节字符。

显示路径多一层讲究：`ds_stream_filter_det`（docs/08 §6.2）的"安全前缀 flush"
以 `'<'`（0x3C，ASCII）为界——多字节字符的全部字节都 ≥ 0x80，不可能横跨这个
边界，所以按 `<` 截留是字符安全的；但"缓冲将满强制 flush"与"整段无标签直接
flush"两个分支可能把一个多字节字符拆进两次回调。两段**拼起来**仍正确，只有
中间态是断的——任何按 piece 渲染的消费方都必须自己拼接。

真正按"字符"处理的地方在 `main.c` 的 PDF 多页后处理里：`line_subject()` /
`defrase_text()` 用 `(b & 0xC0) == 0x80` 识别续字节、`is_cjk_punct3()` 只查
首两字节判 CJK 标点块、逐字符推进而非逐字节。原因在所有权差异：这些函数做
**删除与折叠**，切错一个字节就是改内容，必须 UTF-8 意识；而纯追加的路径
（decode 拼装）天然安全，不需要。

## 5. 词表 129280 的真实构成

模型侧的 `config.json` 写着 `vocab_size: 129280`，四个模型目录全部如此。但 tokenizer.json
里**实际定义**的 id 远没有这么多，逐项分解（`models/DeepSeek-OCR/tokenizer.json` 实测）：

| 来源 | 条数 | id 范围 | 内容举例 |
|------|------|---------|---------|
| `model.vocab`（BPE 词表） | 128000 | 0-127999 | `Ġ`=223、`Ċ`=201、`'!'`=3；id 0/1/2 也是 bos/eos/pad |
| `added_tokens`：与 vocab 重叠 | 3 | 0-2 | `<｜begin▁of▁sentence｜>`(0)、`<｜end▁of▁sentence｜>`(1)、`<｜▁pad▁｜>`(2) |
| `added_tokens`：训练占位符 | 800 | 128000-128799 | `<｜place▁holder▁no▁0｜>`…`<｜place▁holder▁no▁799｜>` |
| `added_tokens`：功能标签 | 27 | 128800-128826 | `<image>`(128815)、`<|det|>`(128818)、`<|User|>`(128825) |
| **实际定义的 id 合计** | **128827** | 0-128826 | — |
| config.json 预留（未定义） | 453 | 128827-129279 | 嵌入矩阵里是未训练的行 |

所以 129280 的正确读法是：**128000 条 BPE 词表 + 1280 个预留槽位**（继承自 DeepSeek-V3
词表），预留槽中 V1/V2/V3 用掉 827 个、剩 453 行空置。Unlimited-OCR-2（V4）额外启用了
4 个：`<PAGE>`(128827)、`<BLOCK>`(128828)、`<FORK>`(128829)、`<CHILD>`(128830)，
added_tokens 总数从 830 变为 834。旧文档"128K + 830 ≈ 129280"的说法不成立——
830 里有 3 个与基础词表重叠，而且 128000+830=128830 也对不上 129280。

嵌入侧对应两份**独立**权重（safetensors 头部实测）：

```
model.embed_tokens.weight  [129280, 1280]  BF16   ← 输入查表(认路)
lm_head.weight             [129280, 1280]  BF16   ← 输出投影(指路)
```

每份 129280×1280×2 字节 ≈ 316 MiB。C 端分别加载进 `ds_ocr.h` 的
`tok_embeddings_bf16` 与 `lm_head_bf16` 字段，不共享（共享与否是训练时的选择，
推理时只需照着权重文件加载；[01 篇](./01-Transformer基础篇.md) 3.5 节讨论了共享的情形）。

最后一个与本节主题直接相关的历史遗留：`ds_ocr.h` L113 把 V1/V2 的图像标记定义为
`DS_TOKEN_IMAGE_START 151655`——这是 Qwen2.5-VL 的 id 空间，**超出本词表已定义的
0..128826**，也超出 129280 行的矩阵本身；而官方 Python 侧
（`models/DeepSeek-OCR-2/modeling_deepseekocr2.py` L751）用的是 `image_token_id =
128815`（即 `<image>`）。id 空间错位是分词系统最阴险的故障形态：越界读不崩溃
（mmap 文件足够大，读到的是别的张量的字节），只是静默地拿错嵌入。

> 🗣️ **说人话**：config 里写 129280，很多人以为词表真有这么多词，其实真正定义了 id 的只有 **128827** 个：128000 个 BPE 基础词（座位号 0-127999）+ 827 个 added_tokens（座位号 0-128826，其中还有 3 个跟基础词抢了同一个座位）。剩下 453 个（128827-129279）是**空包间**——继承了 DeepSeek-V3 留的坑，特意空着好让以后能加新 token 而不打乱 id。V4 正是往空包间里塞了 `<PAGE>`(128827)、`<BLOCK>`(128828) 等 4 个新客。所以旧文档"128K + 830 ≈ 129280"两头都对不上：830 里有 3 个位置重叠，而 128000+830=128830 也够不着 129280。
> *边界*：这些"包间号"超过矩阵实际行数的例外要小心——`ds_ocr.h` 里 V1 用的 151655 就超了所有包间，属于静默拿错数据的越界读（§5 末尾）。

### 5.1 词表的两个质量指标：fertility 与压缩率

词表大小不是"越大越好"的单一维度，它有两个可量化的质量指标：

**fertility（生育率）**：平均每个**词**被切成多少个 token。

$$ \text{fertility} = \frac{\#\text{tokens}}{\#\text{words}} $$

英文 GPT-2 词表约 1.3，中文常见 1.5–2.5（一个汉字常是 1–3 个 token）。
fertility 越高，同样文本的序列越长——**直接放大推理成本**（注意力 O(S²)、
KV cache O(S)）。

**压缩率（compression ratio）**：平均每个 token 承载多少**字符**。

$$ \text{compression} = \frac{\#\text{chars}}{\#\text{tokens}} $$

它是 fertility 的倒数形式（按字符而非词计），更常用于跨语言比较。

**为什么这对本工程重要**：本工程 `DS_DEC_MAX_SEQ` 之类的常量是按 token 计的。
中文文档的 fertility 若为 2.0，一张 1000 字的页面就是 2000 token——**词表设计
直接决定了"一张图能不能塞进上下文"**。这也是 docs/06 §7 动态多裁剪要限制
块数的深层原因：块数 × 每块 token 数 = 总序列长度，而总长度受 KV cache 与
注意力成本双重约束。

**词表大小的权衡**（本工程 129280 属于"大词表"）：

| 词表 | fertility | 序列长度 | 嵌入/输出矩阵 | 长尾 token 训练 |
|---|---|---|---|---|
| 小（32K） | 高 | 长 | 小 | 充分 |
| 大（128K+，本工程） | 低 | 短 | 大（129280×1280×2B ≈ 316 MiB ×2） | 稀疏，长尾欠训练 |

大词表的代价在推理端是**实打实的显存与带宽**：LM head 331 MB 是 decode 每步
最大的单块权重（docs/08 §5.1）。**词表大小是训练时的决定，推理端只能承受**——
这正是 docs/11 §3 把它列在"训练前锁死"清单第一位的理由。

> 🗣️ **说人话**：fertility 和压缩率是同一枚硬币的两面：fertility 问"平均每个词要切成几个 token"，压缩率问"平均每个 token 背几个字符"。fertility 高＝字字都切碎：同样一页中文，fertility 2.0 就是 1000 字变 2000 token——注意力 O(S²)、KV cache O(S)、decode 每步扫 331 MB 的 lm_head，全按 token 数收费（docs/08 §5.1）。大词表（本工程 129280）买的就是低 fertility：高频词整词命中、序列短，代价是 embed+lm_head 两份 316 MiB 矩阵和长尾 token 训练不充分。所以"词表大小"不是越大越好，是拿显存换序列长度——这笔账训练时定死，推理端只能承受。
> *边界*：fertility 是语料相关量：同一张词表喂英文 ≈1.3、喂中文 1.5–2.5，跨语言比较用压缩率才公平；拿英语指标评中文词表会得出错误结论。

### 5.2 训练视角：词表是"练"出来的，账要算两处

第 2 节的玩具语料把 BPE 训练缩到 3 轮；真实训练把同一件事做 **127,741 轮**——
在全部语料上统计所有相邻对的频率 → 合并最高频的一对 → 重统计，直到新增规则
的边际收益抵不过词表膨胀，停在目标规模。与玩具版相比有三个量级差：

- **统计是全语料、全迭代的**：每合并一条规则，所有包含该对的词形计数都要更新
  （工业实现做增量更新，朴素实现每轮重扫）。127,741 条 merge 的 rank 就是
  "合并发生时的语料频率序"——rank 0 的 `Ġ t`、rank 1 的 `Ġ a`（第 11 节实验 1
  可验证）意味着"带空格的词首"是语料中频率最高、最先被合并的一批模式。
- **贪心没有全局最优保证**：第 2 节 (l,o) 与 (o,w) 的 tie-break 取舍就会改变
  后续整棵合并树。所以不同语料/不同实现训出的 merges **必须与 vocab 配套加载**，
  不可混用——§9 bug 1 的理论根源就在这。
- **词表大小是权衡，不是越大越好**：§5.1 的 fertility/压缩率表给了序列长度
  视角；训练视角的成本在**参数量与每步算力**，把账算全：

  ```
  一份词表矩阵 = 129280 × 1280 = 165,478,400 参数
               （embed_tokens 与 lm_head 各一份，合计 ~331M，
                 相对 3B 级 MoE 解码器约占一成）
  decode 每步  = lm_head matvec：165M 次乘加 ≈ 0.33 GFLOP（算力小头）
               + 扫 331 MB BF16 权重（带宽大头，docs/08 §5.1 的 ~8ms 账）
  训练每位置   = 对 129280 维 logits 做全量 softmax + 交叉熵
               （logsumexp，docs/11 §5.1）——词表翻倍，这一项与两份
                 词表矩阵的显存同步翻倍
  ```

  词表大 → fertility 低 → 序列短 → 注意力与 KV cache 便宜，但输出矩阵与
  softmax 变贵；词表小则反过来。129280 取的是"128000 BPE + 1280 预留"的组合：
  **预留槽位的用途是让 id 布局在训练后仍可扩展**——V4 的 `<PAGE>`/`<BLOCK>`/
  `<FORK>`/`<CHILD>` 四个新 id（128827-128830）正落在预留区，模型在训练/继续
  训练中学会了输出它们（第 8 节的 V4 布局标签就是从这些 id 解码出来的）。

## 6. encode 全流程：这条路径偷了个懒

`ds_tokenizer_encode()`（L931-949）的完整路径只有三步：

```
ds_tokenizer_encode(tok, text, &n)
 ├─ text_to_bpe_unicode(text)      ① 每个字节 → 载体字符（malloc len*3+1 的映射串）
 ├─ encode_bpe_word(tok, mapped)   ② 把整段文本当作"一个词"做贪心合并
 │     ├─ split_utf8_symbols()     按 UTF-8 字符切开 → 符号数组
 │     ├─ while 循环合并 rank 最小的相邻对（第 3 节代码）
 │     └─ 逐符号查 vocab_map 得 id；任一符号查不到 → 整体失败返回 NULL
 └─ 返回 malloc 的 id 数组（调用者负责 free）
```

"偷懒"指第 ② 步：**没有预分词**（pre-tokenization）。官方 tokenizer.json 里
`pre_tokenizer` 是四条正则组成的流水线：数字每 1-3 位切一段（`\p{N}{1,3}`）、CJK 连续段
隔离（`[\u4e00-\u9fa5…]`）、英文单词/标点切分、ByteLevel 收尾——预分词保证 BPE 合并只
发生在"段内"。C 实现把整段文本当一个词直接合并，之所以通常不出错，是因为合并表本身
学自"段内"，跨段相邻对（比如 `o`+`Ġ` 之后再接别的）在表里基本不存在，贪心循环自然停在
正确的边界上。但"基本"不是"绝不"：数字长串、中英边界等场景可能与官方切分有出入。

工程的应对不是去实现正则，而是**不信任 encode 的结果**。`ds_ocr.c`（V3/V4 prompt
构造，L2316-2347）的三道保险：**合理性检查**（编码结果为空或超过 10 个 token 即视为
失败）；**fallback ID**（用官方 tokenizer 实测钉死的正确 id 兜底——
`"Multi page parsing."` → `{37460, 4366, 76466, 16}`、`"\ndocument parsing."` →
`{201, 34030, 76466, 16}`，注意首 token 201 就是 Ċ）；**钉扎单测**（这两组 id 同时被
`test_unit.c` 断言，改动分词器立刻炸测试）。

注释里还记录了一个上游坑：新版 transformers（5.x）的 `LlamaTokenizerFast` 编码这两句
会丢空格给出错误切分，**官方实现自己也会错**——所以 fallback 以"实测输出"为准，
而非"再跑一遍某个库"。

另一个关键设计：**特殊 token 根本不经过 encode**。若把字符串 `"<|det|>"` 喂给
encode，贪心合并只会产出 `<`、`|`、`de`、`t|>` 之类的碎片。官方做法是在预分词前先做
added_tokens 整词匹配；本工程的做法更简单——prompt 里的特殊 token 一律用常量 id
直接拼进序列（`DS_TOKEN_BOS`=0、`DS_TOKEN_IMAGE_PLACEHOLDER`=128815，见 `ds_ocr.h`
L110-116 与 [04-完整推理流程篇](./04-完整推理流程篇.md) 的 prompt 拼装一节），
字符串 encode 只负责纯文本指令部分。

## 7. decode 全流程：从 id 回到 UTF-8

decode 比 encode 简单得多，因为所有变换都在**加载时**一次性做完了：

```c
const char *ds_tokenizer_decode(const ds_tokenizer_t *tok, int token_id) {
    if (!tok || token_id < 0 || token_id >= tok->vocab_size) return "";
    return tok->id_to_text[token_id] ? tok->id_to_text[token_id] : "";
}
```

`id_to_text[id]` 存的是**已经还原成 UTF-8 字节**的文本——加载词表时，每个 token 的
BPE 原始串（`id_to_bpe`，含 Ġ/Ċ 等载体字符）先经过 `decode_deepseek_token()` 反变换：
先把 DeepSeek 特殊 token 里的 `▁`（U+2581，`0xE2 0x96 0x81`，全角下划线风格如
`<｜begin▁of▁sentence｜>`）替换成普通空格，再逐码位查 `gpt2_unicode_to_byte` 反表
把载体字符还原为原始字节（L170-230）。运行时 decode 只是 O(1) 查表 + 指针返回，
零拷贝、零分配。

推理主循环里的用法（`ds_ocr.c` L2815-2833）：

```c
const char *piece = ds_tokenizer_decode(tokenizer, token);
if (piece) {
    int piece_len = (int)strlen(piece);
    while (out_len + piece_len + 1 >= capacity) {   /* 输出缓冲倍增扩容 */
        capacity *= 2;
        output = (char *)realloc(output, capacity);
    }
    memcpy(output + out_len, piece, piece_len);     /* 权威输出缓冲:含标签,最后统一清理 */
    out_len += piece_len;
}
```

多字节中文的拼装不需要任何特殊逻辑：每个 piece 都是**字节序列**，逐段 memcpy 追加，
UTF-8 自然愈合——哪怕一个生僻字被拆成 3 个单字节 token，三段拼起来仍是合法 UTF-8
（第 4 节的"中"若没有 id 525 这个整字 token，就会走这条路）。EOS 的 break 发生在这段
代码**之前**（`ds_ocr.c` L2804 附近），结束标记不会混进输出。

两个细节值得驻足：其一，`decode` 返回内部缓冲区指针，注释明确要求"不要跨调用保存"——
下三个 token 的解码会复用同一张表，这是零拷贝的代价与纪律；其二，added_tokens
（`<|det|>` 等）的 `id_to_text` 在加载时用 `strdup(at_content)` 原样存入、**不做**载体
字符反变换（L884-886），decode 出来就是字面的 `"<|det|>"` 标签串，供后处理匹配（下节）。

> 🗣️ **说人话**：encode 本该像官方那样先按正则把句子切成小段再合，但 C 实现图省事，**整段当"一个词"直接合**（§6）。之所以没出大乱子，是因为合并表学自"段内"，跨段的对基本不存在，合并自然停在空格边界——但"基本"不是"绝不"。decode 则相反，特别"勤快"：加载词表时就把每个 token 的原始串一次性反变换成 UTF-8 存好（`id_to_text`），运行时只是 O(1) 查表返回指针，零拷贝零分配。工程也不信任 encode 的结果，`ds_ocr.c` 摆了三道保险：结果为空或超 10 个 token 就判失败；用实测钉死的 id 兜底（`"Multi page parsing."` → `{37460, 4366, 76466, 16}`）；单测把这些 id 钉死。
> *边界*：fallback 靠的是"实测输出"而不是"再跑一遍官方库"——因为官方 transformers 5.x 自己编码这两句会丢空格（§6 注释里的上游坑），照抄库反而错。

## 8. 特殊 token 与 added_tokens：整词占位符

特殊 token 是"整词占位"的原子符号：模型在 `<|det|>` 上输出的是**一个** id，而不是
五个字符。它们不参与 BPE 合并，单独登记在 tokenizer.json 顶层的 `added_tokens`
数组里，每条记录长这样（实测）：

```json
{"id": 128125, "content": "<｜place▁holder▁no▁125｜>",
 "single_word": false, "lstrip": false, "rstrip": false,
 "normalized": false, "special": true}
```

OCR 链路真正关心的是 id 128814-128826 这 13 个（四个模型完全一致）：

| token | id | 用途 |
|-------|----|------|
| `<｜tool▁sep｜>` | 128814 | 工具调用分隔（继承自 V3 底座） |
| `<image>` | 128815 | 图像占位符，V3/V4 prompt 的图像锚点 |
| `<|ref|>` / `<|/ref|>` | 128816 / 128817 | 引用文本起止 |
| `<|det|>` / `<|/det|>` | 128818 / 128819 | 检测框起止（grounding 输出） |
| `<|grounding|>` | 128820 | 定位模式开关 |
| `<td>` `</td>` `<tr>` `</tr>` | 128821-128824 | HTML 表格结构 |
| `<|User|>` / `<|Assistant|>` | 128825 / 128826 | 对话轮次标记 |

（V4 额外追加 `<PAGE>`=128827、`<BLOCK>`=128828、`<FORK>`=128829、`<CHILD>`=128830，
构成结构化版面标签，见 [08-解码策略与后处理篇](./08-解码策略与后处理篇.md)。）

加载侧，`ds_tokenizer_load_from_tokenizer_json()` 对 added_tokens 做三步（L1125-1231）：

1. **预扫**：遍历 `"added_tokens"` 数组找出最大 id（本词表是 128826）；
2. **扩容**：`realloc` 把 `id_to_bpe`/`id_to_text` 从 128000 扩到 128827，
   新区域 memset 清零；
3. **重建**：逐条 `strdup(content)` 写入两张表，并整体重建 `vocab_map` 哈希表。

这套"先扫最大 id 再扩容"的流程正是 bug 3 修出来的（第 9 节）。消费侧分两条线：
**decode 线**——标签串被原样解码进权威输出缓冲，末尾由 `ds_strip_det_tags()`
（`ds_ocr.h` L630 声明）统一剥离；**流式线**——`ds_stream_filter_det()`
（`ds_ocr.c` L197 起）用一个小状态机边生成边拦标签。为什么流式需要缓冲状态机？因为
BPE 可能把标签切成跨 token 的碎片（`"<|de"` + `"t|>"`），不缓冲就无法判断标签边界。

> 🗣️ **说人话**：`<|det|>` 这五个字符，在模型眼里**是一个** id（128818），不是五个字符。它不参与 BPE 合并，单独登记在 `added_tokens` 里，像键盘上一个"整颗按一下就出 emoji"的功能键。所以 prompt 里它的拼接方式是**直接写常量 id**，根本不喂给 encode——你如果真把它喂进去，贪心只会吐出 `<`、`|`、`de`、`t|>` 一堆碎片。加载 added_tokens 时有个坑（§9 bug 3）：词表容量不能拿 `model.vocab` 的最大 id 当上限，得先扫 added_tokens 里的最大 id 再扩容——否则 830 个里只有 3 个能塞进去，其余 827 个被"越界保护"**静默丢掉**，V3 输出里的 `<|det|>` 全碎成渣。
> *边界*：流式场景下标签可能被 BPE 切成横跨两个 token 的碎片（`"<|de"` + `"t|>"`），所以需要一个缓冲状态机，不能见到 `<` 就立刻 flush（§8）。

这条流水线的完整推演见 [08-解码策略与后处理篇](./08-解码策略与后处理篇.md)，本篇只需
记住因果链：**added_tokens 正确加载 → decode 出完整标签串 → 清理逻辑才有得匹配**
——bug 3 里 V3 输出满是碎片的根因就在链条第一环。

顺带一个跨章呼应：`ds_ocr.c` 的解码预热期（V3 前 `min_new_tokens` 步）硬编码禁掉了
id 223 和 EOS 两个 token——223 正是第 4 节算出的载体字符 `Ġ`。模型空转时最爱输出
"只带一个空格"的 token，禁掉它才能保证前几步产出可见文本。

### 8.1 落位：特殊 token 在四代 prompt 里的 id 布局

特殊 token 与图像占位符不是"编码"出来的，是**按常量 id 直接拼进序列**（§6 开头）；
出现的位置由 `ds_ocr.c` 的 prompt 构造段写死。四代的完整布局：

```
V1: [BOS(0)] [img_start(151655)] [视觉token×273] [img_end(151656)] ["\nFree OCR." 4 tok]
V2: [BOS(0)] [图像槽 257+100N 个] ["\nFree OCR." 4 tok]
     ← 无图像起止标记；槽位个数按 Python infer() 的几何算出，
       内容按 masked_scatter 填充语义落位（docs/06 §8.1）
V3: [BOS(0)] [<image>(128815)×N] ["\ndocument parsing." 4 tok]
V4: [BOS(0)] [<PAGE>(128827)] [<image>(128815)×N] ["Multi page parsing." 4 tok]
```

逐条看懂这张图：

- **占位符的个数 = 视觉 token 数**。V3/V4 先逐个嵌入
  `DS_TOKEN_IMAGE_PLACEHOLDER`(128815) 占位，再用编码器输出**整体覆盖**这些
  位置——嵌入查表只是占位动作，真正进入解码器的是 SAM+CLIP 特征。图片大小
  变（273 / 903 / …），占位符就写几个（`ds_ocr.c` 里 `n_img_tokens` 动态取值）。
- **V4 的 `<PAGE>` 在占位符之前**。单页文档也必须有（官方 `infer()` 对单图构造
  `"<PAGE><image>"` + 指令文本）；它同时是 DASH page2d RoPE 的页计数锚点
  （docs/14），所以 prompt 拼装时会把 id 序列存一份给 `ds_dash_build_coords`。
- **V1 的 img_start/img_end 是"越界 id"**。151655/151656 来自 Qwen2.5-VL 的
  id 空间，超出本词表矩阵的 129280 行——嵌入代码照常按指针偏移取值（§5 末尾
  的"id 空间错位"），取到的是相邻张量的字节。V1 能工作属于历史遗留的兼容，
  不是设计。
- **指令文本是唯一走 encode 的部分**：`"\nFree OCR."`、`"\ndocument parsing."`、
  `"Multi page parsing."` 各 4 个 token，且都有实测钉死的 fallback id
  （§6 的三道保险）。BOS/EOS/占位符/页面标记全部是常量直拼，**不过分词器**。

对照记忆：**图像 token 管"看"，特殊 token 管"格式"，指令 token 管"任务"**——
三者在序列里的相对位置就是 prompt 模板本身；换模型版本换的是模板，不是分词器。

> 🗣️ **说人话**：四代 prompt 像四张不同的试卷卷头：V1 是 `[BOS(0)] [img_start(151655)] [273 个视觉槽] [img_end(151656)] ["\nFree OCR." 4 token]`；V3 换成 `[BOS] [<image>(128815)×N] ["\ndocument parsing." 4 token]`；V4 还要在最前面再塞一个 `<PAGE>(128827)`。三件套的分工与位置就是 prompt 模板的全部内容——其中指令是唯一走 encode 的部分（4 个 token，且有钉死的 fallback id，§6），其余全是常量直拼、不过分词器。占位符写几个跟着图变（273/903/…），模板本身不变。
> *边界*：V1 的 151655/151656 是 Qwen2.5-VL 的 id 空间，超出本词表 129280 行——嵌入代码照常按指针偏移取，拿到的是相邻张量的字节（§5 末尾），V1 能工作属历史遗留兼容，别照抄到新模型里。

### bug 1：merges 永远读不到（解析器两处失明）

**症状**：V2 的 prompt `"\nFree OCR."` 被编成 10 个**字符级** token 而非 4 个
（修复 commit 的原话："4 tokens instead of 10 character-level tokens"），
没有任何合并发生；下游解码输出呈 4-4-4 的周期性退化重复。

**根因**（两层叠加）：其一，手写 JSON 解析器里"跳过一个值"的逻辑用花括号配对计数，
但 vocab 对象里的**字符串内容本身就含 `{}`**（某些 token 的拼写），计数错乱后解析游标
跳飞，再也找不到 `model.merges` 字段——merge_map 为空，`merge_rank` 恒返回 INT_MAX，
贪心循环一步都不走。其二，即便找到 merges，当时只认 `"a b"` 简单字符串格式，而
HuggingFace 的实际格式是嵌套数组 `[["Ġ","t"],…]`（第 2 节实测），同样解析为空。
旧文档"按行 split 拿到垃圾"的说法不准确——tokenizer.json 路径根本不按行读，
那是 vocab.json+merges.txt 路径（`load_merges_map()`）的逻辑。

**错误做法 vs 修复做法**：原代码把"跳过一个 JSON 值"的内联逻辑复制粘贴了 6 处
（修复后 `skip_json_value` 的调用点数量），各处各有细微 bug。
修复（commit 6fbc80b）把它们收敛为一个 `skip_json_value()`——
字符串分支正确处理转义与内嵌引号/花括号，结构分支在配对计数时跳过字符串体——
同时给 merges 解析加上嵌套数组分支，两种格式都吃。

**教训**：不要假设词表文件长什么样，先 `head -c 500` 看真文件；手写解析器的
单测必须包含"值里含结构字符"的样本；同一逻辑出现 5 份拷贝时，第 5 份几乎一定是错的。

> 🗣️ **说人话**：这个 bug 是"失明"不是"看错"：手写 JSON 解析器"跳过一个值"用花括号配对计数，可 vocab 里某些 token 的拼写本身就含 `{}`，计数被字符串内容带偏、解析游标跳飞，`model.merges` 从此找不到——merge_map 为空，`merge_rank` 恒返回 INT_MAX，贪心循环一步不走，`"\nFree OCR."` 被编成 10 个字符级 token 而非 4 个，下游输出 4-4-4 周期退化。第二重失明：就算找到了，解析器只认 `"a b"` 字符串格式，HuggingFace 实际是嵌套数组 `[["Ġ","t"],…]`，照样解析为空。修复（6fbc80b）把 6 处拷贝收敛成一个 `skip_json_value()`——同一逻辑抄 6 份，每份各藏一个 bug。
> *边界*：防御起点不是"多测几组输入"而是"先看真文件"——`head -c 500 tokenizer.json` 一眼就能看到嵌套数组格式；"解析成功、结果为空"这种静默失败，比解析报错贵得多。

### bug 2：strdup 缺失，哈希表里的 key 全是同一个悬空缓冲

**症状**：与 bug 1 同一个 commit 修掉。merge_map 建好后内容互相"串值"——
查任何一对都可能命中错误 rank，编码结果时对时错。

**根因**：`map_insert()` 只存**指针**不拷贝内容，而调用方先把合并对拼进栈上临时缓冲
`mk2[8192]` 再插入。循环下一轮覆盖同一块栈内存，表里所有 key 都变成"最后一对"的别名
——修复 commit 原话："when key is a stack-local buffer, all entries point to same
overwritten memory"。

**错误做法 vs 修复做法**：`map_insert(map, cap, mk2, mi)` →
`char *mk2_dup = strdup(mk2); map_insert(map, cap, mk2_dup, mi);`，
并在 `ds_tokenizer_free()` 里统一 `free(m[i].key)`。

**教训**：C 里"谁拥有这块字符串"必须在接口上写死（`ds_tokenizer.h` 对
`id_to_text`/`id_to_bpe` 的生命周期有明确注释）。哈希表要么约定"借用调用方内存"
并在文档里声明，要么一律 strdup 自持——半吊子最危险。第 10 节会看到本工程两张表
恰好各选了一种策略。

> 🗣️ **说人话**：哈希表的 key 存的是指针不是内容，而调用方先把合并对拼进栈上临时缓冲 `mk2[8192]`——循环每一轮都覆盖同一块栈内存，于是表里 12 万多个 key 全是"最后一对"的别名：查谁都可能命中错的 rank，编码时对时错。像酒店前台把所有客人名字写在同一块小白板上，每来一位擦掉重写——回头翻登记册，全楼住的都是最后那位。修复就一行：`strdup` 堆拷贝再插入，`ds_tokenizer_free()` 里统一 `free(m[i].key)`（6fbc80b）。它和 bug 1 同 commit 修掉不是巧合——表内容错乱时，两个症状会互相掩护。
> *边界*：「借用还是自持」必须在接口上写死，半吊子最危险——本工程两张表恰好各选一种（§10.3）；ASan（`make debug`）下这类悬空读当场报警，别靠"时对时错"碰运气。

### bug 3：added_tokens 没有并入词表，830 只加载了 3 个

**症状**（commit 1f57e5d，2026-06-28）：V3 输出里的 `<|det|>`…`<|/det|>` 变成碎片
文本，检测框清理逻辑（依赖完整标签串，第 8 节）再也匹配不上，输出含大量噪点。

**根因**：tokenizer.json 的 `model.vocab` 最大 id 是 127999，加载器据此把词表容量定
为 128000；而 830 个 added_tokens 里只有 3 个（bos/eos/pad，id 0/1/2）落在 128000
以内，其余 827 个（id 128000-128826）被 `aid < vocab_size` 的越界保护**静默丢弃**
——修复 commit 原话："Previously only 3 of 830 added_tokens loaded"。

**错误做法 vs 修复做法**：直接拿 model.vocab 的 max_id 当词表上限。修复是第 8 节的
三步：预扫 added_tokens 求最大 id → `realloc` 扩容 `id_to_bpe`/`id_to_text` 到
128827 → 重建 vocab_map。注意修复还顺手删掉了原代码里"边遍历边往旧 vocab_map 插"
的操作——扩容前插进旧表纯属白做，重建一次才是一致性保证。

**教训**：**"词表大小 ≠ model.vocab 条数"**，HuggingFace 的 id 空间上限由
added_tokens 决定；凡带"越界保护"的分支都要想想——被保护丢掉的数据去哪了？
静默丢弃是最贵的错误处理方式。

三个 bug 的共同点：分词器是"哑"组件——坏了不报错、不崩溃，只在输出质量上缓慢恶化，
从症状回溯到根因要跨过整个推理栈。防御手段见下一节。

## 10. 防御性测试与内存纪律

### 10.1 钉扎测试：test_unit.c 里真实存在的断言

`test_unit.c` 的 `test_tokenizer_real()`（L428-458，经 L765 的 `UT_CASE` 注册）加载
真实模型词表做四类断言：

```c
ds_tokenizer_t *tok = ds_tokenizer_load_from_tokenizer_json(
    "models/DeepSeek-OCR/tokenizer.json");
UT_CHECK(tok != NULL);
int *ids = ds_tokenizer_encode(tok, "Multi page parsing.", &n);
UT_CHECK(ids != NULL && n == 4);
/* 训练期钉扎: 'Multi' ' page' ' parsing' '.' */
UT_CHECK(ids[0] == 37460 && ids[1] == 4366 && ids[2] == 76466 && ids[3] == 16);
…
ids = ds_tokenizer_encode(tok, "\ndocument parsing.", &n);
UT_CHECK(ids != NULL && n == 4);            /* [201, 34030, 76466, 16] */
ids = ds_tokenizer_encode(tok, "云WAF系统", &n);   /* CJK 不崩,n>0 */
ids = ds_tokenizer_encode(tok, "", &n);           /* 空串不崩,NULL/0 */
const char *piece = ds_tokenizer_decode(tok, 37460);
UT_CHECK(piece != NULL && strstr(piece, "Multi") != NULL);  /* 单点往返 */
```

四类断言各有分工：**钉扎**（具体 id 逐一相等，等价于对 encode→decode 的往返校验，
任何加载/合并/映射的回归都会炸）；**健壮性**（CJK 与空串不崩）；**点校验**
（decode(37460) 含 "Multi"）。运行方式：`make test_unit && ./test_unit`
（`UT_SKIP_E2E=1` 可跳过端到端用例）。要诚实地说：现有测试**没有**覆盖全词表
round-trip（对 0..128827 每个 id 验证 encode(decode(id)) 的自洽性），这正是第 11 节
的实验作业。

> 🗣️ **说人话**：钉扎测试是"拿尺子量死"而不是"看着差不多"：`test_unit.c` 把实测 id 写进断言——`"Multi page parsing."` 必须 **[37460, 4366, 76466, 16]**、`"\ndocument parsing."` 必须 **[201, 34030, 76466, 16]**（201 正是 Ċ），另加 CJK/空串不崩的健壮性断言和 decode(37460) 含 "Multi" 的点校验。任何触碰加载、合并、字节映射的改动，这些数字立刻炸——分词器是"哑"组件（§9 三个 bug 全是静默恶化不报错），钉扎就是它的烟雾报警器。`ds_ocr.c` prompt 构造里那两组 fallback id（§6）与这里的断言同源，改一处必须同步另一处。
> *边界*：钉扎只护住被实测过的那几条路——没有全词表 round-trip（0..128827 逐 id 验证 encode(decode(id)) 自洽），词表的暗角依然存在；补齐是第 11 节实验 3 的作业。

### 10.2 词表查找用什么结构：FNV-1a + 开放寻址

`vocab_map`/`merge_map` 是手写哈希表（`ds_tokenizer.c` L341-390）：FNV-1a 64 位哈希
（偏移基数 14695981039346656037 = 0xcbf29ce484222325、素数 1099511628211），开放寻址 + 线性探查，容量取
`next_pow2(条目数×2+1)`——负载因子永远 ≤0.5，探查期望 O(1)。128827 条词表对应容量
262144 = 2¹⁸；merge_map 在 tokenizer.json 路径下固定开 262144，装 127741 条规则，
负载 0.49。一张 26 万槽的表每槽 16 字节（指针+int），约 4 MiB——对"4 个 token 的
prompt"来说奢侈，但换来加载后零重建、查询无锁。

> 🗣️ **说人话**：词表查找的结构是"留一半空位的电话簿"：FNV-1a 64 位哈希（素数 1099511628211，偏移基数 0xcbf29ce484222325）+ 开放寻址线性探查，容量恒取 2 的幂——128827 条词表对应 262144=2¹⁸ 槽，merge_map 装 127741 条规则负载 0.49，一张 26 万槽表约 4 MiB。看似奢侈，其实是笔便宜账：负载一高，线性探查的期望步数就从 O(1) 涨上去，"多花 4 MiB"买到的是加载后零重建、每次查询期望一步命中、无锁——对只需 encode 4 个 token 的 prompt 来说，这点内存是最便宜的保险。
> *边界*：哈希表只在 encode/加载侧；decode 走的是 `id_to_text[id]` 直接下标（§7），两个方向各用各的结构——别把"查词表"想象成同一个操作。

### 10.3 所有权纪律：一张表借用，一张表自持

同一结构体里两张哈希表，内存策略刻意不同（`ds_tokenizer_free()` L951-970 可验证）：

- `vocab_map` 的 key **借用** `id_to_bpe[i]` 的指针——释放时只 `free(tok->vocab_map)`
  桶数组本身，绝不 double-free key（key 的真身随 `id_to_bpe` 循环释放）；
- `merge_map` 的 key **自持**——插入前 `strdup`（bug 2 的修复），释放时逐槽
  `free(m[i].key)`。

这正是 bug 2 用真金白银换来的纪律：字符串进哈希表之前，先回答"这份内存归谁"，
然后把答案写进释放路径。防御性测试管"行为对不对"，所有权纪律管"内存炸不炸"，
两者缺一不可——后者在 ASan（`make debug`）下有任何越界/双重释放都会当场报警。

> 🗣️ **说人话**：同一结构体里两张哈希表，内存策略刻意相反，答案都写在释放路径里：`vocab_map` 的 key **借用** `id_to_bpe[i]` 的指针——释放时只 free 桶数组，key 真身随 `id_to_bpe` 的循环一起释放，绝不再 free 一次（否则 double-free）；`merge_map` 的 key **自持**——插入前 `strdup`（bug 2 的教训），释放时逐槽 `free(m[i].key)`。纪律只有一句话：字符串进哈希表之前，先回答"这份内存归谁"，再把答案写进 `ds_tokenizer_free()`。钉扎测试管"行为对不对"，所有权纪律管"内存炸不炸"，缺一不可。
> *边界*：两种策略别混着抄——给借用表的 key 逐槽 free、给自持表的桶一 free 了事，都会在 ASan 下当场报警；将来加第三张表时，先把所有权约定写进结构体注释再动手。

## 小结

分词系统 = **合并表（BPE 规则，127741 条）+ 词表（128000 条 BPE + 830/834 个
added_tokens，占满 128827 个 id，config 预留到 129280）+ 字节载体字符（256 字节 ↔
可打印码位的双向映射）**。它简单、快、但错了不报错：三个真实 bug 分别打在"格式假设"
（merges 读不到）、"内存所有权"（strdup 悬空）、"id 空间边界"（added_tokens 未扩容）
上，症状全是输出质量恶化而非崩溃。防御三板斧：钉扎单测（`test_tokenizer_real`）、
prompt 编码的 fallback ID、以及"字符串进哈希表先谈所有权"的纪律。
