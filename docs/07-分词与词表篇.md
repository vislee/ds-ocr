## 1. 为什么需要子词分词

词级：词表爆炸 + OOV；字符级：序列过长、语义太碎。BPE 取中：

- 训练期从字符开始，反复合并**最高频相邻对**，直到词表达到目标大小
- 推理期按合并表贪心切分，任何字符串都能表示（无 OOV）

## 2. BPE 训练与编码：合并表是核心

BPE 的全部知识就在一张**合并表**（merges）里，每行 `A B` 表示
"A 和 B 相邻时先合并成 AB"。编码 = 对输入反复查找"rank 最小"的相邻对
并合并，直到无可合并：

```
"lowest" → l+o(w)… 逐步按 rank 合并 → ["low", "est"]
```

复杂度 O(len²) 级；工业实现（HF tokenizers）用优先队列 + 链表近似 O(n log n)。
本工程的 `ds_tokenizer.c` 是教学级朴素实现，正确性优先——这正是后面 bug 的温床。

## 3. Byte-level BPE：GPT-2 的关键一步

GPT-2 把 BPE 的基础字符从 Unicode 码位换成**字节**（0-255），再映射到
可打印的"unicode 载体字符"（空格→Ġ，即 U+0120）。好处：

- 任意二进制/任意语言都可用 256 个基础符号表示，彻底无 OOV
- 中文一个字 ≈ 1~2 个 token；英文平均 1 token ≈ 4 字符

本工程词表里的 `Ġ`（带空格的词首）、`Ċ`（换行）就是这么来的。
这也是为什么日志里到处是 `ĠThe`、`Ċ` 这类奇怪拼写。

## 4. 本工程的词表：129280 从哪来

DeepSeek3B-MoE 解码器 vocab_size = 129280 = **基础 BPE 词表 + special tokens**
（`<|det|>`、`<|ref|>`、`<|grounding|>`、`<td>`、`<tr>` 等 V3 的 830 个
added_tokens）。注意：

- `tok_embeddings`（输入查表）与 `lm_head`（输出投影）**是两份独立权重**
  （`lm_head.weight` ≠ `embed_tokens.weight`），C 端都正确加载了
- 词表扩展后 id 可能与原版对不上——加载必须做 added_tokens 展开

## 5. decode：id → 字节的映射

decode 就是查表 + 载体字符反变换（Ġ→空格）。字节级 BPE 保证**每个合法 id
都能解出字节序列**，拼起来就是 UTF-8 文本。工程细节：多字节中文字符被
切成多个 token，逐 piece 追加即可，最后统一 strip。

## 6. 特殊 token 与 added_tokens

特殊 token 不参与 BPE 合并，是"整词占位"：`<|det|>`（id≈128822 附近）、
`<image>`、EOS(id=1)、BOS(id=0)。编码时必须**优先做整词匹配**，
否则 `<|det|>` 会被切成 `<`, `|`, `de`, `t`, `|>`……输出清理逻辑
（`ds_strip_det_tags`）就再也匹配不上了。

## 7. 三个真实 bug 复盘（本仓库 git log 有据可查）

**bug 1（v1.0）tokenizer.json 的 merge 没读到**
现象：所有输出乱码。根因：`tokenizer.json` 的 merges 是**嵌套数组**
`[["a","b"],…]` 而非 `"a b"` 字符串，解析器按行 split 拿到的是垃圾；
且 JSON 解析时跳过了整个 merges 字段。
教训：**不要假设词表文件格式，写完立刻做 round-trip 测试**。

**bug 2（v1.0）strdup 缺失**
merges 的 key 指向了临时缓冲区，函数返回后悬空。C 工程里
"解析器返回的字符串所有权"必须有纪律（strdup 或 arena）。

**bug 3（v1.0）added_tokens 没有并入词表**
现象：V3 输出里的 `<|det|>` 变成碎片文本。根因：只加载了 BPE 词表，
830 个 added_tokens 没有进 `vocab` 映射，编码时被当普通文本切开。
修复：加载 tokenizer.json 的 added_tokens 并扩展词表 → 128K+830。

三个 bug 的共同点：**分词器是"哑"组件，坏了不报错，只在输出质量上恶化**。
防御手段：round-trip 单测（encode(decode(id)) == id 对特殊 token 逐一验证）。

## 8. 动手实验

1. `grep -n "Ġ" models/DeepSeek-OCR-2/tokenizer.json | head` 直观感受载体字符
2. 写 10 行 C：加载词表，验证 `<|det|>` 的 id 在 V3 与 V1/V2 是否相同
3. 把 `DS_DEBUG_DET=1 ./ds_ocr …` 打开，观察 det 标签在输出缓冲里的原始形态
4. 思考题：为什么 repetition penalty 对 `<|det|>` 这类"结构性 token"几乎无效，
   而 n-gram 阻断对它的抑制更好？（提示：惩罚只压 logit 幅度，n-gram 直接禁 id；
   且 det 序列相邻步的 (n-1)gram 各不相同，见 08 篇的讨论。）

---

**小结**：分词系统 = 合并表（BPE）+ 词表（含 added_tokens）+ 字节载体字符。
它简单、快、但错了不报错；用 round-trip 测试和特殊 token 断言保护它。
