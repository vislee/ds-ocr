## 1. 基线性能与瓶颈分析

### 1.1 优化前后的全景对比

| 阶段 | 总耗时 | SAM+Encoder | Prefill | Decode | 测试平台 |
|------|--------|-------------|---------|--------|---------|
| **v0.5（基线）** | ~97s | ~50s | ~30s | ~19s | M2 Pro |
| **v0.9（当前）** | ~15s | ~9s | ~0.93s | ~5.1s | M2 Pro |
| **加速比** | 6.5× | 5.5× | 32× | 3.7× | — |
| **Python PyTorch** | ~736s | — | — | — | 同平台 |

> **对比意义**：纯 C 推理引擎 v0.5 就已比 Python PyTorch 快 7.5×，而 v0.9 进一步将优势扩大到 **49×**。这并非魔法——每一倍加速都来自对硬件特性的深度理解。

> 🗣️ **说人话**：这张表最有信息量的是「分布」不是总数：97 秒里 Encoding 50、Prefill 30、Decode 19——三个阶段三种病，所以后面是三套完全不同的药（§2 并行化、§3 批量 sgemm、§4 少读字节）。只盯着总数猛修，大概率在 50s 的地方修出一个 49s。分母也要记住：PyTorch 736s 是同机对照——6.5× 是跟自己比，49× 是跟框架比，两个数别混用。
> *边界*：~97s/~15s 绑定特定测试图（1794×1578）+ 空闲 CPU 的口径；图更小、机器更忙，数字都会漂，跨版本对比必须固定基线。

### 1.2 瓶颈定位方法论

优化的第一步不是写代码，而是**测量**。盲目优化往往耗时巨大却收效甚微。

**ds-ocr 的性能剖析流程**：

```
Step 1: 粗粒度测量 → 哪个阶段最慢？
         ┌──────────────────────────────────────────┐
         │  Encoding: 50s  │ Prefill: 30s │ Decode: 19s │
         │     ← 最慢 ─────┘              │            │
         └──────────────────────────────────────────┘

Step 2: 细粒度 Profiler → 阶段内部哪个操作最慢？
         ┌─── Decode 内部 ────────────────────────────┐
         │ QKV: 4.6% │ Attn: 9.9% │ Proj: 3.2%       │
         │ MLP/MoE: 73.7%  ← 绝对瓶颈               │
         │ LM head: 6.9% │ Sampling: 1.7%             │
         └────────────────────────────────────────────┘

Step 3: 针对瓶颈设计优化方案
```

ds-ocr 内置了逐层 Profiler，通过 `-p` 参数启用：

```bash
./ds_ocr -d model_dir -i image.png -p
```

输出类似：

```
=== PROFILER (decode: 5277ms, 226 steps, avg 23.35ms/step) ===
  QKV proj:     241.6 ms (  4.6%)
  Attention:    524.2 ms (  9.9%)
  Out proj:     168.2 ms (  3.2%)
  MLP/MoE:     3890.3 ms ( 73.7%)  ← 主要瓶颈
  LM head:      365.8 ms (  6.9%)
  Sampling:      90.2 ms (  1.7%)

  Per-layer breakdown (ms/step avg):
  Layer    QKV    Attn    Proj     MLP   Total
  0       0.893   1.854   0.596  13.421  16.764
  1       0.928   1.876   0.613  13.602  17.019
  ...
```

> 🗣️ **说人话**：定位瓶颈像看病：先问哪里疼（三阶段粗测 50/30/19s），再拍片子（`-p` 逐算子剖析：MLP/MoE 73.7%），最后才开刀。跳过第二步的代价是真金白银——凭直觉最想去优化 LM head（名字听着就关键），可它只占 6.9%，按 §1.3 的 Amdahl 改快 10× 总成绩才 +7%。所以 Profiler 的输出本身就是优先级列表：按百分比排序干活，别按「听起来重要」排序。
> *边界*：计时本身有观察者效应——剖析数据看相对占比比看绝对毫秒可靠，开着 profile 跑出的总时间别当性能结论。

### 1.3 Amdahl 定律的实战指导

**Amdahl 定律**：加速比 = 1 / [(1 - p) + p/s]

其中 p 是被优化部分的比例，s 是该部分的加速比。

以 Decode 阶段为例：
- MLP/MoE 占 73.7%，若优化到 2× 速：总加速 = 1 / [0.263 + 0.737/2] = **1.58×**
- LM head 占 6.9%，若优化到 10× 速：总加速 = 1 / [0.931 + 0.069/10] = **1.07×**

> **结论**：永远优先优化占比最大的部分。MLP/MoE 的 2× 加速远比 LM head 的 10× 加速更有价值。

> 🗣️ **说人话**：别摸黑优化，先看哪块最疼。你家厨房闹水灾，先铲哪里的水？当然是水龙头开着的那个池子，不是地板角落的一小滩。Amdahl 定律就是在算这个：总提速由"你改的那部分占多大比例"决定。decode 里 MLP/MoE 占 73.7%（§5.1），你把它改快 2× —— 总时间变成 1÷(0.263+0.737/2)=1.58×；可 LM head 只占 6.9%，你就是把它改快 10×，总时间也只有 1÷(0.931+0.069/10)=1.07×。数字摆在一起就明白：花同样力气，砸大水龙头比擦小水渍值钱得多。
> *边界*：这条只在"各部分能独立加速"时成立；如果一个小部分挡在关键路径上、卡住了后面所有人（比如一个必须等它的同步点），它的占比就骗了你。

## 2. Encoding 优化：50s → 9s（5.5×）

### 2.1 问题：V2 的多裁剪串行编码

V2 模型使用动态多裁剪策略处理高分辨率图像：

```
原始图像（如 2000×3000）
  ├── 全局裁剪（1024×1024）→ SAM → DeepEncoder → 256 tokens
  ├── 局部裁剪 1（448×448） → SAM → DeepEncoder → 56 tokens
  ├── 局部裁剪 2（448×448） → SAM → DeepEncoder → 56 tokens
  ├── 局部裁剪 3（448×448） → SAM → DeepEncoder → 56 tokens
  └── 局部裁剪 4（448×448） → SAM → DeepEncoder → 56 tokens
```

**v0.5 的做法**：完全串行处理，先全局后逐个局部：

```c
/* v0.5: 串行 —— 总时间 = global + local1 + local2 + local3 + local4 ≈ 50s */
float *global_tokens = encode_global(ctx, global_crop);   // ~12s
float *local1 = encode_local(ctx, crops[0]);              // ~9.5s
float *local2 = encode_local(ctx, crops[1]);              // ~9.5s
float *local3 = encode_local(ctx, crops[2]);              // ~9.5s
float *local4 = encode_local(ctx, crops[3]);              // ~9.5s
// 总计 ~50s
```

### 2.2 优化：并行 N+1 Workers

**核心洞察**：每个裁剪的编码完全独立（无数据依赖），天然可并行。

**v0.9 的做法**：同时启动 N+1 个线程（N 个局部 + 1 个全局），等待全部完成：

```c
/* v0.9: 并行 —— 总时间 = max(global, max(local)) ≈ 12s → 实测 9s */
int n_parallel = n_crops + 1;   // 4 local + 1 global = 5 workers
crop_task_t *tasks = calloc(n_parallel, sizeof(crop_task_t));
pthread_t *threads = calloc(n_parallel, sizeof(pthread_t));

/* 同时启动所有局部裁剪编码 */
for (int i = 0; i < n_crops; i++) {
    tasks[i].ctx = ctx;
    tasks[i].crop = crops[i];
    tasks[i].tokens_per_crop = tokens_per_crop;
    pthread_create(&threads[i], NULL, crop_worker, &tasks[i]);
}

/* 同时启动全局裁剪编码 */
int gi = n_crops;
tasks[gi].ctx = ctx;
tasks[gi].crop = global_img;
tasks[gi].tokens_per_crop = 256;
pthread_create(&threads[gi], NULL, crop_worker_global, &tasks[gi]);

/* 等待所有任务完成 */
for (int i = 0; i < n_parallel; i++)
    pthread_join(threads[i], NULL);
```

每个 worker 内部执行相同的流水线：

```c
static void *crop_worker(void *arg) {
    crop_task_t *t = (crop_task_t *)arg;
    t->sam_tokens = ds_sam_forward_image(t->ctx, t->crop,
                                          &t->n_sam_tokens, NULL);
    t->enc_tokens = ds_encoder_forward_v2(t->ctx, t->sam_tokens,
                                           t->n_sam_tokens,
                                           &t->n_enc_tokens,
                                           t->tokens_per_crop, ...);
    return NULL;
}
```

### 2.3 性能模型

```
串行时间 = T_global + N × T_local = 12 + 4 × 9.5 = 50s
并行时间 = max(T_global, max(T_local)) = max(12, 9.5) = 12s（理想值）
实测并行 = 9s（M2 Pro 性能核/能效核调度优化）
```

> **为什么实测比理想值更短？** M2 Pro 有 6 个性能核 + 4 个能效核。5 个 worker 分别调度到不同核心，能效核处理较小的局部裁剪（448×448），性能核处理全局裁剪（1024×1024），实际负载比理想的 max 值更均衡。

> 🗣️ **说人话**：从"排成一队挨个做"改成"五个人同时开工"。v0.5 编一张大图，是先把全局大裁剪编完（~12s），再一个个编 4 个局部裁剪（各 ~9.5s），一站到底要 12+4×9.5≈50s。问题是这 5 张裁剪谁都不等谁 —— 全局图不知道局部图长啥样，局部图之间也毫无关系。既然互不相干，为什么让它们排队？v0.9 直接开 5 个线程（1 全局 + 4 局部）同时编，总时间从"求和"变成"取最大"：理想 12s，实测 9s。更有意思的是实测比理论还短——M2 Pro 有 6 性能核 + 4 能效核，大活（1024×1024 全局）分给性能核、小活（448×448 局部）分给能效核，反而比"取最大"更均衡。
> *边界*：这条只在任务真的互相独立时成立；一旦某步要等上一步的产出（比如多个裁剪要拼回同一张特征图），硬并行就会打架。

### 2.4 V1/V3 为何不需要此优化？

V1 和 V3 使用 1024×1024 单图输入，没有多裁剪，编码只需 ~6.4s，已不是瓶颈。

> 🗣️ **说人话**：优化跟着结构走：V1/V3 一张 1024×1024 单图进 SAM，编码 ~6.4s 里没有「几份互不相干的小活」可拆——Amdahl 里可并行的 p≈0，线程开再多也是空转。V2 的多裁剪才有 5 份独立工作可同时发牌。所以「这个优化值几倍」的上限先由模型结构决定，再由实现决定。
> *边界*：单图不并行不等于没得优化——§10.3 的 SAM head 并行对 V1/V3 同样生效，只是颗粒更细。

## 3. Prefill 优化：30s → 0.93s（32×）

### 3.1 问题：逐 Token 的 BF16 矩阵向量乘

Prefill 阶段需要处理整个输入序列（~860 个 token），对每个 token 执行 MoE 前向传播。

**v0.5 的做法**：与 Decode 相同——对每个 token 独立执行 BF16 matvec：

```c
/* v0.5: 860 tokens × (gate + up + down) × 6 experts = ~15,000 次独立 BF16 matvec
 * 每次 matvec: [1, 896] × [896, 1280] → 单向量乘法，BLAS 无法发挥 */
for (int s = 0; s < seq_len; s++) {
    float *x_s = x + s * hidden;
    for (int k = 0; k < top_k; k++) {
        int expert_id = top_indices[s * top_k + k];
        ds_bf16_matvec(gate_buf, x_s, gate_weight, hidden, moe_inter);
        ds_bf16_matvec(up_buf, x_s, up_weight, hidden, moe_inter);
        ds_swiglu(swiglu_buf, gate_buf, up_buf, moe_inter);
        ds_bf16_matvec(out_buf, swiglu_buf, down_weight, moe_inter, hidden);
    }
}
```

**为什么慢？** BLAS 的 sgemm 对**大批量**操作高度优化，而单向量 matvec 根本无法利用：
- CPU 的 SIMD 单元未饱和（NEON/AVX 只用了几分之一）
- 缓存命中率低（每次只读一行权重，下次可能已驱逐）
- 线程池调度开销 >> 实际计算

### 3.2 优化一：共享专家批量 sgemm

**核心洞察**：共享专家（2 个）对所有 token 都激活，输入是 `[seq_len, hidden]` 的完整矩阵。

```c
/* v0.9: 共享专家 —— 一次 sgemm 处理所有 token */
ds_linear_nobias_bf16(s_gate, x_norm, layer->shared_gate_weight_bf16,
                       seq_len, hidden, shared_inter);  // [860, 896] × [896, 2560]
ds_linear_nobias_bf16(s_up, x_norm, layer->shared_up_weight_bf16,
                       seq_len, hidden, shared_inter);   // [860, 896] × [896, 2560]
ds_swiglu_direct(s_swiglu, s_gate, s_up, seq_len, shared_inter);
ds_linear_nobias_bf16(shared_mlp_out, s_swiglu, layer->shared_down_weight_bf16,
                       seq_len, shared_inter, hidden);   // [860, 2560] × [2560, 896]
```

**加速效果**：860 个 token 从 860 次 matvec 变为 3 次 sgemm，BLAS 效率提升 **50-100×**。

### 3.3 优化二：路由专家按 Expert ID 分组

路由专家的挑战是：不同 token 选择不同专家（top-6 of 64），不能简单批量处理。

**核心洞察**：860 个 token 中，平均每个专家被 ~860×6/64 ≈ 80 个 token 选中。把选中同一专家的 token 收集到一起，就能批量 sgemm。

```
v0.5（逐 token）:
  token 0 → expert 3, 17, 22, 41, 55, 60  → 6 次单 matvec
  token 1 → expert 7, 12, 22, 35, 48, 61  → 6 次单 matvec
  ...                                     ─────────────────
  总计 860 × 6 = 5160 次单 matvec

v0.9（按 expert 分组）:
  expert 3:  token [0, 15, 33, ...]  → 一次 sgemm [80, 896] × [896, 1280]
  expert 7:  token [1, 22, 47, ...]  → 一次 sgemm [80, 896] × [896, 1280]
  ...                               ────────────────────────────────────
  总计 ≤64 次 sgemm（大部分 ~80 token 的批量）
```

**代码实现**（`ds_moe_decoder.c`）：

```c
/* 统计每个 expert 被多少 token 选中 */
int *expert_count = calloc(n_experts, sizeof(int));
for (int s = 0; s < seq_len; s++) {
    int *tk_idx = all_top_indices + s * top_k;
    for (int k = 0; k < top_k; k++)
        expert_count[tk_idx[k]]++;
}

/* 为每个 expert 构建 token 索引列表 */
int **expert_tokens = malloc(n_experts * sizeof(int *));
for (int e = 0; e < n_experts; e++)
    expert_tokens[e] = malloc(expert_count[e] * sizeof(int));

/* 逐 expert 批量处理 */
for (int e = 0; e < n_experts; e++) {
    int n_tok = expert_count[e];
    if (n_tok == 0) continue;

    /* Gather: 收集选中此 expert 的所有 token 输入 */
    float *x_expert = malloc(n_tok * hidden * sizeof(float));
    for (int i = 0; i < n_tok; i++)
        memcpy(x_expert + i * hidden,
               x_norm + expert_tokens[e][i] * hidden,
               hidden * sizeof(float));

    /* 批量 sgemm：gate, up, swiglu, down */
    ds_linear_nobias_bf16(e_gate, x_expert, gate_weight,
                           n_tok, hidden, moe_inter);
    ds_linear_nobias_bf16(e_up, x_expert, up_weight,
                           n_tok, hidden, moe_inter);
    ds_swiglu_direct(e_swiglu, e_gate, e_up, n_tok, moe_inter);
    ds_linear_nobias_bf16(e_out, e_swiglu, down_weight,
                           n_tok, moe_inter, hidden);

    /* Scatter-add: 将结果加权写回对应 token 位置 */
    for (int i = 0; i < n_tok; i++) {
        int s = expert_tokens[e][i];
        float w = find_routing_weight(all_top_weights, s, top_k, e);
        for (int j = 0; j < hidden; j++)
            routed_mlp_out[s * hidden + j] += w * e_out[i * hidden + j];
    }
    free(x_expert); free(e_gate); free(e_up);
    free(e_swiglu); free(e_out);
}
```

> **Gather-Compute-Scatter 模式**：这是 MoE 批量推理的经典范式——先 Gather 收集输入、再 Compute 批量计算、最后 Scatter 散射结果。代价是额外的内存分配和拷贝，但换来的 sgemm 加速远超这些开销。

### 3.4 性能模型

```
v0.5: 860 × 6 × 3 × ~1.8ms/BF16_matvec ≈ 27s
v0.9: 共享 3 次 sgemm(~5ms) + 路由 ≤64 次 sgemm(~10ms) + Gather/Scatter(~2ms) ≈ 0.9s
加速比 ≈ 30×
```

> 🗣️ **说人话**：让 CPU 一次横扫一整排权重，而不是一次只碰一格。v0.5 的 prefill 是"一个 token 一个 token 地喂"：860 个 token × 6 个专家 × 3 个投影 ≈ 每小时 1.5 万次"单行点积"。单行点积就像用一把只能铲一勺的勺子挖仓库——CPU 的 SIMD 向量单元（一次能算好几格）根本吃不饱，权重读一行扔一行、缓存全白费。v0.9 换两招：共享专家对全部 token 天然通用，直接拿整块 [860,896] 矩阵一次乘完，860 次单行点积压成 3 次大 sgemm，效率跳 50–100×；路由专家虽然每个 token 选的专家不同，但 860 个 token 平均下来每个专家被 ~80 个 token 选中（860×6÷64），把选同一个专家的 token 收集成一小堆再一起乘 —— 5160 次单行点积塌缩成 ≤64 次批量 sgemm。这就是 Gather-Compute-Scatter（§3.3）：先归堆、再横扫、最后撒回去。
> *边界*：归堆和撒回本身要花内存和拷贝时间；如果每个专家摊到的 token 只有一两个（批量太小），这套搬来搬去反而不划算。

### 3.5 注意力层的批量处理

除了 MoE，Prefill 的注意力层也从逐 token 变为批量矩阵乘法：
- QKV 投影：`[seq_len, hidden] × [hidden, 3×kv_dim]` → 一次 sgemm
- Attention：利用在线 softmax（O(1) 内存），不需要完整注意力矩阵
- Out 投影：`[seq_len, hidden] × [hidden, hidden]` → 一次 sgemm

> 🗣️ **说人话**：MoE 之外注意力也照方抓药：QKV/Out 投影从每 token 一发 matvec 改成 [seq_len, hidden] 整块一次 sgemm；注意力本体用在线 softmax（03 篇 §5.3），边扫边修正、内存 O(1)，不物化 S×S 矩阵。三处改完，0.93s 里 MoE 之外的份额也被顺手清掉——所以 32× 不是单点优化，是把「逐 token 思维」整段拔掉。
> *边界*：在线 softmax 与两遍版的浮点顺序不同、末位有 ULP 差——prefill 与 decode 因此不逐位一致，回归门控比的是 CER 不是位模式（§10.2）。

## 4. Decode 优化：19s → 5.1s（3.7×）

Decode 阶段逐 token 生成，每个 token 独立执行 12 层 decoder 前向传播。优化目标是**减少单步延迟**。

### 4.1 Argmax LM Head（v0.8，8× 单步加速）

**问题**：每个 decode step 需要从 129280 个候选 token 中选最优。v0.5 用 sgemm 计算全部 logit，需要 631MB BF16→F32 转换。

**优化**：贪心解码不需要全部 logit，只需最大值。**边算边比较**（`ds_argmax_matvec_bf16`）：

```c
/* v0.9: argmax matvec —— 逐行 BF16×F32 点积，追踪最大值 */
float best_val = -1e30f;
int best_token = 0;
for (int row = 0; row < 129280; row++) {
    float dot = ds_bf16_dot_f32(x, lm_head_bf16 + row * 1280, 1280);
    if (dot > best_val) { best_val = dot; best_token = row; }
}
// 时间: ~8ms (vs v0.5 的 ~63ms，7.9× 加速)
```

> 🗣️ **说人话**：63ms→8ms 的 8× 是**单操作**加速比，别直接当总提速：优化前 LM head 独占 ~14s（63ms × 226 步，占 decode 19s 的四分之三），这一刀总收益巨大；等它降到 6.9%，同样的倍数按 §1.3 只值 ~+6%。所以教训是：Amdahl 的画像随优化迁移——每砍掉一个瓶颈，下一个的占比自动升值，优先级要重排（§1.2 的方法论闭环）。
> *边界*：8× 只对贪心成立；要完整分布就走 `full_logits_path`，63ms 的老账原样回来（03 篇 §3.6）。

### 4.2 Selective Repetition Penalty（v0.9）

只重算历史中出现过的 token（~100 个 vs 129280 个）：

```c
for (int h = 0; h < n_history; h++) {
    int tid = token_history[h];
    float logit = ds_bf16_dot_row(x, lm_head_bf16, hidden, tid);
    /* HF 语义：正 logit 除以 rp、负 logit 乘以 rp，都朝抑制方向推 */
    logit = (logit > 0) ? logit / rp : logit * rp;
    if (logit > best_val) { best_val = logit; best_token = tid; }
}
```

> 🗣️ **说人话**：惩罚只需要「历史里出现过的 ~100 个 ID」的 logit，不必为它们算全部 129280 个——`ds_bf16_dot_row` 逐个补算单行点积，把 O(词表) 的先算后查变成 O(历史) 的按需查询（03 篇 §3.6）。所以开销从「再扫 331 MB」降到微秒级。
> *边界*：历史要先去重——同一个 ID 出现 50 次就补算 50 次同一行，位图/哈希去重是一行代码的事。

### 4.3 连续 Expert 块（P2，2.4× MoE 加速）

将 64 个 expert 的 gate_up_fused 权重分配在**一块连续内存**中，相邻 expert 共享 4KB 内存页：

```c
/* v0.9: 连续 expert 块 */
size_t per_expert = 2 * moe_inter * hidden * sizeof(uint16_t);
size_t block_size = n_experts * per_expert;
uint16_t *expert_block = malloc(block_size);  // 单次大块分配
for (int e = 0; e < n_experts; e++)
    layer->experts[e].gate_up_fused_bf16 = expert_block + e * per_expert;
```

**效果**：page fault 从 ~351ms/step 降至 ~121ms/step（**2.4× 减少**）。

> 🗣️ **说人话**：page fault 351→121ms 的机理很朴素：mmap 按页（macOS 16 KB）赊账，专家权重东一块西一块散在文件里，decode 每步路由到谁就为谁现赊一批页；把 64 个专家的 gate_up 拼成一块连续内存后，相邻专家共享页、内核预读顺路带上邻居——赊账次数骤降。代价是加载时那次大拷贝（r2 发现它把峰值 RSS 顶到 ~11 GB，§10.4 拆掉了）——所以「连续」是拿内存峰值换页命中，两头要一起算。
> *边界*：连续块帮的是「近邻」——top-6 命中的专家若在块内相距很远，页共享收益打折。

### 4.4 madvise 预取

```c
/* 异步预读下一个 expert 的权重 */
if (k + 1 < top_k) {
    madvise(layer->experts[next_id].down_weight_bf16,
            hidden * moe_inter * 2, MADV_WILLNEED);
}
```

> 🗣️ **说人话**：算第 k 个专家时对第 k+1 个喊一嗓子「马上要用」（`MADV_WILLNEED`），内核异步预读，计算与磁盘 IO 重叠——等真用到时页已在内存。难点是路由顺序运行时才知道，只能逐专家接力预取；层级顺序编译期可知，`ds_decoder_prefill` 能整层提前挂上。所以预取的关键不是 API，是「提前量从哪来」（§7.6 的代价账）。
> *边界*：WILLNEED 只是建议不是命令——内核忙时会忽略；被忽略也不出错，只是那步退化成同步缺页。

### 4.5 Fused Expert Forward

gate + up 投影融合为单次 matvec，输入向量只读一次：

```c
/* v0.9: 1 次 matvec (fused gate+up) */
ds_bf16_matvec(gate_up_buf, x, gate_up_fused_weight, hidden, 2*moe_inter);
memcpy(gate_buf, gate_up_buf, moe_inter * sizeof(float));
memcpy(up_buf, gate_up_buf + moe_inter, moe_inter * sizeof(float));
```

> 🗣️ **说人话**：不是 CPU 算不动，是内存喂不上。把 decode 看成流水线上的一员：他每分钟的活很少，但每一步都要先搬一整箱原料过来——搬箱子的速度，就是他的速度上限。算术强度 I = 干多少活 ÷ 搬多少字节。matvec 每次从内存读一个权重字节，只用它算 1 次浮点，I≈1；而 M2 Pro 的"屋脊点"是 5（算力 1 TFLOPS ÷ 带宽 200 GB/s）。I 落在 5 左边 = 带宽墙这侧，上限就是 1×200 = 200 GFLOPS，恰好 20% 算力。所以 decode 每步要读 ~1.15 GB 权重，理论最快 1.15 GB ÷ 200 GB/s ≈ 5.7 ms，实测 23 ms（§7.4）。想再快，只有两条路：少搬字节（流式 argmax、量化权重、连续 expert 块提高页命中），或者一趟搬来的料喂更多张嘴（batch decode，§9.4，b=8 时 I=8 翻过屋脊点）。
> *边界*：I 只在"每个权重字节只用一次"时是 1；一旦 batch 起来复用权重，这条账全变，matvec 会摇身变成计算-bound。

## 6. V3 R-SWA 优化效果

### 6.1 问题：KV Cache 线性增长

```
生成 1000 token: KV cache ≈ 117 MB
生成 10000 token: KV cache ≈ 1.15 GB  ← 爆内存！（线性，×10）
```

### 6.2 R-SWA 解决方案

**Reference Sliding Window Attention** 将解码注意力分为两段：

```
KV Cache 布局:
[0..prefill_len-1]       [prefill_len..prefill_len+W-1]
├─ Reference 段 ────────┤├──── Sliding Window 段 ─────────┤
│ 视觉 token + prompt   ││ 最近 W=128 个 decode token     │
│ → 全局可见            ││ → 环形缓冲区，新覆盖旧         │
│ → 不参与状态转移      ││ → 固定大小                      │
└────────────────────────┘└───────────────────────────────┘
KV Cache 总大小 = prefill_len + W = 恒定值
```

> 🗣️ **说人话**：把"要永远记住的全部历史"换成"一页永远不撕的底稿 + 一叠永远只有 128 张的新照片"。普通注意力是"聊天记录全留档"：说到第 1000 句，前 999 句都还在，KV cache 攒到 117 MB；说到第 10000 句，攒到 1.15 GB——token 数翻十倍账单跟着翻十倍，直接把内存撑爆。R-SWA 把 KV cache 切成两段（§6.2）：前半段是参考区（视觉 token + prompt），从头到尾一直看得见、大小固定不动；后半段是滑动窗口，只留最近 128 个 decode token，用一个环形缓冲——新照片进一张，最老的就被顶掉一张。于是总大小 = prefill 长度 + 128，是个常数，说到第 10000 句也还是这么大。代价是你牺牲了"记得很远"的能力，但对 OCR（答案主要靠输入图里的信息）亏得起。
> *边界*：这是"丢掉远期上下文"换内存；如果任务真的需要回看很久以前生成的内容（长程推理、多轮纠错），被顶掉的历史就真的找不回来了。

### 6.3 C 实现要点

```c
/* ds_kernels.c: ds_rswa_attention_aligned() */
/* 两段在线 softmax */
for (int h = 0; h < n_heads; h++) {
    /* Reference 段: [0, prefill_len) — 视觉信息始终可见 */
    for (int i = 0; i < prefill_len; i++)
        qk_ref += Q[i] * K[i];

    /* Sliding window 段: [max(0, pos-W), pos) — 近期文本 */
    int win_start = (pos > window_size) ? pos - window_size : 0;
    for (int i = win_start; i < pos; i++)
        qk_win += Q[i] * K[i];

    /* 在线 softmax 合并两段 */
    ...
}
```

> 🗣️ **说人话**：R-SWA 的注意力 = 两段在线 softmax 拼接：参考段 [0, prefill_len) 永远全扫，滑窗段只扫 [pos−128, pos)，两段各自累计 max/sum 再用一个 correction 合并——复用的正是 03 篇 §5.3 的在线算法。所以每步读的行数恒为 prefill_len+128，不随 pos 涨，KV 读流量从 O(S) 变 O(1)。
> *边界*：`win_start = max(0, pos−W)` 的分支不是装饰——pos<W 时滑窗退化为全扫；这类边界写错就是静默数值错误，靠回归门控兜底（§10.2）。

### 6.4 性能对比

| 指标 | V3 (R-SWA) | V2 (标准) |
|------|-----------|----------|
| Decode 速度 | 44.0 tok/s | 44.4 tok/s |
| KV Cache (1000 tok) | prefill_len+128 ≈ 406 | 1000+ |
| KV Cache (10000 tok) | **恒定** 406 | 10000+ |
| 长文档内存 | ✅ 常数 | ❌ 线性增长 |

> 🗣️ **说人话**：最扎眼的是 decode 速度几乎没变（44.0 vs 44.4 tok/s）——R-SWA 本来就不是速度优化，是**内存恒定化**优化：1000 token 时省的读流量还很小，10000 token 时 V2 要扫上万行 KV、V3 仍只扫 prefill_len+128 行。所以它是「长文档不爆内存」的入场券，速度红利要到长序列才兑现（03 篇 §5.7 的手算算例）。
> *边界*：恒定 406 行里 prefill_len 占大头——整页表格的超长 prefill 会让这个「常数」水涨船高，只是不再随生成步数涨。

## 7. 内存带宽瓶颈分析

### 7.1 MoE Decode 每步权重读取量

| 权重 | 大小 (BF16) |
|------|------------|
| QKV + Out 投影 | ~12.7 MB/层 |
| 6 路由专家 | ~39.5 MB/层 |
| 2 共享专家 | ~26.4 MB/层 |
| **单层总计** | **≈ 78.6 MB** |
| **12 层 + LM head** | **≈ 943 + 331 MB** |

> 🗣️ **说人话**：这张表是 decode 每步的「购物清单」：QKV+Out 12.7 MB、6 路由专家 39.5 MB、2 共享专家 26.4 MB，单层 78.6 MB；12 层加 LM head ≈ 943+331 MB——decode 的速度就是「把这些字节从 DRAM 搬到计算单元」的速度。清单六成以上是专家（66/105 MB），所以 §7.3 的结论顺理成章：MoE 的搬运决定 decode 命运。
> *边界*：引用口径以 §7.4 为准——本表把共享专家记成 2 倍（26.4 应为 13.8），按 `ds_ocr.h` 常量逐项重算是 ~1.15 GB 而非 1.27 GB。

### 7.2 理论极限 vs 实测

```
M2 Pro 内存带宽: ~200 GB/s
冷缓存理论极限: 943 MB / 200 GB/s ≈ 4.7 ms/step ≈ 212 tok/s
实测: ~23 ms/step ≈ 44 tok/s
效率: ~20%
```

> 20% 效率的原因：BF16→F32 转换、线程同步、非连续内存访问、memory-bound 计算。

### 7.3 Roofline 模型完整推导：matvec 为什么注定慢

§7.2 的「20% 效率」不是工程失误，而是数学必然。用 Roofline 模型把这件事推导一遍。

**① 算术强度（Arithmetic Intensity）**

$$I = \frac{\text{FLOPs}}{\text{Bytes}} \quad \text{（每从内存读 1 字节能做几次浮点运算）}$$

**② 平台两个参数**（M2 Pro 为例，本篇所有实测的平台）：

- 内存带宽 $B \approx 200$ GB/s
- FP32 峰值算力 $P \approx 1$ TFLOPS（10 核 + AMX 协处理器，Accelerate sgemm 实测量级）

**③ 屋脊点（Ridge Point）**——两个参数的比值：

$$I^* = \frac{P}{B} = \frac{10^{12}}{2\times10^{11}} = 5 \ \text{FLOP/B}$$

$$\text{可达性能} = \min(P,\ I \times B) = \begin{cases} I \times B & I < 5 \quad \text{（memory-bound，带宽墙）} \\ P & I > 5 \quad \text{（compute-bound，算力墙）} \end{cases}$$

**④ 把本仓库的两种核心算子代入：**

| 算子 | FLOPs | Bytes | I | 判定 | 可达性能 |
|------|-------|-------|---|------|---------|
| matvec（decode） | $2 \times 1280 \times N$ | $2N + 4(1280+N) \approx 2N$ | $\approx \mathbf{1}$ FLOP/B | memory-bound | $1 \times 200 = 200$ GFLOPS = **20% 峰值** |
| sgemm（prefill，M=280） | $2 \times 280 \times 1280 \times N$ | $\approx 2N$（权重，激活被 M 行摊薄） | $\approx \mathbf{280}$ FLOP/B | compute-bound | ≈ 峰值 1 TFLOPS |

```
性能(TFLOPS)
 1.0 ┤                          ╭────────────── sgemm 住在这里
     │                       ╭──╯
     │                    ╭──╯   斜率 = B = 200 GB/s
     │                 ╭──╯
0.2  │ matvec ════════╯  ← 天花板 200 GFLOPS（I=1）
     └────────┬──────┬──────────→ 算术强度 I (FLOP/B)
              1      5 ← 屋脊点 I*
```

**⑤ 这就是全部优化史的数学注脚**：

- decode 23.35 ms/步 ≈ 1.15 GB 权重 ÷ 200 GB/s 的 5 倍距离 → 优化只能来自「**少读字节**」（argmax 流式、INT8/INT4 量化、连续 expert 块提高页缓存命中）或「**每次读干更多活**」（batch decode，§9.4）
- prefill 0.72 s ≈ 321 GFLOPs ÷ ~450 GFLOPS → 优化只能来自「**提高算力利用率**」（批量 sgemm、MoE 分组），读权重已经不重要
- 效率 20% 的剩余差距（200 vs 实测 49 GB/s）来自：BF16 展开指令开销、行内累加依赖链、多线程 barrier、页缓存未命中——每一项都有对应的优化案例（§3、§4、§10）

> **手算验证**：matvec I=1 → 每步 FLOPs = 1.15 GB × 1 FLOP/B ≈ 1.15 GFLOPs，与 docs/04 §2.10 的 2×574M 完全一致——算术强度 1 不是巧合，是「每字节权重只用一次」的直接后果。

> 🗣️ **说人话**：这张图最该记住的是「同一个模型、两种命运」：matvec I≈1 坐在带宽墙下（200 GFLOPS，20% 算力），sgemm I≈280 顶到算力天花板（≈1 TFLOPS）——差 280 倍的不是算法聪明程度，是「每个权重字节被用几次」。prefill 的 280 行输出把读权重的一次成本摊成 280 份，decode 的 1 行无从摊。所以 ⑤ 说的两条优化路（少读字节 / 每次读干更多活）不是并列的技巧清单，是 Roofline 左右两侧各自唯一的出路。
> *边界*：Roofline 是稳态上界，不含同步/缺页等现实税——实测有效带宽 ~49 GB/s（⑤ 的剩余差距清单），天花板摸不满是常态。

### 7.4 一次 matvec 的分步带宽账（精化 §7.1）

把单次 BF16 matvec `y = W·x`（`ds_kernels_neon.c` → `ds_bf16_matvec_fused_neon`）的内存流量逐项列出。以路由专家的融合权重 gate_up_fused [1792, 1280] 为例（常数来自 `ds_ocr.h`）：

```
① 读权重 W     1792 × 1280 × 2 B (BF16)   = 4,587,520 B ≈ 4.59 MB   ← 占 99.8%
② 读输入 x     1280 × 4 B (F32)           =     5,120 B ≈ 5.0 KB    ← 常驻 L1，几乎不花时间
③ 写输出 y     1792 × 4 B (F32)           =     7,168 B ≈ 7.0 KB
──────────────────────────────────────────────────────────────────────
合计                                       ≈ 4.60 MB
BF16→F32 转换                              = 0（vshll 在寄存器内完成，不落内存）
```

**理论耗时**：4.60 MB ÷ 200 GB/s = **23.0 μs**。此时算力消耗 = 2×1792×1280 = 4.59 MFLOPs，折合 200 GFLOPS——正好压在 matvec 的 Roofline 天花板上（§7.3 ④）。

**decode 每步的完整账单**（11 个 MoE 层 + 1 个 dense 层 + LM head，V1/V2 配置）：

| 组件 | 每步字节数 | 计算 |
|------|-----------|------|
| 注意力权重（每层 wq+wk+wv+wo） | 13.1 MB × 12 | (3×1280×1280 + 1280×1280) × 2 B |
| Layer 0 dense FFN | 52.6 MB | 3×1280×6848 × 2 B |
| MoE 路由专家（每层 6 个） | 41.3 MB × 11 | 6×3×1280×896 × 2 B |
| MoE 共享专家（每层 2 个） | 13.8 MB × 11 | 2×3×1280×896 × 2 B |
| router gate | 0.16 MB × 11 | 1280×64 × 2 B |
| LM head（流式 argmax） | 331.0 MB | 129280×1280 × 2 B |
| KV 读（300 上下文，F32） | 36.9 MB | 300×2560×12×4 B |
| **合计** | **≈ 1.15 GB** | |

理论下限 1.15 GB ÷ 200 GB/s ≈ **5.7 ms/步**（≈175 tok/s），实测 23.35 ms → **效率 ≈ 24%**，与 §7.2 的口径一致（§7.1 粗表中共享专家 26.4 MB 计成了 2 倍，本表按 `ds_ocr.h` 常量逐项重算，12 层合计 818 MB 而非 943 MB，总量结论不变）。

实测与理论差的 ~4×：barrier 同步（12 层 × 多内核）、BF16 展开的额外指令、页缓存冷启动、能效核拖慢行切分的长尾——这正是 §4、§10 各项优化的攻击面。

> 🗣️ **说人话**：4.60 MB 的账单摊开看：权重占 99.8%，x 和 y 加起来不到 20 KB 且常驻 L1——matvec 就是「权重搬运工」，其他全是零头。所以优化手册里没有「优化输入输出」这一条，全是「少读权重」：BF16 存储已把 F32 的账砍半，INT8/INT4（§9.1）再砍 2×/4×。每步 1.15 GB ÷ 200 GB/s = 5.7 ms 是数学下限，实测 23 ms 的 ~4× 差距是同步、指令开销和页冷的现实税（§10 各刀的攻击面）。
> *边界*：99.8% 的占比依赖「x 在 L1」——一旦 batch 让激活长大出 L1，账单结构就变了（§9.4）。

### 7.5 线程数与缓存层次

**缓存层级的量级感**（Apple Silicon 公开规格，量级正确即可）：

| 层级 | 大小 | 延迟（周期量级） | 本仓库的常客 |
|------|------|----------------|-------------|
| L1D（每核） | ~128 KB | ~4 | decode 的 x[1280]（5 KB）、y[1792]（7 KB）——`ds_expert_forward_fused` 注释「x 在两次 matvec 间常驻 L1」 |
| L2（簇共享） | 数 MB~16 MB | ~15 | 单个专家权重 4.6 MB 恰好装得下 |
| SLC（系统级） | 数十 MB | ~40 | 同层 64 个专家中热門的若干个 |
| DRAM | GB 级 | ~150+ | 全部 6.2 GB 权重的家 |

matvec 的工作集分析：x（5 KB）+ 当前行（2.5 KB）+ 累加器都在 L1，**每周期真正要从 DRAM 拿的只有权重流**——这解释了为什么 matvec 的实测带宽能逼近理论值，也解释了为什么「连续 expert 块」（§4.3）有效：相邻 expert 权重落在相邻内存页，SLC/页缓存命中率上升。

**false sharing（伪共享）**：缓存一致性以 64 B 的 cache line 为单位。两个线程各写自己的变量，但两个变量落在同一 cache line → 硬件互相弹劾，line 在核间来回弹，性能暴跌。本仓库的三道防线：

1. `ds_parallel_for` 的任务按**输出行区间**切分（`ds_matvec_worker` 的 chunk 逻辑），线程写 y 的不同段，段间自然跨过 cache line
2. KV 缓存行对齐：`alloc_decoder_buffers` 中 `kv_row_stride = (kv_dim + 15) & ~15`，行首对齐 64 B——若不对齐，相邻两个位置的 K 行会共享 cache line，注意力并行读时互相污染
3. grouped matvec 以「行对」为切分粒度（`ds_grouped_matvec_bf16`），线程边界永远落在偶数行边界，兼得逐位一致与无伪共享

**线程数怎么选**：decode 路径在 `ds_ocr.c` 里显式用满全部核（`ds_set_threads(ds_get_num_cpus())`），理由写在注释里——129280 行的 LM head matvec 值得 8 线程均分。但线程数不是越多越好：

- 行数 < 线程数 × 合理 chunk 时（如路由 gate 只有 64 行），切分后每线程任务过小，barrier 占比反超计算
- 能效核（E-core）与性能核（P-core）混跑，最慢的核决定 barrier 等待时间——`-t` 手动压到 P-core 数有时更快
- 经验公式：`线程数 ≤ max(1, out_dim / 256)`，让每线程至少摊到几百行

> 🗣️ **说人话**：缓存层级是一张「书桌（L1 ~128 KB）→ 书架（L2，单个专家 4.6 MB 装得下）→ 图书馆（SLC）→ 仓库（DRAM）」的距离表：x（5 KB）和累加器摊在桌上，每拍只等仓库送权重。伪共享则是两个同桌抢同一行书——三道防线（按输出行切、KV 行首 64 B 对齐、行对粒度）都是让各线程各写各的行。线程数经验式 `≤ out_dim/256`：路由 gate 只有 64 行，给 8 线程每人摊 8 行，barrier 比干活贵，所以小矩阵少用线程。
> *边界*：P/E 核混跑时 barrier 由最慢核决定——6P+4E 的机器上 14 线程未必快过 8 线程（`-t` 可手动压到 P 核数）。

### 7.6 madvise 预取原理：page fault 的代价账

mmap 是惰性的：`safetensors_open` 只建立虚拟地址映射，**首次触碰某个虚拟页才触发 page fault**，内核这时才去磁盘读（macOS 页 16 KB，Linux 4 KB）。这笔账在 MoE 上非常难看：

- prefill 一层要触碰全部 64 个专家 mmap ≈ 440 MB ≈ 27,500 个 16 KB 页
- 每个 major fault 含一次磁盘读（NVMe 上 ~50–200 μs）——串行触发时 decode 单步曾被 page fault 拖到 ~351 ms（§4.3）

**MADV_WILLNEED 的解法**：向内核声明「这段地址马上要读」，内核立刻发起**异步**预读，计算与磁盘 IO 重叠：

```c
/* ds_decoder_prefill：算第 l 层时，把第 l+1 层的全部权重（含 64 专家）挂预读 */
madvise((void *)nl->experts[e].gate_weight_bf16,
        (size_t)cfg->dec_moe_inter * hidden * 2, MADV_WILLNEED);

/* ds_decoder_forward：safetensors 按字母序排布，层 10/11 的文件偏移
 * 夹在层 1/2 之间——每步开头预取尾层，避免层 9→10 的磁盘回跳 */

/* moe_forward：算第 k 个专家时预取第 k+1 个（路由顺序运行时才知道，
 * 只能逐专家预取）*/
```

**与 MAP_POPULATE 的对比**：

| | MADV_WILLNEED（本仓库） | MAP_POPULATE |
|---|------------------------|--------------|
| 时机 | 运行中按需、分段 | mmap 时一次性全部 |
| 启动延迟 | 无 | 6.2 GB 全量预读，启动多花数十秒 |
| 物理驻留 | 只驻留真正访问的页 | **全部权重常驻**——MoE「稀疏激活省内存」的初衷报废 |
| 与 RSS 的关系 | 可控（配合 MADV_DONTNEED 可回收） | 直接拉满高水位 |

MAP_POPULATE 不是永远错：如果模型小到能全驻留且只跑一次短推理，它可以换来零 fault 的平稳延迟。但对 6.2 GB 的 MoE，本仓库选择了「WILLNEED 按需预取 + DONTNEED 主动回收」（`ds_drop_source_pages`、`multi_safetensors_madvise_unused`——编码结束后丢弃不再触碰的编码器权重源页，−0.6 GB）的组合。

> **r2 的一条红线**（§10.4）：`ru_maxrss` 是**累计缺页的高水位**，不是瞬时驻留——任何「事后 madvise 降 RSS」的尝试都救不回已经涨上去的峰值。想控 RSS 必须在触碰发生**之前**少触碰。

> 🗣️ **说人话**：mmap 的「惰性」是双刃剑：省了冷专家的内存，代价是首次触碰现场等磁盘（major fault，NVMe 上 ~50–200 μs）。prefill 一层 64 专家 ≈ 27,500 个 16 KB 页，串行缺页能把单步拖到 351 ms（§4.3）。WILLNEED 把「用到才读」改成「提前说、异步读」，磁盘和计算并行——但 RSS 红线要记牢：ru_maxrss 是缺页累计的高水位，事后 DONTNEED 救不回峰值，所以控内存必须在触碰之前少触碰。
> *边界*：MAP_POPULATE 最平稳但 6.2 GB 全驻留，MoE 省内存的初衷作废——选哪种取决于「延迟平稳」和「内存峰值」哪个是硬约束。

## 9. 优化建议与未来方向

### 9.1 短期可行（预计 2-4× decode 加速）

| 优化 | 原理 | 预期收益 | 实现难度 |
|------|------|---------|---------|
| **INT8 权重量化** | BF16→INT8，带宽减半 | 2× decode | 中 |
| **INT4 权重量化** | BF16→INT4，带宽降 4× | 3-4× decode | 高 |
| **Expert 量化混合** | 热门 expert BF16，冷门 INT4 | 2-3× decode | 高 |

> 🗣️ **说人话**：表里的预期收益全部来自同一条公式（§7.3）：decode 是带宽 bound，权重字节砍多少、速度就近涨多少——BF16→INT8 砍一半 ≈ 2×，INT4 砍 3/4 ≈ 3–4×。难易度却倒着排：INT8 便宜（逐通道 scale 即可用），INT4 要分组量化 + 校准，混合精度还得先摸清谁热谁冷。所以先摘低处的果子。
> *边界*：收益受非权重流量封顶——KV 读取 + LM head 占每步约三成（§7.4），它们不参与量化时 INT4 到不了理论 4×。

### 9.2 中期探索

| 优化 | 原理 | 预期收益 |
|------|------|---------|
| **Speculative Decoding** | 小模型预测多 token，大模型验证 | 2-3× decode |
| **Shared + Routed Expert 并行** | 两者无依赖，可在不同线程执行 | 1.3× decode |（**已实现**：r4 的 `ds_grouped_matvec_bf16` 把共享专家与路由专家同类投影合并为同一批并行区，见 §10.7；效果超出本表预估） |
| **KV Cache 压缩** | 量化或蒸馏 KV cache | 长序列场景 |
| **FlashAttention (prefill)** | 减少注意力的内存读写 | prefill 加速 |

### 9.3 长期方向

- **Batched Decode**：多请求批量 decode，提升吞吐量
- **MoE Expert 缓存**：LRU 缓存热门 expert 的 F32 权重
- **异步 I/O**：decode 计算与 expert 权重预取重叠（**部分已实现**：madvise 顺序预取见 §4.4 与 §7.6；真正与计算重叠的异步预取仍未做）
- **动态线程分配**：小 matvec 用少线程，大 matvec 用多线程

> 🗣️ **说人话**：清单里最值得先想清楚的是「MoE Expert LRU 缓存」：它想做的——把热门专家放进快的地方——mmap 的页缓存其实已经在做（按访问热度留存的 SLC/DRAM 页就是天然 LRU）。自建缓存的真增量只有「换成 F32 省掉每步展开指令」，代价是自己管一致性。所以动手前先测还剩多少缺页（§7.6），别造一个操作系统已经造好的轮子。
> *边界*：单请求 CLI 下专家热度由图像内容决定、无跨请求复用——LRU 的收益场景在多请求服务端。

### 9.4 如果继续优化：SIMD batch decode 的原理与本仓库可行性

**原理**：§7.3 说 matvec 的算术强度 I≈1、被带宽墙钉死在 20% 算力——但那是**单个向量**的账。如果把 b 个独立序列的输入打包成矩阵 X[b,1280] 一起乘，同一个权重字节被用 b 次：

$$I_{batch} = \frac{2b \times 1280 \times N}{2N} = b \ \text{FLOP/B}$$

b=8 时 I=8 > 屋脊点 5，越过带宽墙进入计算-bound 区——**同一份权重读一次，喂饱 8 个序列**。这是 vLLM/Orca 等服务引擎吞吐优势的全部数学基础。

**两个实施层次**：

1. **SIMD 寄存器级 batch（小手术）**：NEON 的 128-bit 寄存器可装 4 个 F32 lane。单序列 matvec 里，4 个 lane 装的是同一行权重的 4 个元素；batch 版可以让 4 个 lane 分别装 4 个序列对**同一权重元素**的累加——每条 `vfmaq` 干 4 倍的活，权重读取流量不变。改动集中在 `ds_kernels_impl.h` 新增一个 `_batch4` 内核族。
2. **序列级 batch sgemm（中手术）**：直接把 b 个序列的 decode 步拼成 `[b,1280]×[1280,N]` 的 sgemm——prefill 路径的 `ds_linear_nobias_bf16` 现成可用。真正的工程量在**KV cache 布局**：当前 `[layers, max_seq, kv_row_stride]` 是单序列的，需扩成 `[batch][layers][...]`，且每序列长度不同、EOS 时机不同，需要调度器处理「短序列提前退场」。

**本仓库可行性**：⭐⭐⭐☆☆。单图 CLI 没有 batch 可言，但两个真实场景受益：**PDF 流水**（`recognize_pdf_stream` 逐页解码，页与页独立，天然可 2–4 页并行 batch）和 **`--stream` 交互模式**（连续多图）。困难点是显存：batch=4 时 KV 缓存 ×4（V1/V2 F32 下 480 MB→1.9 GB），以及所有 `ctx` 内的单序列预分配缓冲要改成按 batch 索引。教学定位下建议先做层次 1 的 batch4 内核 + 单元测试（`test_unit` 有现成 matvec 对拍基准）。

> 🗣️ **说人话**：batch 的本质是「拼车」：matvec 单飞时每个权重字节只服务 1 个序列（I=1）；b 个序列拼一班车，同一字节用 b 次（I=b），b=8 就翻过屋脊点 5——不换硬件白拿算力余量。工程难点不在内核（`_batch4` 是小手术）而在 KV 布局与「短序列提前退场」的调度；PDF 流水（页间独立）是本仓库现成的拼车场景，所以可行性排序里它排第一。
> *边界*：拼车要求各序列同步前进——长度差异大时 EOS 后的座位空烧，实际加速低于 b；vLLM 用 continuous batching 解决，那是另一层复杂度。

### 9.5 如果继续优化：投机解码（Speculative Decoding）的原理与本仓库可行性

**原理**：decode 慢是因为自回归串行——一步只能出一个 token，而每步的耗时被「读 1.15 GB 权重」钉死，算力大量闲置。投机解码把闲置算力变废为宝：

```
① Draft：用便宜的方法快速猜出 k 个候选 token（t₁,t₂,…,t_k）
② Verify：大模型把 [prompt, t₁..t_k] 一次性 prefill（sgemm！计算-bound，几乎免费）
③ Accept：从候选中取最长的一致前缀，至少白赚 1 个 token
关键：接受准则经过数学设计（拒嫌采样），验证后的分布与直接用大模型生成完全一致——
     不损精度，纯赚速度。期望加速 ≈ (1−α^(k+1))/(1−α)，α 为 draft 单 token 命中率。
```

本质是一次**瓶颈搬运**：把 b 个串行的 memory-bound matvec 步，合并成一个 compute-bound 的 sgemm 步——与 §9.4 的 batch decode 共享同一条 Roofline 逻辑。

**三条 draft 来源的可行性排序**（针对本仓库）：

| 方案 | 原理 | 本仓库可行性 |
|------|------|-------------|
| **① Prompt-lookup / n-gram 投机** | 「上一 token 在 prompt/近期输出中出现过的 n-gram，其后续直接当候选」——纯查表，零模型、零训练 | ⭐⭐⭐⭐⭐ **最高**。OCR 是复制密集任务（表格行、坐标串、重复表头），命中率天然高；实现在 `ds_ocr.c` decode 循环外加一个 n-gram 索引（token_history 已经在维护），验证直接调 `ds_decoder_prefill` 的多 token 路径 |
| ② Self-speculative（层跳跃） | 用前 h 层当 draft、全部层当验证 | ⭐⭐☆☆☆。本仓库无单模型早退机制；跳层分布与全层分布不一致，需校准或训练 adapter，超出教学边界 |
| ③ 独立小模型 draft | 同词表的 0.5B dense 模型 | ⭐☆☆☆☆。需社区有 129280 词表的兼容小模型，还要在 C 里并装两套引擎 |

**实测预期**：OCR 场景 α 经验可达 0.5–0.8（表格/坐标高度可预测），k=4 时期望加速 1.6–2.4×；且验证步走的是已优化 32× 的 prefill 路径（§3），工程上等于「免费复用」。实现要点：接受判定需要比较 draft/验证的 logit 分布（快速路径不物化 logits，需在投机模式下切回 `full_logits_path`——`ds_decoder_forward` 里这条路是现成的）。

> 🗣️ **说人话**：投机解码是把「串行的带宽账」换成「并行的算力账」：draft 白送 k 个候选，大模型一次 sgemm 验证全部——验证走已优化 32× 的 prefill 路径（§3），近乎免费；拒嫌采样保证分布不变，纯赚速度不损精度。期望加速只看命中率 α：OCR 抄表格/坐标时 α 天然 0.5–0.8，k=4 就是 1.6–2.4×。所以本仓库最优 draft 是 n-gram 查表——零模型零训练，token_history 现成。
> *边界*：命中率的敌人是「自由发挥」的段落——纯复制任务吃肉，摘要/改写类任务可能连本都回不了。

## 10. r1/r2 实录：多模型时代的四轮优化（v1.2）

2026 年的两个优化周期，把方法论从"单模型调优"推进到"多模型 + 回归门控"体系。数字基线：1794×1578 截图、空闲 CPU、`--profile`。

### 10.1 V4 接入与 DASH 修正（r1）

接入第 4 个模型（DASH 块稀疏注意力，详见 14 章）后，V4 输出退化为重复空块。对照官方 Python 逐行定位，修掉 5 个 bug（跨层路由缓存、读预算语义、page 轴角度、entmax 输出顺序、valid 掩码），输出与官方逐字一致——**过程与方法论见 14 章第 6 节**。

### 10.2 回归门控：优化的安全网（r1/r2 之间）

数值优化的最大风险是"改好了速度、改坏了精度"——而 V3/V4 的输出对浮点扰动极其敏感（一个近并列 argmax 翻转会级联放大）。对策：

- `tools/regress.sh`：30 组"图片↔正确文本"冻结标签 + CER 阈值，一条命令判定
- `test_unit`：~350 断言的单元测试 + llvm-cov 覆盖率
- **每个数值实验红即回退**。实测案例：把解码 softmax 的 expf 换成 fast_expf（解码早已在用）后进一步用于编码器 softmax → V3 小图 CER 95.4% → 当场回退。结论沉淀为红线：**编码侧注意力权重精度不可妥协**

> 🗣️ **说人话**：回归门控是优化的「验伤单」：30 组冻结标签 + CER 阈值，一条 `tools/regress.sh` 判生死。价值在 fast_expf 案例里看得最清楚——解码侧用了很久没事，挪到编码侧 softmax 立刻 CER 95.4%：**同一个改动，换个位置就是事故**。没有门控，这种回退靠人眼盯输出；有了门控，才敢做 §10.4/§10.5 那种连击实验。
> *边界*：门控只保证「不比冻结标签差」，不保证「普遍正确」——30 组之外的极端图（畸变、小字号）仍需人工抽检。

### 10.3 编码端：SAM 全局注意力 head 并行（r2）

- **测量**：`--profile` 显示编码占墙钟 44–54%，其中 SAM 的 4 个全局注意力层（4096×4096 全注意力）各 0.83s，且 12 个 head 串行
- **方案**：按 head 并行。关键约束是**逐位一致**——每个 head 的两次 sgemm 形状（M=seq_len）与串行完全相同，并行不改变任何浮点结果，CER 保持 0.00
- **结果**：编码 V1 5.2→2.64s、V2 8.2→3.81s、V4 7.3→3.47s；V3 12.3→6.84s（配合 crop 池化与全局视图重叠）

> 🗣️ **说人话**：head 并行是「逐位一致并行」的范本：12 个 head 的 sgemm 形状与串行完全相同、互不写对方数据——并行只是换了执行顺序，任何一个浮点位都不动，CER 0.00 无需担心。4 个 4096×4096 全注意力层各 0.83s 的串行大块拆成 12 份，编码几乎砍半（V2 8.2→3.81s）。所以找优化先找这种「数学上保证无损」的并行（§10.6 第一条）。
> *边界*：逐位一致的前提是每个 head 内部的求和顺序不变——按 head 切没事，按序列维切行就会改在线 softmax 的扫描顺序（03 篇 §5.3 的边界）。

### 10.4 解码端：专家块去拷贝（r2，意外连击）

- **测量**：DS_RSS_PROBE 探针显示峰值 RSS ~11GB 在**加载结束**即成立：6.2GB 权重 + **3.2GB 专家连续块拷贝**双份驻留；三种 madvise/read() 实验证明 ru_maxrss 是"累计缺页"高水位，事后丢弃无效
- **方案**：删掉 3.2GB 拷贝，decode 走 split 路径（gate/up 分别 matvec，逐元素数学与融合版一致），mmap 专家页只在首次使用时驻留一次
- **结果（一石三鸟）**：RSS −3.1GB（11.7-12.5→8.63-9.43GB）；decode **全线 +10–16%**（51.7→59.0 / 49.5→51.7 / 41.3→46.0 / 45.0→52.0 tok/s）——内存压力下降让专家页缓存命中大幅改善；V3 decode 借此越过 45 tok/s 验收线
- **验证**：30 组回归 28 绿 + 2 组坐标抖动级差异（逐字核对为合格转写，待重新冻结）

> 🗣️ **说人话**：「删掉 3.2 GB 拷贝反而全线提速 10–16%」是笔反直觉的免费午餐：拷贝本意是让专家权重连续、提高页命中（§4.3），但 mmap 源页 + 拷贝双份驻留把峰值 RSS 顶到 ~11 GB——内存压力让页缓存到处挨挤，decode 反而慢。删掉拷贝，权重只驻留一份，缺页少、命中高。所以教训一句话：**内存压力本身就是性能变量**，省内存常常就是省时间。
> *边界*：split 路径（gate/up 分开 matvec）必须逐元素与融合版一致才敢换——r4 的行对粒度进一步把并行版也锁成逐位一致（§10.7）。

### 10.5 有界数值实验：BF16 KV（r2）

KV 缓存 F32→BF16 可省一半注意力读流量，但会引入 0.4% 存储舍入。实验按模型粒度做：**V3 (R-SWA) 全 8 组合回归绿 + decode +8% → 保留；V4 (DASH) 打红（2 组 FAIL）→ 回退 F32**。同一改动在不同注意力方案上结论不同——这就是"有界实验 + 回归门控"的价值：不再凭感觉决定"能不能用低精度"。

> 🗣️ **说人话**：BF16 KV 是「同一把钥匙开不同的锁」：V3（R-SWA）全 8 组合绿 + decode +8% → 收下；V4（DASH）2 组红 → 退回 F32。差别在注意力方案对 KV 舍入的敏感度——R-SWA 读的是窗口内 K/V，DASH 的块稀疏选择对 0.4% 舍入更敏感。这就是「有界实验」的意义：精度问题不靠信仰表态，按模型逐个测、红即回（`kv_bf16 = (version==3)`，03 篇 §5.7 的口径由此而来）。
> *边界*：「V3 绿」不等于「V3 永远绿」——换校准集、换语言要重跑；数值结论绑定测试分布。

### 10.6 新增经验清单

- **逐位一致并行**：按输出维度切分的并行（head/行），只要每个元素的求和顺序不变，就是零精度代价的优化——优先找这类
- **线程局部配置**：crop 波次内"本地任务降级、关键路径任务全速"用线程局部（__thread）门控实现，避免全局开关的竞态
- **动态取件池**：N 任务分批 join 的尾批浪费（14+14+2 的尾巴 12 核空转），原子索引取件天然均衡
- **拷贝即双份**：mmap 加载后任何"复制到连续块"的优化都要问峰值 RSS 是否翻倍——RU_maxrss 是高水位，事后 madvise 救不回来
- **瓶颈在同步不在计算（r4）**：MoE 分组并行首版 t1≡t14——并行区越多 barrier 越多，每层 ~19 个微小型并行区把线程都钉在同步点上；合并同类投影成 3 个大并行区后 MoE 才真正提速
- **行对粒度保逐位一致（r4）**：落单行走不同求和顺序（2 组累加器 vs 成对 8 组）；`ds_grouped_matvec_bf16` 以行对 (2r,2r+1) 为切分粒度，行对永不跨线程拆分

### 10.7 r4 实录：解码 MoE 分组行并行（+66% decode）

**问题**：r2 之后 V4 解码 45.9 tok/s，MoE 前向占解码时间的最大头。首版思路是"把更多算子并行化"——把每层能拆的投影都开并行区，结果 t1 与 t14 耗时几乎相同（MoE 7.7s vs 8.4s）：并行并没有换来加速。

**测量定位**： MoE 层每步要跑 gate/up/down 三类投影 × top_k 专家，首版按投影逐个开并行区，每层产生 **~19 个微小型并行区**。每个并行区进出都要 barrier 同步——8 线程全部到齐才能继续。投影本身太小（几万 FLOP 量级），同步开销吃掉了并行收益：线程时间都花在"等齐"上。

**方案**：`ds_grouped_matvec_bf16`（`ds_moe_decoder.c`）把**同类投影合并为一个并行区**：全部 top_k 专家的 gate/up 合并成 1 个区、down 合并成 1 个区（split 布局共 3 个并行区/层，含共享专家行）。区数从 ~19 降到 3，barrier 开销降一个数量级。

**正确性设计——行对粒度**：按行切分并行时，单个输出行的求和顺序必须与串行版完全一致。若一个专家的 2 行落给不同线程，累加器分组数不同（2 组 vs 8 组），末位 ULP 可能变化。因此切分粒度取**行对 (2r, 2r+1)**：行对永不跨线程拆分，每行求和顺序与逐专家串行版逐位一致。验证：输出 md5 与改动前完全一致，且 V2/V3 交叉验证一致；回归门控 30 PASS / 0 FAIL。

**效果**（V4，test截屏.png，M2 Pro）：

| 指标 | r2 前 | r4 后 | 变化 |
|------|-------|-------|------|
| MoE 前向 | 8.4 s | 3.4 s | **−60%** |
| 解码速度 | 45.9 tok/s | 76.4 tok/s | **+66%** |
| 单图总耗时 | 16.0 s | 11.5 s | **−29%** |

**经验**：并行优化的第一步是数 barrier，不是数 FLOPs——"能并行"≠"值得并行"；同步粒度（每层 3 区）比并行宽度（线程数）更值得先调。线程数扫描 8/10/12/14 差异 <3%，维持默认。

> 🗣️ **说人话**：3.7× 之后为什么难再涨——并行度不是瓶颈，同步才是。厨房里叫了 8 个人来帮忙，结果一点没变快——因为每做完一道工序都要所有人排队点名一次，而每道工序本身只有几秒钟的活。r4 一开始就是踩了这个坑：每层 MoE 拆出 ~19 个"微并行区"，每个区进出都要一次 barrier（8 线程全部到齐才能继续），投影本身才几万 FLOP，线程时间全花在"等齐"上了——所以 t1≡t14，开了并行等于没开。解法不是加人（线程数从 8 扫到 14 差异 <3%），而是减少点名次数：把同类投影合并成 3 个大并行区（§10.7），barrier 开销掉一个数量级，MoE 前向 8.4s→3.4s，decode 45.9→76.4 tok/s。教训一句话：并行优化的第一步是数 barrier，不是数 FLOPs——"能并行"≠"值得并行"。
> *边界*：合并并行区只在"区里本来就够忙"时划算；若把两个都极小的算子合并，省下的 barrier 可能还不够多摊的内存访问开销，得实测。

## 小结

ds-ocr 从 v0.5（97s）到 v0.9（15s）的 6.5× 加速，每一倍都来自对瓶颈的精确测量和针对性优化：

1. **Encoding**：并行 N+1 workers → 5.5×（v0.5→v0.8）
2. **Prefill**：Batched MoE sgemm → 32×（v0.5→v0.8）
3. **Decode**：Argmax LM head + 连续 expert 块 + madvise → 3.7×（v0.5→v0.9）
4. **V3 R-SWA**：KV cache 恒定化 → 长文档无限制解析

**核心方法论**：
- **测量先行**：用 Profiler 精确定位瓶颈
- **Amdahl 定律**：优先优化占比最大的部分
- **硬件友好**：连续内存、批量计算、减少 page fault
- **精度优先**：BF16 路由确保与 Python 一致，优化不能牺牲正确性
- **回归门控**（v1.2 新增）：30 组合冻结标签，任何数值实验红即回退（见第 10 节）

带着这些知识，你可以在自己的推理引擎中应用同样的优化策略——**测量 → 分析 → 优化 → 验证**，循环迭代，直到接近硬件极限。
