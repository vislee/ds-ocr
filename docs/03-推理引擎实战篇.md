## 1. 为什么用纯 C 写推理引擎？

### 1.1 Python 推理 vs C 推理

| | Python (PyTorch) | 纯 C 推理 |
|--|-------------------|-----------|
| **启动速度** | 慢（导入 PyTorch ~2s） | 瞬间 |
| **内存占用** | 大（PyTorch 运行时 ~1GB+） | 小（只有权重+缓冲区） |
| **依赖** | PyTorch, CUDA, Python... | 零依赖（只用系统 BLAS） |
| **移植性** | 依赖 Python 环境 | 任何有 C 编译器的平台 |
| **控制力** | 抽象层厚 | 直接控制每个操作 |
| **适合场景** | 研究/训练 | 生产部署/嵌入式 |

> 🗣️ **说人话**：Python 和 C 的差距不在「算」，在「算的前后左右」：矩阵乘本身两边调的是同一套 BLAS，PyTorch 慢在 ~1GB 运行时、~2s 启动和一层层抽象的养活成本。最诚实的对照是同机数字：同一张图，PyTorch ~736s，本引擎 v0.5 就到 ~97s、v0.9 到 ~15s（docs/05 §1.1）——49× 里没有一倍来自「C 编译器更聪明」，全部来自 §1.3 拆的三笔税。所以选型先问负载形态：decode 密集才值得换，一次大 prefill 换了也白换。
> *边界*：这是部署视角的表；研究期频繁改结构、试算子，Python 的迭代速度仍是 C 比不了的优势。

### 1.2 antirez 的设计哲学

qwen-asr（由 Redis 作者 antirez 开发）的设计哲学：
1. **零依赖**：不需要 Python、PyTorch、CUDA
2. **简洁**：每个函数做一件事，逻辑清晰
3. **高效**：BF16 零拷贝 + 平台优化内核
4. **可读**：代码即文档，从代码就能理解算法

ds-ocr 完全继承了这一哲学，并扩展到视觉和多模态领域。

### 1.3 纯 C 快在哪：把「框架税」拆成三笔

上表说 Python 慢、C 快，但「慢」不是一个整体，它由三笔可以分别计量的开销构成。拆开看才知道哪些场景该换语言、哪些换了也没用。

**第一笔：调度税。** PyTorch eager 模式下，每个算子都要走一次 Python → C++ 的 dispatch：解析参数、推导 shape、检查 device/dtype、查算子注册表。量级在 5–10 μs/op（估算，随算子复杂度浮动）。decode 一步 12 层、每层十几个算子（RMSNorm、QKV 三个 matvec、RoPE、注意力、gate、6 个专家 × 3 个 matvec、combine……）≈ 150+ 个算子 → 光调度就是 1 ms 量级。本仓库里这些「算子」是直接函数调用（`decoder_layer_forward` 里一行一个），成本是纳秒级。

**第二笔：临时张量税。** 框架每个算子都要分配输出张量（allocator 命中缓存也要记账、要维护引用计数、要处理生命周期）。本仓库 decode 的中间缓冲在 `alloc_decoder_buffers` 里一次性分配、全程复用（`ctx->dec_x`、`ctx->dec_q`、`ctx->dec_k`……），每步零 malloc；层间连 memcpy 都省了，靠指针交换（§6.4）。

**第三笔：布局税。** 框架内核必须处理任意 stride、非连续张量、广播、类型提升，于是热循环里塞满分支和 stride 计算。本仓库的权重是 mmap 出来的行主序 BF16，`ds_bf16_matvec_fused_neon` 直接按 `o * in_dim` 算行首、按 `k` 线性推进，没有任何 stride 检查——因为布局在加载时就已经定死了。

> **边界**：这三笔税在 prefill 里占比很小。prefill 是几个大 GEMM，每个 GEMM 几毫秒，框架的 dispatch 开销被摊成千分之一，而 cuBLAS/Accelerate 的 sgemm 和手写内核一样快。所以「纯 C 更快」不是普适结论，是 **decode 形态**（算子多、每个算子小、每步都要走一遍）的结论。反过来说，如果你的负载是「一次大 batch 的 prefill」，换语言几乎没有收益。

> 🗣️ **说人话**：把 Python 的「慢」想象成三张账单：调度税是每点一个菜都要重新问一遍厨房——150+ 个算子 × 5–10 μs ≈ 1 ms/步；临时张量税是每道菜都用新盘子、吃完还得有人收——本仓库 `alloc_decoder_buffers` 一次分配、每步零 malloc；布局税是后厨必须会做全世界的菜系——任意 stride/广播的分支塞满热循环。纯 C 把三张账单一次撕掉：函数直调、缓冲复用、布局加载期定死（§2.2）——所以同样的硬件，钱花在数学上而不是框架上。
> *边界*：三笔税的相对大小随负载浮动——模型越小、batch 越小，调度税占比越高；上大 batch serving 后框架把开销摊薄，差距会缩回内核本身。

## 2. Safetensors：权重的存储与加载

### 2.1 Safetensors 格式

Safetensors 是 HuggingFace 推出的模型权重格式，比 PyTorch 的 `.bin` 更安全、更快：

```
┌─────────────────────────────────────┐
│ 8 bytes: N = header JSON 长度       │
├─────────────────────────────────────┤
│ N bytes: header JSON                │
│  {"tensor_name": {                  │
│    "dtype": "BF16",                 │
│    "shape": [1280, 896],            │
│    "data_offsets": [start, end]     │
│  }, ...}                            │
├─────────────────────────────────────┤
│ 数据区域: 原始二进制 (BF16/F32/...)  │
│  tensor1 的数据 | tensor2 的数据 | ...│
└─────────────────────────────────────┘
```

这个「header 在前、裸数据在后」的排布不是审美选择，它直接决定了三件事：

1. **打开文件只需读前 8 字节 + header**，就能拿到全部张量的 dtype/shape/偏移，不需要反序列化整个文件。对比 PyTorch 的 `.bin`（pickle）：pickle 是「可执行指令流」，加载等于执行一段代码——慢，而且有任意代码执行风险。Safetensors 的 header 是纯 JSON，解析器只做字符串→数字，不执行任何东西。
2. **数据区是裸二进制**，所以可以 mmap 之后按偏移直接取指针：`safetensors_data()` 就是 `基址 + 8 + header_size + data_offset`（`ds_safetensors.c`）。没有解码、没有拷贝、没有中间对象。
3. **`data_offsets` 是相对数据区起点、不是文件绝对偏移**。所以 header 变长（多存几个张量、多几个字段）时，数据区整体后移，但所有偏移值不用改——这让「改 header 不动数据」成为可能，也让 `safetensors_data()` 的指针算术只有一次加法。

代价只有一处：header 是 JSON，得先 `malloc` 一份带 NUL 结尾的副本再解析（`sf->header_json`），因为 mmap 区里的 JSON 后面紧跟二进制数据、没有终止符。这份拷贝只发生一次，量级几十 KB。

> 🗣️ **说人话**：safetensors 像一本「先放目录、再放正文」的书：前 8 字节写目录长度，接着是 JSON 目录（每个张量的 dtype/shape/偏移），后面全是裸数据。目录是纯数据不是代码——对比 pickle 那种「可执行指令流」，加载等于执行一段程序，又慢又危险；这里只需「读目录、按偏移取正文」两步，所以「打开文件」和「用上权重」之间没有任何解码步骤。`data_offsets` 相对数据区起点，目录再长也不用改偏移，`safetensors_data()` 的指针算术永远只有一次加法。
> *边界*：header 只记录 dtype、不做语义校验——BF16 的张量被当 F32 读只会产出数值垃圾而不报错，这类错误靠单元测试和回归门控兜底（docs/05 §10.2）。

### 2.2 零拷贝 mmap 加载

传统方式：打开文件 → read 到内存 → 解析  
mmap 方式：把文件映射到虚拟地址空间 → 直接用指针访问

**在 ds-ocr 中的实现**（`ds_safetensors.c`）：

```c
safetensors_file_t *safetensors_open(const char *path) {
    /* 1. 打开文件 */
    int fd = open(path, O_RDONLY);
    
    /* 2. 获取文件大小 */
    struct stat st;
    fstat(fd, &st);
    size_t file_size = st.st_size;
    
    /* 3. mmap: 将文件映射到内存 */
    void *data = mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, fd, 0);
    
    /* 4. 解析 header JSON（前 8 bytes 是长度，后面是 JSON） */
    uint64_t header_len;
    memcpy(&header_len, data, 8);
    char *header_json = (char *)data + 8;
    
    /* 5. 解析 JSON，记录每个 tensor 的偏移和形状 */
    /* ... */
}
```

> **关键优势**：mmap 是**惰性加载**——只有实际被访问的页才会从磁盘读入。对于 3B 参数的模型，大部分专家权重可能根本不会被访问到（MoE 稀疏激活），节省大量内存。

> 🗣️ **说人话**：零拷贝不是拷贝得更快，而是根本没有拷贝这回事。常规「读文件」是：磁盘 → 内核缓冲 → 你 malloc 出来的内存，同一份字节搬了两趟。mmap 干的是另一件事——它把文件所在的那几页物理内存，直接挂到进程地址空间上、起个名字。于是「取某个张量」变成：按名字查到地址 + 解引用指针，中间一次 memcpy 都没有。第一次碰到某页才触发缺页中断、从磁盘拉进来；从头到尾不碰的专家权重，磁盘 IO 和物理内存都还是 0。
> *边界*：映射后若文件被删或被改写，映射页会失效或读到脏数据——mmap 靠 fd 的生命周期兜底，别映射完就 unlink。

### 2.3 多分片支持

大模型权重通常分成多个文件（`model-00001-of-00003.safetensors` 等）：

```c
typedef struct {
    safetensors_file_t *shards[8];  /* 最多 8 个分片 */
    int num_shards;
} multi_safetensors_t;

/* 统一查找：在所有分片中搜索 tensor */
const safetensor_t *multi_safetensors_find(const multi_safetensors_t *ms,
                                            const char *name,
                                            safetensors_file_t **out_sf);
```

> 🗣️ **说人话**：多分片就是「一个模型拆进 8 个抽屉」：`multi_safetensors_find` 挨个抽屉翻，命中即返回该分片的 mmap 指针，上层不必知道权重躺在哪个文件——所以查找成本 = 最多 8 次按名查找，相对推理可忽略。ds-ocr 解码器单分片就够，这个结构更多是给分片模型留的口子。
> *边界*：`shards[8]` 是硬编码上限，更多分片要改结构体；每个分片是独立 mmap，8 片就是 8 段地址空间、8 次 open。

### 2.4 BF16 权重的零拷贝访问

```c
/* 获取 BF16 数据的直接指针（不复制） */
uint16_t *safetensors_get_bf16_direct(const safetensors_file_t *sf,
                                       const safetensor_t *t) {
    return (uint16_t *)((char *)sf->data + sf->header_size + t->data_offset);
}

/* 获取 F32 数据（需要转换，会复制） */
float *safetensors_get_f32(const safetensors_file_t *sf,
                            const safetensor_t *t) {
    uint16_t *bf16 = safetensors_get_bf16_direct(sf, t);
    size_t n = safetensor_numel(t);
    float *f32 = (float *)malloc(n * sizeof(float));
    /* BF16 → F32 转换 */
    uint32_t *d = (uint32_t *)(void *)f32;
    for (size_t i = 0; i < n; i++)
        d[i] = ((uint32_t)bf16[i]) << 16;
    return f32;
}
```

> **策略**：解码器权重（占 95%+）用 BF16 零拷贝，编码器权重（较小）用 F32 预转换。因为解码器是逐 token 推理（计算密度低），BF16→F32 的逐行转换开销可忽略；而编码器是批量计算，预转换更高效。

> 🗣️ **说人话**：`safetensors_get_bf16_direct` 是「白拿」——指针直接指进 mmap 区，零拷贝零分配；`safetensors_get_f32` 是「付费」——malloc 一块两倍大的内存、逐元素 `<<16` 展开。分工由此而来：95%+ 的解码器权重白拿（matvec 里 `vshll` 反正会顺手展开，§4.4），小编码器权重付一次费换 sgemm 的干净 F32 输入。所以「要不要转换」是按使用模式算出来的账（§3.5），不是按精度。
> *边界*：白拿的指针生命周期跟着 mmap 走，不能 free、不能写——`MAP_PRIVATE` 只读映射一写就 `SIGSEGV`（§2.5）。

### 2.5 mmap 的代价模型：缺页、page cache 与 RSS

§2.2 讲了 mmap 的好处，这里补它的**成本结构**——因为「零拷贝」不等于「零开销」，只是把开销从「拷贝」换成了「缺页」。

**虚拟内存 ≠ 物理内存。** `mmap` 返回的是一段虚拟地址区间，`file_size` 字节立刻记进 VIRT（虚拟地址空间），但 RSS（常驻物理内存）是 0。第一次触碰某一页时触发**缺页中断**：内核查 page cache，命中则只建页表（minor fault），未命中则从磁盘读（major fault，通常连带预读若干页）。

**成本量级。** 一次 minor fault 约 1 μs（估算），major fault 是磁盘延迟。3B 参数的 BF16 权重 = 6.2 GB ÷ 4 KB = **151 万页**；若全冷、每页 1 μs，就是 1.5 s 量级（估算，实际被内核 readahead 大幅摊薄——顺序访问时一次缺页会预读几十页）。这就是为什么「冷启动」和「热启动」的加载时间差一个数量级（docs/09 §5.5 的冷/热态）。

**page cache 是共享的。** `MAP_PRIVATE` 只读映射的干净页，就是内核 page cache 里的那一份物理页——不是副本。两个进程加载同一个模型，物理内存只算一份；进程退出，页还在 page cache 里，下次启动直接 minor fault。这是 mmap 相对 `read()` 到私有堆的另一层收益：`read()` 的副本是进程私有的，退出即消失。

**RSS 可以主动归还。** 加载阶段每个 tensor 都被摸过一遍（校验、预转换），6 GB 的源页因此全部变成常驻。`multi_safetensors_madvise_unused()`（`ds_safetensors.c`）在加载完成后对整段映射做 `MADV_DONTNEED`，把这些**干净的文件页**的页表项丢掉——代码注释记的量级是 ~4–5 GB。此后任何指针触碰会重新缺页、从 page cache 拉回，所以它只降 RSS，不影响热态跑分。

> **边界**：`MADV_DONTNEED` 对 `MAP_PRIVATE` 文件映射丢的是页表项、不是数据，安全；但如果映射期间文件被截断或删除，重新缺页会直接 `SIGBUS`。另外 `MAP_PRIVATE` 是只读语义下的写时复制——真去写会 `SIGSEGV`（`safetensors_get_bf16_direct` 的注释明确写了这一点）。

> 🗣️ **说人话**：mmap 不是「免费拿到 6.2 GB」，是「按页赊账」：mmap 那一刻只有 VIRT 涨、RSS 为 0，每碰一页记一笔缺页——3B 的 BF16 权重约 151 万页，全冷 1.5 s 量级，靠 readahead 摊薄。`MADV_DONTNEED` 则是「还账」：丢掉干净页的页表项，RSS 立降 ~4–5 GB，下次要用再从 page cache 赊回来，几乎免费。所以 RSS 的含义不是「用了多少」而是「现在押着多少页」——它是策略变量，不是宿命（docs/05 §7.6）。
> *边界*：冷/热启动差一个数量级，意味着基准测试必须先热身一遍再计时——docs/09 §5.5 的冷/热态口径就是这么来的。

## 3. BF16 精度：存储一半，计算全精度

### 3.1 什么是 BF16？

| 格式 | 符号位 | 指数位 | 尾数位 | 范围 | 精度 |
|------|--------|--------|--------|------|------|
| FP32 | 1 | 8 | 23 | ±3.4e38 | ~7位十进制 |
| FP16 | 1 | 5 | 10 | ±65504 | ~3位十进制 |
| **BF16** | 1 | 8 | 7 | ±3.4e38 | ~2位十进制 |

BF16 的巧妙之处：**保持 FP32 的指数范围，只减少尾数精度**。
- 和 FP32 范围相同（不会溢出）
- 精度只有 FP32 的 1/65536（尾数 7 位 vs 23 位，但对深度学习足够）
- 只需 FP32 一半的存储空间

**为什么是 1/65536，而不是「少 16 位所以精度减半」？** 因为浮点数的精度不是线性的，是**相对精度**：尾数 23 位 → 7 位，可表示的相邻两数间距从 $2^{-23}$ 变成 $2^{-7}$，比值 $2^{16} = 65536$。但「有效十进制位数」只从 ~7 位降到 ~2–3 位（$2^{-7} \approx 0.8\%$ 相对误差），因为十进制位数是 $\log_{10}$ 关系。

**为什么深度学习能忍 0.8% 的相对误差？** 因为神经网络的计算是**大量项求和**，误差按随机方向抵消（$\sqrt{n}$ 增长而非 $n$），而权重本身在训练时就带着这个量级的噪声。真正不能忍的是**指数范围**：FP16 的 5 位指数最大 65504，attention score、LayerNorm 的方差、梯度累积都容易越界；BF16 拿 FP32 的 8 位指数，永不溢出。这就是「宁可少尾数、不能少指数」的取舍。

> **边界**：BF16 的 7 位尾数在**累加**场景会出事——如果累加器也用 BF16，$1 + 0.008$ 会直接舍回 1，长序列求和会系统性丢小项。所以本仓库的累加器一律是 F32（§3.2），BF16 只用于**存储**。

> 🗣️ **说人话**：BF16 是把 FP32 的笔记本撕掉下半页：指数 8 位原样保留（范围照旧 ±3.4e38，永不溢出），尾数从 23 位砍到 7 位（相对精度差 2^16 = 65536 倍，十进制位数 ~7 → ~2–3）。深度学习吃的是范围不是细度：attention score、LayerNorm 方差动辄上千，FP16 的 5 位指数在 65504 就爆；而 0.8% 的相对误差在几万项求和里按 √n 随机抵消——「宁可少尾数、不能少指数」这笔账就是这么算的，所以 BF16 是存储格式的胜利，不是算术的妥协。
> *边界*：在没有 bfdot 的 CPU 上，「BF16 计算」实际是展开成 F32 再算——本仓库的 BF16 更像存储格式而非计算格式（§4.4 的两条路径）。

### 3.2 BF16 ↔ FP32 转换

```
BF16 (16bit):  S EEEEEEEE MMMMMMM
FP32 (32bit):  S EEEEEEEE MMMMMMMMMMMMMMMMMMMMMMM

转换: FP32 = BF16 << 16  (高位对齐，低位补零)
```

**在代码中**：

```c
/* BF16 → FP32 */
uint32_t f32_bits = ((uint32_t)bf16_value) << 16;
float f32_value;
memcpy(&f32_value, &f32_bits, sizeof(float));

/* FP32 → BF16 (截断低16位) */
uint32_t f32_bits;
memcpy(&f32_bits, &f32_value, sizeof(uint32_t));
uint16_t bf16_value = (uint16_t)(f32_bits >> 16);
```

> 🗣️ **说人话**：BF16 是存的时候丢精度，算的时候一分不欠。BF16 的位模式，就是 FP32 砍掉低 16 位尾数后的样子。关键动作是那个 `<< 16`：把 16 位搬回高 16 位、低位补 0，它当场又变成一个合法的 FP32。所以 matvec 里权重是「粗格」的，但累加器 `sum` 从头到尾是 F32，乘加走的是硬件的「先加宽再做 FMA」。一条 `vshll_n_u16` 同时办了两件事：省下内存带宽，又没让算术降级。
> *边界*：补零≠恢复精度——真正的低位信息在存 BF16 那一刻就永久丢了，后面算得再准，也只是「准确地用着一份有损的权重」。

### 3.3 BF16 权重的矩阵乘法

ds-ocr 的核心操作：**用 BF16 权重和 F32 输入做矩阵乘法，输出 F32 结果**。

```c
/* y = x @ W_bf16^T  (x: F32, W: BF16, y: F32) */
void ds_linear_nobias_bf16(float *y, const float *x, const uint16_t *W_bf16,
                            int seq_len, int in_dim, int out_dim) {
    /* 内部实现：
     * 逐行遍历 W_bf16，每行：
     *   1. BF16 → F32 (on-the-fly)
     *   2. dot(x, row_f32) → y[row]
     */
}
```

> **为什么不预先全部转 F32？** 因为解码器权重巨大（几 GB），全转 F32 会翻倍内存。逐元素 on-the-fly 转换只需少量寄存器，不增加内存占用。

**这个「矩阵乘法」在硬件上到底发生什么。** 以 `ds_bf16_matvec_fused_neon`（`ds_kernels_neon.c` L125）为例，内层循环每轮处理 **2 个输出行 × 32 个输入元素**，用 8 个 F32 累加器（每行 4 个）：

```
每轮 32 元素 × 2 行 = 64 个 MAC，指令构成：
  8 条 vld1q_f32      ← x 的 32 个元素（两行共用，只读一次）
  8 条 vld1q_u16      ← 两行各 4 条，共 64 个 BF16
  16 条 vshll_n_u16   ← 每个 u16x8 拆成低/高半区，各一条加宽+左移
  16 条 vfmaq_f32     ← 16 × 4 lane = 64 个 FMA
```

三个设计点值得单独看：

1. **x 只读一次、两行共用**。这是「一次处理 2 行」的全部收益：x 的 8 次载入被 2 行摊薄，访存指令数减半。
2. **每行 4 个独立累加器**。Apple Firestorm 的 FMA 延迟约 4 拍（代码注释），如果只有一个累加器，`acc = fma(acc, w, x)` 会串行停等；4 条链交替填满这 4 拍，吞吐才跑得起来。
3. **`vshll_n_u16` 一条指令干两件事**：u16 → u32 的零扩展 + 左移 16 位。BF16→F32 的位模式转换因此不落内存、不占额外指令槽。

**算术强度算一遍**：每轮 64 个 MAC = 128 FLOP，从 DRAM 读的只有权重 64 × 2 B = 128 B（x 的 32 × 4 B = 128 B 常驻 L1，不产生 DRAM 流量）。$I = 128 / 128 = 1.0$ FLOP/B——正好是 §6.1 说的「≈1」。如果把 x 也算进流量，$I$ 会掉到 0.5，但那是 L1 命中率的问题，不是 DRAM 的问题。这就是为什么 decode 被带宽钉死（docs/05 §7.3 的 Roofline 推导）。

> 🗣️ **说人话**：decode 的「矩阵乘法」其实是根流水线：每轮并行处理 2 行 × 32 元素，x 的 32 个数只读一次、两行共用（访存指令省一半）；权重 BF16 进寄存器，一条 `vshll` 当场展开成 F32、一条 `vfma` 完成乘加，全程不落内存。每行 4 个累加器不是大方——FMA 延迟约 4 拍，单累加器会串行停等，4 条链交错才喂饱。算下来 I = 128/128 = 1.0 FLOP/B，正好踩在 §6.1 的「≈1」上——所以提速只剩「少读字节」一条路（docs/05 §7.3）。
> *边界*：2 行 × 32 元素的展开假设 in_dim 是 32 的倍数——1280/896 恰好满足，换模型配置时要重新核对尾部处理。

### 3.4 流式 Argmax：不计算全部 logits

对于 12 万词的词表，计算全部 logits（lm_head @ x）需要 129280 × 1280 = 1.65 亿次乘法。但贪心解码只需要 argmax——**最大值在哪就行**。

**流式 Argmax**（`ds_kernels.c` → `ds_argmax_matvec_bf16`）：

```c
int ds_argmax_matvec_bf16(const float *x, const uint16_t *W_bf16,
                           int in_dim, int out_dim) {
    int best_id = 0;
    float best_val = -1e30f;
    
    /* 逐行计算点积，同时追踪最大值 */
    for (int row = 0; row < out_dim; row++) {
        float dot = ds_dot_f32_impl(x, bf16_to_f32_row(row), in_dim);
        if (dot > best_val) {
            best_val = dot;
            best_id = row;
        }
    }
    return best_id;
    /* 不需要存储 129280 个 logits！ */
}
```

> **节省内存**：流式 argmax 不需要分配 129280 × 4 bytes = 512KB 的 logits 缓冲区。但对于需要重复惩罚等后处理的场景，仍需完整 logits。

### 3.5 on-the-fly 转换的带宽账：转换一次不如每次便宜

§3.2 讲了位运算原理，这里算**经济账**：为什么「每次用时转」比「提前转好放着」更划算。

设一段权重有 N 个元素，会被使用 T 次（decode 一步 = 1 次，一段 OCR 生成 226 个 token = 226 次）。两种策略的**累计内存流量**：

| 策略 | 一次性成本 | 每次使用成本 | T 次使用总流量 | 额外内存驻留 |
|------|-----------|-------------|---------------|-------------|
| 预转换成 F32 | 读 2N + 写 4N | 读 4N（读 F32 副本） | 6N + 4NT | +4N（F32 副本） |
| **on-the-fly** | 0 | 读 2N（读 BF16 原件） | **2NT** | 0 |

以 T=226 代入：预转换 ≈ 910N，on-the-fly ≈ 452N——**稳态流量直接减半**，还省下一份 F32 副本的内存。以 lm_head（N = 129280 × 1280 ≈ 1.66 亿元素）为例：

- 预转换：一次读 331 MB + 写 662 MB，之后每步 decode 还要读 662 MB 的 F32 副本，且这 662 MB 常驻内存
- on-the-fly：每步只读 331 MB 的 BF16 原件，转换发生在 NEON 寄存器里（`ds_kernels_neon.c` 的 `ds_bf16_matvec_fused_neon` 用 `vshll_n_u16` 一条指令完成「u16 加宽成 u32 并左移 16 位」），**不落内存、不占额外带宽**

这就是本仓库的取舍依据（`ds_moe_decoder.c` 文件头注释）：解码器权重巨大且逐 token 使用 → on-the-fly；编码器权重小且一次性批量使用 → 预转换一次（`ds_kernels.c` 的 `ds_bf16_to_f32_buf`，超过 64K 元素的大转换还会进线程池并行，见 §8.4）。

> **手算算例**：一个专家的 gate_up_fused 权重 [1792, 1280]，N = 229 万。预转换一次 = 读 4.6 MB + 写 9.2 MB；decode 中它每步被读一次 BF16 = 4.6 MB。若预转换，则首次多付 13.8 MB 流量 + 常驻 9.2 MB 内存——对一个每步都要用的权重，on-the-fly 从第一步起就更便宜。

> 🗣️ **说人话**：预转换像「把整本字典抄成大字版再用」：抄一次（读 2N 写 4N），之后每次读大字版（4N），还白占一层书架；on-the-fly 像「用时眯眼看小字」：每次只读原版 2N，「翻译」发生在 NEON 寄存器里、不占内存流量。decode 一步读一遍、226 步读 226 遍，T 越大复利越猛——T=226 时稳态流量 910N vs 452N，直接减半还省一份副本内存。所以大而反复用的权重永远 on-the-fly。
> *边界*：T 很小时反过来——编码器权重全程只扫一遍，预转换一次换 sgemm 全程吃干净 F32（`ds_bf16_to_f32_buf`，§8.4）。

### 3.6 流式 argmax 的完整带宽账：省的不是 512 KB，是 331 MB

§3.4 说流式 argmax「省了 512KB 的 logits 数组」——这其实是账目里最小的一项。把它和「物化全部 logits」的完整路径对比（数字来自 `ds_moe_decoder.c` → `ds_decoder_forward` 的注释与代码，M2 Pro 实测）：

**路径 A：物化 logits（旧做法 / 现在的 full path）**

```
1. （首次）BF16→F32 转换 lm_head：读 331 MB + 写 662 MB → 常驻 662 MB F32 副本
2. 每步 sgemm：读 662 MB F32 权重 + 写 517 KB logits（129280 × 4 B）
3. 每步 argmax：读回 517 KB logits
   每步总流量 ≈ 663 MB   → 理论下限 663 MB ÷ 200 GB/s ≈ 3.3 ms
   v0.5 逐行 BF16 物化实测 ~55–63 ms（转换开销 + 无 sgemm 批量）
```

**路径 B：流式 argmax（`ds_kernels.c` → `ds_argmax_matvec_bf16`）**

```
1. 每步直接在 BF16 权重上逐行点积：读 331 MB BF16
2. logits 永不落盘——冠军值和 ID 只在寄存器/栈上
   每步总流量 ≈ 331 MB   → 理论下限 ≈ 1.7 ms
   实测 ~8 ms（含多线程同步与 BF16 展开开销）
```

三笔账分开看：

| 维度 | 物化路径 | 流式 argmax | 省下 |
|------|---------|------------|------|
| **内存驻留** | 662 MB F32 副本 + 517 KB logits | 0 | **−662 MB** |
| **每步读流量** | 662 MB（F32） | 331 MB（BF16） | **÷2**（§3.5 的 T=∞ 极限） |
| **写+读回 logits** | 517 KB × 2 | 0 | 微不足道，但省一次分配 |
| **实测每步耗时** | ~55–63 ms（v0.5） | ~8 ms | **~8×**（docs/05 §4.1） |

> **为什么「不物化」还能做重复惩罚？** §7.3 的惩罚只需要历史 token（约几百个）的 logit。流式 argmax 之后用 `ds_bf16_dot_row`（`ds_kernels.c`）对这几个 ID 逐个补算点积即可——把 O(129280) 的「全量先算后查」变成 O(历史长度) 的「按需补算」，这就是 docs/05 §4.2 的 Selective Repetition Penalty。需要全量分布的温度采样才走回物化路径（`ds_decoder_forward` 中的 `full_logits_path` 标签）。

> 🗣️ **说人话**：「省 512 KB」是账单里最便宜的一行，大头是**根本不物化**：物化路径每步读 662 MB 的 F32 副本、还要养着这 662 MB 常驻内存；流式 argmax 只读 331 MB 的 BF16 原件，冠军值和 ID 活在寄存器里，logits 数组从头到尾不存在。8× 的实测加速（55–63 ms → ~8 ms）没有一个字节是「搬得更快」，全是「压根没搬」。所以快慢是按需切换的工程决策，不是信仰——要完整分布（温度采样）才回物化路径。
> *边界*：「补算」只对贪心+惩罚成立；要 top-p/温度采样就得老实付 662 MB 那笔账（§7.2）。

### 3.7 舍入：截断与就近舍入差在哪

§3.2 的 `f32_bits >> 16` 是**截断**（round toward zero），而 `ds_f32_to_bf16_neon`（`ds_kernels_neon.c` L90）做的是**就近舍入**：

```c
/* 截断：直接丢低 16 位 */
bf16 = (uint16_t)(f32_bits >> 16);

/* 就近舍入：先加半个 ULP（0x8000），让进位把「四舍五入」带进高 16 位 */
u = (u + 0x8000) & 0xFFFF0000u;
bf16 = (uint16_t)(u >> 16);
```

**为什么加 0x8000 就等于四舍五入？** 被丢弃的低 16 位取值范围是 `[0, 0xFFFF]`，中点是 `0x8000`。加上中点后，低 16 位 ≥ 0x8000 的那些数会向高位进位（相当于「入」），< 0x8000 的不会（相当于「舍」）。一次整数加法 + 一次掩码，没有分支、没有浮点运算。

**两种做法的误差差一倍。** 截断的误差恒在 $[0, 1\text{ ULP})$，期望 $0.5$ ULP 且**有偏**（永远向下）；就近舍入的误差在 $[-0.5, 0.5]$ ULP，期望 $0$。对单次转换差别不大，但对「反复转换」或「大量元素求和」的场景，有偏误差会累积成系统性漂移。

> **边界**：`+0x8000` 在「被丢弃部分恰为 0x8000」（精确半途）时恒进位，严格 IEEE RNE（round-to-nearest-even）此时应向偶数舍入。差异只有半个 ULP、只出现在精确半途点，工程上可接受——代码注释里明确记了这个偏差。硬件 `BFCVT` 指令（bfdot 路径用的）才是严格 RNE。

**为什么本仓库两处用不同策略？** 因为用途不同：`safetensors_get_f32` 的 `<< 16` 是**无损**的（BF16 的 16 位原样搬到高位、低位补零，信息一点不丢，只是「展开」）；`ds_f32_to_bf16_neon` 是**有损压缩**（F32 → BF16 必须丢 16 位），所以必须舍入。前者是解码，后者是编码，别混为一谈。

> 🗣️ **说人话**：截断与就近舍入的差别，就是「小数部分一律不要」和「四舍五入」的差别：前者误差恒在 [0, 1 ULP) 且永远向下，攒多了系统性漂移；后者 ±0.5 ULP、期望为零。实现上就近舍入便宜得惊人——给 F32 位模式加 0x8000（半个 ULP），进位自动把「五入」带进高 16 位，再掩码截断：两条整数指令、无分支无浮点。方向别搞反：BF16→F32 的 `<<16` 是无损展开，F32→BF16 才需要舍入——所以「展开无损、压缩有损」八个字就够记住两处策略。
> *边界*：两条路径差半个 ULP 意味着「同一权重经不同加载路径位模式可能不同」——回归门控（docs/05 §10.2）比的是最终 CER、不锁中间位模式，所以两套策略能共存。

## 4. 数学内核：从通用到平台优化

### 4.1 三级内核架构

ds-ocr 和 qwen-asr 都采用**三级内核架构**：

```
ds_kernels.h           ← 统一 API（平台无关）
    │
ds_kernels_impl.h      ← 编译时平台检测 + 宏分发
    │
    ├── ds_kernels_generic.c   ← 通用 C 实现（任何平台）
    ├── ds_kernels_neon.c      ← ARM NEON 优化（Apple Silicon）
    └── ds_kernels_avx.c       ← x86 AVX2+FMA 优化（Intel/AMD）
```

**编译时自动选择**（`ds_kernels_impl.h`）：

```c
#ifdef __ARM_NEON
    #define ds_bf16_matvec_fused_impl ds_bf16_matvec_fused_neon
    #define ds_dot_f32_impl ds_dot_f32_neon
#elif defined(__AVX2__) && defined(__FMA__)
    #define ds_bf16_matvec_fused_impl ds_bf16_matvec_fused_avx
    #define ds_dot_f32_impl ds_dot_f32_avx
#else
    #define ds_bf16_matvec_fused_impl ds_bf16_matvec_fused_generic
    #define ds_dot_f32_impl ds_dot_f32_generic
#endif
```

> 🗣️ **说人话**：三级架构像连锁餐厅的菜谱管理：总部只发一份统一菜单（`ds_kernels.h` 的 API），后厨按城市配不同的灶（generic/NEON/AVX 三份实现），开哪家店编译期就定（`ds_kernels_impl.h` 的宏分发）。收益是上层一行不改：`ds_dot_f32` 在 Apple Silicon 跑 NEON、在老服务器跑 generic，调用方毫不知情——所以跨平台不是「多写几份代码」的体力活，是「一份接口 + N 份后厨」的组织活。
> *边界*：编译期分发换不来「同一份二进制跨 CPU 代际」——M1/M2 共存要靠运行时探测切函数指针（§4.5）。

### 4.2 以 dot product 为例

**通用实现**：

```c
/* ds_kernels_generic.c */
float ds_dot_f32_generic(const float *a, const float *b, int n) {
    float sum = 0.0f;
    for (int i = 0; i < n; i++) sum += a[i] * b[i];
    return sum;
}
```

**NEON 实现**（4× 并行）：

```c
/* ds_kernels_neon.c */
float ds_dot_f32_neon(const float *a, const float *b, int n) {
    float32x4_t sum_vec = vdupq_n_f32(0.0f);
    int i = 0;
    for (; i + 3 < n; i += 4) {
        float32x4_t a_vec = vld1q_f32(a + i);
        float32x4_t b_vec = vld1q_f32(b + i);
        sum_vec = vfmaq_f32(sum_vec, a_vec, b_vec);  /* FMA: sum += a*b */
    }
    /* 水平求和 + 处理剩余元素 */
    float sum = vaddvq_f32(sum_vec);
    for (; i < n; i++) sum += a[i] * b[i];
    return sum;
}
```

**AVX2 实现**（8× 并行）：

```c
/* ds_kernels_avx.c */
float ds_dot_f32_avx(const float *a, const float *b, int n) {
    __m256 sum_vec = _mm256_setzero_ps();
    int i = 0;
    for (; i + 7 < n; i += 8) {
        __m256 a_vec = _mm256_loadu_ps(a + i);
        __m256 b_vec = _mm256_loadu_ps(b + i);
        sum_vec = _mm256_fmadd_ps(a_vec, b_vec, sum_vec);
    }
    /* 水平求和 + 剩余处理 */
}
```

**上面是教学简化版，真实代码多一个累加器。** `ds_dot_f32_neon`（`ds_kernels_neon.c` L367）用 `acc0`/`acc1` 两个累加器交替：

```c
for (; i + 8 <= n; i += 8) {
    acc0 = vfmaq_f32(acc0, a0, b0);   // 前 4 个
    acc1 = vfmaq_f32(acc1, a1, b1);   // 后 4 个
}
float sum = vaddvq_f32(vaddq_f32(acc0, acc1));
```

**为什么多一个累加器就能快？** 因为 FMA 有**延迟**（结果不是下一拍就能用）。单累加器时，第 $i+1$ 轮的 `vfmaq` 必须等第 $i$ 轮的结果，硬件只能空转等延迟；两个累加器时，两条链互不依赖，可以背靠背发射。这是「指令级并行（ILP）」最便宜的一种形式——不增加任何内存流量，只多占一个寄存器。

**水平求和为什么不能省。** SIMD 算完是 4 个 lane 各持一个部分和，必须归约成一个标量。`vaddvq_f32` 是 ARMv8 专有的「4 lane 一次收完」指令；x86 上要 `hadd` + `shuffle` 好几条。这一步也是**数值顺序与标量版不同的根源**：SIMD 是「先分组求和再相加」，标量是「从左到右累加」，浮点加法不满足结合律，所以末位会有 ULP 差异（`ds_kernels_neon.c` 文件头注释明确记了这一点，靠回归门控兜底）。

> 🗣️ **说人话**：SIMD 点积就是把「一个一个乘」改成「四条传送带一起乘」：一条 `vfmaq_f32` 喂 4 个乘加，1280 维从 1280 拍压到 320 拍。两个细节决定真机速度：① 双累加器不是为了精度，是填 FMA 的约 4 拍延迟——两条链背靠背发射不空转，所以多占一个寄存器换满吞吐是最便宜的交易；② `vaddvq_f32` 收尾把 4 条带的部分和归约成标量。「先分组再相加」的顺序与标量版不同、浮点不满足结合律，末位会差 ULP——这正是回归门控要盯的（docs/05 §10.2）。
> *边界*：余数尾巴走标量循环，慢但正确；1280/896 这类维度天然整除，尾巴分支几乎不热。

### 4.3 BLAS 加速的矩阵乘法

对于大矩阵乘法（prefill 阶段），ds-ocr 和 qwen-asr 都调用系统 BLAS：

```c
/* macOS: Accelerate Framework (cblas_sgemm) */
/* Linux: OpenBLAS (cblas_sgemm) */

/* C = A @ B^T: A[seq,K], B[N,K], C[seq,N] */
void ds_matmul_t(float *C, const float *A, const float *B, int M, int K, int N) {
    cblas_sgemm(CblasRowMajor, CblasNoTrans, CblasTrans,
                M, N, K, 1.0f, A, K, B, K, 0.0f, C, N);
}
```

> **为什么 BLAS 更快？** BLAS 库针对特定 CPU 微架构做了极致优化（cache 友好分块、指令级并行、寄存器分配），比手写循环快 5-10×。

**「cache 友好分块」具体在分什么。** 朴素三重循环 `for i, for j, for k` 的问题是：内层 k 循环每走一步都要从 B 里取一个元素，而 B 的一整行（K 个元素）在 L1 里放不下时，每次都要回 L2/L3 取。BLAS 的做法是把三个矩阵各切一块，让「A 的一块 × B 的一块 → C 的一块」全部落在寄存器 + L1 里：

```
朴素循环：每个 C[i][j] 都要把 A 的第 i 行、B 的第 j 列各读一遍
  → 计算 2K FLOPs，访存 2K × 4 B → 算术强度 ≈ 0.25 FLOP/B（带宽 bound）

分块后：取一块 Mc×Kc 的 A、Kc×Nc 的 B，算 Mc×Nc 的 C
  → 计算 2·Mc·Nc·Kc FLOPs，访存 (Mc+Nc)·Kc × 4 B
  → 强度 = 2·Mc·Nc / (4·(Mc+Nc)) = Mc·Nc / (2·(Mc+Nc))
  → 取 Mc=Nc=64：强度 = 64×64 / (2×128) = 16 FLOP/B，翻过屋脊点（5）
```

这就是为什么 prefill 的 sgemm 是 compute-bound 而 decode 的 matvec 是 memory-bound（§6.1）：**分块把「读一次权重」的活从 1 次乘加提升到 Mc 次乘加**，而 matvec 的 M=1，无从分块。

> **边界**：分块收益依赖矩阵足够大。M=1（decode）时分块退化为原样；M=8（小 batch）时强度只到 8，仍在屋脊点左侧。所以「用 BLAS 加速 decode」是无效的——本仓库 decode 走自写 matvec，prefill 才走 `ds_matmul_t`（`ds_kernels.c` L841）。

> 🗣️ **说人话**：BLAS 快在「让每个权重字节被反复使用」：朴素三重循环每算一个 C[i][j] 都要重读 A 行、B 列（强度 ≈0.25，带宽 bound）；切成 64×64 的块后，同一块权重在寄存器 + L1 里服务 64 行输出，强度跳到 16 FLOP/B、翻过屋脊点 5（docs/05 §7.3），瓶颈从内存换成算力——sgemm 能吃满 AMX 就是这个道理。decode 的 matvec M=1 无块可切，强度钉在 1，所以 BLAS 帮不上 decode 的忙。
> *边界*：同一行 `ds_matmul_t` 在 macOS 走 Accelerate（可吃 AMX）、Linux 走 OpenBLAS——性能上限由链接的 BLAS 决定，跨平台跑分要分开记。

### 4.4 BF16 融合矩阵向量乘

单 token 解码时，核心操作是 `y = W_bf16^T @ x`（矩阵×向量）。ds-ocr 提供了高度优化的融合实现：

```c
/* ds_kernels_neon.c — NEON 优化的 BF16 matvec */
void ds_bf16_matvec_fused_neon(float *y, const float *x, const uint16_t *W_bf16,
                                 const float *bias, int in_dim, int out_dim) {
    /* 同时做 BF16→F32 转换 + 点积 + 加 bias
     * 利用 NEON 的 BF16 指令直接在 BF16 上做乘法
     * 避免了先转 F32 再乘的额外内存访问 */
}
```

> **上面注释里「直接在 BF16 上做乘法」是旧话，需要拆开看。** 本文件有**两条** matvec 路径（`ds_kernels_neon.c` 文件头注释）：
>
> | 路径 | 指令 | 每 4 个 BF16 MAC 需几条指令 | 硬件要求 |
> |---|---|---|---|
> | `vshll+vfma`（M1 默认） | `vshll_n_u16` 加宽 + `vfmaq_f32` 乘加 | 2 条 | 所有 ARMv8 |
> | `bfdot`（M2+） | `bfdot` 一条完成 8 个 BF16 MAC | 0.5 条 | ARMv8.6-A FEAT_BF16 |
>
> 只有 `bfdot` 路径是「真在 BF16 上乘」；`vshll` 路径是「先无损展开成 F32 再乘」——它省的是**内存带宽**（权重以 BF16 驻留），不是算术指令。两条路径的**数值结果不同**：`bfdot` 要求输入 x 先从 F32 压窄成 BF16（这一步有损），`vshll` 的 x 保持 F32 原样（与标量版逐位一致）。所以 `bfdot` 不是无条件升级，而是「用一点精度换 4× 指令密度」的取舍——注意累加器两边都是 F32，精度损失只发生在 x 的压窄上。

**「融合」到底融了什么。** 三个动作被塞进同一个循环：① BF16→F32 转换（寄存器内，不落内存）；② 点积累加；③ bias 初始化（`float s0 = bias ? bias[o] : 0.0f`，直接作为累加器初值，省一次单独的加法循环）。融合的收益不是「少算」，而是**少一趟内存往返**：分开做的话，转换结果得先写回一块 F32 缓冲、再读回来做点积，多出 2× 权重体积的流量（§3.5 的账）。

> 🗣️ **说人话**：「融合」省的不是计算，是来回跑腿：分离做法要把 BF16 先转 F32 写进一块缓冲（写 2N），再读回来做点积（读 2N）——权重体积的流量凭空翻两番（§3.5 的账）。融合版让转换发生在寄存器里，权重从内存到 FMA 全程只读一次；bias 顺手当累加器初值，连单独的加法循环都省了。NEON 两条路径（`vshll+vfma` 与 M2+ 的 `bfdot`）共用这个骨架，差别只在「展开」那一步花几条指令——所以融合的账本上只有「内存往返」一个科目。
> *边界*：融合算完的 [2×896] 输出还要按 896 切成 gate/up 两段——融合省的是读 x 的趟数，不是省掉 SwiGLU 前的数据摆布（docs/05 §10.4 的 split 路径连摆布也免了）。

### 4.5 编译期定候选、运行时定人选

§4.1 的宏分发是**编译期**的：`#ifdef __ARM_NEON` 决定编哪份代码。但有一类选择编译期做不了——同一份 Apple 二进制要同时跑 M1（无 `FEAT_BF16`）和 M2+（有）。

`ds_kernels_dispatch_init()`（`ds_kernels.c` L116）解决这个问题：两份内核都编进去，启动时探测 CPU 能力、切**函数指针**。

```c
/* 探测：macOS 读 sysctl，Linux 读 AT_HWCAP2 */
sysctlbyname("hw.optional.arm.FEAT_BF16", &has_bf16, &len, NULL, 0);

/* 切指针 */
if (has_bf16) {
    ds_bf16_matvec_fused_impl_ptr = ds_bf16_matvec_fused_neon_bf16;  /* bfdot */
} else {
    ds_bf16_matvec_fused_impl_ptr = ds_bf16_matvec_fused_neon;       /* vshll+vfma */
}
```

**为什么用函数指针而不是 `if` 分支。** 分支在热循环里每轮都要判一次，还会阻断内联；函数指针只在入口解引用一次，循环体是干净的直接调用。代价是**不能内联**（多一次间接跳转，纳秒级），相对于每步毫秒级的 matvec 可忽略。

**惰性初始化。** `ds_dispatch_ensure_init()` 在第一次 matvec 时自动探测，所以上层可以完全不调 `ds_kernels_dispatch_init()`——任何路径都不会用到未初始化的函数指针。

> **边界**：`ds_dispatch_initialized` 是普通 `int`、非原子。多线程同时首次调用会重复探测，但各线程探测结果恒相同（写同值），实践无害——代码注释明确记了这个取舍。

> 🗣️ **说人话**：编译期 `#ifdef` 是「出厂前装好哪种灶」，运行时探测是「进店看客人点什么」：同一份 Apple 二进制要同时跑 M1（无 FEAT_BF16）和 M2+（有），只能两份内核都编进去、启动时 `sysctlbyname` 探测能力、切函数指针。用指针不用 if 分支，因为分支在热循环里每轮都判、还阻断内联；指针只在入口解引用一次。`ds_dispatch_ensure_init` 的惰性初始化保证上层忘了调 init 也不会踩空指针——所以上层可以完全不知道这层分发的存在。
> *边界*：函数指针挡住了内联和跨内核的编译器优化——对毫秒级 matvec 可忽略，但给微秒级小内核也套这层分发，间接跳转就开始可见。

## 5. KV 缓存：自回归推理的加速器

### 5.1 为什么需要 KV 缓存？

自回归解码时，每个新 token 需要和**所有之前的 token** 做注意力计算。如果没有缓存：

```
Step 1: 计算 K₁,V₁ → Q₁·K₁ → 输出
Step 2: 计算 K₁,K₂,V₁,V₂ → Q₂·[K₁,K₂] → 输出  (重复计算 K₁,V₁!)
Step 3: 计算 K₁,K₂,K₃,V₁,V₂,V₃ → Q₃·[K₁,K₂,K₃] → 输出  (重复更严重!)
```

KV 缓存：**把已计算的 K、V 存起来，每步只算新 token 的 K、V**：

```
Step 1: 算 K₁,V₁ → 存入缓存 → Q₁·K₁ → 输出
Step 2: 算 K₂,V₂ → 存入缓存 → Q₂·[缓存K₁,K₂] → 输出  (不重复计算!)
Step 3: 算 K₃,V₃ → 存入缓存 → Q₃·[缓存K₁,K₂,K₃] → 输出
```

> **节省**：Step t 的注意力计算从 O(t²d) 降到 O(td)（只需计算新 Q 与缓存 KV 的点积）。

> **部署前必算的一条——KV 缓存显存公式**：
>
> ```
> KV 字节 = 2(K 和 V 各一份) × n_layers × max_seq × n_kv_heads × head_dim × 每元素字节
> ```
>
> 代入本仓库 V1 解码器（12 层、MHA 10 个 KV 头 × head_dim 128 = 1280、F32 缓存、以 max_seq=2048 为例）：
> 12 × 2048 × 1280 × 2 × 4 B ≈ **252 MB**——KV 缓存不是免费的加速器，它是"用内存换重复计算"。
> 三个降本旋钮：① V3 把缓存换成 BF16（`kv_bf16`，`ds_ocr.h`）→ **约 126 MB**；
> ② GQA 把 n_kv_heads 压到几分之一（V2 编码器 14 个 Q 头共享 2 个 KV 头，01 章 §6.5）→ 账面再缩 7 倍；
> ③ max_seq 是线性项——上下文每翻一倍这笔账跟着翻倍（与 13 章 §4 的平方注意力账一起看）。

> 🗣️ **说人话**：KV 缓存是用内存换掉那个 t² 里的平方。第 t 步注意力要拿新 Q 去撞前面 t−1 个 token 的 K。没有缓存，就得把 K₁、V₁ 重新算一遍、再算一遍……t 步累计重算是 O(t²)。缓存把「已经算过的 K/V」像追剧笔记一样记下来，第 t 步只算 1 个新 K/V、读 t−1 条旧笔记，累计降到 O(t)。
> 那条显存公式的每一项都是一份真账单：`2` 是 K 和 V 各存一份；`L` 是 12 层各记各的；`S` 是每多存一个词就多一行；`n_kv × d_head` 是一行多宽；末尾的字节是精度。代入 V4：每 token 就是 12 × 1280 × 2 × 4 B = 120 KiB——8192 个 token 堆成 960 MiB，和 3 GB 权重同一量级，这就是它稳坐「部署第一成本」的原因。
> *边界*：缓存只有在「每个 token 都几乎复用全部历史」时才划算；注意力本来就只看滑窗的话，缓存大半的位置纯属白占内存。

### 5.2 KV 缓存的数据结构

**ds-ocr 中的 KV 缓存**（`ds_ocr.h`）：

```c
/* KV 缓存: [layers × max_seq × kv_dim] */
float *kv_cache_k;  /* Key 缓存 */
float *kv_cache_v;  /* Value 缓存 */
int kv_cache_len;   /* 当前已缓存的位置数 */
int kv_cache_max;   /* 最大缓存容量 */
```

**内存布局**：`kv_cache_k[layer][position][kv_dim]`

```c
/* 分配 KV 缓存 */
int max_seq = 4096;
int kv_dim = n_kv_heads * head_dim;  /* 10 * 128 = 1280 */
size_t kv_size = (size_t)12 * max_seq * kv_dim * sizeof(float);
/* 12 层 × 4096 位置 × 1280 维 × 4 bytes = ~240MB */
ctx->kv_cache_k = (float *)calloc(1, kv_size);
ctx->kv_cache_v = (float *)calloc(1, kv_size);
```

### 5.3 解码时存取 KV 缓存

```c
/* 写入：新 token 的 K、V 存入缓存 */
int cache_offset = ctx->kv_cache_len;
float *cache_k = ctx->kv_cache_k + (size_t)layer_idx * kv_cache_max * kv_dim
                  + cache_offset * kv_dim;
float *cache_v = ctx->kv_cache_v + (size_t)layer_idx * kv_cache_max * kv_dim
                  + cache_offset * kv_dim;
memcpy(cache_k, k, kv_dim * sizeof(float));
memcpy(cache_v, v, kv_dim * sizeof(float));

/* 读取：因果注意力时，使用缓存中的全部 K、V */
float *full_k = ctx->kv_cache_k + (size_t)layer_idx * kv_cache_max * kv_dim;
float *full_v = ctx->kv_cache_v + (size_t)layer_idx * kv_cache_max * kv_dim;
ds_causal_attention(attn_out, q, full_k, full_v,
                    1, cache_offset + 1, ...);
```

**为什么读的时候要传 `cache_offset + 1` 而不是 `kv_cache_max`。** 因为缓存是**预分配、追加写**的：`kv_cache_max` 是容量（4096 或 8192），`kv_cache_len` 是实际已写入的位置数。注意力只能扫 `[0, cache_offset]` 这段有效区，扫到容量末尾会读到 `calloc` 的零——那些零会让 softmax 把概率分给「不存在的 token」。这是 KV 缓存实现里最容易错的一处：**容量 ≠ 长度**。

**在线 softmax：为什么不能先算完所有 score 再归一化。** 教科书 softmax 是两遍：先算全部 score 求 max，再算 exp 求和，再归一化。但 decode 时 `k_end` 可达几千，存下全部 score 要额外几千个 float，而且要多扫一遍 K。`ds_causal_attention_heads`（`ds_kernels.c` L2485）用**单遍在线算法**：

```c
for (int j = 0; j < k_end; j++) {
    float score = ds_dot_f32(q_row, k_row, head_dim) * scale;
    if (score > max_score) {                       /* 新最大值出现 */
        float correction = ds_fast_expf(max_score - score);  /* < 1 */
        sum_exp = sum_exp * correction + 1.0f;     /* 旧和整体缩水 */
        ds_vec_scale_add(o_row, v_row, correction, head_dim); /* 旧输出也缩水 */
        max_score = score;
    } else {
        float wt = ds_fast_expf(score - max_score); /* ≤ 1 */
        sum_exp += wt;
        ds_vec_axpy_inplace(o_row, v_row, wt, head_dim);
    }
}
```

**关键在 `correction`。** 之前所有项都是按旧 `max_score` 归一化的（即乘了 $e^{s_i - m_{old}}$）。新最大值 $m_{new} > m_{old}$ 出现后，旧项必须整体乘 $e^{m_{old} - m_{new}} < 1$ 才能对齐到新基准。所以 `sum_exp` 和输出累加器 `o_row` 都要乘这个 correction——**一个标量修正，同时作用于分母和分子**，比值不变。

**为什么必须先减 max。** 因为 $e^{s}$ 在 $s > 88$ 时溢出 F32（`ds_fast_expf` 的边界就是 ±88）。attention score 是 $q \cdot k / \sqrt{d}$，$q,k$ 各元素量级 ~1、$d=128$ 时点积可达几十，不减去 max 直接 exp 就爆了。减 max 后所有指数都 ≤ 0，$e^{\le 0} \in (0, 1]$，永不溢出。

> **边界**：在线 softmax 的**数值结果与两遍版不完全逐位相同**——它把「先算全部再归一化」换成了「边算边修正」，浮点运算顺序变了。差异在 ULP 量级，但意味着「换一种扫描顺序」就会改变末位（这也是 §8.4 强调「按 head 切分而非按行切分」的原因：每个 (head, 行) 的在线序列必须与串行版一致）。

> 🗣️ **说人话**：KV 缓存是「预租的大仓库 + 记账本」：`kv_cache_max` 是容量（4096/8192 位），`kv_cache_len` 是已入库件数——注意力只扫已入库那段，扫到空仓位读到的 `calloc` 零会让 softmax 给不存在的 token 分概率（容量 ≠ 长度）。在线 softmax 则是「边收卷边记最高分」：新冠军出现，旧和与旧输出整体乘 correction 缩到新基准、比值不变，一遍扫完不用先存几千个 score（docs/05 §6.3 的 R-SWA 正是复用它）。
> *边界*：correction 修的是「按旧基准算出来的历史」，所以旧输出要整体缩放再叠加新 V（`ds_vec_scale_add`）——这次修正是在线版比两遍版多付的算术。

### 5.4 GQA 对 KV 缓存的影响

| 架构 | Q头 | KV头 | KV缓存大小 |
|------|-----|------|-----------|
| MHA (ds-ocr解码器) | 10 | 10 | 10 × 128 = 1280/position |
| GQA (qwen-asr解码器) | 16 | 8 | 8 × 128 = 1024/position |
| GQA (ds-ocr V2编码器) | 14 | 2 | 2 × 64 = 128/position |

GQA 通过共享 KV 头，直接减少了 KV 缓存的内存占用。qwen-asr 使用 GQA 后，KV 缓存减少 50%。

**共享 KV 头为什么不会把模型变傻。** 因为 Q 头之间本来就有大量冗余：MHA 里 10 个 Q 头各自算一套 K/V，但训练后的 K/V 投影矩阵往往高度相关。GQA 的做法是**只保留少数几套 K/V，让多个 Q 头共用**——表达能力略降，但参数量和缓存都按比例缩。

**映射关系就一行代码**（`ds_causal_attention_heads`）：

```c
int heads_per_kv = n_heads / n_kv_heads;   /* 14 / 2 = 7 */
int kv_h = h / heads_per_kv;               /* Q 头 0..6 → KV 头 0，7..13 → KV 头 1 */
```

**为什么是「连续分组」而不是「交错分配」。** 连续分组让同一个 KV 头服务的 Q 头在内存上相邻，注意力循环里 `k_row`/`v_row` 的地址对 7 个 Q 头完全一样——**同一份 K/V 行被 7 个 Q 头复用，L1 命中率天然高**。交错分配会让 7 个 Q 头跳着访问不同 KV 头，缓存行利用率下降。

**账算一遍。** V2 编码器 14 Q 头 / 2 KV 头：每位置 KV = 2 × 64 = 128 个元素，而 MHA 要 14 × 64 = 896 个——**7× 缩减**。qwen-asr 解码器 16 Q / 8 KV 是 2× 缩减。注意 GQA 只减 **KV 缓存和 K/V 投影的参数量**，不减 Q 投影、不减注意力的 QK 点积次数（Q 头数没变）——所以它是「省内存」而不是「省算力」。

> **边界**：GQA 的缩减倍数 = `n_heads / n_kv_heads`，但**不能无限压**。压到 `n_kv_heads = 1` 就是 MQA，缓存最小但质量损失明显（所有 Q 头抢同一份 K/V）；实践中 4–8 个 KV 头是常见甜点。MLA（DeepSeek-V2，13 篇 §3）走的是另一条路：不共享头，而是把 K/V 压成低秩潜向量，缓存比 MQA 还小但保留全部表达能力。

> 🗣️ **说人话**：GQA 像「10 个学生共用 2 本参考书」：Q 头照旧 10 个（算力没省），K/V 只备少数几套（缓存与投影按 n_heads/n_kv_heads 倍缩）。映射只有 `kv_h = h / heads_per_kv` 一行；选「连续分组」是让同书的学生坐相邻——同一行 K/V 连用多次、L1 热。本仓库解码器是 MHA（10 KV 头，`ds_ocr.h` L102），GQA 在 V2 编码器（14→2）和 qwen-asr（16→8）——所以先查 `n_kv_heads` 再谈省了多少。
> *边界*：同一份 `ds_causal_attention_heads` 按配置出 MHA/GQA 两种行为——头数相等还是共享，是配置出来的不是写死的。

### 5.5 KV 缓存的字节账：为什么它是部署的第一成本

把上面的表换算成真实字节（BF16 每元素 2 B，F32 每元素 4 B）：

$$ \text{KV bytes} = 2 \times L \times S \times n_{kv} \times d_{head} \times \text{bytes\_per\_elem} $$

本工程 V1 解码器（`ds_ocr.h` L97-102：`DS_DEC_LAYERS=12`、`DS_DEC_KV_HEADS=10`、
`DS_DEC_HEAD_DIM=128`，标准 MHA 非 GQA），按版本分列（`alloc_decoder_buffers` 的
`kv_bf16 = (model_version == 3) ? 1 : 0` 是唯一权威）：

- **V1/V2（F32，max_seq=4096）**：每 token $2 \times 12 \times 10 \times 128 \times 4 = 122{,}880$ B = **120 KiB/token**；
  4096 token 上下文：$122{,}880 \times 4096 = 503{,}316{,}480$ B ≈ **480 MiB**
- **V3（BF16，max_seq=8192）**：每 token 减半到 **60 KiB/token**；8192 token 同样是 **480 MiB**
  ——BF16 省下的一半正好换来 2× 的位置数（`ds_ocr.h` L444-445 注释："BF16 模式省一半驻留与一半解码注意力读流量"）
- **V4（F32，max_seq=8192）**：精度敏感保持 F32（有界实验 V3 全绿、V4 打红），
  8192 token 翻倍到 **960 MiB**

**这就是为什么"长上下文"是显存问题而非算力问题**：权重是常数（3 GB），
KV 随上下文线性增长。三条主流对策：

| 对策 | 做法 | 本工程对应 |
|---|---|---|
| 减 $n_{kv}$ | MQA/GQA/MLA 共享 KV 头 | GQA（qwen-asr）、MLA（DeepSeek-V2 论文，13 篇 §3） |
| 减 $S$ | 滑窗/稀疏注意力，只保留部分历史 | **V3 R-SWA**（05 篇 §6）、**V4 DASH 块稀疏**（14 篇） |
| 减 bytes | KV 量化（BF16→INT8/FP8） | 未实现；BF16 KV 已是 V3 的优化点（05 篇 §10） |

> **一个反直觉的结论**：R-SWA 与 DASH 这类"稀疏注意力"的首要收益不是
> 省算力，而是**把 KV 从 O(S) 压成 O(W) 或 O(块数)**——decode 每步要读
> 全部 KV，读的字节数就是延迟。docs/09 §1 的带宽账里，KV 读取与权重读取
> 是同一量级的两个大头。

> 🗣️ **说人话**：KV 的账单按 token 计价：V1/V2 每 token 120 KiB（2×12×1280×4 B），4096 token 堆成 480 MiB——与 3 GB 权重同量级，且随上下文**线性**增长。三个旋钮各管一项：V3 换 BF16 存储（`kv_bf16`，仅 V3 开）字节减半，正好换来 8192 个位置；GQA 砍 n_kv；R-SWA/DASH 砍 S。权重是常数、KV 是变量——所以「长上下文是显存问题而非算力问题」的数学形式，就在这行公式里。
> *边界*：省下来的字节未必变成「更小的内存」，也可能变成「更长的上下文」——V3 拿 BF16 省的一半换了 2× 位置数（§5.7）。

### 5.6 qwen-asr 的动态 KV 缓存扩展

qwen-asr 支持动态扩展 KV 缓存：

```c
static int kv_cache_grow(qwen_ctx_t *ctx, int required) {
    if (required <= ctx->kv_cache_max) return 0;
    int new_max = ctx->kv_cache_max;
    while (new_max < required) new_max *= 2;  /* 倍增策略 */
    
    /* 重新分配 + 拷贝旧数据 */
    float *new_k = (float *)calloc(1, total_size);
    float *new_v = (float *)calloc(1, total_size);
    for (int l = 0; l < layers; l++) {
        memcpy(new_k + l * new_stride, old_k + l * old_stride, copy_size);
        memcpy(new_v + l * new_stride, old_v + l * old_stride, copy_size);
    }
    /* ... */
}
```

> 🗣️ **说人话**：倍增扩展是「仓库不够就租两倍大的」：required 超容量时 new_max 一路翻倍到够用，再逐层 memcpy 搬家。翻倍让扩容摊销成 O(1)/token——最坏一次搬家贵，平摊到几千次生成里可忽略。ds-ocr 没采用：OCR 的 prefill 长度可预知，按 max_seq 一次 `calloc` 更简单，所以省掉整个搬家具的环节。
> *边界*：搬家瞬间新旧两份同时驻留，内存峰值翻倍——长上下文下这一下就是几百 MB。

### 5.7 KV 缓存分版本数学账：prefill 写入 vs decode 读写

§5.5 给出了公式和一个粗略例子，这里按**本仓库真实配置**（`ds_ocr.c` → `alloc_decoder_buffers`）把四个版本一次算清。先确定两个仓库常量：

- `kv_dim = DS_DEC_KV_HEADS × DS_DEC_HEAD_DIM = 10 × 128 = 1280`，行对齐步长 `kv_row_stride = (1280 + 15) & ~15 = 1280`（1280 恰好是 16 的倍数，无填充）
- 每位置每层要存 K、V 两行：`2 × 1280 = 2560` 个元素；12 层合计每位置 30,720 个元素

代入 `KV bytes = 2 × layers × max_seq × kv_heads × head_dim × bytes/elem`：

| 版本 | max_seq | 存储精度 | 公式代入 | K+V 总量 | 每生成 1 token 增量 |
|------|---------|---------|---------|---------|-------------------|
| **V1/V2** | 4096 | F32（4 B） | 2×12×4096×1280×4 | 503,316,480 B = **480 MiB** | 120 KiB |
| **V3**（R-SWA） | 8192 | **BF16**（2 B） | 2×12×8192×1280×2 | 503,316,480 B = **480 MiB** | 60 KiB |
| **V4**（DASH） | 8192 | F32（4 B） | 2×12×8192×1280×4 | 1,006,632,960 B = **960 MiB** | 120 KiB |

三个值得注意的点：

1. **V3 和 V1 的缓存字节数相同，但 V3 装了 2× 的位置**——这就是 BF16 KV 存储（`ctx->kv_bf16`，写入时经 `ds_kv_store_row` 做 F32→BF16 截断）的直接收益：长文档场景下同样的 480 MiB 从「4096 个位置」扩展到「8192 个位置」。注意精度开关按版本收窄：`alloc_decoder_buffers` 中 `kv_bf16 = (model_version == 3) ? 1 : 0`——有界实验（docs/05 §10.5）显示 V3 全绿、V4 对 KV 精度敏感打红，所以 V4 仍是 F32（`ds_ocr.h` L444-445 头文件注释里的「V3/V4」是收窄前的旧话，以 `alloc_decoder_buffers` 的代码为准）。
2. **R-SWA 改变的是「读多少」，不是「占多少」**：V3 的缓存按 append-only 预分配 8192 槽，但 decode 每步注意力只读「参考段（prefill_len≈908）+ 滑窗 128」≈1036 行，而不是全部历史。
3. **prefill 与 decode 的读写模式完全不同**：

```
prefill（一次，批量写）：
  V1 例：280 个 prefix token → 每层写 280 行 × 2560 元素 × 4 B = 2.87 MB
  12 层合计写 34.4 MB（一次 sgemm 顺带完成，无回读）

decode（每步，读全部历史 + 写 1 行）：
  V1 例，上下文 300：每步每层读 300 行 × 2560 × 4 B = 3.07 MB
  12 层合计读 36.9 MB/步（注意力主循环里逐行流式读）
  写只有 12 × 2560 × 4 B = 120 KiB/步（新 token 的 K/V）
```

> **手算算例**：V3 一页 6-crop 文档 prefill_len ≈ 908，生成 1000 个 token。若没有 R-SWA，第 1000 步注意力要读 1908 行 BF16 = 1908 × 2560 × 2 B × 12 层 ≈ 117 MB；有 R-SWA 恒定读 (908+128) 行 ≈ 61 MB。生成到第 7000 步时差距拉到 3.7×——这就是 §5.5 说的「读的字节数就是延迟」。

> 🗣️ **说人话**：三个版本一张表看清「同一份 480 MiB 的三种花法」：V1/V2 花 在 4096 个 F32 位置，V3 花在 8192 个 BF16 位置（精度换长度），V4 花 在 8192 个 F32 位置（960 MiB，DASH 对 KV 精度敏感）。再记一个不对称：**prefill 只写不读**（280 行 × 12 层一次 34.4 MB，sgemm 顺带完成），**decode 每步读全部历史、只写 1 行**（120 KiB）——读写不对称，所以优化该往「读」上使劲（§5.5）。
> *边界*：字节账按 `kv_row_stride` 算而不是裸 kv_dim——本例 1280 恰好 16 对齐无填充，换 head 配置若产生填充，账要重算（docs/05 §7.5 的 cache line 对齐）。

## 6. Prefill vs Decode：两种推理模式

### 6.1 两种模式的区别

| | Prefill | Decode |
|--|---------|--------|
| **输入** | 多个 token（整个 prompt） | 单个 token |
| **计算方式** | 批量矩阵乘法 (sgemm) | 矩阵×向量 (matvec) |
| **注意力** | 因果掩码 + 批量 | 因果掩码 + KV缓存 |
| **KV缓存** | 全部写入 | 只写1个位置 |
| **瓶颈** | 计算（sgemm 快） | 内存带宽（matvec 慢） |
| **速度** | 快（并行） | 慢（串行） |

> 🗣️ **说人话**：Prefill 和 Decode 就好比一叠卷子 vs 一次一份。Prefill 像老师一次批一整叠卷子：几十上百个 token 打包成一个大矩阵，sgemm 把「读权重」这笔开销摊薄在几百行输出上，算术单元吃满，是计算瓶颈、但快。Decode 像「一次只批一份，还得等它写出来才有下一份」：单个 token 的 matvec 强度约等于 1——每读一个权重只做一次乘加，几 GB 权重读个遍却只喂出一个数。于是瓶颈从算力换成内存带宽：读权重花的时间，基本就是这一步的时间。
> *边界*：两种形态的分界在 batch。一次并行跑很多序列时，decode 会「胖」成小 GEMM、往 prefill 那侧靠，带宽瓶颈被摊薄——单请求引擎享受不到这层红利。

**两种模式的耗时公式。** 把 Roofline 写成两行，差异一目了然：

$$T_{\text{prefill}} = \max\left(\frac{2 \cdot S \cdot P_{\text{act}}}{P_{\text{peak}}},\ \frac{\text{bytes}(W)}{B}\right) \qquad T_{\text{decode}} = \frac{\text{bytes}(W)}{B}$$

- **Prefill**：FLOPs 是 $2SP_{\text{act}}$（S 个 token × 每 token 激活参数 × 2），随 S 线性增长；而读权重只有一次。S 足够大时第一项主导 → **compute-bound**。
- **Decode**：FLOPs 是 $2P_{\text{act}}$（只 1 个 token），但读权重还是那么多。第二项恒主导 → **memory-bound**，且**与 S 无关**。

（$P_{\text{act}}$ 是**每 token 实际激活**的参数，不是总参数——MoE 下两者差 8 倍，见 §9.3。）

**代入本仓库数字**（每步读 1.15 GB 权重、算术强度 I≈1 → 每 token ≈ 1.15 GFLOP；B = 200 GB/s、$P_{\text{peak}}$ ≈ 1 TFLOPS，均取自 docs/05 §7.3–7.4）：

| 模式 | FLOPs | 算力耗时 | 带宽耗时 | 实际瓶颈 |
|---|---|---|---|---|
| Prefill（S=280） | 280 × 1.15 = 322 GFLOP | 322 ms | 6.2 GB / 200 = 31 ms | **算力**（10×） |
| Decode（S=1） | 1.15 GFLOP | 1.15 ms | 1.15 GB / 200 = 5.7 ms | **带宽**（5×） |

**这张表就是「为什么 decode 慢」的全部答案。** 同一个模型，prefill 每个 token 摊到 1.15 ms 算力、31/280 = 0.11 ms 带宽；decode 每个 token 要 5.7 ms 带宽、只用 1.15 ms 算力。**decode 的算力单元有 80% 时间在等内存**——这就是 docs/05 §7.2 说的「20% 效率」。

**为什么 prefill 的绝对耗时和实测对不上。** 因为 $P_{\text{peak}}$ = 1 TFLOPS 是保守量级，而 prefill 走 Accelerate 的 sgemm（可用 AMX 协处理器，实际吞吐远高于此）。上表只用来说明「哪一项主导」，不是绝对耗时预测。

**为什么 decode 的耗时与上下文长度无关（近似）。** 因为权重读取是常数项（1.15 GB），KV 读取随上下文增长（§5.5）。上下文 300 时 KV 只占 36.9 MB（3%），上下文 8000 时 KV 涨到 984 MB（46%）——**长上下文下 decode 会从「权重 bound」变成「KV bound」**，这是 §5.5 说「长上下文是显存问题」的另一面。

### 6.2 Prefill 的实现

**ds-ocr 中**（`ds_moe_decoder.c` → `ds_decoder_prefill`）：

```c
void ds_decoder_prefill(ds_ctx_t *ctx, const float *input_embeds, int seq_len) {
    /* 分配批量缓冲区 */
    float *x = (float *)malloc(seq_len * hidden * sizeof(float));
    float *Q = (float *)malloc(seq_len * q_dim * sizeof(float));
    /* ... */
    
    for (int l = 0; l < cfg->dec_layers; l++) {
        /* 批量 RMSNorm */
        ds_rms_norm(x_norm, x, layer->input_norm, seq_len, hidden, eps);
        
        /* 批量 QKV 投影（sgemm） */
        ds_linear_nobias_bf16(Q, x_norm, layer->wq_weight_bf16, seq_len, hidden, q_dim);
        
        /* 批量注意力 */
        ds_causal_attention(attn_out, Q, full_k, full_v, seq_len, total_seq, ...);
        
        /* MoE：批量 gate + 逐 token 专家 */
        ds_linear_nobias_bf16(gate_scores, x_norm, layer->gate_weight_bf16,
                               seq_len, hidden, n_experts);  /* 批量路由 */
        for (int s = 0; s < seq_len; s++) {
            /* 逐 token 做专家前向（和 decode 相同） */
        }
    }
}
```

### 6.3 Decode 的实现

**ds-ocr 中**（`ds_moe_decoder.c` → `ds_decoder_forward`）：

```c
int ds_decoder_forward(ds_ctx_t *ctx, const float *input_embed) {
    /* 使用预分配的单 token 缓冲区 */
    float *x = ctx->dec_x;       /* [1280] */
    float *q = ctx->dec_q;       /* [1280] */
    float *k = ctx->dec_k;       /* [1280] */
    
    for (int l = 0; l < cfg->dec_layers; l++) {
        /* 单 token 前向 */
        decoder_layer_forward(ctx, x, out, l, ctx->kv_cache_len);
        /* 指针交换，避免 memcpy */
        float *tmp = x; x = out; out = tmp;
    }
    
    /* 最终归一化 + argmax */
    ds_rms_norm(x, x, dec->norm, 1, hidden, eps);
    return ds_argmax_matvec_bf16(x, dec->lm_head_bf16, hidden, vocab);
}
```

> 🗣️ **说人话**：decode 一步 = 12 次同一个 `decoder_layer_forward` + 末尾一次 argmax。全部中间量（`dec_x`、`dec_q`、`dec_k`…）都是 `alloc_decoder_buffers` 预分配的固定槽位，每步零 malloc；层间不拷数据，靠 x/out 指针交换（§6.4）。所以每步的开销几乎只剩「读权重」本身——docs/05 §7 整章算的就是这笔账。
> *边界*：函数有两条出口：贪心走流式 argmax，`full_logits_path` 标签走物化全量 logits——温度采样必须走后者（§7.2）。

### 6.4 指针交换优化

注意 `decoder_layer_forward` 中的指针交换：

```c
/* 不做 memcpy，而是交换指针 */
float *tmp = x; x = out; out = tmp;
```

这避免了每次层输出时 1280×4 = 5KB 的内存拷贝。12 层下来节省 60KB 拷贝/步，生成 1000 个 token 就是 60MB 的节省。

**为什么指针交换是安全的。** 前提是 `x` 和 `out` 是**两块独立的预分配缓冲**，且每层只读 `x`、只写 `out`。交换后下一层的「输入」就是上一层的「输出」，两块缓冲轮流当输入/输出——这就是经典的**双缓冲（double buffering）**。

**为什么不能只用一个缓冲。** 如果 `x` 和 `out` 是同一块内存，`decoder_layer_forward` 写到一半就会覆盖还没读完的输入（比如 RMSNorm 先读全部 `x` 算方差，再逐元素归一化——如果输出写回同一块，方差算完但归一化时读到的已经是新值）。双缓冲把「读」和「写」物理隔开，代价只是多一块 5 KB。

**为什么不用 memcpy 而用交换。** memcpy 是「把 out 的内容搬到 x」，交换是「把两个名字换一下」。前者要搬 5 KB，后者只改两个指针值（零字节）。12 层 × 1000 token = 12000 次拷贝，每次 5 KB，合计 60 MB——这些字节全部是纯开销，不产生任何计算结果。

> **边界**：指针交换要求两块缓冲**大小相同、生命周期覆盖整个 decode**。如果某层输出维度不同（比如 MoE 的专家输出是 `[top_k, hidden]` 而不是 `[hidden]`），就不能直接交换，得先 combine 回 `[hidden]`。本仓库的 `ds_expert_combine` 就是干这个的。

> 🗣️ **说人话**：交换指针 = 把两个名字换一下，一个字节不搬；memcpy = 把 5 KB 搬一遍。12 层 × 226 步省下几十 MB 纯开销字节。前提是双缓冲：`x` 只读、`out` 只写、物理隔离——同一块内存的话，RMSNorm 先读全量算方差、再逐元素归一化，写到一半就把没读完的输入覆盖了。这是系统编程最古老的免费午餐，音频 ring buffer 用的是同一个把戏，所以判断标准只有一条：这层的写者是不是也是读者。
> *边界*：双缓冲只在「层间形状一致」时成立；MoE 专家输出是 [top_k, hidden]，得先 `ds_expert_combine` 回 [hidden] 才能进下一轮交换。

## 7. 采样与解码：从 logits 到文字

### 7.1 贪心解码（Greedy）

最简单的解码方式：每次选概率最大的 token。

```c
/* ds_argmax_matvec_bf16: 流式找到最大 logit 的 token ID */
int token = ds_argmax_matvec_bf16(x, dec->lm_head_bf16, hidden, vocab);
```

> 🗣️ **说人话**：贪心 = 每步只留冠军，不看第二名差多少。对 OCR 这恰好是对的：任务是「抄写」图里的字，多样性没有价值，随机只会引入错字。配套快路径是流式 argmax（§3.4/§3.6）：每步 331 MB 的 BF16 读一遍、logits 不落内存，~8 ms/步——所以贪心不只是「简单」，在 OCR 里它同时是最快且最对的。
> *边界*：贪心早期选错没有回头路；OCR 不靠回溯，靠重复惩罚（§7.3）和 n-gram 阻断（§7.4）兜住复读。

### 7.2 温度采样（Temperature Sampling）

当 `temperature > 0` 时，引入随机性：

```c
/* 1. 对 logits 应用温度 */
for (int i = 0; i < vocab; i++)
    logits[i] = expf((logits[i] - max_logit) / temperature);

/* 2. Softmax 归一化 */
double sum_exp = 0.0;
for (int i = 0; i < vocab; i++) sum_exp += logits[i];
for (int i = 0; i < vocab; i++) logits[i] /= sum_exp;

/* 3. 加权随机采样 */
float r = (float)rand() / RAND_MAX;
float cum = 0.0f;
for (int i = 0; i < vocab; i++) {
    cum += logits[i];
    if (cum >= r) { token = i; break; }
}
```

> **温度越高**，分布越平坦，生成越随机；**温度越低**，越接近贪心。

**温度到底在改什么。** 它改的不是「概率」，是**logit 的尺度**。softmax 是 $p_i = e^{z_i}/\sum e^{z_j}$，把 $z_i$ 换成 $z_i/T$ 后：

$$p_i = \frac{e^{z_i/T}}{\sum_j e^{z_j/T}}$$

$T < 1$ 时 logit 差距被**放大**（除以小于 1 的数），分布变尖；$T > 1$ 时差距被**压缩**，分布变平；$T \to 0$ 时退化为 argmax（最大值独占全部概率）；$T \to \infty$ 时退化为均匀分布。

**手算一个 4 词表的例子**（logits = [2, 1, −1, 0]）：

| T | p₀ | p₁ | p₂ | p₃ | 说明 |
|---|---|---|---|---|---|
| 0.5 | 0.865 | 0.117 | 0.002 | 0.016 | 尖：冠军拿 86.5% |
| 1.0 | 0.644 | 0.237 | 0.032 | 0.087 | 原始分布 |
| 2.0 | 0.455 | 0.276 | 0.102 | 0.167 | 平：冠军只拿 45.5% |

注意 logit 差距（2 vs −1，差 3）在 T=0.5 时被放大成等效差 6，在 T=2 时被压缩成等效差 1.5。**温度不改变 logit 的排序**（除以正数保序），所以 argmax 永远不变——它只改变「次优 token 有多少机会」。

**为什么代码里先减 `max_logit`。** 同 §5.3 的在线 softmax：$e^{z/T}$ 在 $z/T > 88$ 时溢出。减 max 后最大项恒为 $e^0 = 1$，其余 ≤ 1，永不溢出。注意**减 max 必须在除以 T 之前或之后都行**（因为 $\max_i(z_i/T) = (\max_i z_i)/T$，T>0 时保序），但代码里写成 `(logits[i] - max_logit) / temperature` 更直观。

**轮盘赌采样为什么用累积和。** 把 $[0,1]$ 按概率切成若干段，抽一个均匀随机数 $r$，落在哪段就选哪个 token。累积和 `cum` 就是段的右端点。这个算法要求**概率已归一化**（$\sum p_i = 1$），否则 `cum` 永远到不了 1，尾部 token 永远抽不到。

> **边界**：温度采样必须**物化全部 logits**（要完整分布才能轮盘赌），所以它走不了 §3.4 的流式 argmax 快路径——这是 `ds_decoder_forward` 里 `full_logits_path` 标签存在的原因。另外 `rand()` 的周期和质量对采样有影响，生产环境应该用更好的 PRNG。

### 7.3 重复惩罚（Repetition Penalty）

防止模型重复输出相同内容：

```c
float rp = ctx->repeat_penalty;  /* 1.0 = 无惩罚, 1.1~1.5 常用 */
for (int i = 0; i < token_history_len; i++) {
    int tid = ctx->token_history[i];
    if (logits[tid] > 0) logits[tid] /= rp;   /* 正 logit 缩小 */
    else logits[tid] *= rp;                     /* 负 logit 放大（更负） */
}
```

**为什么正负要分开处理。** 因为惩罚的目标是「降低这个 token 的相对概率」，而 logit 的**符号决定了除法/乘法的方向**：

| logit | 操作 | 效果 | 例（rp=1.3） |
|---|---|---|---|
| +2.0 | 除以 1.3 | 变小 → 概率降 | 2.0 → 1.54 |
| −2.0 | 乘 1.3 | 更负 → 概率降 | −2.0 → −2.6 |

如果统一用除法，负 logit 会**变大**（−2.0 / 1.3 = −1.54，比原来更接近 0），概率反而**升高**——惩罚变成了奖励。这是重复惩罚实现里最常见的 bug。

**为什么用除法/乘法而不是减法。** 因为 softmax 对 logit 的响应是**指数**的：减去一个常数 $c$ 会让概率乘 $e^{-c}$，是**乘性**惩罚；而除以 $rp$ 是**改变尺度**，对高 logit 的绝对降幅大、对低 logit 降幅小——更符合「已经很高的词才需要压」的直觉。

**为什么只惩罚历史里出现过的 token。** 因为词表 129280 个，历史只有几百个。遍历历史（O(历史长度)）而不是遍历词表（O(129280)），这就是 §3.6 说的 Selective Repetition Penalty——但前提是**你得先知道哪些 ID 需要惩罚**，所以流式 argmax 路径下要先用 `ds_bf16_dot_row` 把这几个 ID 的 logit 补算出来。

> **边界**：`rp` 过大（>1.5）会让模型「不敢说话」，输出变得生硬、语法破碎；`rp` 对**标点、功能词**同样生效，所以有些实现会维护一个「不惩罚白名单」。另外这个惩罚是**无状态**的——它不区分「刚说过」和「很久以前说过」，长文本里早期出现的词会被永久压制。

### 7.4 N-gram 阻断

防止重复输出相同的 n-gram（连续 n 个 token 的组合）：

```c
int ngram_n = ctx->no_repeat_ngram_size;  /* 默认 35 */
if (ngram_n > 0 && token_history_len >= ngram_n - 1) {
    int prefix_len = ngram_n - 1;
    /* 检查历史中是否有匹配的 n-gram 前缀 */
    for (int i = 0; i <= hist_len - prefix_len - 1; i++) {
        int match = 1;
        for (int j = 0; j < prefix_len; j++) {
            if (hist[i+j] != hist[hist_len-prefix_len+j]) { match = 0; break; }
        }
        if (match) {
            /* 禁止完成该 n-gram 的 token */
            logits[hist[i + prefix_len]] = -1e30f;
        }
    }
}
```

> 🗣️ **说人话**：采样三件套 + 流式 argmax，就是「一个旋钮、一笔税、一张封条、一次边跑边记」。温度是调节分布「形状」的旋钮：每个 logit 先除以 T 再 softmax，T 越小分布越尖（越像贪心），T 越大越平（越随机）。重复惩罚是给「说过的词」加税——正 logit 除以 1.3、负 logit 乘 1.3，让它下次更难开口，专治复读。n-gram 阻断是贴封条：一旦当前结尾和历史某处拼出同一条 N−1 长的前缀，就禁止那个会凑成完整 N-gram 的 token，等于不许说完整句式的口头禅。
> 流式 argmax 则是「边跑边记最高分」：不把 129280 个 logit 排队、排完再挑冠军，而是逐行点积、只留一个最大值和它的 ID，省掉 512 KB 的 logits 数组。要做重复惩罚时，再对历史里那几百个 ID 补算一次点积——把 O(词表) 的「全量先算后查」变成 O(历史长度) 的「按需补算」。
> *边界*：只有贪心能这么省；温度采样要完整分布才能轮盘赌，必须老老实实把全部 logits 物化出来。

**N-gram 阻断的复杂度账。** 上面是双层循环：外层扫历史每个起点（`hist_len - prefix_len` 个），内层比 `prefix_len` 个 token。最坏 $O(\text{hist} \times n)$。代入 `n=35`、历史 1000 token：$(1000-34) \times 34 \approx 3.3$ 万次比较——微秒级，可以接受。

**为什么 `n=35` 这么大。** 因为 n-gram 阻断的目标不是「防单词重复」（那是重复惩罚的活），而是防**整段句式复读**——模型卡在循环里时会一字不差地重复几十个 token。`n` 太小（如 3）会把正常语言里常见的三元组也封掉，输出变得不自然；`n=35` 意味着「只有连续 34 个 token 完全一致才封」，几乎不会误伤。

**为什么用 `-1e30f` 而不是 `-inf`。** 因为后面要算 `expf(logit - max)`，`-inf - max` 是 `-inf`，`expf(-inf) = 0`，数学上没问题；但 `-inf` 参与减法/比较时容易产生 NaN（`-inf - (-inf)`）。用 `-1e30f` 这个「足够小的有限数」既保证 `expf` 下溢到 0，又不会污染后续算术。这是数值实现里的常见防御手法。

> **边界**：n-gram 阻断是**硬约束**——被封的 token 概率直接归零，没有商量余地。如果所有候选都被封（极端情况），argmax 会返回一个被禁的 ID 或 0，所以 `ds_argmax_matvec_bf16_excluding` 才需要 §3.4 提到的「精确重扫」逻辑：冠军被禁时按禁用行切段重扫，拿到真正的次优 token。

### 7.5 Token 解码：从 ID 到文字

BPE tokenizer 把 token ID 解码为 UTF-8 文本：

```c
/* ds_tokenizer.c */
const char *ds_tokenizer_decode(const ds_tokenizer_t *tok, int token_id) {
    /* 查表：id_to_text[token_id] */
    return tok->id_to_text[token_id];
}
```

> 🗣️ **说人话**：ID → 文字就是查一次 129280 项的表，但查出来的是 BPE 的 byte 级碎片——直接拼接可能打出乱码。所以工程上要按 UTF-8 边界缓冲：不完整的多字节序列先攒着，等后续 token 凑齐再吐给上层，流式 UI 尤其要处理这点。
> *边界*：特殊 token（起始/分隔/格式符）要在此层过滤，别当正文输出；07 章（分词与词表篇）有 BPE 词表的完整展开。

## 8. 线程池与并行计算

### 8.1 为什么需要线程池？

解码器每步要做大量矩阵×向量运算，每个操作只占 1 个 CPU 核心。多核 CPU 可以**并行处理多个操作**。

**但并行不是免费的，先算 Amdahl 上限。** 设可并行部分占比 $p$、线程数 $n$，加速比上限：

$$S(n) = \frac{1}{(1-p) + p/n}$$

（注意这里的 $p$ 是「**可并行的工作占比**」，与 docs/05 §1.3 里那个「**你优化的那部分占比**」是同一个公式、不同的代入对象——05 用它判断「该优化哪一块」，这里用它判断「加线程能拿到多少」。）

代入本仓库 decode 的实际情况：matvec 占 ~95%（$p=0.95$，估算），8 核：

$$S(8) = \frac{1}{0.05 + 0.95/8} = \frac{1}{0.05 + 0.11875} = 5.93\times$$

**8 核只能拿到 5.9×，不是 8×。** 那 5% 的串行部分（层间同步、argmax 收尾、采样、tokenizer）把上限钉死了。而且这还是理想值——实际还要扣掉 barrier 开销、内存带宽争抢（§8.4 的粒度门槛）。

**为什么线程数不是越多越好。** 上式对 $n$ 求极限：$S(\infty) = 1/(1-p) = 20\times$。但实际曲线在 $n$ 超过物理核数后**下降**——线程切换、缓存失效、内存带宽饱和。本仓库把上限硬编码为 `DS_MAX_THREADS = 16`（`ds_set_threads` 截断），就是防这个。

> **边界**：Amdahl 假设「串行部分与并行部分可重叠」不成立。真实情况更接近 Gustafson 定律（问题规模随核数增长），但 decode 的串行部分（每步必须等上一步出 token）是**真串行**，Amdahl 在这里是合适的模型。另外 $p=0.95$ 是估算值，实际占比随模型和上下文长度变化。

> 🗣️ **说人话**：Amdahl 的冷水很具体：matvec 占 ~95%（p=0.95），8 核上限 5.93×，核数翻到 16（`DS_MAX_THREADS`）也只 ~7.5×——串行的那 5%（层间同步、argmax 收尾、采样）是天花板上的钉子。所以「加核」是最贵的优化：要买硅片还买不满。便宜的路是改 p 本身——把串行段并行化、把 barrier 压掉（§8.5 的 19→1），每挤出一个百分点的并行占比，比多加一颗核值钱。
> *边界*：p=0.95 是 decode 的估算；prefill 的 p 接近 1（大 GEMM 天然可切）——同一条公式在两种形态下给出的行动建议完全相反。

### 8.2 ds-ocr 的线程池

```c
/* ds_kernels.c */
void ds_set_threads(int n);  /* 设置线程数（默认: CPU 核数） */
```

**典型使用场景**：

1. **批量 linear**：将 `seq_len × out_dim` 的矩阵乘法按行分给多个线程
2. **QKV 融合**：3 个矩阵乘法（Q、K、V）并行执行
3. **多 crop 并行**：ds-ocr 多裁剪编码时，每个 crop 独立编码

**ds-ocr 多 crop 并行**（`ds_ocr.c`）：

```c
/* 启动并行编码 */
for (int i = 0; i < n_crops; i++) {
    tasks[i].ctx = ctx;
    tasks[i].crop = crops[i];
    pthread_create(&threads[i], NULL, crop_worker, &tasks[i]);
}

/* 等待所有 crop 完成 */
for (int i = 0; i < n_crops; i++) {
    pthread_join(threads[i], NULL);
}
```

### 8.3 qwen-asr 的分块编码

qwen-asr 的音频编码器将长音频分块处理：

```c
int n_chunks = (mel_frames + chunk_size - 1) / chunk_size;
/* 每个 chunk 独立通过 Conv2D stem + Transformer */
for (int c = 0; c < n_chunks; c++) {
    /* 处理 chunk c... */
}
```

**分块与多 crop 并行的区别。** 两者都是「把大输入切成小块」，但目的不同：

| | 多 crop 并行（ds-ocr） | 分块编码（qwen-asr） |
|---|---|---|
| **切分依据** | 图像空间位置（不同裁剪区域） | 时间轴（音频帧序列） |
| **块间关系** | 完全独立，可任意并行 | 有重叠/上下文依赖，需拼接 |
| **并行方式** | 每 crop 一个 pthread | 通常串行，或按块并行后合并 |
| **合并方式** | 结果拼接成 token 序列 | 重叠区去重/加权 |

**为什么音频要分块。** 因为 Transformer 的注意力是 $O(L^2)$：一段 30 秒音频的 mel 帧数可达几千，全序列注意力的显存和算力都撑不住。分块把 $O(L^2)$ 降成 $O((L/c)^2 \cdot c) = O(L^2/c)$——代价是块边界处的注意力被截断，所以块之间要留**重叠区**（overlap），靠重叠部分的上下文补偿。

> **边界**：分块会损失跨块的长程依赖。如果音频里有一句话跨越块边界，分块编码可能把它切断。所以分块大小不能太小，且重叠区要足够覆盖典型语句长度。

> 🗣️ **说人话**：分块是把 O(L²) 的注意力账本撕成 c 页：每页 (L/c)²、合计 L²/c——30 秒音频几千帧的平方账直接除以块数。代价在缝合处：块边界的注意力被切断，要靠重叠区补上下文，像两张接片必须留一段重叠才对得上景。这与 ds-ocr 的多 crop 并行（§8.2）不同：音频块之间有依赖、合并要处理重叠，所以不能像裁剪那样各编各的直接拼。
> *边界*：块大小是折中——太小则重叠占比升高（白算），太大又滑回 O(L²) 的老路。

### 8.4 fork-join 线程池解剖：任务粒度、静态切分与 barrier

§8.2 只展示了「怎么用」，这里拆开 `ds_kernels.c` 的实现看「怎么做到每次并行只付两次同步」。整池只有约 200 行，三个角色：

**① 常驻 worker：`ds_worker_loop`**

线程池在 `ds_set_threads` 时一次性创建 n−1 个常驻 pthread（主线程自带 tid=0），每个 worker 循环等待条件变量：

```c
/* 等活：cond_work 广播后各 worker 拿到自己的 tid 和 n_threads */
pthread_mutex_lock(&tp.mutex);
while (!tp.has_work) pthread_cond_wait(&tp.cond_work, &tp.mutex);
int tid = ...; int nt = tp.n_threads;
pthread_mutex_unlock(&tp.mutex);   /* 执行期不持锁！ */

fn(tid, nt, arg);                  /* 干活：写区间互不相交，无需加锁 */

pthread_mutex_lock(&tp.mutex);
if (++tp.n_done >= tp.n_threads - 1)   /* 最后完成者负责唤醒主线程 */
    pthread_cond_signal(&tp.cond_done);
pthread_mutex_unlock(&tp.mutex);
```

**② fork-join 入口：`ds_parallel_for(fn, arg)`**

```c
/* 伪代码（真实实现在 ds_kernels.c） */
pthread_cond_broadcast(&tp.cond_work);  /* 入口：唤醒全部 worker */
fn(0, tp.n_threads, arg);               /* 主线程不闲着，自己跑 tid=0 */
while (tp.n_done < tp.n_threads - 1)    /* 出口 barrier（while 防
    pthread_cond_wait(...);             /*  虚假唤醒）*/
```

同步成本 = **入口一次广播 + 出口一次 barrier**，执行期间零锁零原子操作。

**③ 任务切分：静态区间，不是 work-stealing**

以 matvec 的线程体 `ds_matvec_worker` 为例：

```c
int chunk = (t->out_dim + n_threads - 1) / n_threads;  /* 均分，向上取整 */
int start = tid * chunk;
/* 线程 i 只写 y[start..end)，只读 W 的 [start*in_dim, end*in_dim) 区间 */
```

注意本仓库选的是**静态切分**而非 work-stealing，原因有三：

1. **写区间天然互不相交**——按输出行切，各线程写 y 的不同段，执行期才能零锁（①里敢解锁干活的前提）
2. **负载天然均匀**——matvec 每行 FLOPs 相同（都是 in_dim 次乘加），按行均分即负载均分；work-stealing 的任务队列原子操作反而比干活还贵
3. **逐位可复现**——每行的累加顺序不因线程数改变，结果与单线程逐位一致（r4 的 grouped matvec 甚至以「行对」为切分粒度保证这一点，见 §8.5）

> 🗣️ **说人话**：线程池并行矩阵乘法是发牌时就按人头分好，不是抢活。把 out_dim 行分给 n 个线程：1280 行、8 线程，每线程 160 行，写 y 的不同段、读 W 的不同段，天然不重叠。所以执行期间可以完全不持锁——各自算完，只回主线程报到一次。仓库刻意不用 work-stealing：推理内核每行 FLOPs 一模一样，负载天生均匀，抢活的原子操作可能比干活本身还贵；静态切分还有个好处——每行累加顺序不随线程数改变，结果逐位可复现。
> *边界*：行数不是线程数整倍数时，向上取整会让最后一个线程少干一截，线程越多这条尾巴越显眼——所以极小的矩阵进池反而更慢（仓库门槛是 256 KB）。

work-stealing 适合任务大小不可预测的场景（如并行排序）；推理内核的负载是编译期可知的，静态切分是更便宜的正确选择。

**④ 粒度门槛：小任务不值得进池**

`ds_bf16_to_f32_buf` 给出了明确的阈值注释：n ≥ 65536（256 KB）才进线程池，小转换串行做——因为一次 barrier 的同步开销（微秒级）会吃掉小任务本身的耗时。**任务粒度 < 同步开销时，并行就是负优化**。

### 8.5 并行区合并：把 19 次 barrier 压成 1 次

barrier 是线程池最贵的操作，优化的第二方向（第一是 §8.4 的零锁执行）是**减少并行区个数**。decode 一步 12 层 × 多次 matvec，若每次 matvec 独立进池，barrier 次数会随矩阵个数线性增长。两个真实案例：

**案例 1：grouped matvec（`ds_grouped_matvec_bf16`）**

MoE decode 一步要对 8 个「专家×矩阵」组合做 matvec（6 路由 + 2 共享，各含 gate_up 与 down）。旧实现每专家独立调用 → 每层约 19 个微并行区，barrier 开销淹没矩阵本身。合并后把所有行对折叠成一个并行区：

```c
/* 旧：19 次 ds_parallel_for（每次 1 广播 + 1 barrier）
 * 新：1 次 ds_parallel_for，行对粒度切分，
 *     每行累加顺序不变 → 与串行版逐位一致 */
ds_grouped_matvec_bf16(out, X[], W[], n_units, rows_per_unit, in_dim);
```

**案例 2：QKV 融合（`qkv_ds_matvec_worker`）**

Q、K、V 三张权重表共享同一个输入 x。旧做法 3 次独立 matvec = 3 个并行区；融合后一个并行区同时喂三张权重表，barrier 从 3 次降到 1 次。

**案例 3：融合专家前向（`ds_expert_forward_fused`）**

gate+up 权重预拼接为 `gate_up_fused_bf16`（[2×896, 1280]），x[1280] 一次读入喂 1792 行输出，并行区从分离版的 2 个减为 1 个——注释原话：「线程池只派发 1 个并行区（分离版要 2 个），减少 barrier 次数」。

> **通用规律**：多线程内核的耗时 ≈ 计算时间 + barrier 次数 × 同步成本。当单次计算只有几十微秒时，barrier 次数就是性能本身。优先做「数学等价的合并」（融合、折叠），让每步的并行区个数成为常数。

> 🗣️ **说人话**：barrier 是全体线程的「到齐点名」：19 个微并行区 = 每层点名 19 次，活还没干先排死了队。合并的思路是「同类活攒一车再发」：8 个「专家×矩阵」的 matvec 折成 1 个 `ds_grouped_matvec_bf16` 并行区、QKV 三表共用 1 个区、gate_up 预拼接成 [1792,1280] 一次喂完。数学等价（行对粒度保证逐位一致），所以同步次数能从线性降到常数——r4 实测 MoE 前向 8.4s→3.4s、decode +66%（docs/05 §10.7）。
> *边界*：合并要求各单元形状一致才能共用切分逻辑——形状各异的算子硬折进一个区要加 padding 或分支，可能得不偿失。

| **权重精度** | BF16 (解码器) + F32 (编码器) | BF16→F32预转换 (编码器) + BF16 (解码器) |

> 🗣️ **说人话**：这张表的读法：两边骨架完全同构（音频↔图像、编码器→投影→解码器），ds-ocr 等于把 qwen-asr 的流水线逐段换成多模态件。真正的分岔只有一处——解码器 Dense vs MoE（§9.3），以及随之来的权重精度分工（解码器 BF16 零拷贝、编码器 F32 预转换，§2.4）——所以看架构先看 FFN 形态，其余差异多是「换了输入」的连锁反应。
> *边界*：位置编码三件套（RoPE+2D PE+相对位置）是图像侧多出来的复杂度，音频只有 RoPE+正弦——对比时别把投影层差异误记成架构差异。

### 9.3 核心差异：MoE vs Dense

ds-ocr 解码器使用 MoE，qwen-asr 使用 Dense FFN。这是两者最大的架构差异：

**qwen-asr Dense 解码器层**：
```c
/* 简单直接的 SwiGLU FFN */
qwen_linear_nobias_bf16(gate_buf, x_norm, l->gate_up_fused_bf16, ...);
qwen_swiglu_multiply(gate_buf, gate_buf, 1, intermediate);
qwen_linear_nobias_bf16(ffn_out, gate_buf, l->down_weight_bf16, ...);
```

**ds-ocr MoE 解码器层**：
```c
/* 复杂的路由 + 多专家 + 共享专家 */
ds_moe_router_bf16(scores, x_norm, layer->gate_weight_bf16, ...);
ds_moe_top_k(top_indices, top_weights, scores, 64, 6);
for (int k = 0; k < 6; k++) {
    ds_expert_forward(expert_outputs + k*hidden, x, ...);
}
ds_expert_combine(output, expert_outputs, top_indices, top_weights, ...);
/* + 共享专家 */
```

**MoE 在推理侧到底省了什么、没省什么。** 这是最容易误读的一处，拆成三笔账：

| 维度 | Dense（qwen-asr） | MoE（ds-ocr） | 省了吗 |
|---|---|---|---|
| **参数量** | 全部参数都参与 | 64 专家全存着 | **不省**（权重总量更大） |
| **每步读的权重** | 全部 | 只读 6/64 专家 + 2 共享 | **省 ~8×** |
| **每步 FLOPs** | 全部 | 只算 6/64 | **省 ~8×** |
| **显存驻留** | 全部常驻 | 冷专家可被 mmap 惰性丢弃 | **省**（§2.2） |

**算一遍每步读多少。** 单个专家的 gate_up [1792, 1280] BF16 = 4.59 MB，down [1280, 896] BF16 = 2.29 MB，合计 6.88 MB（= 3 × 1280 × 896 × 2 B）。6 路由 + 2 共享 = 8 个专家 × 6.88 MB × **11 个 MoE 层**（layer 0 是 dense FFN）≈ **606 MB/步**，与 docs/05 §7.4 的逐项账单一致。如果 64 个专家全读，就是 64 × 6.88 × 11 ≈ **4.8 GB/步**——比整个模型权重还大。所以 MoE 的「稀疏激活」在 decode 里是**带宽的救命稻草**，不是锦上添花。

**路由本身的开销。** `ds_moe_router_bf16` 是一次 [1280] × [1280, 64] 的 matvec，读 1280 × 64 × 2 B = 164 KB——相对于 606 MB 的专家权重，可以忽略。`ds_moe_top_k` 是 64 选 6 的选择法，64 × 6 = 384 次比较，微秒级。

**为什么 top-6 而不是 top-1。** top-1 路由会让每个专家承担过大的梯度方差，训练不稳定；top-6 让每个 token 的输出是 6 个专家的加权和，相当于「集成」，容错性更好。代价是每步多读 5 个专家的权重——这是**用带宽换质量**的取舍。

> **边界**：MoE 的稀疏性只在**单请求 decode** 时转化为带宽收益。batch decode 时不同 token 路由到不同专家，一个 batch 里可能凑齐全部 64 个专家——此时「稀疏」失效，MoE 反而比同等激活参数的 Dense 更慢（要读全部专家）。这是 MoE 服务端部署的核心难题（专家并行/All-to-All 通信）。

> 🗣️ **说人话**：MoE 的账分「存」和「运」两本：64 个专家全存着（3B 参数、6.2 GB mmap），每步只运 8 个（6 路由 + 2 共享，606 MB）——**存的钱照付，运的钱省 ~8×**。Dense 是存多少运多少。decode 是带宽动物园，「运」这本账才是生死账；这也解释了 mmap 与 MoE 为什么是天作之合——没被路由的冷专家连缺页都不产生（§2.5）。
> *边界*：2 个共享专家是保底工资：无论路由怎么跳它们每步必被读（13.8 MB/层是常数项），只有 41.3 MB 的路由部分是波动项——预测内存行为时把两项分开看。

## 10. 训练视角对照：推理引擎省掉了什么

本篇反复出现「内存带宽是第一约束」「MoE 稀疏激活省内存」，把这些账放到训练视角下会看到另一番景象——理解这个对照，你就明白为什么训练框架（PyTorch）和推理引擎（本仓库）注定是两种软件。

### 10.1 一次 matmul 在两边各做几件事？

**推理**：只算前向一遍。

$$Y = XW^T \quad \text{（1 次 GEMM，读完权重即可丢弃指针——mmap 下连读都可能是第二次才发生）}$$

**训练**：同一次 matmul 前后还要挂两个额外的 GEMM（反向传播链式法则的结果）：

| 计算 | 公式 | 用途 | 形状（以本仓库 QKV 投影为例） |
|------|------|------|------------------------------|
| 前向 | $Y = XW^T$ | 算输出 | [S,1280]×[1280,3840] |
| 激活梯度 | $dX = dY \cdot W$ | 把梯度传回上一层 | [S,3840]×[3840,1280] |
| 权重梯度 | $dW = dY^T \cdot X$ | 给优化器更新权重 | [3840,S]×[S,1280] |

所以训练的**计算量约为推理的 3×**（经验法则：前向 1、反向 2）。而且前向的所有中间激活（每层的 x_norm、Q/K/V、注意力输出、SwiGLU 的 gate/up……）都必须**留到反向用**——这正是训练显存随 seq 长度平方级/线性级膨胀的根源，也是推理引擎可以完全无视的东西（本仓库 decode 的中间缓冲只有一组预分配的 1280 维向量，`alloc_decoder_buffers`）。

**为什么反向是前向的 2×，不是 1×。** 因为链式法则要求两个梯度：

- $dX = dY \cdot W$：把梯度传给**上一层**（形状同 X）
- $dW = dY^T \cdot X$：给**本层权重**的更新量（形状同 W）

两个都是与 $Y = XW^T$ 同量级的 GEMM，所以 1（前向）+ 2（反向）= 3×。注意 $dW$ 的形状是 $[\text{out}, \text{in}]$，与 W 完全一致——这就是为什么优化器能直接拿它更新权重。

**激活显存为什么是瓶颈。** 前向的每个中间结果都要留到反向（否则反向时得重算）。以一层为例：`x_norm` [S,1280]、`Q`/`K`/`V` 各 [S,1280]、注意力输出 [S,1280]、`gate/up` [S,1792]、`ffn_out` [S,1280]——每 token 每层 8192 个 float = **32 KiB**。12 层 × S=4096 × 32 KiB ≈ **1.6 GB**，而且这还只是单样本、只算了 FFN 主干（不含 MoE 的 6 个专家中间量）。这就是为什么训练要「梯度检查点」（用重算换显存）。

> **边界**：3× 是**计算量**的经验值，不含注意力的 $O(S^2)$ 项。长序列时注意力的反向（要存 $S \times S$ 的注意力矩阵或重算）会让倍数远超 3×。

> 🗣️ **说人话**：推理的 matmul 是「读一遍、扔指针」；训练的同一个 matmul 身后拖着两个影子 GEMM——dX（梯度传给上一层）和 dW（优化器的更新量），算术量 3×。更要命的是前向全部中间量得留到反向：每 token 每层 32 KiB 激活，12 层 × S=4096 ≈ 1.6 GB——这就是推理引擎敢把中间缓冲缩到一组 1280 维向量的底气（`alloc_decoder_buffers`），训练框架想都不敢想，只能靠梯度检查点拿重算换显存。
> *边界*：「读一遍就扔」也解释了为什么推理敢用 mmap 惰性映射而训练不敢——训练里每个参数迟早被 dW 更新写回，映射必须可写、页省不回来（§10.3 第 2 点）。

### 10.2 显存账：参数 × 16 字节的推导

以 AdamW + 混合精度（PyTorch 默认）为例，每个参数在训练显存里的「全家福」：

| 项目 | 字节/参数 | 说明 |
|------|----------|------|
| BF16 权重副本（前向用） | 2 | autocast 的工作精度 |
| FP32 master 权重 | 4 | 优化器真正更新的那份（避免低精度累加误差） |
| FP32 梯度 | 4 | $dW$ |
| Adam 动量 m（一阶） | 4 | 梯度的指数滑动平均 |
| Adam 动量 v（二阶） | 4 | 梯度平方的滑动平均 |
| **合计** | **18** | 常被粗略记作 **≈16 B/参数**（不算激活） |

$$\text{训练显存} \approx 16 \times P + \text{激活显存}$$

代入本仓库模型（P ≈ 3B）：

- **推理（本引擎）**：权重 6.2 GB（BF16 mmap，MoE 稀疏访问下物理驻留更少）+ KV 缓存 0.5 GB + 小缓冲 ≈ **7 GB 量级**（实测峰值 RSS 8.6–9.4 GB，docs/05 §10.4）
- **训练**：3e9 × 16 B = **48 GB** 起步，再加激活（batch × seq × hidden × 层数 × 每层十几个中间量）——必须 A100 80 GB 级别或多卡分摊

**16 倍的差距里，有 2× 来自精度（2 B vs 4 B 存储），其余全部来自「优化器状态 + 梯度」这些推理引擎根本不需要存在的东西。**

> **类比**：推理是「闭卷考试只答题」——题目（权重）看一遍就能往下写；训练是「答题 + 对答案 + 改错题本」——每道题都要留草稿（激活）、记错误（梯度）、攒复习重点（Adam 动量）。备考的负担是考试的好几倍，而且草稿纸（激活显存）随题目长度暴涨。

### 10.3 这个对照对本仓库意味着什么

1. **MoE 的省是推理视角的省**：64 个专家只激活 6 个，decode 每步只碰 ~606 MB 专家权重（§9.3 的账）；训练时每个专家都要为「万一被路由到」保留梯度与动量，稀疏性省不了优化器状态——MoE 训练显存仍按全部 3B 参数 × 16 B 起算。
2. **mmap 惰性加载是推理专属的福利**：训练中每个参数迟早被反向触碰 + 被优化器更新，页缓存逃不掉；推理的冷专家（未被路由）永远不产生 page fault（docs/05 §7.6）。
3. **「算力强度」的最优解不同**：训练的 GEMM 足够大（batch × seq 维度撑起 M），天然在 Roofline 计算-bound 一侧；decode 的 matvec 强度≈1，只能靠 docs/05 的带宽优化——这解释了为什么训练框架的优化手册（大 batch、混合精度、梯度检查点）几乎不能照搬给推理引擎。

## 小结

你现在理解了纯 C 推理引擎的实现细节：

1. **Safetensors + mmap**：零拷贝权重加载，代价是缺页与 RSS（§2.5）
2. **BF16**：存储减半，计算全精度，on-the-fly 转换（带宽账见 §3.5–3.6，舍入见 §3.7）
3. **三级内核**：generic → NEON/AVX → BLAS，编译期定候选、运行期定人选（§4.5）
4. **KV 缓存**：避免重复计算，GQA 减少缓存大小（分版本字节账见 §5.7，在线 softmax 见 §5.3）
5. **Prefill vs Decode**：批量 vs 单 token 两种模式，Roofline 两行公式见 §6.1
6. **采样**：贪心/温度/重复惩罚/n-gram 阻断
7. **线程池**：零锁静态切分 + 并行区合并（§8.4–8.5），Amdahl 上限见 §8.1；训练 vs 推理的显存与计算账（§10）
