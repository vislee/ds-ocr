## 1. 为什么用纯 C 写推理引擎？

### 1.1 Python 推理 vs C 推理

| | Python (PyTorch) | 纯 C 推理 |
|--|-------------------|-----------|
| **启动速度** | 慢（导入 PyTorch ~2s） | 瞬间 |
| **内存占用** | 大（PyTorch 运行时 ~1GB+） | 小（只有权重+缓冲区） |
| **依赖** | PyTorch, CUDA, Python... | 零依赖（只用系统 BLAS） |
| **移植性** | 依赖 Python 环境 | 任何有 C 编译器的平台 |
| **控制力** | 抽象层厚 | 直接控制每个操作 |
| **适合场景** | 研究/训练 | 生产部署/嵌入式 |

### 1.2 antirez 的设计哲学

qwen-asr（由 Redis 作者 antirez 开发）的设计哲学：
1. **零依赖**：不需要 Python、PyTorch、CUDA
2. **简洁**：每个函数做一件事，逻辑清晰
3. **高效**：BF16 零拷贝 + 平台优化内核
4. **可读**：代码即文档，从代码就能理解算法

ds-ocr 完全继承了这一哲学，并扩展到视觉和多模态领域。

## 2. Safetensors：权重的存储与加载

### 2.1 Safetensors 格式

Safetensors 是 HuggingFace 推出的模型权重格式，比 PyTorch 的 `.bin` 更安全、更快：

```
┌─────────────────────────────────────┐
│ 8 bytes: N = header JSON 长度       │
├─────────────────────────────────────┤
│ N bytes: header JSON                │
│  {"tensor_name": {                  │
│    "dtype": "BF16",                 │
│    "shape": [1280, 896],            │
│    "data_offsets": [start, end]     │
│  }, ...}                            │
├─────────────────────────────────────┤
│ 数据区域: 原始二进制 (BF16/F32/...)  │
│  tensor1 的数据 | tensor2 的数据 | ...│
└─────────────────────────────────────┘
```

### 2.2 零拷贝 mmap 加载

传统方式：打开文件 → read 到内存 → 解析  
mmap 方式：把文件映射到虚拟地址空间 → 直接用指针访问

**在 ds-ocr 中的实现**（`ds_safetensors.c`）：

```c
safetensors_file_t *safetensors_open(const char *path) {
    /* 1. 打开文件 */
    int fd = open(path, O_RDONLY);
    
    /* 2. 获取文件大小 */
    struct stat st;
    fstat(fd, &st);
    size_t file_size = st.st_size;
    
    /* 3. mmap: 将文件映射到内存 */
    void *data = mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, fd, 0);
    
    /* 4. 解析 header JSON（前 8 bytes 是长度，后面是 JSON） */
    uint64_t header_len;
    memcpy(&header_len, data, 8);
    char *header_json = (char *)data + 8;
    
    /* 5. 解析 JSON，记录每个 tensor 的偏移和形状 */
    /* ... */
}
```

> **关键优势**：mmap 是**惰性加载**——只有实际被访问的页才会从磁盘读入。对于 3B 参数的模型，大部分专家权重可能根本不会被访问到（MoE 稀疏激活），节省大量内存。

### 2.3 多分片支持

大模型权重通常分成多个文件（`model-00001-of-00003.safetensors` 等）：

```c
typedef struct {
    safetensors_file_t *shards[8];  /* 最多 8 个分片 */
    int num_shards;
} multi_safetensors_t;

/* 统一查找：在所有分片中搜索 tensor */
const safetensor_t *multi_safetensors_find(const multi_safetensors_t *ms,
                                            const char *name,
                                            safetensors_file_t **out_sf);
```

### 2.4 BF16 权重的零拷贝访问

```c
/* 获取 BF16 数据的直接指针（不复制） */
uint16_t *safetensors_get_bf16_direct(const safetensors_file_t *sf,
                                       const safetensor_t *t) {
    return (uint16_t *)((char *)sf->data + sf->header_size + t->data_offset);
}

/* 获取 F32 数据（需要转换，会复制） */
float *safetensors_get_f32(const safetensors_file_t *sf,
                            const safetensor_t *t) {
    uint16_t *bf16 = safetensors_get_bf16_direct(sf, t);
    size_t n = safetensor_numel(t);
    float *f32 = (float *)malloc(n * sizeof(float));
    /* BF16 → F32 转换 */
    uint32_t *d = (uint32_t *)(void *)f32;
    for (size_t i = 0; i < n; i++)
        d[i] = ((uint32_t)bf16[i]) << 16;
    return f32;
}
```

> **策略**：解码器权重（占 95%+）用 BF16 零拷贝，编码器权重（较小）用 F32 预转换。因为解码器是逐 token 推理（计算密度低），BF16→F32 的逐行转换开销可忽略；而编码器是批量计算，预转换更高效。

## 3. BF16 精度：存储一半，计算全精度

### 3.1 什么是 BF16？

| 格式 | 符号位 | 指数位 | 尾数位 | 范围 | 精度 |
|------|--------|--------|--------|------|------|
| FP32 | 1 | 8 | 23 | ±3.4e38 | ~7位十进制 |
| FP16 | 1 | 5 | 10 | ±65504 | ~3位十进制 |
| **BF16** | 1 | 8 | 7 | ±3.4e38 | ~2位十进制 |

BF16 的巧妙之处：**保持 FP32 的指数范围，只减少尾数精度**。
- 和 FP32 范围相同（不会溢出）
- 精度只有 FP32 的 1/256（但对深度学习足够）
- 只需 FP32 一半的存储空间

### 3.2 BF16 ↔ FP32 转换

```
BF16 (16bit):  S EEEEEEEE MMMMMMM
FP32 (32bit):  S EEEEEEEE MMMMMMMMMMMMMMMMMMMMMMM

转换: FP32 = BF16 << 16  (高位对齐，低位补零)
```

**在代码中**：

```c
/* BF16 → FP32 */
uint32_t f32_bits = ((uint32_t)bf16_value) << 16;
float f32_value;
memcpy(&f32_value, &f32_bits, sizeof(float));

/* FP32 → BF16 (截断低16位) */
uint32_t f32_bits;
memcpy(&f32_bits, &f32_value, sizeof(uint32_t));
uint16_t bf16_value = (uint16_t)(f32_bits >> 16);
```

### 3.3 BF16 权重的矩阵乘法

ds-ocr 的核心操作：**用 BF16 权重和 F32 输入做矩阵乘法，输出 F32 结果**。

```c
/* y = x @ W_bf16^T  (x: F32, W: BF16, y: F32) */
void ds_linear_nobias_bf16(float *y, const float *x, const uint16_t *W_bf16,
                            int seq_len, int in_dim, int out_dim) {
    /* 内部实现：
     * 逐行遍历 W_bf16，每行：
     *   1. BF16 → F32 (on-the-fly)
     *   2. dot(x, row_f32) → y[row]
     */
}
```

> **为什么不预先全部转 F32？** 因为解码器权重巨大（几 GB），全转 F32 会翻倍内存。逐元素 on-the-fly 转换只需少量寄存器，不增加内存占用。

### 3.4 流式 Argmax：不计算全部 logits

对于 12 万词的词表，计算全部 logits（lm_head @ x）需要 129280 × 1280 = 1.65 亿次乘法。但贪心解码只需要 argmax——**最大值在哪就行**。

**流式 Argmax**（`ds_kernels.c` → `ds_argmax_matvec_bf16`）：

```c
int ds_argmax_matvec_bf16(const float *x, const uint16_t *W_bf16,
                           int in_dim, int out_dim) {
    int best_id = 0;
    float best_val = -1e30f;
    
    /* 逐行计算点积，同时追踪最大值 */
    for (int row = 0; row < out_dim; row++) {
        float dot = ds_dot_f32_impl(x, bf16_to_f32_row(row), in_dim);
        if (dot > best_val) {
            best_val = dot;
            best_id = row;
        }
    }
    return best_id;
    /* 不需要存储 129280 个 logits！ */
}
```

> **节省内存**：流式 argmax 不需要分配 129280 × 4 bytes = 512KB 的 logits 缓冲区。但对于需要重复惩罚等后处理的场景，仍需完整 logits。

### 3.5 on-the-fly 转换的带宽账：转换一次不如每次便宜

§3.2 讲了位运算原理，这里算**经济账**：为什么「每次用时转」比「提前转好放着」更划算。

设一段权重有 N 个元素，会被使用 T 次（decode 一步 = 1 次，一段 OCR 生成 226 个 token = 226 次）。两种策略的**累计内存流量**：

| 策略 | 一次性成本 | 每次使用成本 | T 次使用总流量 | 额外内存驻留 |
|------|-----------|-------------|---------------|-------------|
| 预转换成 F32 | 读 2N + 写 4N | 读 4N（读 F32 副本） | 6N + 4NT | +4N（F32 副本） |
| **on-the-fly** | 0 | 读 2N（读 BF16 原件） | **2NT** | 0 |

以 T=226 代入：预转换 ≈ 910N，on-the-fly ≈ 452N——**稳态流量直接减半**，还省下一份 F32 副本的内存。以 lm_head（N = 129280 × 1280 ≈ 1.66 亿元素）为例：

- 预转换：一次读 331 MB + 写 662 MB，之后每步 decode 还要读 662 MB 的 F32 副本，且这 662 MB 常驻内存
- on-the-fly：每步只读 331 MB 的 BF16 原件，转换发生在 NEON 寄存器里（`ds_kernels_neon.c` 的 `ds_bf16_matvec_fused_neon` 用 `vshll_n_u16` 一条指令完成「u16 加宽成 u32 并左移 16 位」），**不落内存、不占额外带宽**

这就是本仓库的取舍依据（`ds_moe_decoder.c` 文件头注释）：解码器权重巨大且逐 token 使用 → on-the-fly；编码器权重小且一次性批量使用 → 预转换一次（`ds_kernels.c` 的 `ds_bf16_to_f32_buf`，超过 64K 元素的大转换还会进线程池并行，见 §8.4）。

> **手算算例**：一个专家的 gate_up_fused 权重 [1792, 1280]，N = 229 万。预转换一次 = 读 4.6 MB + 写 9.2 MB；decode 中它每步被读一次 BF16 = 4.6 MB。若预转换，则首次多付 13.8 MB 流量 + 常驻 9.2 MB 内存——对一个每步都要用的权重，on-the-fly 从第一步起就更便宜。

### 3.6 流式 argmax 的完整带宽账：省的不是 512 KB，是 331 MB

§3.4 说流式 argmax「省了 512KB 的 logits 数组」——这其实是账目里最小的一项。把它和「物化全部 logits」的完整路径对比（数字来自 `ds_moe_decoder.c` → `ds_decoder_forward` 的注释与代码，M2 Pro 实测）：

**路径 A：物化 logits（旧做法 / 现在的 full path）**

```
1. （首次）BF16→F32 转换 lm_head：读 331 MB + 写 662 MB → 常驻 662 MB F32 副本
2. 每步 sgemm：读 662 MB F32 权重 + 写 517 KB logits（129280 × 4 B）
3. 每步 argmax：读回 517 KB logits
   每步总流量 ≈ 663 MB   → 理论下限 663 MB ÷ 200 GB/s ≈ 3.3 ms
   v0.5 逐行 BF16 物化实测 ~55–63 ms（转换开销 + 无 sgemm 批量）
```

**路径 B：流式 argmax（`ds_kernels.c` → `ds_argmax_matvec_bf16`）**

```
1. 每步直接在 BF16 权重上逐行点积：读 331 MB BF16
2. logits 永不落盘——冠军值和 ID 只在寄存器/栈上
   每步总流量 ≈ 331 MB   → 理论下限 ≈ 1.7 ms
   实测 ~8 ms（含多线程同步与 BF16 展开开销）
```

三笔账分开看：

| 维度 | 物化路径 | 流式 argmax | 省下 |
|------|---------|------------|------|
| **内存驻留** | 662 MB F32 副本 + 517 KB logits | 0 | **−662 MB** |
| **每步读流量** | 662 MB（F32） | 331 MB（BF16） | **÷2**（§3.5 的 T=∞ 极限） |
| **写+读回 logits** | 517 KB × 2 | 0 | 微不足道，但省一次分配 |
| **实测每步耗时** | ~55–63 ms（v0.5） | ~8 ms | **~8×**（docs/05 §4.1） |

> **为什么「不物化」还能做重复惩罚？** §7.3 的惩罚只需要历史 token（约几百个）的 logit。流式 argmax 之后用 `ds_bf16_dot_row`（`ds_kernels.c`）对这几个 ID 逐个补算点积即可——把 O(129280) 的「全量先算后查」变成 O(历史长度) 的「按需补算」，这就是 docs/05 §4.2 的 Selective Repetition Penalty。需要全量分布的温度采样才走回物化路径（`ds_decoder_forward` 中的 `full_logits_path` 标签）。

## 4. 数学内核：从通用到平台优化

### 4.1 三级内核架构

ds-ocr 和 qwen-asr 都采用**三级内核架构**：

```
ds_kernels.h           ← 统一 API（平台无关）
    │
ds_kernels_impl.h      ← 编译时平台检测 + 宏分发
    │
    ├── ds_kernels_generic.c   ← 通用 C 实现（任何平台）
    ├── ds_kernels_neon.c      ← ARM NEON 优化（Apple Silicon）
    └── ds_kernels_avx.c       ← x86 AVX2+FMA 优化（Intel/AMD）
```

**编译时自动选择**（`ds_kernels_impl.h`）：

```c
#ifdef __ARM_NEON
    #define ds_bf16_matvec_fused_impl ds_bf16_matvec_fused_neon
    #define ds_dot_f32_impl ds_dot_f32_neon
#elif defined(__AVX2__) && defined(__FMA__)
    #define ds_bf16_matvec_fused_impl ds_bf16_matvec_fused_avx
    #define ds_dot_f32_impl ds_dot_f32_avx
#else
    #define ds_bf16_matvec_fused_impl ds_bf16_matvec_fused_generic
    #define ds_dot_f32_impl ds_dot_f32_generic
#endif
```

### 4.2 以 dot product 为例

**通用实现**：

```c
/* ds_kernels_generic.c */
float ds_dot_f32_generic(const float *a, const float *b, int n) {
    float sum = 0.0f;
    for (int i = 0; i < n; i++) sum += a[i] * b[i];
    return sum;
}
```

**NEON 实现**（4× 并行）：

```c
/* ds_kernels_neon.c */
float ds_dot_f32_neon(const float *a, const float *b, int n) {
    float32x4_t sum_vec = vdupq_n_f32(0.0f);
    int i = 0;
    for (; i + 3 < n; i += 4) {
        float32x4_t a_vec = vld1q_f32(a + i);
        float32x4_t b_vec = vld1q_f32(b + i);
        sum_vec = vfmaq_f32(sum_vec, a_vec, b_vec);  /* FMA: sum += a*b */
    }
    /* 水平求和 + 处理剩余元素 */
    float sum = vaddvq_f32(sum_vec);
    for (; i < n; i++) sum += a[i] * b[i];
    return sum;
}
```

**AVX2 实现**（8× 并行）：

```c
/* ds_kernels_avx.c */
float ds_dot_f32_avx(const float *a, const float *b, int n) {
    __m256 sum_vec = _mm256_setzero_ps();
    int i = 0;
    for (; i + 7 < n; i += 8) {
        __m256 a_vec = _mm256_loadu_ps(a + i);
        __m256 b_vec = _mm256_loadu_ps(b + i);
        sum_vec = _mm256_fmadd_ps(a_vec, b_vec, sum_vec);
    }
    /* 水平求和 + 剩余处理 */
}
```

### 4.3 BLAS 加速的矩阵乘法

对于大矩阵乘法（prefill 阶段），ds-ocr 和 qwen-asr 都调用系统 BLAS：

```c
/* macOS: Accelerate Framework (cblas_sgemm) */
/* Linux: OpenBLAS (cblas_sgemm) */

/* C = A @ B^T: A[seq,K], B[N,K], C[seq,N] */
void ds_matmul_t(float *C, const float *A, const float *B, int M, int K, int N) {
    cblas_sgemm(CblasRowMajor, CblasNoTrans, CblasTrans,
                M, N, K, 1.0f, A, K, B, K, 0.0f, C, N);
}
```

> **为什么 BLAS 更快？** BLAS 库针对特定 CPU 微架构做了极致优化（cache 友好分块、指令级并行、寄存器分配），比手写循环快 5-10×。

### 4.4 BF16 融合矩阵向量乘

单 token 解码时，核心操作是 `y = W_bf16^T @ x`（矩阵×向量）。ds-ocr 提供了高度优化的融合实现：

```c
/* ds_kernels_neon.c — NEON 优化的 BF16 matvec */
void ds_bf16_matvec_fused_neon(float *y, const float *x, const uint16_t *W_bf16,
                                 const float *bias, int in_dim, int out_dim) {
    /* 同时做 BF16→F32 转换 + 点积 + 加 bias
     * 利用 NEON 的 BF16 指令直接在 BF16 上做乘法
     * 避免了先转 F32 再乘的额外内存访问 */
}
```

## 5. KV 缓存：自回归推理的加速器

### 5.1 为什么需要 KV 缓存？

自回归解码时，每个新 token 需要和**所有之前的 token** 做注意力计算。如果没有缓存：

```
Step 1: 计算 K₁,V₁ → Q₁·K₁ → 输出
Step 2: 计算 K₁,K₂,V₁,V₂ → Q₂·[K₁,K₂] → 输出  (重复计算 K₁,V₁!)
Step 3: 计算 K₁,K₂,K₃,V₁,V₂,V₃ → Q₃·[K₁,K₂,K₃] → 输出  (重复更严重!)
```

KV 缓存：**把已计算的 K、V 存起来，每步只算新 token 的 K、V**：

```
Step 1: 算 K₁,V₁ → 存入缓存 → Q₁·K₁ → 输出
Step 2: 算 K₂,V₂ → 存入缓存 → Q₂·[缓存K₁,K₂] → 输出  (不重复计算!)
Step 3: 算 K₃,V₃ → 存入缓存 → Q₃·[缓存K₁,K₂,K₃] → 输出
```

> **节省**：Step t 的注意力计算从 O(t²d) 降到 O(td)（只需计算新 Q 与缓存 KV 的点积）。

### 5.2 KV 缓存的数据结构

**ds-ocr 中的 KV 缓存**（`ds_ocr.h`）：

```c
/* KV 缓存: [layers × max_seq × kv_dim] */
float *kv_cache_k;  /* Key 缓存 */
float *kv_cache_v;  /* Value 缓存 */
int kv_cache_len;   /* 当前已缓存的位置数 */
int kv_cache_max;   /* 最大缓存容量 */
```

**内存布局**：`kv_cache_k[layer][position][kv_dim]`

```c
/* 分配 KV 缓存 */
int max_seq = 4096;
int kv_dim = n_kv_heads * head_dim;  /* 10 * 128 = 1280 */
size_t kv_size = (size_t)12 * max_seq * kv_dim * sizeof(float);
/* 12 层 × 4096 位置 × 1280 维 × 4 bytes = ~240MB */
ctx->kv_cache_k = (float *)calloc(1, kv_size);
ctx->kv_cache_v = (float *)calloc(1, kv_size);
```

### 5.3 解码时存取 KV 缓存

```c
/* 写入：新 token 的 K、V 存入缓存 */
int cache_offset = ctx->kv_cache_len;
float *cache_k = ctx->kv_cache_k + (size_t)layer_idx * kv_cache_max * kv_dim
                  + cache_offset * kv_dim;
float *cache_v = ctx->kv_cache_v + (size_t)layer_idx * kv_cache_max * kv_dim
                  + cache_offset * kv_dim;
memcpy(cache_k, k, kv_dim * sizeof(float));
memcpy(cache_v, v, kv_dim * sizeof(float));

/* 读取：因果注意力时，使用缓存中的全部 K、V */
float *full_k = ctx->kv_cache_k + (size_t)layer_idx * kv_cache_max * kv_dim;
float *full_v = ctx->kv_cache_v + (size_t)layer_idx * kv_cache_max * kv_dim;
ds_causal_attention(attn_out, q, full_k, full_v,
                    1, cache_offset + 1, ...);
```

### 5.4 GQA 对 KV 缓存的影响

| 架构 | Q头 | KV头 | KV缓存大小 |
|------|-----|------|-----------|
| MHA (ds-ocr解码器) | 10 | 10 | 10 × 128 = 1280/position |
| GQA (qwen-asr解码器) | 16 | 8 | 8 × 128 = 1024/position |
| GQA (ds-ocr V2编码器) | 14 | 2 | 2 × 64 = 128/position |

GQA 通过共享 KV 头，直接减少了 KV 缓存的内存占用。qwen-asr 使用 GQA 后，KV 缓存减少 50%。

### 5.5 KV 缓存的字节账：为什么它是部署的第一成本

把上面的表换算成真实字节（BF16 每元素 2 B，F32 每元素 4 B）：

$$ \text{KV bytes} = 2 \times L \times S \times n_{kv} \times d_{head} \times \text{bytes\_per\_elem} $$

本工程 V1 解码器（`ds_ocr.h` L97-102：`DS_DEC_LAYERS=12`、`DS_DEC_KV_HEADS=10`、
`DS_DEC_HEAD_DIM=128`，标准 MHA 非 GQA），BF16 每元素 2 B：

- 每 token：$2 \times 12 \times 10 \times 128 \times 2 = 61{,}440$ B = **60 KiB/token**
- 8192 token 上下文：$61{,}440 \times 8192 = 503{,}316{,}480$ B ≈ **480 MiB**
- 若用 F32：翻倍到 960 MiB；V3/V4 已改 BF16 存储（`ds_ocr.h` L444-445 注释：
  "BF16 模式省一半驻留与一半解码注意力读流量"），V1/V2 仍是 F32

**这就是为什么"长上下文"是显存问题而非算力问题**：权重是常数（3 GB），
KV 随上下文线性增长。三条主流对策：

| 对策 | 做法 | 本工程对应 |
|---|---|---|
| 减 $n_{kv}$ | MQA/GQA/MLA 共享 KV 头 | GQA（qwen-asr）、MLA（DeepSeek-V2 论文，13 篇 §3） |
| 减 $S$ | 滑窗/稀疏注意力，只保留部分历史 | **V3 R-SWA**（05 篇 §6）、**V4 DASH 块稀疏**（14 篇） |
| 减 bytes | KV 量化（BF16→INT8/FP8） | 未实现；BF16 KV 已是 V3 的优化点（05 篇 §10） |

> **一个反直觉的结论**：R-SWA 与 DASH 这类"稀疏注意力"的首要收益不是
> 省算力，而是**把 KV 从 O(S) 压成 O(W) 或 O(块数)**——decode 每步要读
> 全部 KV，读的字节数就是延迟。docs/09 §1 的带宽账里，KV 读取与权重读取
> 是同一量级的两个大头。

### 5.6 qwen-asr 的动态 KV 缓存扩展

qwen-asr 支持动态扩展 KV 缓存：

```c
static int kv_cache_grow(qwen_ctx_t *ctx, int required) {
    if (required <= ctx->kv_cache_max) return 0;
    int new_max = ctx->kv_cache_max;
    while (new_max < required) new_max *= 2;  /* 倍增策略 */
    
    /* 重新分配 + 拷贝旧数据 */
    float *new_k = (float *)calloc(1, total_size);
    float *new_v = (float *)calloc(1, total_size);
    for (int l = 0; l < layers; l++) {
        memcpy(new_k + l * new_stride, old_k + l * old_stride, copy_size);
        memcpy(new_v + l * new_stride, old_v + l * old_stride, copy_size);
    }
    /* ... */
}
```

### 5.7 KV 缓存分版本数学账：prefill 写入 vs decode 读写

§5.5 给出了公式和一个粗略例子，这里按**本仓库真实配置**（`ds_ocr.c` → `alloc_decoder_buffers`）把四个版本一次算清。先确定两个仓库常量：

- `kv_dim = DS_DEC_KV_HEADS × DS_DEC_HEAD_DIM = 10 × 128 = 1280`，行对齐步长 `kv_row_stride = (1280 + 15) & ~15 = 1280`（1280 恰好是 16 的倍数，无填充）
- 每位置每层要存 K、V 两行：`2 × 1280 = 2560` 个元素；12 层合计每位置 30,720 个元素

代入 `KV bytes = 2 × layers × max_seq × kv_heads × head_dim × bytes/elem`：

| 版本 | max_seq | 存储精度 | 公式代入 | K+V 总量 | 每生成 1 token 增量 |
|------|---------|---------|---------|---------|-------------------|
| **V1/V2** | 4096 | F32（4 B） | 2×12×4096×1280×4 | 503,316,480 B = **480 MiB** | 120 KiB |
| **V3**（R-SWA） | 8192 | **BF16**（2 B） | 2×12×8192×1280×2 | 503,316,480 B = **480 MiB** | 60 KiB |
| **V4**（DASH） | 8192 | F32（4 B） | 2×12×8192×1280×4 | 1,006,632,960 B = **960 MiB** | 120 KiB |

三个值得注意的点：

1. **V3 和 V1 的缓存字节数相同，但 V3 装了 2× 的位置**——这就是 BF16 KV 存储（`ctx->kv_bf16`，写入时经 `ds_kv_store_row` 做 F32→BF16 截断）的直接收益：长文档场景下同样的 480 MiB 从「4096 个位置」扩展到「8192 个位置」。注意精度开关按版本收窄：`alloc_decoder_buffers` 中 `kv_bf16 = (model_version == 3) ? 1 : 0`——有界实验（docs/05 §10.5）显示 V3 全绿、V4 对 KV 精度敏感打红，所以 V4 仍是 F32（§5.5 引用的头文件注释「V3/V4 已改 BF16」是收窄前的旧话，以 `alloc_decoder_buffers` 的代码为准）。
2. **R-SWA 改变的是「读多少」，不是「占多少」**：V3 的缓存按 append-only 预分配 8192 槽，但 decode 每步注意力只读「参考段（prefill_len≈908）+ 滑窗 128」≈1036 行，而不是全部历史。
3. **prefill 与 decode 的读写模式完全不同**：

```
prefill（一次，批量写）：
  V1 例：280 个 prefix token → 每层写 280 行 × 2560 元素 × 4 B = 2.87 MB
  12 层合计写 34.4 MB（一次 sgemm 顺带完成，无回读）

decode（每步，读全部历史 + 写 1 行）：
  V1 例，上下文 300：每步每层读 300 行 × 2560 × 4 B = 3.07 MB
  12 层合计读 36.9 MB/步（注意力主循环里逐行流式读）
  写只有 12 × 2560 × 4 B = 120 KiB/步（新 token 的 K/V）
```

> **手算算例**：V3 一页 6-crop 文档 prefill_len ≈ 908，生成 1000 个 token。若没有 R-SWA，第 1000 步注意力要读 1908 行 BF16 = 1908 × 2560 × 2 B × 12 层 ≈ 117 MB；有 R-SWA 恒定读 (908+128) 行 ≈ 61 MB。生成到第 7000 步时差距拉到 3.7×——这就是 §5.5 说的「读的字节数就是延迟」。

## 6. Prefill vs Decode：两种推理模式

### 6.1 两种模式的区别

| | Prefill | Decode |
|--|---------|--------|
| **输入** | 多个 token（整个 prompt） | 单个 token |
| **计算方式** | 批量矩阵乘法 (sgemm) | 矩阵×向量 (matvec) |
| **注意力** | 因果掩码 + 批量 | 因果掩码 + KV缓存 |
| **KV缓存** | 全部写入 | 只写1个位置 |
| **瓶颈** | 计算（sgemm 快） | 内存带宽（matvec 慢） |
| **速度** | 快（并行） | 慢（串行） |

### 6.2 Prefill 的实现

**ds-ocr 中**（`ds_moe_decoder.c` → `ds_decoder_prefill`）：

```c
void ds_decoder_prefill(ds_ctx_t *ctx, const float *input_embeds, int seq_len) {
    /* 分配批量缓冲区 */
    float *x = (float *)malloc(seq_len * hidden * sizeof(float));
    float *Q = (float *)malloc(seq_len * q_dim * sizeof(float));
    /* ... */
    
    for (int l = 0; l < cfg->dec_layers; l++) {
        /* 批量 RMSNorm */
        ds_rms_norm(x_norm, x, layer->input_norm, seq_len, hidden, eps);
        
        /* 批量 QKV 投影（sgemm） */
        ds_linear_nobias_bf16(Q, x_norm, layer->wq_weight_bf16, seq_len, hidden, q_dim);
        
        /* 批量注意力 */
        ds_causal_attention(attn_out, Q, full_k, full_v, seq_len, total_seq, ...);
        
        /* MoE：批量 gate + 逐 token 专家 */
        ds_linear_nobias_bf16(gate_scores, x_norm, layer->gate_weight_bf16,
                               seq_len, hidden, n_experts);  /* 批量路由 */
        for (int s = 0; s < seq_len; s++) {
            /* 逐 token 做专家前向（和 decode 相同） */
        }
    }
}
```

### 6.3 Decode 的实现

**ds-ocr 中**（`ds_moe_decoder.c` → `ds_decoder_forward`）：

```c
int ds_decoder_forward(ds_ctx_t *ctx, const float *input_embed) {
    /* 使用预分配的单 token 缓冲区 */
    float *x = ctx->dec_x;       /* [1280] */
    float *q = ctx->dec_q;       /* [1280] */
    float *k = ctx->dec_k;       /* [1280] */
    
    for (int l = 0; l < cfg->dec_layers; l++) {
        /* 单 token 前向 */
        decoder_layer_forward(ctx, x, out, l, ctx->kv_cache_len);
        /* 指针交换，避免 memcpy */
        float *tmp = x; x = out; out = tmp;
    }
    
    /* 最终归一化 + argmax */
    ds_rms_norm(x, x, dec->norm, 1, hidden, eps);
    return ds_argmax_matvec_bf16(x, dec->lm_head_bf16, hidden, vocab);
}
```

### 6.4 指针交换优化

注意 `decoder_layer_forward` 中的指针交换：

```c
/* 不做 memcpy，而是交换指针 */
float *tmp = x; x = out; out = tmp;
```

这避免了每次层输出时 1280×4 = 5KB 的内存拷贝。12 层下来节省 60KB 拷贝/步，生成 1000 个 token 就是 60MB 的节省。

## 7. 采样与解码：从 logits 到文字

### 7.1 贪心解码（Greedy）

最简单的解码方式：每次选概率最大的 token。

```c
/* ds_argmax_matvec_bf16: 流式找到最大 logit 的 token ID */
int token = ds_argmax_matvec_bf16(x, dec->lm_head_bf16, hidden, vocab);
```

### 7.2 温度采样（Temperature Sampling）

当 `temperature > 0` 时，引入随机性：

```c
/* 1. 对 logits 应用温度 */
for (int i = 0; i < vocab; i++)
    logits[i] = expf((logits[i] - max_logit) / temperature);

/* 2. Softmax 归一化 */
double sum_exp = 0.0;
for (int i = 0; i < vocab; i++) sum_exp += logits[i];
for (int i = 0; i < vocab; i++) logits[i] /= sum_exp;

/* 3. 加权随机采样 */
float r = (float)rand() / RAND_MAX;
float cum = 0.0f;
for (int i = 0; i < vocab; i++) {
    cum += logits[i];
    if (cum >= r) { token = i; break; }
}
```

> **温度越高**，分布越平坦，生成越随机；**温度越低**，越接近贪心。

### 7.3 重复惩罚（Repetition Penalty）

防止模型重复输出相同内容：

```c
float rp = ctx->repeat_penalty;  /* 1.0 = 无惩罚, 1.1~1.5 常用 */
for (int i = 0; i < token_history_len; i++) {
    int tid = ctx->token_history[i];
    if (logits[tid] > 0) logits[tid] /= rp;   /* 正 logit 缩小 */
    else logits[tid] *= rp;                     /* 负 logit 放大（更负） */
}
```

### 7.4 N-gram 阻断

防止重复输出相同的 n-gram（连续 n 个 token 的组合）：

```c
int ngram_n = ctx->no_repeat_ngram_size;  /* 默认 35 */
if (ngram_n > 0 && token_history_len >= ngram_n - 1) {
    int prefix_len = ngram_n - 1;
    /* 检查历史中是否有匹配的 n-gram 前缀 */
    for (int i = 0; i <= hist_len - prefix_len - 1; i++) {
        int match = 1;
        for (int j = 0; j < prefix_len; j++) {
            if (hist[i+j] != hist[hist_len-prefix_len+j]) { match = 0; break; }
        }
        if (match) {
            /* 禁止完成该 n-gram 的 token */
            logits[hist[i + prefix_len]] = -1e30f;
        }
    }
}
```

### 7.5 Token 解码：从 ID 到文字

BPE tokenizer 把 token ID 解码为 UTF-8 文本：

```c
/* ds_tokenizer.c */
const char *ds_tokenizer_decode(const ds_tokenizer_t *tok, int token_id) {
    /* 查表：id_to_text[token_id] */
    return tok->id_to_text[token_id];
}
```

## 8. 线程池与并行计算

### 8.1 为什么需要线程池？

解码器每步要做大量矩阵×向量运算，每个操作只占 1 个 CPU 核心。多核 CPU 可以**并行处理多个操作**。

### 8.2 ds-ocr 的线程池

```c
/* ds_kernels.c */
void ds_set_threads(int n);  /* 设置线程数（默认: CPU 核数） */
```

**典型使用场景**：

1. **批量 linear**：将 `seq_len × out_dim` 的矩阵乘法按行分给多个线程
2. **QKV 融合**：3 个矩阵乘法（Q、K、V）并行执行
3. **多 crop 并行**：ds-ocr 多裁剪编码时，每个 crop 独立编码

**ds-ocr 多 crop 并行**（`ds_ocr.c`）：

```c
/* 启动并行编码 */
for (int i = 0; i < n_crops; i++) {
    tasks[i].ctx = ctx;
    tasks[i].crop = crops[i];
    pthread_create(&threads[i], NULL, crop_worker, &tasks[i]);
}

/* 等待所有 crop 完成 */
for (int i = 0; i < n_crops; i++) {
    pthread_join(threads[i], NULL);
}
```

### 8.3 qwen-asr 的分块编码

qwen-asr 的音频编码器将长音频分块处理：

```c
int n_chunks = (mel_frames + chunk_size - 1) / chunk_size;
/* 每个 chunk 独立通过 Conv2D stem + Transformer */
for (int c = 0; c < n_chunks; c++) {
    /* 处理 chunk c... */
}
```

### 8.4 fork-join 线程池解剖：任务粒度、静态切分与 barrier

§8.2 只展示了「怎么用」，这里拆开 `ds_kernels.c` 的实现看「怎么做到每次并行只付两次同步」。整池只有约 200 行，三个角色：

**① 常驻 worker：`ds_worker_loop`**

线程池在 `ds_set_threads` 时一次性创建 n−1 个常驻 pthread（主线程自带 tid=0），每个 worker 循环等待条件变量：

```c
/* 等活：cond_work 广播后各 worker 拿到自己的 tid 和 n_threads */
pthread_mutex_lock(&tp.mutex);
while (!tp.has_work) pthread_cond_wait(&tp.cond_work, &tp.mutex);
int tid = ...; int nt = tp.n_threads;
pthread_mutex_unlock(&tp.mutex);   /* 执行期不持锁！ */

fn(tid, nt, arg);                  /* 干活：写区间互不相交，无需加锁 */

pthread_mutex_lock(&tp.mutex);
if (++tp.n_done >= tp.n_threads - 1)   /* 最后完成者负责唤醒主线程 */
    pthread_cond_signal(&tp.cond_done);
pthread_mutex_unlock(&tp.mutex);
```

**② fork-join 入口：`ds_parallel_for(fn, arg)`**

```c
/* 伪代码（真实实现在 ds_kernels.c） */
pthread_cond_broadcast(&tp.cond_work);  /* 入口：唤醒全部 worker */
fn(0, tp.n_threads, arg);               /* 主线程不闲着，自己跑 tid=0 */
while (tp.n_done < tp.n_threads - 1)    /* 出口 barrier（while 防
    pthread_cond_wait(...);             /*  虚假唤醒）*/
```

同步成本 = **入口一次广播 + 出口一次 barrier**，执行期间零锁零原子操作。

**③ 任务切分：静态区间，不是 work-stealing**

以 matvec 的线程体 `ds_matvec_worker` 为例：

```c
int chunk = (t->out_dim + n_threads - 1) / n_threads;  /* 均分，向上取整 */
int start = tid * chunk;
/* 线程 i 只写 y[start..end)，只读 W 的 [start*in_dim, end*in_dim) 区间 */
```

注意本仓库选的是**静态切分**而非 work-stealing，原因有三：

1. **写区间天然互不相交**——按输出行切，各线程写 y 的不同段，执行期才能零锁（①里敢解锁干活的前提）
2. **负载天然均匀**——matvec 每行 FLOPs 相同（都是 in_dim 次乘加），按行均分即负载均分；work-stealing 的任务队列原子操作反而比干活还贵
3. **逐位可复现**——每行的累加顺序不因线程数改变，结果与单线程逐位一致（r4 的 grouped matvec 甚至以「行对」为切分粒度保证这一点，见 §8.5）

work-stealing 适合任务大小不可预测的场景（如并行排序）；推理内核的负载是编译期可知的，静态切分是更便宜的正确选择。

**④ 粒度门槛：小任务不值得进池**

`ds_bf16_to_f32_buf` 给出了明确的阈值注释：n ≥ 65536（256 KB）才进线程池，小转换串行做——因为一次 barrier 的同步开销（微秒级）会吃掉小任务本身的耗时。**任务粒度 < 同步开销时，并行就是负优化**。

### 8.5 并行区合并：把 19 次 barrier 压成 1 次

barrier 是线程池最贵的操作，优化的第二方向（第一是 §8.4 的零锁执行）是**减少并行区个数**。decode 一步 12 层 × 多次 matvec，若每次 matvec 独立进池，barrier 次数会随矩阵个数线性增长。两个真实案例：

**案例 1：grouped matvec（`ds_grouped_matvec_bf16`）**

MoE decode 一步要对 8 个「专家×矩阵」组合做 matvec（6 路由 + 2 共享，各含 gate_up 与 down）。旧实现每专家独立调用 → 每层约 19 个微并行区，barrier 开销淹没矩阵本身。合并后把所有行对折叠成一个并行区：

```c
/* 旧：19 次 ds_parallel_for（每次 1 广播 + 1 barrier）
 * 新：1 次 ds_parallel_for，行对粒度切分，
 *     每行累加顺序不变 → 与串行版逐位一致 */
ds_grouped_matvec_bf16(out, X[], W[], n_units, rows_per_unit, in_dim);
```

**案例 2：QKV 融合（`qkv_ds_matvec_worker`）**

Q、K、V 三张权重表共享同一个输入 x。旧做法 3 次独立 matvec = 3 个并行区；融合后一个并行区同时喂三张权重表，barrier 从 3 次降到 1 次。

**案例 3：融合专家前向（`ds_expert_forward_fused`）**

gate+up 权重预拼接为 `gate_up_fused_bf16`（[2×896, 1280]），x[1280] 一次读入喂 1792 行输出，并行区从分离版的 2 个减为 1 个——注释原话：「线程池只派发 1 个并行区（分离版要 2 个），减少 barrier 次数」。

> **通用规律**：多线程内核的耗时 ≈ 计算时间 + barrier 次数 × 同步成本。当单次计算只有几十微秒时，barrier 次数就是性能本身。优先做「数学等价的合并」（融合、折叠），让每步的并行区个数成为常数。

| **注意力** | MHA (解码器) + GQA (V2编码器) | GQA (解码器) + MHA (编码器) |
| **位置编码** | RoPE + 2D PE + 相对位置 | RoPE + 正弦PE |
| **权重精度** | BF16 (解码器) + F32 (编码器) | BF16→F32预转换 (编码器) + BF16 (解码器) |

### 9.2 代码结构对比

### 9.3 核心差异：MoE vs Dense

ds-ocr 解码器使用 MoE，qwen-asr 使用 Dense FFN。这是两者最大的架构差异：

**qwen-asr Dense 解码器层**：
```c
/* 简单直接的 SwiGLU FFN */
qwen_linear_nobias_bf16(gate_buf, x_norm, l->gate_up_fused_bf16, ...);
qwen_swiglu_multiply(gate_buf, gate_buf, 1, intermediate);
qwen_linear_nobias_bf16(ffn_out, gate_buf, l->down_weight_bf16, ...);
```

**ds-ocr MoE 解码器层**：
```c
/* 复杂的路由 + 多专家 + 共享专家 */
ds_moe_router_bf16(scores, x_norm, layer->gate_weight_bf16, ...);
ds_moe_top_k(top_indices, top_weights, scores, 64, 6);
for (int k = 0; k < 6; k++) {
    ds_expert_forward(expert_outputs + k*hidden, x, ...);
}
ds_expert_combine(output, expert_outputs, top_indices, top_weights, ...);
/* + 共享专家 */
```

## 10. 训练视角对照：推理引擎省掉了什么

本篇反复出现「内存带宽是第一约束」「MoE 稀疏激活省内存」，把这些账放到训练视角下会看到另一番景象——理解这个对照，你就明白为什么训练框架（PyTorch）和推理引擎（本仓库）注定是两种软件。

### 10.1 一次 matmul 在两边各做几件事？

**推理**：只算前向一遍。

$$Y = XW^T \quad \text{（1 次 GEMM，读完权重即可丢弃指针——mmap 下连读都可能是第二次才发生）}$$

**训练**：同一次 matmul 前后还要挂两个额外的 GEMM（反向传播链式法则的结果）：

| 计算 | 公式 | 用途 | 形状（以本仓库 QKV 投影为例） |
|------|------|------|------------------------------|
| 前向 | $Y = XW^T$ | 算输出 | [S,1280]×[1280,3840] |
| 激活梯度 | $dX = dY \cdot W$ | 把梯度传回上一层 | [S,3840]×[3840,1280] |
| 权重梯度 | $dW = dY^T \cdot X$ | 给优化器更新权重 | [3840,S]×[S,1280] |

所以训练的**计算量约为推理的 3×**（经验法则：前向 1、反向 2）。而且前向的所有中间激活（每层的 x_norm、Q/K/V、注意力输出、SwiGLU 的 gate/up……）都必须**留到反向用**——这正是训练显存随 seq 长度平方级/线性级膨胀的根源，也是推理引擎可以完全无视的东西（本仓库 decode 的中间缓冲只有一组预分配的 1280 维向量，`alloc_decoder_buffers`）。

### 10.2 显存账：参数 × 16 字节的推导

以 AdamW + 混合精度（PyTorch 默认）为例，每个参数在训练显存里的「全家福」：

| 项目 | 字节/参数 | 说明 |
|------|----------|------|
| BF16 权重副本（前向用） | 2 | autocast 的工作精度 |
| FP32 master 权重 | 4 | 优化器真正更新的那份（避免低精度累加误差） |
| FP32 梯度 | 4 | $dW$ |
| Adam 动量 m（一阶） | 4 | 梯度的指数滑动平均 |
| Adam 动量 v（二阶） | 4 | 梯度平方的滑动平均 |
| **合计** | **18** | 常被粗略记作 **≈16 B/参数**（不算激活） |

$$\text{训练显存} \approx 16 \times P + \text{激活显存}$$

代入本仓库模型（P ≈ 3B）：

- **推理（本引擎）**：权重 6.2 GB（BF16 mmap，MoE 稀疏访问下物理驻留更少）+ KV 缓存 0.5 GB + 小缓冲 ≈ **7 GB 量级**（实测峰值 RSS 8.6–9.4 GB，docs/05 §10.4）
- **训练**：3e9 × 16 B = **48 GB** 起步，再加激活（batch × seq × hidden × 层数 × 每层十几个中间量）——必须 A100 80 GB 级别或多卡分摊

**16 倍的差距里，有 2× 来自精度（2 B vs 4 B 存储），其余全部来自「优化器状态 + 梯度」这些推理引擎根本不需要存在的东西。**

> **类比**：推理是「闭卷考试只答题」——题目（权重）看一遍就能往下写；训练是「答题 + 对答案 + 改错题本」——每道题都要留草稿（激活）、记错误（梯度）、攒复习重点（Adam 动量）。备考的负担是考试的好几倍，而且草稿纸（激活显存）随题目长度暴涨。

### 10.3 这个对照对本仓库意味着什么

1. **MoE 的省是推理视角的省**：64 个专家只激活 6 个，decode 每步只碰 ~66 MB 专家权重；训练时每个专家都要为「万一被路由到」保留梯度与动量，稀疏性省不了优化器状态——MoE 训练显存仍按全部 3B 参数 × 16 B 起算。
2. **mmap 惰性加载是推理专属的福利**：训练中每个参数迟早被反向触碰 + 被优化器更新，页缓存逃不掉；推理的冷专家（未被路由）永远不产生 page fault（docs/05 §7.6）。
3. **「算力强度」的最优解不同**：训练的 GEMM 足够大（batch × seq 维度撑起 M），天然在 Roofline 计算-bound 一侧；decode 的 matvec 强度≈1，只能靠 docs/05 的带宽优化——这解释了为什么训练框架的优化手册（大 batch、混合精度、梯度检查点）几乎不能照搬给推理引擎。

## 小结

你现在理解了纯 C 推理引擎的实现细节：

1. **Safetensors + mmap**：零拷贝权重加载
2. **BF16**：存储减半，计算全精度，on-the-fly 转换（带宽账见 §3.5–3.6）
3. **三级内核**：generic → NEON/AVX → BLAS，编译时自动选择
4. **KV 缓存**：避免重复计算，GQA 减少缓存大小（分版本字节账见 §5.7）
5. **Prefill vs Decode**：批量 vs 单 token 两种模式
6. **采样**：贪心/温度/重复惩罚/n-gram 阻断
7. **线程池**：零锁静态切分 + 并行区合并（§8.4–8.5）；训练 vs 推理的显存与计算账（§10）
