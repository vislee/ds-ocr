## 1. 为什么量化主要在省"带宽"

decode 单 token 的 FLOPs 很少（~0.9 GFLOP），但**要读的权重**是固定的：
MoE 激活 8 专家 ≈ 60MB + LM head 331MB + 注意力 13MB ≈ 400MB/步。
M4 Max 带宽 ~400GB/s，理想 ~1ms/步；实际 ~25ms/步——差距来自小 matvec
无法饱和带宽。**把 BF16 权重换成 INT8，流量减半，理论 decode 直接翻倍**
（本工程 --int4 在内存受限机器上正是这个收益；带宽富裕的 M4 Max 上
收益被启动开销吃掉，故 README 标注"内存受限设备收益最大"）。

## 2. 数值格式阶梯

| 格式 | 位宽 | 指数/尾数 | 相对误差 | 硬件加速 |
|---|---|---|---|---|
| FP32 | 32 | 8/23 | — | 全平台 |
| BF16 | 16 | 8/7 | ~0.4% | NEON bfdot、AMX、TPU |
| FP16 | 16 | 5/10 | ~0.05% | GPU 友好，动态范围小 |
| INT8 | 8 | — | ~0.4%（per-row） | VNNI/dotprod |
| INT4 | 4 | — | ~2-5%（分组） | llama.cpp k-quants |

BF16 与 F32 共享指数位 → **转换就是移位**（`BF16<<16` 直接按 F32 解释），
这是本工程全篇"零拷贝/廉价转换"的物理基础。

## 3. 本工程的 INT8 per-row 非对称量化

`ds_quantize.c`（`--int4` 开启，名字历史遗留，实为 INT8）：

```
对每行 W[i,:]:
  scale_i = (max - min) / 255          # 行内非对称区间
  zero_i  = -min / scale_i
  q[i,j]  = round((W[i,j] - min) / scale_i)   # u8
反量化: W[i,j] ≈ scale_i * (q[i,j] - zero_i)
```

per-row（通道级）的关键：同一行内权重分布相近，一个 scale 够用；
如果整张张量共用一个 scale，outlier 行会拉爆精度。这是 LLM.int8()/
AWQ 一系工作的共同出发点。实测 RMS 误差 0.007–0.010，OCR 输出与
BF16 一致（见 README 量化表）。

## 4. 量化误差从哪来：outliers

LLM 激活有系统性大 outlier（某些通道幅值大 20-100×），权重相对温和。
所以：权重 INT8 容易、激活 INT8 难。SmoothQuant 的思路是把激活的 scale
数学上"搬"到权重上（W×s，A/s）；AWQ 的思路是识别显著通道做 per-channel
缩放保护。本工程只量化**权重**且每步重算反量化因子进 F32 累加，
避开激活量化的坑——这是"正确性优先"的教学实现。

## 5. mmap 与页缓存：单机部署的隐形引擎

本工程权重全部 mmap 零拷贝：

- 首次访问触发 major page fault（~60-100μs/page）→ madvise(WILLNEED)
  异步预读（decode 层 10/11 在文件布局上"绕回"，必须提前预取）
- `expert_block` 把 64 专家 gate_up 拼成 440MB 连续块：相邻专家共享页，
  page fault 减少 2.4×（v0.9 实测）
- 6.3GB 模型在 36GB 内存机型上第二次运行全部命中 page cache，
  prefill 从 3.3s 掉到 0.7s——**跑分前先想清楚测的是 SSD 还是内存**

进阶：`MADV_RANDOM`/THP/hugepage、锁页（mlock）、以及冷启动优化
（启动时顺序预读全模型 vs 惰性页入，是延迟与内存占用的权衡）。

## 6. 平台分发：NEON bfdot / vshll / AVX-512

`ds_kernels_impl.h` 编译期选择 + 运行时 CPU 探测：

- M1（无 FEAT_BF16）：vshll 移位转换 BF16→F32 再 FMA
- M2+（FEAT_BF16）：`bfdot` 单指令 8 个 BF16 MAC，指令密度 4×
- x86：AVX-512（16 宽）→ AVX2+FMA（8 宽）→ 标量
- 分发只在首次 matvec 时做一次（`ds_dispatch_ensure_init`）

## 7. 与业界方案对照

| 方案 | 特点 | 与本工程差异 |
|---|---|---|
| llama.cpp (GGUF) | 块级 k-quant（q4_K 等），CPU 优先 | 它量化带分组统计+ scales；本工程 INT8 per-row 更简单 |
| vLLM (PagedAttention) | KV cache 分页、continuous batching、多并发 | 本工程单请求单流；批处理是下一步方向 |
| MLC/TVM | 编译期生成内核 | 本工程手写内核，教学透明 |

## 8. 动手实验

1. `--int4` 前后 `--profile` 对比 LM head / MoE 占比变化
2. `DS_BF16_CACHE_MB=6000` 打开 F32 权重缓存，测 prefill 差异（内存换时间）
3. 冷态 vs 热态跑分：`sudo purge` 后首跑，对比第二次
4. 思考题：为什么 INT8 量化对 LM head（129280×1280）收益最大而对
   专家权重收益次之？（提示：两者每步都被全量读取，但 LM head 是
   带宽占用第一大户。）

---

**小结**：量化省的是字节、部署拼的是页缓存与预取。先量化"每步必读的
大权重"，再用连续布局消灭 page fault，最后按平台挑指令集——三步做完，
单机 CPU 推理就能逼近带宽理论上限。
