## 1. 为什么量化主要在省"带宽"：decode 每步的带宽账

### 1.1 每一步到底读了哪些字节

decode（自回归生成）每吐一个 token，都要把"这次前向用到的权重"从内存过一遍——MoE 每层 64 个路由专家只激活 top-6（`DS_DEC_TOP_K = 6`，`ds_ocr.h`），外加 2 个共享专家，每步激活 **8 个专家**。下面账本的每一行都追溯到 `models/DeepSeek-OCR-2/config.json` 与 safetensors 文件头（形状已在 `model-00001-of-000001.safetensors` 的 JSON header 里逐张核对；1 MB = 10⁶ 字节）：

| 每步必读的权重 | 单份形状 | 每步份数 | 每步字节（BF16） |
|---|---|---|---|
| 输入 embedding 查行 | 1×1280×2B | 1 | ≈2.6 KB |
| 注意力 Q/K/V/O 投影 | 各 1280×1280×2B = 3.28 MB | 12 层 | ≈157.3 MB |
| MoE 路由 gate | 64×1280×2B = 0.16 MB | 11 层 | ≈1.8 MB |
| 6 个路由专家 | 每专家 (896×1280 + 896×1280 + 1280×896)×2B = 6.88 MB | 66 | ≈454.2 MB |
| 2 个共享专家 | 每层 (1792×1280 + 1792×1280 + 1280×1792)×2B = 13.76 MB | 11 层 | ≈151.4 MB |
| Layer 0 稠密 FFN | (6848×1280)×3×2B | 1 | ≈52.6 MB |
| LM head | 129280×1280×2B = **331.0 MB** | 1 | ≈331.0 MB |
| **权重合计** | | | **≈1,148 MB** |
| KV cache（F32） | 12 层 × 2(K,V) × 1280 × 4B = 122,880 B/位置 | pos 个 | pos=1000 → ≈123 MB |

- **LM head 独占 331 MB（约 29%）**：词表 129280 × 隐藏 1280 每步全量扫一遍（流式 argmax），是单笔最大的内存事务。它的 F32 副本（sgemm 回退路径用）是 662 MB——引擎日志打印的"631.1 MB"其实是 MiB 口径（`ds_moe_decoder.c` 里 `n * sizeof(float) / 1048576.0` 却标着 `MB`）。
- **专家权重是大头**：每步 8 个专家 ≈ 605.7 MB，占全部流量一半以上——这正是 `--int4` 只量化专家的原因（§3.5）。
- KV cache 不是常数：每多生成一个 token，下一步注意力就多读 122,880 B。V3 的 R-SWA 把它封顶（参考段 + W=128 滑窗），见 05 章第 6 节。

### 1.2 每步的计算量：只有 ~1.15 GFLOP

同样的账按乘加（MAC = 2 FLOP）再算一遍：注意力 157 MFLOP + Layer 0 稠密 FFN 52.6 MFLOP + 11 个 MoE 层（路由 0.16 + 6 专家 41.3 + 共享 13.8 MFLOP/层）607 MFLOP + LM head 331 MFLOP ≈ **1.15 GFLOP**，即"激活参数 ≈5.74 亿 × 2"：

```
算术强度（Arithmetic Intensity，AI） = FLOP ÷ 读字节 = 1.15G ÷ 1.15G ≈ 1.0 FLOP/B
```

每读 1 字节只做 1 次浮点运算——这是 [02-MoE混合专家篇](./02-MoE混合专家篇.md) 第 8 节"参数多不等于计算多"在部署侧的代价。

### 1.3 roofline：理论下限与实测差 8 倍

**roofline 模型**：算术强度低时性能由内存带宽封顶（斜坡段），高时由峰值算力封顶（平台段），交界处叫**脊点（ridge point）= 峰值算力 ÷ 带宽**。判断 decode 在哪一段不需要精确峰值算力：只要处理器的 FLOP/s 超过"带宽 × 1.0"（M2 Pro 上即 >0.2 TFLOP/s），AI≈1 的 decode 就必然落在斜坡段——**内存受限（memory-bound）**：

```
M2 Pro:   1,148 MB ÷ 200 GB/s ≈ 5.7 ms/步    实测 23.35 ms/步（05 章 profiler）→ 效率 ~24%
M4 Max:   1,148 MB ÷ 410 GB/s ≈ 2.8 ms/步    实测 ~21-25 ms/步（README 42-47 tok/s）→ 效率 ~12%
（带宽为官方规格：M2 Pro 200 GB/s；14 核 M4 Max 410 GB/s，满血 16 核 546 GB/s）
```

差距从哪来？（1）**小 matvec 饱和不了带宽**：每行只有 1280 个元素、逐行流水，在途读请求深度不足以打满 200-410 GB/s；（2）BF16→F32 转换、线程同步、路由/top-k/softmax/采样这些串行小算子无法与读权重重叠；（3）冷态还有页故障（§5）。反过来，热态的大 matvec 可以逼近带宽——08 章实测流式 argmax 全热时 1.6 ms（331 MB ÷ 200 GB/s = 1.65 ms，贴着下限），冷时 8 ms。**量化省的是"每步必读字节"这条下限，页缓存与预取决定你能多接近它。**

### 1.4 `--int4` 的真实收益边界

量化把 2 字节的 BF16 换成 1 字节的 INT8，**但 `--int4` 只量化专家权重**（§3.5）：

```
BF16 每步:  157.3(注意力) + 1.8(路由) + 605.7(专家) + 52.6(Layer0) + 331.0(LM head) ≈ 1,148 MB
INT8 每步:  157.3 + 1.8 + ~306.6(专家量化+元数据) + 52.6 + 331.0 ≈ 849 MB   → 流量 ×0.74
理论上限:   decode ≈ 1.35×（不是 2×——专家只占每步流量的 53%）
```

- **内存收益可能比速度收益更值钱**：专家权重从 ≈4.77 GiB 变成 2.34 GiB，**净省 ≈2.4 GB 驻留内存**——在 16 GB 机器上这可能决定"跑得动"还是"开始换页"。所以 README 标注"INT8 建议用于内存受限设备与无 BF16 硬件的 x86"。
- **在 M2+ 上它可能不提速**：M2+ 有硬件 `bfdot`（§6.3），软件 INT8 反量化 + FMA 在单 token decode 上跑不过它；README 的 M2 Pro 对照表里两者总耗时相同（71.1s vs 71.1s）。量化收益取决于"带宽"与"指令效率"哪个是当前短板。

> README 量化表写"Expert weight 3176 MB → 2399 MB（1.3× smaller）"，两个数字口径不一致：3176 是 BF16 **gate_up_fused** 总量（(64×4.59 MB + 9.18 MB)×11 层 = 3,330,539,520 B = 3176.6 MiB，来自引擎日志）；2399 是 INT8 **gate_up + down** 总量（2,515,634,176 B = 2399.0 MiB）。同口径比较都是 ≈2.0×：gate_up+down 为 4763.4 → 2399.0 MiB；gate_up 单项为 3176.6 → 1598.0 MiB。

## 2. 数值格式阶梯：FP32 / BF16 / FP16 / INT8 / INT4

### 2.1 位布局：三种浮点一格之差

```
FP32 (1+8+23)   s eeeeeeee mmmmmmmmmmmmmmmmmmmmmmm
BF16 (1+8+7)    s eeeeeeee mmmmmmm                 ← 指数与 FP32 完全相同
FP16 (1+5+10)   s eeeee mmmmmmmmmm                 ← 指数只有 5 位
INT8            iiiiiiii                           ← 均匀格点，靠 scale/offset 映射
```

| 格式 | 位宽 | 指数/尾数 | 相对舍入误差(半 ulp) | 表示范围 | 硬件加速 |
|---|---|---|---|---|---|
| FP32 | 32 | 8/23 | — | ±3.4×10³⁸ | 全平台 |
| BF16 | 16 | 8/7 | 2⁻⁸ ≈ 0.39% | ±3.4×10³⁸ | NEON bfdot、AMX、TPU |
| FP16 | 16 | 5/10 | 2⁻¹¹ ≈ 0.049% | ±65504 | GPU 原生 |
| INT8 (per-row) | 8 | — | ≈0.4%（§3.2 推导） | 256 级均匀格点 | VNNI/dotprod |
| INT4 (分组) | 4 | — | ≈6.7% 理想 / 0.13-0.21 实测（§2.3） | 16 级 | llama.cpp k-quants |

BF16 与 FP16 同为 16 位，取舍相反：BF16 尾数少 3 位（精度低 ~8 倍）但指数与 FP32 等宽，**永远不会像 FP16 那样在大权重处上溢**（>65504 变 Inf）——LLM 权重的动态范围远比"多两三位尾数"重要，这是全链路选 BF16 的原因（推导见 03 章第 3 节）。

### 2.2 BF16 ←→ F32：一条移位指令

BF16 的位模式就是 FP32 截掉低 16 位尾数，所以 **BF16 → F32 只是"左移 16 位补零"，F32 → BF16 是"加 0x8000 舍入后右移 16 位"**——没有任何乘除，这是本工程"mmap 零拷贝 + 在线转换"的物理基础：

```c
/* ds_kernels_neon.c — ds_bf16_to_f32_neon（节选） */
uint16x8_t bf = vld1q_u16(src + i);                 /* 读 8 个 BF16 */
uint32x4_t lo = vshll_n_u16(vget_low_u16(bf), 16);  /* 逐元素左移 16 位 → F32 位模式 */
vst1q_f32(dst + i, vreinterpretq_f32_u32(lo));      /* 按位重解释为 F32，零乘加 */

/* ds_kernels_neon.c — ds_f32_to_bf16_neon（节选）: 加 0x8000 再截半 = round-to-nearest-even */
uint32x4_t b0 = vaddq_u32(vreinterpretq_u32_f32(v0), vdupq_n_u32(0x8000));
uint16x4_t r0 = vshrn_n_u32(b0, 16);
```

标量版同样只有一行：`uint32_t f32_bits = ((uint32_t)w[i]) << 16;` 再 memcpy 进 float——全工程的 BF16 matvec（NEON/AVX/标量）都在循环体内做这件事。

### 2.3 INT8/INT4 的误差从哪来

浮点舍入是**相对误差**（随指数缩放），INT 量化的误差是**绝对误差**：256（或 16）个格点均分数值区间，格距 = scale，最大误差 = scale/2，均匀分布假设下误差 RMS = scale/√12。对均匀分布在 [-1,1] 的权重（RMS = 1/√3 ≈ 0.577，range/RMS ≈ 3.46），INT8 per-row 的相对 RMS ≈ (2/255/√12)/0.577 ≈ **0.39%**；INT4（15 级）理想值是 (2/15/√12)/0.577 ≈ **6.7%**。真实权重有长尾（range/RMS 远大于理想值），误差按同样的比例放大——这正是 `ds_quantize.h` 里"INT8 RMS < 0.01（README 实测 0.007-0.010），对比 INT4 的 0.13-0.21"几个数的来历。真正麻烦的不是权重而是激活（§4）。

## 3. 本工程的 INT8 per-row 非对称量化

### 3.1 量化公式与真实代码

实现全部在 `ds_quantize.c`（约 413 行），核心是逐行（per-row）非对称 INT8：

```
对每行 W[r,:]:
  min_r = min(W[r,:]),  max_r = max(W[r,:])
  scale_r  = (max_r - min_r) / 255        # 行内非对称区间均分 255 格
  offset_r = min_r                        # 存 min 而不是 zero-point
  q[r,j]   = clamp(round((W[r,j] - min_r) / scale_r), 0, 255) - 128
反量化:  W[r,j] ≈ scale_r × (q[r,j] + 128) + offset_r
```

```c
/* ds_quantize.c — int8_quantize_row（节选） */
float range = max_val - min_val;
float scale = range / 255.0f;
if (scale < 1e-10f) scale = 1e-10f;      /* 全零行保护：防除零 */
*row_offset = min_val;                   /* offset 直接存 min */
float inv_scale = 1.0f / scale;          /* 预计算倒数：循环内只做乘法 */
for (int c = 0; c < in_dim; c++) {
    int v = (int)roundf((values[c] - min_val) * inv_scale);
    if (v < 0) v = 0; if (v > 255) v = 255;
    qrow[c] = (int8_t)(v - 128);         /* [0,255]→[-128,127]，NEON 端加常量还原 */
}
```

结构体 `ds_int4_block_t`（名字同为历史遗留）每行只存 2 个 F32 元数据：`scale[out_dim]` + `offset[out_dim]`。

### 3.2 拿 4 个权重手算一遍

设某行权重的 4 个值 `W = [0.50, -0.62, 0.13, -0.05]`（min = -0.62，max = 0.50，range = 1.12，scale = 1.12/255 ≈ 0.004392，offset = -0.62）：

```
量化:  q(0.50)  = round((0.50+0.62)/0.004392) = 255 → int8 = 127
       q(-0.62) = round(0/0.004392)           =   0 → int8 = -128
       q(0.13)  = round(0.75/0.004392)        = 171 → int8 =   43
       q(-0.05) = round(0.57/0.004392)        = 130 → int8 =    2

反量化: 0.004392×255 - 0.62 =  0.5000（无误差）;  0.004392×171 - 0.62 =  0.1311（误差 +0.0011）
        0.004392×130 - 0.62 = -0.0490（误差 +0.0010）
最大可能误差 = scale/2 ≈ 0.0022，任何值都不例外
```

### 3.3 matvec 的分解技巧：把反量化拆成两个归约

朴素做法先逐元素反量化再乘加——两遍内存流量。`ds_quantize.c` 把公式展开：

```
y[r] = Σ_j (scale_r·(q[r,j]+128) + offset_r)·x[j]
     = scale_r · Σ_j (q[r,j]+128)·x[j]  +  offset_r · Σ_j x[j]
       └──── dot 归约（4 路 NEON 累加）────┘  └─ x_sum 归约 ─┘
```

两个归约互相独立，一遍扫描同时完成，最后 `y = scale·dot + offset·x_sum`：

```c
/* ds_quantize.c — int8_matvec_neon（节选） */
int8x16_t qv = vld1q_s8(qrow + c);                         /* 读 16 个 int8 */
int16x8_t q0 = vaddq_s16(vmovl_s8(vget_low_s8(qv)), bias); /* +128 还原量化级 */
float32x4_t f0 = vcvtq_f32_s32(vmovl_s16(vget_low_s16(q0)));/* int16→int32→F32 */
acc0 = vmlaq_f32(acc0, f0, xv0);                           /* FMA 累加 dot */
xsum = vaddq_f32(xsum, vaddq_f32(xv0, xv1));               /* 顺便累加 x_sum */
y[r] = scale_v * dot_sum + off_v * x_sum;                   /* 每行一次收尾 */
```

这就是"**只量化权重 + 每步重算反量化因子**"：内存里只有 1 字节的 q，scale/offset 在寄存器里逐行乘出来，累加全程 F32。

### 3.4 量化粒度：per-tensor / per-row / per-group

| 粒度 | 元数据开销 | 精度 | 适用 |
|---|---|---|---|
| per-tensor（全张量 1 组 scale） | 8 B/张量 | 差：outlier 行拉爆格距 | 激活、分布均匀的张量 |
| per-row（本工程） | 8 B/行（scale+offset） | 好：行内分布相近 | 权重（行 = 一个输出通道） |
| per-group（如 g=32/128） | 8 B/32~128 值 | 最好 | INT4 必需（格太粗） |

同一行内权重分布相近（同一输出通道的连接强度），一个 scale 够用；整张张量共用一个 scale 时，个别大幅值行会撑大格距、牺牲其余行——这是 LLM.int8()/AWQ 的共同出发点。per-row 的代价可忽略：gate_up_fused [1792,1280] 的元数据是 1792×8B = 14 KB，只占 4.59 MB 权重的 0.31%。

### 3.5 `--int4` 的覆盖范围、精度与真实身份

**先回答命名问题：`--int4` 里没有任何 INT4。** 证据链：`ds_quantize.c` 文件头自述"Per-Row INT8 Weight Quantization"，`int8_quantize_row` 按 255 级量化（INT4 只有 15 级）；`ds_int4_quantize_bf16()` 注释写着*"将 BF16 权重量化为 INT8（'Int4' 只是历史命名）"*；`main.c` usage 文本为 `--int4  INT8 quantize MoE expert weights`，`ds_ocr.h` 的 `int4_enabled` 注明"flag name is --int4 for compatibility"；README 章节标题就是"INT8 Quantization (`--int4`)"。仓库里不存在任何 4-bit 数据路径——真 INT4 属于未来工作（05 章第 9 节）与 llama.cpp 的 k-quant（§7）。

覆盖范围（`ds_ocr.c: ds_quantize_moe_int4`）：11 个 MoE 层（Layer 1-11）的 **64 个路由专家的 gate_up_fused 与 down_weight + 2 个共享专家**。Layer 0 稠密 FFN、所有注意力投影、路由 gate、LM head 保持 BF16——前三者每步流量占比小或对精度敏感，LM head 则没有 INT8 matvec 路径。量化发生在 `ds_load` 之后、首次推理之前，一次性 3-8 s（README），产物是约 2.34 GiB（引擎日志口径 2399 MB）的堆上 INT8 副本（`experts_int4[]`），原 BF16 mmap 页此后不再被 decode 触碰。

精度（三处口径，全部可溯源）：

| 来源 | RMS 相对误差 | 说明 |
|---|---|---|
| `ds_quantize.h` 门槛 | < 0.01 | 设计验收线 |
| 本机重跑 `./test_int4`（固定种子合成权重） | 0.0043-0.0044 | 三个典型形状全部 PASS，压缩比 2.0× |
| README 量化收益表 | 0.007-0.010 | 真实权重的历史实测口径 |

三者一致：0.4% 量级的相对误差（§2.3 理论值 0.39% 正落在区间内），OCR 输出与 BF16 一致（README："OCR accuracy ✅ Matches BF16"）。

### 3.6 如果要真 INT4

INT4 意味着 15 级格点（理想 6.7%、真实权重 13-21%，§2.3），per-row 的一个 scale 救不回来，必须 per-group（每 32/64 值一组 scale+zero，q4_K 还用二级 scale）+ 校准数据修正显著通道（GPTQ/AWQ）；代价还有 4-bit 跨字节的打包/解包与反量化次数×4。这些都超出"单机教学引擎"的边界，所以本工程停在"INT8 per-row + 完整误差度量（`ds_int4_quant_error_rms`）+ `test_int4` 四项单元测试"这一格。

## 4. 量化误差从哪来：outliers 与激活量化难题

### 4.1 激活的系统性 outlier

LLM.int8() 的核心观察：激活（注意力/FFN 的中间结果）存在**系统性的大幅值通道（outlier，异常值）**——少数固定维度的幅值是其他通道的 20-100 倍，且跨 token 持续出现；权重本身相对温和。后果不对称：**权重 INT8 容易，激活 INT8 难**——权重分布平坦，per-row scale 就够；激活按同样方式量化时，outlier 通道会撑大整个格距，其余 99% 通道的精度崩掉。

### 4.2 两类解法的数学

**SmoothQuant** 把 outlier 压力从激活"搬"到权重——对每个通道 j 取缩放因子 s_j，插入数学恒等变换：

```
Y = X·W  =  (X·diag(s)) · (diag(s)⁻¹·W)  =  X'·W'
其中 s_j = max|X_j|^α / max|W_j|^(1-α)，α ∈ [0.5, 0.9]
```

α 越大，激活 X' 被压得越平（好量化），权重 W' 被反向放大（难量化）——用一个 α 在两端换平衡，使两侧都能过 INT8；W' 要离线重写进权重文件，这是"校准/转换"的代价。

> 算例直觉：设通道 7 的激活幅值是别的 64 倍。取 s₇ = 32，则 X'₇ = X₇/32 落回正常
> 范围，而 W'₇ = 32·W₇ 也只是放大到普通量级——两边各自都能被 INT8 的 256 级格点
> 覆盖。s 从激活/权重幅值统计出，这正是"校准集"的用途。

**AWQ** 不搬移而做**显著通道保护**：~1% 的权重通道对应大幅值激活、对模型质量贡献最大；它用同一恒等式，但 s 取自激活幅值统计、专保护显著通道，并在量化误差分析下最优化 s，再配混合精度（显著通道保留 FP16）——"权重-only、无需训练"，与本工程约束最接近。

### 4.3 本工程的取舍

本工程绕开了整个激活量化问题：**只量化权重，激活与累加全程 F32**（§3.3 的 matvec 里 x 从头到尾是 float）。代价是每步多算 scale·dot + offset·x_sum 的收尾（每行几条指令），换来不需要校准数据、不修改权重文件，以及一个干净的精度基线——`ds_bf16_simulate_python` 打开时中间结果截断回 BF16 以对齐 PyTorch autocast 的数值行为（见 05 章第 10 节"回归门控"）。这是"正确性优先"的教学实现；要往下走一步（激活也 INT8），SmoothQuant/AWQ 是必经之路。

## 5. mmap 与页缓存：单机部署的隐形引擎

### 5.1 机制：虚拟内存、page cache 与两种缺页

**mmap（memory-mapped I/O，内存映射文件）**把文件挂到进程虚拟地址空间，`read()` 的"内核缓冲区→用户缓冲区"拷贝消失，权重文件本身就是数据结构：

```
进程虚拟地址                物理内存（page cache，页缓存）    磁盘
┌─────────────┐  页表映射   ┌──────────────────┐
│ mmap 区域    │──按 16KB ──▶│ 文件页(干净页)    │◀── 缺页时按需读入
│ (6.3GB)     │   一页一表项 │ 或匿名页          │
└─────────────┘             └──────────────────┘
首次触碰某页 → Page Fault（缺页中断）:
· minor fault: 页已在 page cache（如上一轮进程读过）→ 只建映射，~微秒级
· major fault: 页在磁盘 → 触发块 I/O → Apple Silicon ~60μs/页（ds_moe_decoder.c 注释口径）
```

加载链（格式详见 03 章第 2 节）：`safetensors_open()` 对每个分片 `mmap` 整个文件 → `safetensors_get_bf16_direct()` 返回 mmap 区域内的**裸指针**（零拷贝），matvec 时逐元素 `<<16` 转 F32。Apple Silicon 页大小 **16 KB**（`getconf PAGESIZE` = 16384；x86_64 Linux 为 4 KB）——6.31 GiB 单分片权重 ≈ **41.4 万个页表项**，这是理解后面所有数字的尺度。

### 5.2 madvise(WILLNEED)：把随机缺页变成异步预读

decode 每步只访问 8 个专家的权重，模式是"每层随机跳 6 个位置"——预读最不友好。不干预时，冷态下每个专家的 6.88 MB（BF16）要按 16 KB 逐页 major fault：420 页 × 60 μs ≈ 25 ms，光一层就吞掉整个步预算。解法是 `madvise(MADV_WILLNEED)`——告诉内核"这片马上要用"，异步预读把"同步逐页 fault"变成"计算与 I/O 重叠"：

```c
/* ds_moe_decoder.c — CPU decode 路径（节选）：预取下一个专家的三块权重 */
if (k + 1 < top_k) {
    int next_id = top_indices[k + 1];
    size_t inter_bytes = (size_t)hidden * moe_inter * 2;
    madvise((void *)layer->experts[next_id].gate_weight_bf16, inter_bytes, MADV_WILLNEED);
    madvise((void *)layer->experts[next_id].up_weight_bf16,   inter_bytes, MADV_WILLNEED);
    madvise((void *)layer->experts[next_id].down_weight_bf16, inter_bytes, MADV_WILLNEED);
}
```

预取窗口取"下一个专家"而非"下面 6 个"：madvise 本身有内核开销，窗口太大反而把还没轮到的页顶掉 page cache 里的热页。

### 5.3 expert_block 连续块：一次 2.4× 的实测与其退场

v0.9 曾把每层 64 个路由专家 + 共享专家的 gate_up_fused 权重从 mmap **拷贝**进一块 `malloc` 的连续内存（`expert_block_bf16`），动机：相邻专家尾首共享 16 KB 页；一次 `madvise` 覆盖 top-6 的地址区间；Metal 路径可按块零拷贝注册。[05-性能优化实战篇](./05-性能优化实战篇.md) 第 4.3 节实测：decode 期间 page fault 开销从 ~351 ms 降到 ~121 ms（**2.4×**）。

但 r2 又把它拆掉（05 章第 10.4 节）：3.33 GB 连续块是 mmap 之外的第二份驻留（峰值 RSS ~11 GB 的主要成分），DS_RSS_PROBE 探针证明高水位在加载结束即成立，事后 madvise 救不回来。删掉拷贝、decode 改走 mmap 分离权重（gate/up 分别 matvec，逐元素数学等价）后：RSS −3.1 GB，decode 反而全线 +10-16%（页缓存命中率改善）。**教训**：连续布局消灭缺页的收益是真实的，但"拷贝"本身有内存与缓存污染的代价；r2 后的方案是"保持 mmap + 逐专家 madvise 预取"。顺带修正一个流传数字："440 MB"是每层 **64 个路由专家 gate+up+down** 的 BF16 总量（64×6.88 MB = 440.4 MB），v0.9 连续块的实际内容只有 gate_up_fused（302.8 MB/层，11 层共 3.33 GB）。

### 5.4 加载后的页回收：MADV_DONTNEED

反向操作同样重要。权重加载会把整份 mmap 摸一遍（每个 tensor 都读过），清洁文件页全部驻留；其中专家/编码器权重已拷贝或 F32 化，mmap 源页不再被读。`multi_safetensors_madvise_unused()`（`ds_safetensors.c`，`DS_NO_MADVISE=1` 可关）在加载完成后对每个分片 `madvise(..., MADV_DONTNEED)` 立即归还 ~4-5 GB 物理页；`ds_drop_source_pages()`（`ds_ocr.c`）在 LM head F32 化后归还那 331 MB BF16 源页。它们是 MAP_PRIVATE 的**干净**文件页——此后任何触碰都从 page cache 廉价重入（minor fault，无磁盘 I/O），正确性不受影响。

### 5.5 冷态 vs 热态：跑分前先想清楚测的是 SSD 还是内存

mmap 的性能下限由存储介质决定、上限由带宽决定，同一个二进制可以差出数倍：**热态**（第二次运行，6.3 GB 全在 page cache）所有缺页都是 minor，prefill/decode 逼近带宽下限——README M4 Max 的 prefill 0.7-1.9 s 区间里，位置主要由序列长度决定，热度决定落在区间哪一端；**冷态**（刚开机或清过缓存）首次触碰变成 major fault，读放大由预读策略决定，macOS 用 `sudo purge` 清页缓存（§9 实验 3）。所以基准测试要固定"冷/热"状态并如实标注；对照实验则要主动制造两态（`sudo purge` → 冷态一跑 → 立刻热态一跑）。

### 5.6 进阶开关

- `MADV_RANDOM`：声明访问模式为随机、关闭内核默认 readahead（预读）；本工程用显式 WILLNEED 替代，粒度更可控。
- 透明大页（THP，Transparent Huge Page，Linux）：2 MB 页把 41 万页表项压到几千，TLB（Translation Lookaside Buffer，地址翻译缓存）未命中率下降，代价是缺页粒度变粗、内存碎片化；Linux 部署值得用 `madvise(MADV_HUGEPAGE)` 做 A/B。
- `mlock`：把权重页锁进物理内存防换出——内存受限机型上反而危险（挤掉其他进程），本工程刻意不用；DONTNEED 机制已给了"随时可放弃驻留"的自由。
- 冷启动两个极端：启动时顺序预读全模型（TTFT 变长换稳定延迟）vs 完全惰性页入（首 token 快、前几步抖动）。本工程取中间态：只对"马上要用"的窗口 WILLNEED，加载后的闲置页 DONTNEED 退场。

## 6. 平台分发：NEON bfdot / vshll / AVX-512

### 6.1 完整的决策树

热内核（matvec/argmax/点积）的分发是"**编译期定候选，运行时定人选**"两级结构（`ds_kernels_impl.h` + `ds_kernels.c: ds_kernels_dispatch_init`）：

```
编译期（决定哪些实现被编进二进制）
├─ __ARM_NEON 定义？
│   ├─ 是：编入 vshll 版 +（若 __ARM_FEATURE_BF16_VECTOR_ARITHMETIC）bfdot 版
│   │        函数指针默认指向 vshll 版（安全的下限）
│   └─ 否：只剩 generic 版
└─ x86：__AVX2__ && __FMA__ ？ → 编入 AVX 文件
          └─ 文件内 __AVX512F__ && __AVX512BW__ ？ → 512 位实现，否则 256 位实现

运行时（ds_kernels_dispatch_init，首次 matvec 前完成一次）
├─ ARM + Apple：sysctlbyname("hw.optional.arm.FEAT_BF16")
├─ ARM + Linux：getauxval(AT_HWCAP2) & HWCAP2_BF16
│     ├─ 有 FEAT_BF16 → 指针切到 bfdot 版（"BF16 dispatch: bfdot path"）
│     └─ 无（如 Apple M1）→ 保持 vshll 版（"vshll path (no FEAT_BF16)"）
└─ x86：不再运行时探测——AVX-512/AVX2 由编译器按 -march=native 决定
```

ARM 上多编一份 bfdot 只在 `__ARM_FEATURE_BF16_VECTOR_ARITHMETIC`（由 `-mcpu`/`-march` 决定）时发生；x86 上 AVX-512 与 AVX2 二选一编译。**首次调用惰性初始化**由 `ds_dispatch_ensure_init()` 兜底（未初始化则调一次 dispatch_init），任何入口直接调 matvec 都安全。本机（Apple Silicon M2+）运行 `./test_int4` 的第一行输出即分发结果：`BF16 dispatch: bfdot path (FEAT_BF16 detected)`。

### 6.2 vshll 路径：M1 的"移位 + FMA"两拍

没有 FEAT_BF16 的芯片（Apple M1 等）上，BF16 乘加拆两拍：

```c
/* ds_kernels_neon.c — vshll 路径（节选） */
uint16x8_t r0 = vld1q_u16(w0 + k);                           /* 读 8 个 BF16 */
acc0 = vfmaq_f32(acc0,
    vreinterpretq_f32_u32(vshll_n_u16(vget_low_u16(r0), 16)), /* 左移 16 位→F32 */
    x0);                                                      /* 再 FMA */
```

`vshll_n_u16` 是 §2.2 移位原理的指令级体现：一条指令把 4 个 u16 加宽成 u32 并左移 16 位，位模式即 F32。每 4 个 BF16 MAC 花 2 条指令（vshll + vfma）。

### 6.3 bfdot 路径：M2+ 的"单指令 8 MAC"

ARMv8.6-A 的 FEAT_BF16 提供 `bfdot`（BFloat16 DOT product）：

```c
/* ds_kernels_neon.c — bfdot 路径（节选，Apple clang 15 缺 bfloat16 内建，用内联汇编） */
static inline float32x4_t bfdot_f32(float32x4_t acc, bfloat16x8_t a, bfloat16x8_t b) {
    __asm__("bfdot %0.4s, %1.8h, %2.8h" : "+w"(acc) : "w"(a), "w"(b));
    return acc;
}
a0 = bfdot_f32(a0, vld1q_bf16(BP(w0+k)), xb0);   /* 8 个 BF16 MAC → 4 个 F32 累加 */
```

一条 `bfdot` 完成 8 个 BF16 乘加进 4 个 F32 累加器——同样的 8 个 MAC，vshll 路径要 4 条指令，**指令密度差 4×**。细节：bfdot 两个操作数都必须是 BF16，所以 x（F32）要先压窄（`f32x8_to_bf16x8`），权重保持文件位模式不转——转换开销集中在对 x 的少量压窄上。

### 6.4 x86：AVX-512 → AVX2 → 标量

x86 没有 BF16 乘加，仍是移位思想：

```c
/* ds_kernels_avx.c — AVX-512 路径（节选） */
__m256i r0a = _mm256_loadu_si256((const __m256i *)(w0 + k));         /* 16 个 BF16 */
a0 = _mm512_fmadd_ps(_mm512_castsi512_ps(
        _mm512_slli_epi32(_mm512_cvtepu16_epi32(r0a), 16)), xv0, a0); /* 加宽+左移+FMA */
```

`_mm512_cvtepu16_epi32` 加宽 16 路 + `_mm512_slli_epi32` 左移 16 位 = NEON `vshll` 的 x86 对应物。BF16 matvec 主循环 16 宽（AVX-512F+BW），无 AVX-512 时编出 AVX2+FMA 的 8 宽版本，最后是 `ds_kernels_generic.c` 的标量参考实现。Makefile 在 Linux/x86 上用 `-march=native`，同一份代码在老至强上自动落回 AVX2 甚至 generic——这正是编译期分发树存在的意义。

### 6.5 与量化的关系

分发层对量化透明：`ds_int4_matvec` 内部同样调 `ds_dispatch_ensure_init()` 和线程池，但 INT8 路径目前只有 NEON（widen→F32→vmla）与 generic 两种（见 `ds_quantize.c`），没有 bfdot/AVX-512 专属版本——这是 §1.4"M2+ 上 INT8 可能跑不过 BF16"的直接原因之一：BF16 主路径有硬件点积，INT8 靠软件反量化。

## 7. 与业界方案对照：llama.cpp、vLLM、MLC

| 方案 | 核心技术 | 解决什么问题 | 与本工程的差异 |
|---|---|---|---|
| llama.cpp（GGUF） | k-quant 块级量化（q4_0/q4_K：32 值一块 + 二级 scale），mmap，CPU 优先 | 在 4-bit 级别压住精度损失：块内统计 + 6-bit 二级 scale，配 imatrix 校准 | 本工程 per-row INT8 无分组统计、不校准；GGUF 自带元数据，safetensors+config.json 更"原始"，利于教学 |
| vLLM（PagedAttention） | KV cache 按 block 分页（块表间接寻址）、continuous batching、张量并行 | 多并发下的吞吐与显存碎片：不同请求的 KV 混存于固定小块，消除预留浪费 | 本工程单请求单流，KV 是连续 `[layers, max_seq, kv_dim]` F32 数组（4096 槽，V3/V4 8192）；并发调度是下一步方向 |
| MLC / TVM | 编译期生成平台内核（Metal/Vulkan/CUDA），元调度 | 把"每个平台最优内核"从手写变成编译产物，覆盖 GPU/手机 | 本工程手写三套内核（§6），教学透明是第一目标；MLC 的 group-wise 量化同样需要校准 |

三个方案对应三道部署难题：llama.cpp 管"**权重有多小**"（量化格式学），vLLM 管"**并发有多高**"（KV 与调度学），MLC 管"**内核有多快**"（编译学）。理解这三条线，再读任一项目源码都能对号入座。

本工程的教学取舍也就在这三条线上：**不做 k-quant**——分组统计与校准集会把"量化"从一道数学题变成一条数据管线，掩盖"字节数决定带宽"这条主线；**不做 batching**——单请求单流让 decode 的带宽账保持纯净（批量会摊薄每步流量，账就没法逐项对上）；**不引编译器**——手写三套内核 + `ds_kernels_impl.h` 的函数指针表，让"编译期定候选、运行时定人选"的每个分支都肉眼可读。这些不是能力上限，而是把一层楼盖透：先能在纸面上算出 §1.1 的每一行，再去抄 llama.cpp 的 `ggml-quants.c` 或 vLLM 的 `block_manager.py` 才有对照系。KV 侧本工程做到了 R-SWA 恒定缓存（05 章第 6 节），这是它对第二道题的回答。

## 8. 部署实践：内存账与机型适配

### 8.1 一台机器上的完整内存账

仓库里四个可部署模型（`du` 实测权重目录，safetensors 均为单分片 BF16）：

| 模型 | 权重目录 | 解码器差异 | 部署要点 |
|---|---|---|---|
| DeepSeek-OCR（V1） | 6.2 GiB | SAM+CLIP 双编码器（无滑动窗口） | 编码器 F32 副本偏大（两套视觉栈） |
| DeepSeek-OCR-2（V2） | 6.3 GiB | DeepEncoder V2（Qwen2-0.5B） | 本篇账本的主角：单分片 6,778,573,880 B ≈ 6.31 GiB |
| Unlimited-OCR（V3） | 6.3 GiB | R-SWA 滑窗，KV 上限 8192 | KV cache 翻倍（≈960 MiB），长文档场景 |
| Unlimited-OCR-2（V4） | 6.2 GiB | DASH 块稀疏注意力 | 同 V3 的 KV 尺度 |

以 V2 为例，一次完整推理的驻留内存（RSS，Resident Set Size）构成：

```
权重 mmap 驻留     ≤ 文件大小（只有被触碰的页驻留；加载摸全 → 一度 ≈ 全量）
  - 加载后 MADV_DONTNEED 归还已拷贝/F32 化的源页（§5.4，~4-5 GB）
编码器 F32 副本    SAM/CLIP/DeepEncoder 权重按 F32 加载（形状小，精度敏感）
KV cache           V1/V2: 4096 槽 × 122,880 B/位置 ≈ 480 MiB；V3/V4 8192 槽 ≈ 960 MiB
LM head F32 副本   仅 sgemm 回退路径（温度采样/ngram 过多时）触发一次，+662 MB
--int4 副本        +≈2.4 GB INT8（此后专家 BF16 页退场，净省 ≈2.4 GB）
峰值口径           05 章第 10.4 节实测（r2 去拷贝后）：8.63-9.43 GB
```

两个 mmap 部署的通用规律在此得到验证：**RSS 可以超过文件大小**（F32/量化副本是 mmap 之外的堆内存），**ru_maxrss 是单调高水位**——事后 madvise/free 降低的是"当下驻留"，不改写峰值记录；探针（`DS_RSS_PROBE=1`）要在加载各阶段打点才能定位峰值时刻。

### 8.2 内存受限 vs 带宽富裕：什么时候开 `--int4`

| 机型 | 短板 | `--int4` 的效果 | 依据 |
|---|---|---|---|
| 16 GB 笔记本（如 M2 Pro） | 内存容量逼近上限 | RSS 净省 ≈2.4 GB，避免换页级联卡顿；速度收益次之 | README："recommended for memory-constrained devices" |
| 36 GB 桌面机（M4 Max）+ M2+ bfdot | 不缺带宽也不缺内存 | decode 与 BF16 基本持平（README M2 Pro Metal 表：71.1s vs 71.1s）；多付 3-8 s 量化与 2.4 GB 副本 | §1.4 + §6.5 |
| x86（无 BF16 硬件） | BF16 靠移位+FMA 两拍模拟 | INT8 与 BF16 每字节指令数同量级，带宽减半开始兑现 | §6.4/§6.5 |

推而广之：**量化收益 = 省下的字节 × 带宽短板程度 − 反量化指令代价**。部署前先用 §1.1 的账本判断目标机型落在哪一格，再决定要不要为省 2.4 GB 付出精度与启动时间。

### 8.3 冷启动的两难与工程折中

"首 token 延迟（TTFT）"与"步间延迟抖动"不可兼得：全量预读（启动时把 6.3 GB 顺序读一遍）TTFT 变长但首步起就稳定；完全惰性页入（本工程默认）TTFT 最短，但前几步 decode 要现场付 major fault。本工程的折中是窗口化 WILLNEED（§5.2）+ 加载后 DONTNEED 回收（§5.4）。若部署形态是"常驻服务"，预热脚本（跑一次空图推理让 page cache 全热）是零代码的替代方案；若是"命令行一次性任务"，接受惰性页入并如实测量（§9 实验 3）即可。

## 9. 动手实验

以下旗标与环境变量均已在源码核实存在（`main.c`、`ds_kernels.c`、`ds_safetensors.c`、`ds_ocr.c`）。

1. **量化前后对照**：同一张图，`--profile` 各跑一次 `./ds_ocr -d models/DeepSeek-OCR-2 -i image.png --profile` 与 `... --profile --int4`。观察 stderr 的 `INT8 quantization: %.2fs, %zu MB INT8 vs %.1f MB BF16` 行（约 3-8 s 一次性开销）；`Decode`/`MLP/MoE` 段变化是否接近 §1.4 预测的 1.35× 上限（M2+ 上可能接近 1.0×）；OCR 输出是否逐字一致。
2. **F32 视图缓存（内存换时间）**：`DS_BF16_CACHE_MB=4000 ./ds_ocr ... --profile` 对比不设时的 `Prefill`。该开关（默认 OFF）让 prefill 的 sgemm 路径把 BF16→F32 转换结果按源指针缓存复用（`ds_kernels.c: bf16_cache`），代价是最多 4000 MB 的 F32 堆副本——对照 RSS 一起看。
3. **冷态 vs 热态跑分**：同一张图连跑两次记录 `--profile` 的 `Encoding/Prefill/Decode`，然后 `sudo purge`（清 page cache，需 macOS）跑第三次。差值就是 page cache 的贡献；把三次的 `DS_RSS_PROBE=1` 输出并排看，验证"峰值 RSS 在加载结束即成立"。
4. **验证页回收机制**：`DS_NO_MADVISE=1 ./ds_ocr ... --profile` 关闭加载后的 `MADV_DONTNEED`（§5.4），对比 `DS_RSS_PROBE=1` 报告的 max_rss 差值。
5. **思考题**：为什么 INT8 量化对 LM head（每步必读 331 MB、占 29%）"理论收益最大"，本工程却没有量化它？提示：收益 = 流量占比 ×（1 − 压缩比）× 带宽短板，再减去"没有现成 INT8 argmax 内核"的工程成本——若要实现，`ds_int4_matvec` 的分解技巧（§3.3）能否直接搬到 `ds_argmax_matvec_bf16` 上？

## 小结

量化与部署是同一枚硬币的两面：**量化改写 §1.1 账本里每项的字节数，部署决定这些字节离处理器有多近**。五个可复用的结论：

1. **先记账再优化**：decode 每步 ≈1,148 MB / 1.15 GFLOP，AI≈1.0 FLOP/B，注定 memory-bound；任何优化先问"它改了账本的哪一行"。
2. **量化的收益有边界**：`--int4` 只量化专家（53% 流量），理论 1.35×；在 M2+ bfdot 面前可能打平——第一收益是内存（−2.4 GB）。"int4 实为 INT8"是历史遗留，证据链在 §3.5。
3. **数值格式的本质是位布局**：BF16 = F32 的高 16 位，一条移位完成转换；per-row INT8 用 0.6% 的元数据把相对误差压到 0.4% 量级。
4. **mmap 的性能是"状态函数"**：同一二进制冷/热可差数倍；WILLNEED 预取把缺页变重叠，DONTNEED 把死页变自由，连续块的教训是"拷贝即双份"。
5. **平台分发两级结构**：编译期定候选、运行时定人选，首次 matvec 惰性初始化；bfdot 对 vshll 的 4× 指令密度就是 M2 与 M1 的 decode 差距来源。
