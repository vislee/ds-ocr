## 2. 必读论文：三个梯队

**读法**：每篇只回答三个问题——解决什么病、核心公式是什么、工程上要付出什么
代价（显存/带宽/实现复杂度）。然后立刻跳到对应 C 函数，把公式逐项"指认"出来。
梯队内按依赖排序；梯队间建议"读一篇 → 对一次代码"，不要攒着一起读。

### 2.1 梯队一：基础组件——读懂"积木"

这 5 篇对应 Transformer 的 5 个零件（01 章全覆盖）。读懂之后，任何新架构
论文对你来说都只是"零件的重新排列组合"。

**1. Attention Is All You Need**（arXiv:1706.03762, NeurIPS 2017）
- **带走一个思想**：QK^T/√d + softmax 本质是一次**可微查表**——每个位置按相似度对所有位置的价值向量加权求和；循环被彻底移除，序列内任意两位置一步连通。
- **工程代价**：注意力矩阵 O(N²) 的显存与带宽——FlashAttention、R-SWA、DASH 三代稀疏方案共同的靶子。
- **本仓库对应**：`ds_causal_attention_aligned`（ds_kernels.c）——因果掩码 + online softmax 的完整实现。
- **自查**：缩放因子为什么是 √d 而不是 d？（答案：01 章 §5.3）

**2. Layer Normalization → RMSNorm**（arXiv:1910.07467, NeurIPS 2019）
- **带走一个思想**：LayerNorm 的减均值步骤可以去掉，只按均方根缩放——少一趟归约，效果几乎不掉。现代大模型（LLaMA/Qwen/DeepSeek 系）全线换用 RMSNorm。
- **工程代价**：几乎为零，反而省一次 mean 归约；代价是接受"尺度不受均值影响"的理论松绑。
- **本仓库对应**：`ds_rms_norm`（ds_kernels.c，NEON/AVX/generic 三级分发）。
- **自查**：RMSNorm 相比 LayerNorm 砍掉了什么、为什么可行？（答案：01 章 §8）

**3. BPE for NMT + GPT-2 报告**（arXiv:1508.07909, ACL 2016 / GPT-2, 2019）
- **带走一个思想**：高频字节对反复合并成子词——词表存"零件"不存"成品"；GPT-2 再把"字符"换成"字节"，256 个基础条目兜底一切 UTF-8 文本。
- **工程代价**：编码按合并表优先级贪心匹配；词表越大 LM head 的 matvec 越贵（本仓库 129,280 行 × 1280 维，decode 每步都要扫）。
- **本仓库对应**：`ds_tokenizer_encode`（ds_tokenizer.c）；词表 129,280 的来历见 07 章 §4。
- **自查**：词表里没有的生僻字符为什么也能得到 token？（答案：07 章 §3）

**4. RoFormer / RoPE**（arXiv:2104.09864, 2021）
- **带走一个思想**：用旋转把**相对位置**注入 Q/K 内积——对 (m,n) 位置对，内积只依赖 m−n；位置信息不再靠加性向量"外挂"。
- **工程代价**：每步要给 Q/K 逐元素旋转；KV cache 里存的是旋转后的 K——改位置方案就得重算缓存（V4 page2d 就动了这里）。
- **本仓库对应**：`ds_apply_rope_neox`（ds_kernels.c）；V4 把它扩成 tok+page 双轴（`ds_dash_build_coords`，ds_dash.c，见 14 章 §3）。
- **自查**：手推 RoPE 对 (m,n) 的内积只依赖 m−n。（答案：01 章 §4.3）

**5. GLU Variants Improve Transformer**（arXiv:2002.05202, 2020）
- **带走一个思想**：FFN 加一个门控分支（SiLU(g)⊙u）稳定优于无门控版本；SwiGLU 从此成为大模型 FFN 的默认，参数摆布上把 4d 换成 8/3·d 保持计算量。
- **工程代价**：一个矩阵变 gate/up 两个矩阵 + 逐元素乘——这正是 05 章 §10.4"专家块去拷贝"优化要处理的形状（gate/up 分开 matvec 的 split 路径）。
- **本仓库对应**：`ds_swiglu_direct`（ds_kernels.c）。
- **自查**：gate 和 up 两个分支在权重矩阵上怎么摆、激活在哪一步？（答案：02 章 §4）

### 2.2 梯队二：视觉与多模态——图像如何变成 token

V1/V3/V4 的视觉侧是 SAM+CLIP 拼接，V2 换成 DeepEncoder V2（Qwen2-0.5B 骨干）。
这 6 篇是"一张图怎么变成 273 个 token"的全部渊源（06 章全覆盖）。

**6. ViT**（arXiv:2010.11929, ICLR 2021）
- **带走一个思想**：图像切成 16×16 patch，每个 patch 线性投影成一个"词"——图像从此就是一句"话"，Transformer 原封不动搬过来用。
- **工程代价**：patch 数随分辨率平方增长，全注意力的 N² 项在视觉侧比文本侧更疼（SAM 1024² 输入 → 4096 patch 的全局层）。
- **本仓库对应**：`sam_patch_embed`（ds_visual_tokenizer.c）。
- **自查**：本仓库 1024×1024 输入为何最终只有 256 个基础视觉 token？（答案：06 章 §1）

**7. CLIP**（arXiv:2103.00020, ICML 2021）
- **带走一个思想**：4 亿图文对上的对比学习，让视觉特征带上**语义先验**——OCR 解码器负责"认字"，CLIP 特征提供"这是什么版式/什么语义"的上下文。
- **工程代价**：训练要海量图文对与大 batch；推理侧只是多一个 24 层编码器的前向（本仓库 CLIP-L：24 层 / hidden 1024 / 16 头）。
- **本仓库对应**：`ds_clip_encoder_forward`（ds_deep_encoder.c）——SAM 特征与 CLIP 特征拼接后过投影（2048→1280）。
- **自查**：SAM 特征与 CLIP 特征各贡献什么？（答案：06 章 §3/§4）

**8. SAM（Segment Anything）**（arXiv:2304.02643, ICCV 2023）
- **带走一个思想**：ViT 里穿插**窗口注意力**（window attention）+ 少量全局层，把视觉注意力的 N² 压进窗口——证明"局部为主、全局点睛"就够用。
- **工程代价**：窗口调度与相对位置偏置的实现复杂度；全局层仍是 N²，是编码阶段最贵的单点（每层 0.83s，05 章 §10.3）。
- **本仓库对应**：`window_attn_forward`（ds_visual_tokenizer.c）；全局层的 head 并行优化实录见 05 章 §10.3。
- **自查**：SAM ViT-B 12 层里有几层全局注意力、为什么这样穿插？（答案：06 章 §3；全局层数见 05 章 §10.3）

**9. GQA**（arXiv:2305.13245, EMNLP 2023）
- **带走一个思想**：多个 Q 头共享一组 KV 头——KV cache 与 KV 投影按分组比缩小，质量接近 MHA。本仓库编码器 V2 是 14 个 Q 头共享 2 个 KV 头（7:1）。
- **工程代价**：KV 头变少后内核要多一层 broadcast/索引映射。
- **本仓库对应**：wk/wv 权重形状 [128, 896]（kv_dim=2×64，hidden=896，`DS_ENC_V2_*` 常量见 ds_ocr.h）——对照解码器的 10Q/10KV 纯 MHA，一次看全两种形态。
- **自查**：GQA 让 KV cache 缩小几倍？（答案：03 章 §5）

**10. NaViT（Patch n' Pack）**（arXiv:2307.06304, 2023）
- **带走一个思想**：不同分辨率/长宽比的图像打包进同一序列训练——"原生动态分辨率"。本仓库的动态多裁剪（dynamic_preprocess，多 crop 拼接 + image_newline）是它的工程近亲。
- **工程代价**：序列长度不定 → 缓冲区、位置编码、KV 上限都要按最坏情况预留（`DS_MAX_LOCAL_CROPS` 等常量，ds_ocr.c）。
- **本仓库对应**：多 crop 流程（ds_ocr.c）；思想对照见 06 章 §6。
- **自查**：crop 数不定时，预填充序列长度的上限怎么定？（答案：06 章 §6）

**11. ViT-22B / QK-Norm**（arXiv:2302.05442, 2023）
- **带走一个思想**：超大规模 ViT 训练不稳，对 Q/K 各自做 RMSNorm（head 维度内）能压住 attention logits 的爆炸——训练侧的稳定技巧反哺推理实现。
- **工程代价**：每 head 一次小归约，内核要处理 head 维度的 stride——向量化不如整行 RMSNorm 顺。
- **本仓库对应**：`ds_rms_norm_per_head`（ds_kernels.c；当前仅通用实现、未进 NEON/AVX 分发——第 5 节 W1 的现成课题）。
- **自查**：per-head 归一化与整张 Q 矩阵归一化的区别在哪？（答案：01 章 §8）

### 2.3 梯队三：稀疏与系统——把注意力做省

从 FlashAttention 到 MoE 再到三份模型报告：这条线回答"长序列/大词表上，
注意力与 FFN 怎么算得起"，直接通向本仓库的三种注意力方案（全局 / R-SWA /
DASH）。

**12. FlashAttention v1/v2**（arXiv:2205.14135 / 2307.08691, 2022/2023）
- **带走一个思想**：**online softmax**——分块扫描 K/V，维护 running max/sum，永不物化 N² 注意力矩阵；把"IO 感知"变成注意力内核设计的第一性约束。
- **工程代价**：实现复杂度高（分块、rescale、数值稳定性）；CPU 上没有 GPU 的分块红利，但 online softmax 的数值形式照样适用。
- **本仓库对应**：`ds_causal_attention_aligned`（ds_kernels.c）内部的 online softmax（running max/sum）；完整推导见 13 章 §2。
- **自查**：online softmax 的 rescale 公式长什么样？（答案：13 章 §2）

**13. Switch Transformer / Mixtral**（arXiv:2101.03961, 2021 / arXiv:2401.04088, 2024）
- **带走一个思想**：MoE 把 FFN 换成 N 个专家 + 路由器，每 token 只激活 top-k 个——**参数容量与计算量解耦**；Mixtral 证明 8 选 2 就能打平稠密大模型。
- **工程代价**：专家权重分散 → 访问碎片化、内存驻留压力（本仓库 64 个专家 3.2GB 的拷贝教训，05 章 §10.4）；负载不均时热点专家成瓶颈。
- **本仓库对应**：`moe_forward`（ds_moe_decoder.c）——64 路由专家 top-6 + 2 共享专家的完整路由与门控。
- **自查**：从路由得分到专家输出加权聚合，顺序是什么？（答案：02 章 §9）

**14. DeepSeek-V2**（arXiv:2405.04434, 2024）
- **带走一个思想**：MLA 压 KV、共享专家吃通用知识、负载均衡损失养路由——本仓库解码器的直接祖先（去 MLA 化的 3B 变体：kv_lora_rank=None，注意力退回标准 MHA，MoE 骨架保留）。
- **工程代价**：路由逐 token 做 softmax + top-k，且必须用 BF16 与 Python 对齐——选错专家会级联放大成胡言乱语。
- **本仓库对应**：`ds_moe_decoder.c` 全篇（gate BF16 路由、专家 matvec、共享专家融合）。
- **自查**：路由为什么必须 BF16 而不能随手升 F32？（答案：02 章 §6）

**15. DeepSeek-OCR 技术报告**（contexts optical mapping, 2025.10）
- **带走一个思想**：**上下文光学会压缩（contexts optical mapping）**——文本渲染成图像、再被视觉编码器压缩成少量视觉 token。"视觉即压缩"是整个项目的立论：1000 个文字 token 可能只要 ~100 个视觉 token。
- **工程代价**：全局视图与局部 crop 两条 token 流要各自维护 token 数与位置编码；压缩率越高，对识别精度的要求越苛刻。
- **本仓库对应**：`ds_ocr.c` 的编码管线（全局视图 pad 1024 → SAM → CLIP → 投影出 273 token；小图与多 crop 走 dynamic_preprocess）与 `detect_model_version`（ds_ocr.c）的四路版本分支。
- **自查**：V1 全局视图为什么输出 273 个 token？（答案：06 章 §1/§7——16×16 网格 + 16 个换行 + 1 个分隔）

**16. Unlimited-OCR 技术报告**（arXiv:2606.23050；原文在 models/Unlimited-OCR/Unlimited-OCR.pdf）
- **带走一个思想**：**R-SWA（参考集 + 滑动窗口）**——全部视觉 token 恒为"参考集"可见，其余 token 只看最近 128 个：单页长文档解析不需要全注意力。
- **工程代价**：参考集让每 query 的读集合仍随 prefill 长度线性增长；解码侧要配 n-gram 守卫（本仓库默认 ngram=35）防整段循环。
- **本仓库对应**：`ds_rswa_attention_aligned`（ds_kernels.c）；优化效果与带宽分析见 05 章 §6。
- **自查**：R-SWA 下一个 query 最多能看多少个 KV？（答案：14 章 §7 对比表）

**17. V4 / DASH 块稀疏注意力**（官方代码 models/Unlimited-OCR-2/dash_attention.py + config 的 sparse_attention_config 节点）
- **带走一个思想**：把 KV 按 128 token 分块，用 head 摘要（head_cls）路由出 top-M=16 候选块，entmax15 归一成先验、转成 K=12 槽的 log-prior 偏置，与局部窗 128 取并集——**注意力预算按页按块花**；page2d 再把"第几页"烧进 RoPE。四代模型里最新的注意力方案。
- **工程代价**：解码要维护页坐标状态机与按层路由缓存（idx_k_hist）；对 KV 精度敏感——BF16 KV 实验在 V4 打红（05 章 §10.5）。
- **本仓库对应**：ds_dash.c 全文件（`ds_dash_build_coords` / `ds_dash_attention_prefill` / `ds_dash_attention_decode`）+ ds_moe_decoder.c 的 V4 分支；完整数学与 5 个真实 bug 复盘见 14 章 §4/§6。
- **自查**：为什么 V4 的版本检测必须排在 V3 之前？（答案：14 章 §1）

> **注**：15/16 为项目所引模型的官方报告（models/ 目录内含原文；
> V4 暂以官方代码为准），其余 arXiv 号为社区通行编号，建议以标题
> 检索官方页面为准。

**读法建议（进阶版）**：读每篇时同时做两件事——(1) 在本仓库找到对应函数，把
论文公式逐项指认出来；(2) 记下论文没讲、但代码必须回答的问题（KV stride 怎么
定、精度在哪一层收敛、并行切到哪一维）。(2) 的答案分散在 03/05/09 三章。

## 3. 模型家族谱系：从 V1 到 V4

```
DeepSeek-LLM ──→ DeepSeek-V2（MLA+MoE，解码器骨架的出处）
      │                    │
      │                    ├──→ V1 DeepSeek-OCR (2025.10)
      │                    │      SAM + CLIP 双编码器 + 投影 + 3B-MoE 解码器
      │                    │         │
      │                    │         └──→ V2 DeepSeek-OCR-2
      │                    │                编码器换 DeepEncoder V2
      │                    │                （Qwen2-0.5B 骨干、因果流查询、14Q/2KV GQA）
      │                    │
      └── Qwen2-0.5B（V2 编码器骨干）
                           │
     Baidu Unlimited-OCR（V3）：沿用 V1 视觉侧 + 同款 MoE 解码器，
         注意力改 R-SWA（参考集 ∪ 滑窗 128），单页长文档
                           │
                           └──→ V4 Unlimited-OCR-2
                 注意力改 DASH 块稀疏（head_cls 路由 top-M=16 → entmax15
                 → 12 槽 log-prior 偏置 ∪ 局部窗 128），
                 位置编码改 page2d 二维 RoPE，多页文档
```

四代模型的解码器骨架完全一致（12 层，64 路由专家 top-6 + 2 共享，
hidden 1280，`moe_intermediate_size` 896）——差异全在**视觉侧与注意力调度**：

| 代 | 模型 | 视觉侧 | 解码器注意力 | 位置编码 | 目标场景 |
|---|------|--------|-------------|---------|---------|
| V1 | DeepSeek-OCR | SAM + CLIP 拼接 + 线性投影 | 全局因果注意力 | 1D RoPE | 单图通用 |
| V2 | DeepSeek-OCR-2 | DeepEncoder V2（因果流查询 + GQA） | 全局因果注意力 | 1D RoPE | 单图通用 |
| V3 | Unlimited-OCR | 沿用 V1 视觉侧 | R-SWA（参考集 ∪ 滑窗 128） | 1D RoPE（theta=10000） | 单页长文档 |
| V4 | Unlimited-OCR-2 | 沿用 V3 视觉侧 | DASH（路由 12 块 ∪ 局部窗 128） | page2d（tok 63 对 + page 1 对） | 多页文档 |

这正是 01/06 两篇 + 本仓库 `detect_model_version`（ds_ocr.c）四路分支
所对应的内容。一个容易踩的坑：V4 的检测必须在 V3 之前——V4 的 config
同样含 `sliding_window_size`，检查顺序错了会把 V4 误判成 V3（14 章 §1）。

## 4. 推理系统论文：服务化视角

前三节是"模型里"的论文；这一节是"模型外"的——当你把单次推理变成多请求
服务时，会撞上它们当年撞上的墙。

**Orca**（OSDI 2022）
- **解决什么病**：静态 batching 里整批要等最慢的请求，GPU 大量空转。
- **核心机制**：iteration-level 调度——每生成一个 token 就重新组批，请求随到随进、随完随走；这是 continuous batching 的源头。
- **对本工程的可搬点**：`ds_decoder_forward_batch` 已有多 crop 批量前向，把它升级成"任务池 + 每 decode 步重组批"，就是 Orca 思想的单机版（第 5 节 W4 照此立项）。

**PagedAttention / vLLM**（SOSP 2023, arXiv:2309.06180）
- **解决什么病**：按最大长度给每请求预留连续 KV 空间，内部/外部碎片浪费过半显存。
- **核心机制**：把 KV cache 切成固定大小的 block（物理页），逻辑连续、物理离散、按需分配；并行采样共享前缀只存一份。
- **对本工程的可搬点**：本工程"每请求独占连续 KV"是它的单请求特例；KV 行 stride ≥ kv_dim 且 64B 对齐的设计（03 章 §5）已为换页表寻址留了余地——动手前先想清楚"逻辑位置 → 物理位置"的映射放在哪一层。

**投机解码**（Leviathan et al. arXiv:2302.01318 / Chen et al. arXiv:2302.04088, 2023）
- **解决什么病**：decode 是逐 token 的 matvec，算术强度低、卡在带宽上，大模型"一口一口吃"效率低。
- **核心机制**：小模型（或 n-gram/草稿头）一次起草 k 个 token，大模型一次前向并行验证——接受前缀中首个不一致处之前的部分，拒绝则从该处重采样；验证是并行 sgemm，把 decode 拉回 compute 一侧。
- **对本工程的可搬点**：OCR 找"草稿模型"不现实（视觉 token 是专有表示），但 det 标签这类结构化输出可以用文法约束采样逼近"一次多步"；更实际的低风险路径是 n-gram 草稿——本仓库 decode 已在维护最近 token 历史（08 章 §5）。

**MLC / TVM**
- **解决什么病**：手写内核门槛高、平台适配慢，每种硬件都要人来写一遍。
- **核心机制**：把算子调度（tiling、layout、向量化）声明成搜索空间，编译期自动搜索生成内核（TVM auto-tuning / MLC 的张量程序抽象）。
- **对本工程的可搬点**：本工程选了手写内核（NEON/AVX/generic 三级，ds_kernels_impl.h 分发），换来零依赖与逐位可控。读 MLC 的意义在于理解"调度空间"——你手写的每次循环重排，都是它搜索空间里的一点（对照 03 章 §4）。

## 5. 进阶方向：一个月进阶计划

从读者到作者，不是"多读十篇论文"，而是"四周各交付一个可验证的里程碑"。
每个任务都绑定本仓库真实工具，并遵守 05 章 §10.2 的方法论——**红即回退**：

| 周 | 主题 | 动手任务 | 可验证里程碑 |
|----|------|---------|-------------|
| W1 | 内核与对拍 | 给 `ds_rms_norm_per_head` 写 NEON 或 AVX 版本（当前仅 ds_kernels.c 通用实现），与 generic 路径逐位对拍 | `make test` 的 test_kernels 全绿；`make coverage-unit` 覆盖率不回退；`bash tools/regress.sh` 30 组全绿 |
| W2 | 采样策略 | 在 `ds_decoder_forward` 的贪心+温度之上补 top-p（nucleus）采样，对比 OCR 任务上贪心 vs top-p 的输出质量 | 用 `tools/regress.sh` 证明"它没用"（或有用）——负结果同样是好实验；08 章 §8 的对比实验可直接复用 |
| W3 | KV 精度与带宽 | 把 V3 的 KV cache F32→INT8（复用 09 章 §3 的 per-row 方案），`--profile` 对比 decode 每步耗时与 tok/s | 读流量按 05 章 §7 的带宽模型对账；`tools/regress.sh` 全绿。只在 V3 上做——记住 BF16 KV 在 V4 打红的教训（14 章 §7） |
| W4 | 批处理 | 把 `ds_decoder_forward_batch` 扩成 2-4 路并发 OCR 的 continuous batching（任务池 + 每 decode 步重组批） | 4 图并发总耗时 < 4×单图 × 0.6；精度回归全绿 |
| 周末 | 精度对齐 | 用 `DS_BF16_SIMULATE_PYTHON` 与 Python 逐层对拍，定位下一个精度敏感点（候选：注意力 softmax 的归约顺序） | 产出一份"精度敏感点清单"，格式仿 14 章 §6 的 bug 复盘（症状→根因→教训） |

三个真实优化案例（都在 05 章 §10 的 r1/r2 实录），告诉你这些课题的"标准
答案长什么样"：

- **SAM head 并行（r2）**：按 head 切分并行、每个元素的求和顺序不变——"逐位一致并行"零精度代价，编码耗时近乎减半（V1 5.2→2.64s）。W1 写并行内核时优先找这类切法。
- **专家块去拷贝（r2）**：删掉 3.2GB 的专家连续块拷贝，decode 全线 +10–16%、峰值 RSS −3.1GB。教训：mmap 之后的任何"复制"都要先问峰值 RSS。
- **fast_expf 事故（r1/r2）**：编码侧 softmax 换近似 exp → V3 小图 CER 95.4%，当场回退。教训：数值实验必须过回归门控，一条阈值红就回退。
